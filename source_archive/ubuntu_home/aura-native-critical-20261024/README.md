## 方案与已经完成的部分

目标是把“取得DPU执行权→原生提交→原生wait→确认完成→释放执行权”放在**同一次原生调用**内。释放执行权不依赖Python线程再次得到GIL；输入准备在取得执行权前，解码、身份决策、GUI/日志在释放后。YOLO、YuNet、SFace必须共用原生仲裁，仍为同一个DPU owner。

`native_lease.hpp`是无VART依赖的C++执行权原型。保持30ms cap/5ms guard、YOLO等待优先、输入TTL、完成未知则fence全部新准入；在原生回调返回后即执行保护决策并释放，不等上层调用者返回。回调只允许编译的原生函数，不能用Python/ctypes回调绕回解释器。prototype并未实现真实runner接线、完整恢复策略/状态交接、关闭时资源生命周期和业务发布门禁，这些必须在部署前完成。

7组检查实际在Ubuntu普通编译、AddressSanitizer/UndefinedBehaviorSanitizer及KV260本机编译运行，均通过。覆盖窄窗口拒绝、原30ms cap、主任务截止更新复查、异常/未确认完成fence、TTL过期、主任务优先、上层调用者延迟时YOLO仍可取得执行权、fork继承拒绝；fence分组里含两种失败方式。统计按7组报告，不能相加成21个独立用例。KV260编译无警告、约12.15秒；测试无模型/VART调用、不创建硬件owner、提交真实DPU作业0。生产相机PID29563和故障计数在隔离前后保持。

该原型的时间端点是原生仲裁内部的决策点和unlock后观测点，均保留。普通Linux依旧可能在native执行期间被调度走；本原型既不是硬实时证明，也不能证明新路径真实运行一定小于30ms。不得通过删计时、移走仍持有的执行权、清计数或调高阈值来宣称通过。

## 下一步真实接入与验收

1. 在已有camera/DPU owner内接VART C++，将YOLO和两可选CNN接入同一个原生仲裁。保持xmodel/指纹/tensor顺序/量化和INT8身份空间，执行前后的buffer与生命周期清晰绑定；没有第二owner/第二相机。Python原调度器只能代理原生状态，不能继续握住另一把会阻塞YOLO的旧执行权锁。
2. 原恢复/故障累计、TTL/取消、SFace前两probe不发布与未知完成fence全部迁移/对齐。原生完成事实、业务结果新鲜度与输出返回时刻分别报告。模型原始输出和最终检测/特征要用相同输入比对，不能仅因更快就接受精度变化。
3. 先做1～3分钟短对照淘汰无效方案，再在正常业务中积累长稳。YOLO保持至少9.5Hz、人脸处理不低于现有有效基线，SFace真人/多人/陌生人准确率和源帧龄不退化；同时检查GUI约8fps及音频。CPU排队仍大时，才对原生推理线程做有界资源配置，单独对照，不能把C++或一次nice试验当作调度保证。
4. 新路径真实三模型负载、故障注入/恢复、正常负载下的长稳和实际冷启动均通过后，才替换正式版本。不能承诺通用Linux在任意故障/负载下永不超过30ms；工程完成标准是约定的业务负载下满足延迟/吞吐/准确率，异常仍有有界保护和可恢复性。
