### 2.2 实际工作流

1. **人确定目标与约束。** 明确当前范围、质量要求、硬件条件和可操作边界，例如保持语音特性、减少跟随顿挫、保留原运行根。
2. **AI 先读取原件。** 核对项目书、当前源码、配置、发布清单和故障样本，区分观察事实与待验证解释。
3. **形成最小候选。** 生成或修改 RTL、Python/C/C++、Tcl、配置和测试，保存基线与对应版本。
4. **用真实工具反馈检验。** 分别执行语法/软件检查、仿真、综合实现、固定输入板测和业务观察；每层结果只支持其覆盖的范围。
5. **拒绝失败并修订。** 保存失败候选和反例；新增证据推翻早期结论时，明确收回原判断，不清零故障或复制历史 PASS。
6. **人参与实体评价。** 用户执行物理接线/上电，反馈听感、画面与转动效果；AI 协助关联版本、数据和回执。
7. **提炼可复用流程。** 将成功条件、失败触发、检查入口和边界整理为 Skill、脚本或工作流文档。

双机协作的原始要求和共享入口落地见 Q21。两台机器分别写自己的回执；“文件已同步”“本机服务通过”“实板业务通过”是三个独立状态。

## 3. C01：平台工件一致性与 DFX 运行时修复

**工程问题。** 早期模型识别异常不能仅由“VART 返回成功”解释。历史审计发现 clockfix XSA 的 HWH 与内嵌位流来自不同构建状态，随后独立重建又发现最终 DCP 的 DPU reset 连接存在问题。平台正常启动、工具执行成功与模型计算正确需要分别验证。

**历史提示词原文节录｜Q01。**

> 请修复 KV260 clockfix 构建产物来源不一致的问题，完成一次独立的离线硬件重建。

**AI 回答原文节录｜Q01。**

> 独立离线综合、布局布线和 bitgen 已完成，但整体验收未通过；当前产物不可上板。

引文仅去除 Markdown 强调符号，文字不改写。完整原文及禁止改动范围见 Q01 附件。

**协作形成的工程工作。** 在独立目录核对 BD、时钟/复位、XSA/HWH/位流来源，而不是因生成了 BIT 就直接部署。后续 DFX manager 修复覆盖共享状态加锁与父设计全部子包/监听清理，主要修改 `daemon_helper.c`、`dfx-mgrd.c`。［Q02、E03］

**验证与结果。** 后续历史冷启动验收记录新 manager、ZOCL 和官方 DPU 自动启动，原模型/原图结果与基线一致、26 项原文件哈希一致；回读核验 5,223 个证据文件，累计 23 次分类结果通过。这些数字属于当时平台修复验收，不代表项目全部业务通过。［Q03、E03］

**纠错轨迹。** “推理接口成功”不足以排除硬件或工件错误；“综合、实现与 bitgen 完成”也不足以确认可部署。将复位连通、位流身份、同图参考与断电启动纳入验证后，结论才可由离线完成推进到对应平台的板级通过。

**团队决策与复用经验。** 用户明确要求独立重建并保留原模型/输入，限制变量；团队据此建立“工件必须属于同一构建链”的检查方式。可复用到任何含 BIT/XSA、驱动、设备树和模型目标指纹的异构工程。

## 5. C03：YuNet / SFace 的 DPU 适配与质量验证

**历史提示词原文｜Q04。**

> yunet和sface能放到dpu上面么

**后续执行要求原文｜Q05。**

> 那就先把能放在dpu上的先开始，自己规划

**设计与实现。** AI 协助将公开模型适配为 B4096 可执行 INT8 工件。YuNet 通过卷积子图重构，保留 CPU 解码/后处理边界；SFace 对包括 27 处 PReLU 在内的算子及全连接头进行等价改写，再进行校准、量化和目标编译。公开网络及权重属于上游成果，项目工作是适配、验证与系统集成。［H09—H16、E32］

| 主要工程文件 | 作用 |
| --- | --- |
| `reconstruct_yunet.py`、`rewrite_sface_v2.py` | 网络重构与等价算子改写 |
| `quantize_yunet.py`、`quantize_sface_public.py` | 校准与公开质量评测 |
| `compile_candidate.py`、`compiler-manifest.json` | 编译目标、分区、端口与版本关联 |
| `hardware_vectors.py`、板测 JSON | 固定输入与目标板输出对照 |

**质量验证。** SFace 独立 1,000 对公开测试，FP32 与 INT8 模拟准确率均为 98.8%；误接收却由 0/500 变为 1/500，误拒绝由 12/500 变为 11/500。因此“总体准确率相同”不能解释为全部样例或风险无变化。校准身份与评估身份分离，阈值由训练部分选择。［E09］

YuNet 在 256 张公开图、阈值 0.6 下，INT8 对 FP32 参考框的恢复比例为 316/322≈98.14%，匹配框 IoU 中位数约 0.9736；这是一致性结果，**不是人工真值 AP 或 mAP**。［E10］

**执行验证。** 历史固定输入记录给出 YuNet 约 124→61ms、SFace 约 521→13.6ms，并记录三模型 YOLO 10 / YuNet 5 / SFace 2Hz 的短时执行。这是对应适配器路径的计时，不能混作纯 DPU 核耗时或整机加速比。更早 SFace 7.68ms 等数据属于不同阶段和条件。［Q04、Q05、E08、E11］

**纠错与取舍。** 早期“结构适合”只形成候选，编译和固定向量通过后才承认工程可执行；发现 USB 音频异常时保留回退和后续排查。完整身份业务、独立质量评测和固定输入板测各有证据范围，不能相互替代。

## 6. C04：DPU 调度、共享锁与跨模型审查纠错

**工程问题。** 在单 B4096 上，YOLO 主检测与 YuNet/SFace 可选任务共享不可抢占的执行资源。相机、UI 和身份状态又共享部分软件锁，DPU 空闲并不保证任务能及时进入。历史失败候选 468 次尝试中有 355 次因锁忙撤回，出现 14 段结果过期缺口，最长 3.75 秒。［Q06、E12］

**修正路径。** AI 辅助增加时隙通知等待，再以独立取消 Event、源帧时效和 retry deadline 做提交前检查，移除这项准入对共享状态锁的依赖，保留正式业务状态提交的锁纪律。接受版本的 60.326829 秒窗口中，YOLO 9.96240Hz、人脸发布 3.76284Hz；80/80 次通知等待成功，无新增锁忙撤回或结果缺口。该窗口输入未配对，不据此宣称严格 CPU 加速比。［E12］

**可直接追溯的自我纠错。**

| 北京时间与原始记录 | 当时判断／新增证据／修订 |

## 7. C05：人脸随动的顿挫、降频反例与 PL 连续推进

**工程问题。** 用户持续反馈边界附近反复启动/停止、突转和抽动。用户希望越线后更快、平滑地回到画面中央，并提出降低人脸刷新频率的想法。团队需要同时兼顾观测新鲜度、控制许可与动作连续性。

**提示词原文｜Q10。**

> 这样吧，能不能做这个转轴跟随降低刷新人脸的频率以至于提高这个平滑效果

**AI 回答原文节录｜Q10。**

> 人脸输入从每秒 12.5 次降到 5 次后，4 秒内出现了 6 次到期停止，反而更顿。

这项结论来自软件模拟，原答复同时说明当时板端参数未改，未声称实体改善。它否决了“直接降低检测频率就会更顺”的未经检验假设。［E16］

**实现取舍。** 先处理边界启停、感知历史和源有效期，再将 v14 改为新脸源续期、PL 每 20ms 连续推进 4µs，替代原来 PS 每张图仅推进小步的限制。保持源时效、失源停止及行程限制，避免把重复旧帧当成新的动作许可。［E15］

**验证与结果。** v14 历史记录含 199 项主机检查、61 项板端纯软件检查；真人窗口中记录 107 次提交、4 次软件中央结束，末次 STOP/1400µs，失源中断保留。用户当轮反馈如下：

> 明显更顺，速度也合适

该节录仅去除选项前的连字符；完整选项、用户选择与 AI 保留版本的回复见 Q11。用户观察支持当轮平顺度改善，未测出精确角度、跟踪 RMSE 或机械全行程。

**团队决策。** 用户把模糊的“平滑”进一步限定为越线快回中、区内保持；AI 通过模拟反例和控制实现迭代落实需求。较新随动恢复、方向调整与关闭状态分别记录在对应保存时点，不能把 v14 的旧 PID 或旧 READY 当作当前状态。［E25］

**沉淀方法。** 将检测频率、目标更新频率和执行轨迹频率分开设计；软件模拟先排除会触发时效停止的候选，再由实体反馈选择速度与行为。

## 8. C06：LLM 输出、语音等待与 GPU 资源协调

**工程目标。** 在保持既有 27B、OmniVoice 16 步合成、音色及业务字段的条件下减少等待，避免把删减模型能力或降低声音要求当作优化。Windows 部分的详细开发对话未完整同步，以下按实际工程文件和测量结果整理。

**输出层的工程改动。** `dialogue_stream.py` 与相关回归实现正文优先、内部短字段解析和原字段映射；保持情绪/动作及完整内容校验。旧格式与短字段各 4 次模型阶段测量的中位数如下。［H20—H22、H36—H37、E17］

| 阶段 | 原格式 | 短字段格式 |
| --- | ---: | ---: |
| 首正文 | 1754.07ms | 1344.27ms |
| 台词字段就绪 | 2762.88ms | 2287.70ms |
| 完整结构结束 | 4737.30ms | 3745.70ms |

两组回复措辞与长度有变化，样本少；这组结果不代表真实播放、固定的端到端提速或 TTS 本体加速。

**路由层的定位与修正。** 保存的 18 轮记录最终均走 Ollama，却先尝试原生通道，暖态准备耗时约 0.80—1.19 秒。关闭 `compact_grammar` 后，先核对共享配置，再核对 Windows 运行时是否真正加载。后续两轮软件起答 3.59/3.87 秒、首 PCM 3.234/3.469 秒，准备阶段均 0ms；上下文不同，非严格 A/B，也未包含说话结束到请求提交的全部等待。［Q13、Q14、E21］

**资源层的实现。** `common/gpu_coordination.py`、`gpu_runtime.local.json` 和 `omnivoice_voice.py` 处理观测、准入、租约、有界排队、取消与背压。历史 adaptive 三组非缓存语音观察记录最低空闲 1656MiB；最终合并回归 637 项、0 失败，包含多类既有业务，不能全算作 GPU 专项测试。［E18—E20、H23—H30］

**可追溯纠错｜Q15。** 用户要求保持声音特性并将合成放板端后，AI 收回过于绝对的表述：当前实现限制 CUDA 不能推出同模型只能 GPU/Windows。发现 CPU 后端候选后改为同模型可行性评估；ARM 构建、KV260 合成、速度和音质仍未验证。［E22］

**团队价值。** 用户保持质量约束，团队依阶段计时选择输出、路由与生命周期改动。旧 GPU 平台的预算和收益未直接迁作新桌面 RTX 5090 的验收结果。

## 9. C07：板端业务、来源约束与长期记忆

**工程目标。** 将业务和存储逐步收敛到板端，在会话、身份和来源约束下处理事实、摘要、更正及遗忘；Windows 保留相应模型推理。记忆正确性既涉及存储，也涉及实际构造提示词并召回。

**提示词原文节录｜Q16。**

> 记忆库最后会放在板端，那我们的大语言模型用关键词搜索会不准确，这个问题怎么解决

**当时 AI 建议。** 采用板端存储、结构化事实查询、关键词与语义混合检索，并保持身份及会话隔离。这是设计建议；现有附件不足以证明完整向量检索方案已按建议部署，本文未把建议写为成果。

**实际工程文件。** `common/board_memory.py` 和 `board/runtime/board_memory_policy.py` 实现来源、状态、提交与回收策略；`test_public_worker.py`、公开模型验证和采用决策记录摘要约束。完整播放 ACK 后提交助手历史，摘要有效后再回收原文；否定语义校验失败时保留待处理来源，不能只以“生成过摘要”判断成功。［H31—H35、E24］

**自然到期验证。** 公开输入对应记录在约 115.80 秒时用户/助手正文各 1 行，自然到约 333.44 秒后各 0 行，同一有效摘要保留，任务已提交；没有强行修改时钟或触发删除。原始状态为：

> STORAGE_PASS_RECALL_PENDING

该状态证明存储与保留流程，原件明确 `actual_prompt_retrieval_observed=false`，不能据此宣称该轮真实同会话召回已通过。［E23］

**较新使用反馈。** 后续交接保存了用户多轮记忆正常的反馈，同时保留“非超过五分钟摘要检索验收”的限制。字幕一源修复后有一轮真人完整播放回执，保存状态为 PAUSED、mic=false、无播放，跟随/转轴输出关闭。它是较新业务快照，不能由更早 ec12/FAULT 报告覆盖。［E25］

**可复用经验。** 将“事实存在”“摘要有效”“源文可回收”“检索命中”“模型答对”“声音完整播放”分成独立检查点。更正、撤销和迟到任务都必须带来源关系；通过公开输入验证机制，避免把私有身份库与对话正文装入参赛材料。

## 10. C08：显示、动画与真实现场反馈

**工程范围。** 板端角色、字幕、口型/状态投影、视觉页及启动过程共同构成交互界面。AI 辅助处理渲染、页面切换、状态来源和自启动，同时保留物理显示异常的独立排查。

**页面同步修复。** 视觉页边界浮层改为切页时主动隐藏并等待 ACK，屏蔽过期回调。历史记录中 16 项本机回归、4 轮板端 X11 隐藏及快速切页通过，ACK 10—33ms。软件 unmapped 与肉眼显示效果、重启后的行为分别验收。［E28］

**启动提速的真实边界｜Q19。** 用户要求加快玩偶自启动。旧启动观测为 GTK 子进程约开机 45.4 秒启动、GUI API 约 90.8 秒就绪，显示配置阶段约 26.182 秒。候选在确认显示模式安全后提前初始化 GTK，systemd 仍等显示与 GUI 都就绪。预检与 279 项组件核对通过，但当轮没有重启或实屏首帧测量，不能填写已节省多少秒。［E26］

**显示故障的纠错｜Q20。** 用户描述四角变黑、插拔 HDMI 画面变化，但没有观察动态内容。AI 将其保留为“是否保持最后一帧未知”，不将黑边、不闪或 DRM connected 直接认作正常恢复。后续 EDID 注入和模式重建也曾在软件侧成功、实屏仍花，保留失败并回退。［E27］

**较新进展。** 字幕一源修复和真人完整播放记录在后续交接中保存；较新的技术报告还记录了自然负载观察与真实页面素材。这些进展可以更新较早状态，但不能反向证明自动冷启动花屏已根治或完成同版全功能长稳。［E25、E32］

**团队决策与复用方法。** 用户的视觉观察是必要输入，AI 的系统字段是另一类证据。将软件渲染计数、窗口状态、物理首帧、动态刷新与用户反馈分别记录；由此避免出现“接口正常所以屏幕必然正常”的错误结论。

## 11. C09：从工程失败提炼通用 PYNQ Skill

**提炼目标。** 赛题评价可复用经验，不要求所有 Skill 都必须使用 PYNQ。项目另行实现 `pynq-contract-testgen`，将接口契约与 HWH 检查、驱动及测试生成从 AURA 业务中抽离。原 A/B/C 工程主题规划与这个已实现的补充包分别登记。［E01、E29］

**输入与产出。** 输入 AXI4-Lite uint32 接口合同、HWH、测试向量及可选模拟模块；生成 PYNQ 调用代码、测试骨架、合同报告和复现入口。检查实例、地址空间、偏移/位宽/权限、启动/完成和超时，HWH 状态严格区分 MATCHED、INCOMPLETE 与冲突。

| 来源观察或失败 | 提炼后的规则 | 已有验证 |
| --- | --- | --- |
| 文档、硬件描述和访问代码可能不一致 | 先校验合同与 HWH，再生成访问代码 | 合同与解析单元测试 |
| 单一项目常量限制复用 | 同一生成器用于加法器与 CRC32，分离实例/布局/命令位 | 两个示例分别生成并执行 |
| 模拟通过容易被写成板测通过 | 缺省模拟，真实 PYNQ 采用独立入口 | 包内记录明确无 PYNQ 导入及板卡访问 |
| 本地路径和临时文件可能掩盖依赖 | 在新目录复制并重复运行，核对来源 SHA | 解包后的独立目录复现 |

**实测范围。** Python 3.8.10 下 15 项单元测试通过，加法 36 例、CRC32 37 例，共 73 个模拟用例通过；新目录复现和 ZIP CRC/逐文件 SHA 核对通过。28 文件初版约 36.7KB。［Q17、E29、E30］

**失效边界。** 本队现用 KV260 系统没有 PYNQ 环境；示例 HWH 是明确标注的合成解析样例。真实 Overlay、PYNQ 板、跨板适配和陌生队伍复用均未验证。通用性由改变 IP 的离线示例提供初步支持，不能据此声明已取得官方额外加分。

**使用入口。** 原包执行 `python3 -B scripts/reproduce.py --out <新目录>`。用于其他题目时替换接口合同、真实 HWH、向量和对应模型，重新检查约束。本文说明提炼来源和验证范围，原 Skill 源码与证据仍以工程包为准。
