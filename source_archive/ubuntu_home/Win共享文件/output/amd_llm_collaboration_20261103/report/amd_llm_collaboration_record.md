**后续输入 原话**

> 呃，等一下，你详细看一下。通过经过这个论文分析的话，给我看一下我这个项目需要怎么改一下，才能有很大的创新性，就是去找一个方向就行。

**AI自我修正 原话**

> 我核对到一个关键点：原手册已经要求最新帧、租约和旧目标复核，所以这些不能再算新增创新。建议新增的核心是“根据允许的跟随误差计算画面有效期”，让同一个期限同时约束DPU调度和FPGA输出。下面我会把它与固定超时方案的区别、模块改动和对照实验整理成一份单方向说明。

### 修改与人工判断

候选方向由共享DPU调度、人脸模型和运动监督的并列增补，收敛为“感知有效期如何共同约束推理安排和动作许可”。AI重读手册后发现最新帧、租约和旧目标复核已在原要求中，因此修正了创新归属。团队进一步要求只集中一个方向，避免把完成原任务重复计算为新增贡献。

| 需要改动的位置 | 形成的候选设计 |

### 结果与可复用经验

该轮形成aura_single_innovation_direction_20261007.md，并提出固定期限与可变期限、普通调度与期限调度、软件检查与PL检查三类对照。消息和文档证明方案已形成；该案例不据此登记可变期限算法的板级收益。[S04]

纠错方法：导出失败先定位到导出阶段，确认已完成的路由结果和配套文件，再决定是否重建。资源、时序、软件回归与实物动作保持各自的证据入口。

## 7 记忆存储与超时反例纠错

### 7.1 摘要提交后回收原文

协作目标是在来源和会话范围内保存用户信息，助手历史以完整播放确认为提交条件；摘要经过校验并提交后，原文才进入回收流程。原协作索引关联board_memory.py、board_memory_policy.py与公开worker测试。[S02、S03]

自然到期记录显示：闭合年龄约115.80秒时用户和助手正文各1行，约333.44秒后各0行；两者关联同一有效摘要，任务已提交，未强改时钟、强制压缩或删除。原状态为STORAGE_PASS_RECALL_PENDING，actual_prompt_retrieval_observed=false。[S18]

工程判断：存储和回收已有验证，实际问答是否正确召回另立验收项。优化摘要容量时同时保留来源、更正、遗忘和迟到回写约束，失败任务不因统计方便而被写成成功。

### 7.2 PYNQ迟到完成反例

接口生成工具首轮15项单元测试中14项通过，test_late_completion_does_not_bypass_timeout失败。合同期限100ms，完成标志到200ms才被软件观察到；旧逻辑先接受完成，再判断超时，导致迟到结果被误收。[S19]

| 步骤 | 失败与纠正轨迹 |
| --- | --- |
| 输入与期望 | 模拟MMIO读取将时钟推进至0.2秒并返回done=1；应抛出TimeoutError |
| 旧逻辑错误 | 先判断done，直接退出轮询，未触发应有的超时异常 |
| 实际修改 | 状态读回后计算remaining；先拒绝remaining<0，再判断完成 |
| 回归验证 | 保留迟到完成反例；15项单元测试最终通过 |

修复位置为templates/driver.py.tmpl，反例位于tests/test_generator.py。保存日志逐项包含迟到完成、永不完成、读清除、元数据冲突等测试；生成后加法36例、CRC37例共73例通过，新目录源码SHA一致。[S20至S23]

### 从观察形成约束

另一项实际观察是工程HWH存在地址窗口，但aura_m3_regs_0的REGISTER元素数为0。因此工具区分元数据匹配、不完整与冲突，缺项时输出受限骨架，已知冲突不绕过。软件轮询的期限检查不能中断已阻塞的MMIO，也不证明硬件最坏执行时间；现有验证范围为离线生成和模拟。[S19、S20]
