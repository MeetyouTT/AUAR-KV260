# 下一步：启用已验证的 KV260 运行时修复

## 现在做什么

两项修复已经一起通过有限板测，但测试结束后恢复了原基线。接下来在备用卡上受控启用修复版 DFX manager 与 ZOCL，完成更长时间的复验，再继续 PWM。

本目录准备联合输入包和操作顺序。它是主机准备结果，**尚未在板端启用**。Ubuntu 在本次检查中未发现 `/dev/serial/by-id`，因此还没有重新读取板端状态。

无需重新烧录 SD 卡。用户需要把使用备用卡的 KV260 接回电源和 Ubuntu 的 USB 串口；网线可以继续直连 Win11。

## 接回板卡后的执行顺序

1. **重新读取状态。** 核对备用卡、内核、当前应用、管理器、驱动、运行库和 DRM 占用；重新记录 boot ID。之前的恢复结果不替代这次实时检查。发现其它应用活动或文件变化时，先查明，不直接切换。
2. **保存新的恢复点。** 在板端独立目录保存原管理器、客户端、unit、配置、VART、原模块、活动应用、文件哈希及完整内核日志；传输联合包，检查每个成员和整包哈希。
3. **受控启用。** 正常卸载官方应用，记录原驱动可能出现的一次已知退出引用错误；确认无活动应用、无 DRM 客户端和模块占用，再正常卸载原 ZOCL、加载已验证修复模块。通过独立临时 systemd 配置启动修复管理器，日志保存到独立文件；使用 SOCK_SEQPACKET 检查就绪。
4. **先确认官方功能。** 核对 1 CU、B4096、300 MHz、0xa0010000、指纹 0x101000056010407；用原 ResNet18 XMODEL 和原样图复跑，要求完整 Top-5 与基线一致，Samoyed 0.949879。
5. **扩大运行观察。** 准备新的逐阶段命令清单：30 轮受控应用切换及同图推理、至少 30 分钟推理与内存/日志采样。记录 daemon RSS、系统内存、内核 slab、模块引用、inotify 和每次操作的退出码。新增目标引用错误、异常或管理器 ERROR 时停止该轮，保存现场并按实际状态恢复；已有属性警告原样记录。
6. **复核 M3。** 检查 M3 固件哈希、DPU 查询和同图结果。新的长期复验不是之前 M3 寄存器或 FPS 成绩的重复声明；本阶段不连接执行器。
7. **决定固定使用方式。** 当前开机的受控启用通过后，再准备开机加载顺序、原文件保留和恢复入口。永久启用与重启验收尚未实施，不能只把程序复制到原路径就称完成。

第 5 步的较长运行是计划，尚未执行；采样结果决定是否需要继续增加时长或调整方案，不能提前宣称无内存泄漏。

## 恢复顺序

1. 正常卸载当前活动应用，确认无占用。
2. 对候选管理器发送其原有 SIGINT，刷新完整日志后停止；删除仅本次创建且哈希符合的临时配置，恢复原服务。
3. 在修复驱动下卸载原服务自动加载的官方应用，再正常卸载修复 ZOCL，使用原参数加载原模块。
4. 原管理器加载官方应用，恢复原 VART，复跑同模型同图，逐份核对原文件哈希。

失败时先读实际活动应用、服务和模块状态，不盲目重放旧控制器，不 force 卸载、不通过改厂商规则隐藏错误。

## 仍需保留的实际问题

基线 fstab 有两条 /boot 配置，实际挂载正常；重复配置的修正应独立保存恢复点并验证。overlay 属性警告及已有 DRC、时序约束限制仍存在，长期复验需保留日志。

PWM 是后续新模块，尚未实现或验收。完成运行时启用与复验后，再确认 PWM 引脚、电平、周期范围和默认安全输出，开展主机设计和审阅。
