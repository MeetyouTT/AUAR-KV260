# DFX manager 候选板端复验

前提：固定源码候选已通过主机回归、AArch64 构建、原镜像符号与加载器检查；备用卡身份、原驱动、官方活动应用、运行库及占用状态已经只读核实。

执行顺序：

1. 在新工作目录保存原管理器、客户端、服务、配置、默认固件、VART 配置、原 ZOCL、运行文件哈希和日志；传输并核对候选包。
2. 使用原管理器正常卸载官方应用。单独审阅已知原 ZOCL 退出引用错误，最多允许该目标节点出现一次；其他新内核错误停止推进。
3. 正常卸载原 ZOCL，临时加载已验证修复模块。停止已没有活动应用的原管理器，通过 `/run/systemd/system/dfx-mgr.service.d/` 的独立临时配置启动候选。
4. 沿用原配置和默认官方应用。候选 stdout/stderr 保存到本轮独立文件，完整保留诊断，避免大量查询导致 journal 限流影响错误统计。
5. 验证官方同模型同图推理；执行 1000 次列表查询并记录内核监视项；对一个明确命名、未加载的测试目录执行 50 次创建／删除，确认实时发现和回收。
6. 在修复 ZOCL 下完成官方应用三轮加载／卸载、M3 一次加载及同模型同图推理；逐阶段审阅内核及候选管理器原始诊断。
7. 正常卸载 M3，停止候选，删除仅由本轮创建且内容哈希符合的临时服务配置，恢复原服务；再恢复原 ZOCL 和官方应用，复跑同图并核对原文件哈希。

原 `/usr/bin/dfx-mgrd`、客户端、厂商服务、配置和默认固件保持原文件。候选是本轮有限验证对象，未永久安装。没有 SD/QSPI 烧录、板卡重启、PWM、MMIO 或执行器操作。

每一阶段独立记录实际退出码、UART 完整性和内核时间范围。未预期的失败先保存状态并停止原计划，依据实际活动应用、模块和服务状态采取已授权的恢复措施，不盲目重跑失败阶段。
