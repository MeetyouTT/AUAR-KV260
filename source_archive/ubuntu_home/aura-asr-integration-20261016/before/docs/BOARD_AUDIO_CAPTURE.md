## 互动页操作

点击“开始录音”后显示实际采样时长，再次点击“停止录音”结束；最长20秒自动结束。“取消本轮”会清除录音结果并返回可开始状态。录音中不能播放缓存声音，播放和暂停期间不能开始录音。语音主机未连接时只显示录音完成，不显示虚构转写或回答。

录音结果在板端内存中有界保留，取消、替换或退出后失效，不自动写入 WAV。现有预览、目标选择、音量与设置继续使用原服务。此次按钮验收使用 GTK/XTest 原生点选，实际手指触摸尚未复验。

触屏实现采用 [RecordingController](../tools/board_recording.py) 与原后台渲染命令线程。主机161项、板端18项相关软件测试通过；原生点选录得62000样本/3.875秒，自动结束为320000样本/20秒。完整证据与限制见上述报告。

## 实际设备格式

本轮读取 MCP01 的 USB 音频描述符与混音器：

| 方向 | 设备 | 实际硬件格式 |
| --- | --- | --- |
| 输入 | `hw:CARD=MCP01,DEV=0` | S16_LE、16000 Hz、单声道 |
| 输出 | `hw:CARD=MCP01,DEV=0` | S16_LE、48000 Hz、双声道 |

摄像头也有 USB 麦克风，不能默认按声卡序号录音。新适配器固定使用 MCP01 的稳定 CARD_ID；本轮没有调整麦克风增益、静音或播放音量。

## 独立运行

在包含相应源码的 KV260 项目根目录运行，现有本地 UI 服务须可读且没有正在播放或暂停的声音：

```bash
python3 -B tools/board_audio_capture.py --seconds 3 --output /home/root/aura-recordings/check.wav
```

时长为 0.2—20 秒。输出 WAV 和 `.wav.json` 元数据采用新文件方式创建，已有文件不会被覆盖。实际 WAV 为 16 kHz 单声道 PCM16，可以直接交给现有 Paraformer 音频格式入口；它不能直接当作要求 24 kHz 的旧缓存语音片段播放。

CLI 使用 `127.0.0.1:8783/api/state` 确认播放器状态；服务不可读或正在播报/暂停时拒绝启动。该入口不会停止现有播放。录音是显式命令，不会开机自动启动。

## 接入现有媒体链

[capture.py](../board/runtime/audio/capture.py) 提供 `Mcp01Capture` 和 `CapturedAudio`：

1. `start()` 开始一个有界录音，已有未消费录音不会被覆盖。
2. `stop()` 提前停止并返回完整样本；`take()` 只消费一次结果。
3. `cancel()` 丢弃在途和待消费音频，回收录音进程与设备锁。
4. `CapturedAudio.audio` 是现有 `AudioRef`，`pcm` 是原始字节，可交给 `MediaSessionManager.begin()`；无需新增另一套问答归属字段。

进程通过固定样本上限与额外超时保护限制录音长度，返回值校验真实字节数、样本数和格式。每次录音有独立 ID 和采录代次；错误、短音频、截断或越界不发布为有效结果。临时锁阻止两个新采录适配器同时占用设备。

触屏控制器已将本地录音和缓存播放操作统一串行。独立 CLI 只有启动前状态检查，适用于维护状态，不能保证其他独立程序不会随后启动播放。跨设备传输、网络重连和主机返回结果仍需由统一主服务接入；取消录音本身不等于取消 Windows 的模型计算。

`started_mono_ms`、`ended_mono_ms` 是本板进程启动/完成记录，不是麦克风首样本或声学时刻。后续 Light-ASD 仍须测声画偏移和漂移。
