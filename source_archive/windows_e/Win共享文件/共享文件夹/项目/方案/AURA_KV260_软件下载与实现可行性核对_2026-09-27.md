# AURA / KV260 软件准备与实现可行性核对

核对日期：2026-09-27。范围为项目三份三十天计划、FPGA 框架、2026-09-19 实现详解、2026-09-26 外设规格及已有镜像审查证据。报告中的历史建议作为证据审视，不作为新的操作授权。本次没有删除、安装软件或操作板卡。

## 判断

项目具有可实施的技术路线。2022.2 工具链配 Vitis AI 3.0 有官方验证依据；KV260 DPU、视觉检测、人脸相关推理以及主机端视听模型分别有公开实现。但是，本次没有找到与你们全部功能、引脚、镜像和模型组合完全一致的成品工程，也没有取得当前整机通过测试的证据。因此可以确认有可靠起点，不能确认“重装后一次成功”或“三十天全部完成”。

当前目标按三十天计划理解：板端 DPU 检测与身份链、PS 跟踪和身份库、自研 PL 运动监督与双麦方向、板端音视频和界面，以及主机上的 Light-ASD、ASR、VLM、TTS。早期“身份只放 Windows”“Light-ASD 不必做”的简化描述不能代替当前目标。

## 1. 版本与构建路线

建议固定候选组合：Vivado 2022.2、Vitis 2022.2、PetaLinux 2022.2、Vitis AI 3.0，以及该版本发布的 DPUCZDX8G 4.1。AMD 的版本表支持这组关系。这里的 3.0 是 Vitis AI 发布版本，4.1 是 DPU IP 版本，不能把两者当成冲突。[官方兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)

必须先固定最终构建路线：

| 路线 | 公开依据 | 配套要求 | 对当前项目的意义 |
|---|---|---|---|
| Vitis 平台 / overlay | 官方 `kria-vitis-platforms` 的 `xlnx_rel_v2022.2` 分支含 KV260 平台和 DPU overlay；benchmark 的构建入口使用 `v++` 生成 `xclbin` | VART 与 XRT 配套，保持平台、加载文件和设备树一致 | 建议作为从头重建时优先验证的参考路线；它有明确 KV260 源码起点，但尚未在你们机器上复现 |
| Vivado 直接集成 DPU | AMD 支持在 Vivado 设计中加入 DPU 和自研逻辑 | 对 Kria/MPSoC，VART 按 standalone、无 XRT 方式构建；采用对应配方 | 可以沿用已有 RTL 工作方式，但此前自定义工程的时钟、复位和系统配套问题仍需关闭 |

以上是两种选择，不是两套运行时一起安装。也不能仅凭库文件名含 `xrt` 判定实际走哪条路线；需检查有效构建配置及运行时行为。[官方系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)

官方 KV260 工程可作为参考；这不表示它与已下载镜像字节完全同源，也不表示任意替换它的位流后原镜像必然工作。应先复现原参考，再加入最小 AXI 寄存器，证明 DPU 与自研逻辑在同一次配置中共存。[KV260 参考源码](https://github.com/Xilinx/kria-vitis-platforms/tree/xlnx_rel_v2022.2/kv260)、[benchmark 构建入口](https://github.com/Xilinx/kria-vitis-platforms/blob/xlnx_rel_v2022.2/kv260/overlays/examples/benchmark/Makefile)

模型与应用证据：[Vitis AI 3.0 模型支持表](https://docs.amd.com/r/3.0-English/ug1354-xilinx-ai-sdk/Models-Supported-by-Vitis-AI-Library-v3.0)、[KV260 官方快速开始](https://xilinx.github.io/Vitis-AI/3.0/html/docs/quickstart/mpsoc.html)、[ByteTrack 作者仓库](https://github.com/FoundationVision/ByteTrack)。人脸“支持表存在”不等于所有旧模型下载链接今天都可用，更不等于已经适配本队 B2304；仍须实际取得工件并测试。

主机模型证据：[Light-ASD 作者代码与权重](https://github.com/Junhua-Liao/Light-ASD)、[SenseVoice 接口与样例](https://k2-fsa.github.io/sherpa/onnx/sense-voice/python-api.html)、[中文 VITS 工件](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/vits.html)、[Qwen2.5-VL-3B 模型卡](https://huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct)。

不要将 Vitis AI 3.0 的旧版模型编译环境与 Qwen、Light-ASD 的主机推理环境强行合成一个 Python 环境。建议模型编译容器、ASD 环境、VLM 环境、语音环境分别锁定，通过服务接口交换数据。这是降低依赖冲突的工程建议，具体 Python / PyTorch / CUDA 版本须结合实际 GPU 和冒烟测试确定。

项目不需要 Android 系统、Android Studio 或 APK；用户此前提到的“安装包”应按 Linux 构建机、ARM64 板端和主机模型三个位置区分。

## 3. 有哪些事情已有先例，哪些仍不能保证

1. **有官方同板起点：** KV260 预构建 DPU 镜像、参考平台和检测例程。适合优先建立可信基线。
2. **有同类功能实现：** 人脸推理、ByteTrack、Light-ASD、SenseVoice、VITS、Qwen。它们分别证明该模块可实现，不能代替整机并发测试。
3. **未验证的系统组合：** 同一配置中 DPU + 自研控制 + 双麦 + 相机 + 显示；同一主机上 ASD 和 VLM 的资源竞争；跨设备音视频时间对应。这些是本项目最主要的集成风险。

旧自定义模型是 B2304 路线；官方模型性能表的 KV260 测试配置是 B4096F。因此官方表中的吞吐不能直接当本队性能，已有 B2304 模型也不能直接认定适合新镜像。以板端实际 DPU 架构/指纹与模型编译目标匹配为准。[官方性能配置表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/ModelZoo_VAI3.0_Github_web.htm)

Light-ASD 的作者 demo 接受视频并输出逐人说话状态，不等于已经提供适合转动摄像头、实时局域网和多人切换的完整服务。保持目前“主机处理、有限候选、有限窗口”的方向合理；不能把模型名里的 Light 理解为可直接放进 KV260 DPU。

板端身份是当前正式目标。Windows 人脸示例可用于对照，不能把主机结果算成板端 DPU 身份已完成。检测、关键点、特征模型共享 DPU 后的帧龄和排队必须实测。

外设方面仍要保留真实平台约束：参考平台的 Pmod 音频功能可能与自研双麦/舵机引脚冲突；实际屏幕输出路径要在最终平台验证。重装 Vivado 不能解决引脚冲突、音频时钟漂移或不匹配的显示管线。

## 4. 现在应该按什么顺序做

1. 保存已校验的官方镜像、审查证据、独有源码、约束及许可证资料。可重装工具，但不把“只留镜像、其余全删”当作可恢复备份。
2. 以备用卡运行官方镜像和原配示例，留下冷启动与重复推理结果；这一关可以独立于完整工具链重装进行。
3. 安装/验证 2022.2 构建工具，优先复现选定的官方 KV260 参考。记录源码提交、DPU 包、有效运行时配方和最终产物哈希。
4. 保持参考 DPU 配置，先加入一个最小可读寄存器，再逐个加入运动和双麦逻辑。每次验证相机、显示及 DPU 未回退。
5. B 并行验证板端检测和身份候选；C 在主机运行 Light-ASD、ASR、TTS、VLM 固定样例。全部单项通过后才接整机实时链。
6. 通过重复冷启动、固定输入回归、整机长时间负载和断连/取消测试后，冻结最终镜像、模型、服务环境及恢复步骤。此时才能追求以后“一次烧录、按清单启动”。

建议验收沿用综合报告：10 次冷启动、10 次正常重启、固定输入重复推理及数小时负载，并单独验证实际运动波形。这些是项目建议门槛，不是 AMD 官方认证指标。不能只观察输出分类名不变，应检查原始输出、错误日志与任务完成状态。

## 5. 尚未闭合的核对项

| 项目 | 当前缺口 | 如何闭合 |
|---|---|---|
| GPU 主机能力 | 显卡型号、显存、驱动、内存及是否为当前 Windows 电脑未确认 | 读取硬件清单并运行一张图片和一个 ASD 视频 |
| 最终平台路线 | Vitis 与 Vivado 路线尚未完成一次受控重建 | 选择一条并完成原参考复现；不要先混装运行库 |
| 最终模型工件 | YOLO、人脸权重及各依赖精确版本未形成已测试锁定清单 | 取得工件、校验、编译、板测后固定哈希 |
| 官方镜像运行 | 本地传输和压缩检查通过，尚无此次新卡板测结果 | 官方例程、相机/显示/网络、冷启动测试 |
| 旧工程异常 | 时钟、复位语义及最新硬件与旧系统混配问题未关闭 | 保留对照，核对设计和有效配置，板端回归 |
| 下载完整性 | 文档/发布入口存在不代表所有大包实际取得 | 每个包记录源链接、大小、发布校验值（若有）、本地 SHA256、解压结果 |

本次结论是“路线有依据，部分包可确定，关键集成仍需验证”。不把未知项填成已通过，也不据此声称 Ubuntu 或所有已安装工具损坏。
