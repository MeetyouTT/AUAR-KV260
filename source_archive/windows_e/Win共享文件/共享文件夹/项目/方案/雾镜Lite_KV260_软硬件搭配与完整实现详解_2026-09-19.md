## 1. 最终要做出什么设备

雾镜 Lite 是一台放在桌面或展台上的固定式视听交互终端。它有摄像头、屏幕、麦克风、扬声器和一个有限角度的水平转轴。设备可以调整朝向，但本期没有移动底盘，也不把水平转动等同于能够俯仰或观察任意位置。

一次预期的完整体验是：

1. 来访者进入摄像头视野，系统检测到人，屏幕玩偶进入关注状态。
2. 系统选定当前交互对象，转轴缓慢调整朝向，让这个人靠近画面中央。
3. 用户按住说话键提问，松开后提交录音。
4. 系统取得本轮实际画面，将语音识别结果和图片交给本地主机上的视觉语言模型。
5. 扬声器播放回答，屏幕显示字幕和对应动画。
6. 用户明确同意后，系统保存姓名、人脸特征和经过确认的偏好。
7. 已登记用户离开后重新出现，系统在识别有把握时恢复身份并问候。
8. 接入双 I2S 麦克风并通过测试后，系统可以用粗声音方向辅助判断应该与哪位来访者交互。

“看到有人”“知道哪个人在说话”“知道这个人叫什么”“理解他展示的物品”是四种不同能力，分别需要检测、视听关联、人脸识别和图像语义理解，不能用同一个检测结果替代。

### 1.1 本期能力与后续扩展

| 层级 | 计划内容 | 在整机中的作用 |
|---|---|---|
| P0 基础产品 | 人体检测、跟踪、单轴随动、运动保护、板端界面、按键语音、看图问答、身份登记与记忆 | 构成完整实体交互体验 |
| P1 创新目标 | 双 I2S 麦克风、FPGA 粗方向判断、视听目标确认 | 提高多人场景下选人的可靠性 |
| P2 条件增强 | 主动转头观察、物品登记、历史事件、图像预处理加速、语音唤醒和全双工 | 主线稳定后按证据选择 |
| P3 后续预研 | 纯板端大模型、更多运动自由度等 | 单独评估资源与工程工作量 |

实施时先打通“检测—选人—FPGA 控制—实体转动—新画面”的基础闭环，再接入对话和身份等能力。这个先后顺序不意味着取消完整产品目标。

## 2. 整套系统由哪些计算部分组成

### 2.1 四个位置，各自做什么

| 位置 | 承担工作 | 输出结果 |
|---|---|---|
| KV260 的 PS，运行 ARM/Linux | 相机与音频采集、图像预后处理、跟踪、选人、场景管理、视觉控制、界面与对话编排 | 当前对象、运动请求、对话请求、界面状态 |
| KV260 的 PL，即 FPGA 可编程逻辑 | DPU 神经网络加速、自研运动 IP、自研音频方向 IP | 检测网络结果、受约束 PWM、声音方向事件 |
| Windows GPU 主机 | ASR 语音识别、VLM 看图问答、TTS 语音合成、人脸识别与身份库 | 问题文字、回复文字、音频、身份结果 |
| Linux 开发环境 | 构建硬件工程、准备匹配的系统与模型部署工件 | 位流、平台、设备树、模型及部署包 |

Windows 主机属于首版完整产品的运行依赖。Linux 构建环境主要在开发和重新构建时使用，不要求每次演示都参与推理；它可以是另一台电脑，也可以是经过验证的同一台电脑上的 Linux 环境。

### 2.2 PS、PL、DPU、IP 到底是什么

PS 可以理解为板卡上运行程序和操作系统的处理器部分。PL 是可通过硬件设计配置出的数字电路。你用 Verilog 描述计数器、状态机、比较器和数据通路，再由工具把它们实现到 PL 中。

IP 在这里表示可集成的硬件功能模块。例如一个运动 IP 可以包含寄存器、命令检查、限速、PWM 和故障状态机。它不是一个单独购买的外接器件，也不是网络中的 IP 地址。

本项目使用的 DPUCZDX8G 是放在 PL 中的神经网络推理加速模块。DPU 与自研运动、音频模块共用 FPGA 的逻辑、存储、乘法运算和互连资源，因此要一起做资源与时序预算。更换匹配的模型工件和重新配置整个 FPGA 是两种不同操作。[AMD DPU 系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)

### 2.3 整机逻辑关系

~~~mermaid
flowchart TD
    CAM["USB 摄像头"] --> CAP["KV260 PS：统一采集与帧缓存"]
    CAP --> DPU["KV260 PL：DPU 人体检测"]
    DPU --> TRACK["PS：后处理、跟踪、当前对象"]
    MIC["共时钟 I2S 双麦"] --> DOA["PL：采样、互相关、方向与质量"]
    DOA --> FUSE["PS：视听目标确认"]
    TRACK --> FUSE
    FUSE --> CTRL["PS：视觉误差与受限转向请求"]
    CTRL --> GUARD["PL：命令检查、有效期、限速、PWM"]
    GUARD --> SERVO["舵机与水平转盘"]
    SERVO --> CAM
    USBMIC["USB 对话麦克风"] --> DIALOG["PS：录音与对话编排"]
    CAP --> DIALOG
    DIALOG --> HOST["Windows：ASR、VLM、TTS、身份"]
    HOST --> DIALOG
    DIALOG --> OUT["板端扬声器、字幕与玩偶"]

~~~

图中的方框表示职责，最终不必每个方框都单独启动一个进程。应按阻塞风险和故障隔离需要划分程序。

### 3.1 板卡接口怎样对应

以下接口名称与连接器标号来自 AMD UG1089，接线前仍需确认手中载板的版本与丝印。

| 板卡接口 | 手册标号 | 本项目用途 |
|---|---|---|
| Pmod 2×6 扩展口 | J2 | 双麦信号、PWM、停止与可用的控制信号 |
| FTDI USB UART/JTAG | J4 | 电脑调试连接 |
| HDMI / DisplayPort | J5 / J6 | 屏幕视频输入 |
| 千兆以太网 | J10 | 连接 Windows 主机 |
| microSD | J11 | 系统与文件存储 |
| 12 V 电源输入 | J12 | 板卡供电 |

板卡上的 SW1 是固件更新按钮、SW2 是复位按钮，不能把它们直接定义为用户说话键或外部停止键。官方资料区分载板 rev. 1.0 和 rev. 2.0，工程文件必须与实物对应。[AMD 接口说明](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Interfaces)

## 4. 实体结构、供电和布线怎样安排

### 4.1 推荐的结构关系

固定底座放置承重与驱动结构，上部旋转部分放置摄像头和面向用户的屏幕。双麦优先安装在与摄像头共同转动的刚性支架上，这样“音频左侧”和“图像左侧”可以通过一次几何标定建立关系。

KV260、功放和其他较重部件的位置，需根据外壳尺寸、重心、散热和走线决定。它们留在底座可以减少转动惯量，但需要为相机、显示和音频留出柔性的运动线束；放在转动部分则需要重新核算重量和电缆扭矩。选定一种结构后，再进行控制标定和最终测试。

转盘与轴承承受机身重量，舵机通过联轴器或传动结构施加转矩。只检查舵机标称扭矩还不够，还要检查惯量、加减速、传动空回、线缆拖拽和偏心。竖直水平转轴主要需要克服惯性、摩擦与线束阻力，不能直接用“重量乘半径”替代全部选型计算。

单水平轴只能改变左右朝向。若相机俯角和视场无法覆盖桌面物品，水平转动不会自动解决这个问题；需要调整安装位置或把俯仰轴作为另一个机械变更。

### 4.2 电源树

~~~text
合适的板卡电源 ──> KV260 ──> 配套散热与预算内的 USB 外设
合适的舵机电源 ──> 保护/使能或断电通路 ──> 舵机
屏幕规定的电源 ──> 显示屏
音频规定的电源 ──> 功放/有源音箱

PL PWM ──> 经核验的电平接口 ──> 舵机信号输入
控制信号的地参考按最终电路正确连接
~~~

AMD 给 KV260 的电源要求为 12 V、3 A；Pmod 电源能力标注为 3.3 V、100 mA。USB 单口上限和所有端口总预算也需要同时满足：官方列出的单口上限为 900 mA，四口合计预算为 2.1 A。这些是接口供电边界，不是整机实测功耗。[AMD 电源预算](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Powering-the-Starter-Kit-and-Power-Budgets)

实现时重点确认：

1. 舵机额定电压、启动与堵转电流，以及电源是否承受得住瞬时负载。
2. 屏幕的视频线与供电线分别是什么，不能默认插入 HDMI 就能供电。
3. 使用无源扬声器时是否已有合适功放；音频信号输出不能直接承担扬声器功率。
4. 摄像头和音频设备同时接入后，USB 总电流与传输是否稳定。
5. 电机大电流回路与麦克风、控制信号的回流路径是否造成噪声和电压波动。

共地指为非隔离控制建立正确参考，并不意味着让电机的大电流流过细小的 Pmod 地线。电平不兼容时增加合适的接口电路；不得把未经确认的高电压信号送入 FPGA 引脚。

### 4.3 Pmod 信号数量要先算清

按常见 Pmod 布局，12 个位置中包含电源和地，不能按 12 根普通信号使用。本项目可先按 8 根信号的预算审核，最终以原理图与约束文件为准。

| 信号用途 | 数量 | 方向 |
|---|---:|---|
| 双麦共用 BCLK、WS | 2 | PL 输出 |
| 左右麦各自 SD | 2 | PL 输入 |
| 舵机 PWM | 1 | PL 输出 |
| 外部停止检测 | 1 | PL 输入 |
| 按需执行器使能 | 1 | PL 输出 |
| 按需位置确认输入 | 1 | PL 输入 |
| 合计 | 8 | 已占满这一示例预算 |

这是一张功能预算表，不是已经冻结的引脚表。若平台、显示或音频参考设计已经使用 Pmod，必须重新分配。说话键等额外输入可以优先使用 UI 或经验证的 USB 按键，不能继续往已占满的口上叠加。

正式接线表必须逐项填写：载板版本、连接器脚位、芯片管脚、信号方向、电压标准、上拉/下拉、时钟约束、外设型号和核验依据。

### 4.4 停止键与线束

停止键应在设备外部可直接触及。其逻辑状态进入 PL，而是否同时切断执行器供电或使能，要依据舵机和机构的实际失效行为设计。PL 未配置时不能依赖尚不存在的 FPGA 状态机，因此上电默认禁能需要电路和启动流程共同保证。

线束只支持已经验证的有限转角。装配时先手动检查全行程是否拉紧、夹线或碰撞，再做小角度通电。不得用扩大 PWM 范围去补偿机械干涉。

## 5. KV260 平台和开发工具如何搭配

### 5.1 内存、存储与启动

KV260 有 4 GB DDR4，PS 程序、图像缓存和 DPU 数据都会消耗内存与带宽。官方套件所用 SOM 不装配 eMMC，启动体系包括 QSPI 固件与 microSD 次级启动存储，不能照搬其他 K26 产品的存储假设。[KV260 产品资料](https://docs.amd.com/r/en-US/ds986-kv260-starter-kit/Product-Details)

建议保留一张可恢复的已验证系统卡。工作卡保存板端软件、配置和轮转日志；主机大模型放在 Windows 的合适磁盘上。日志、音频和图片都设置容量上限，避免长时间运行把存储写满。

### 5.2 每个工具究竟负责哪一步

| 工具或组件 | 作用 | 典型产物或运行位置 |
|---|---|---|
| Vivado | 设计 PS/PL 连接、综合 RTL、布局布线、检查时序与引脚 | 硬件设计、位流、硬件平台导出 |
| Vitis | 所选平台的软件或加速应用构建与链接 | 应用程序或平台相关加速包 |
| PetaLinux | 为选定硬件准备 Linux、设备树、驱动和用户态组件 | 匹配硬件的系统部署工件 |
| Vitis AI 量化器与编译器 | 处理受支持模型并针对实际 DPU 编译 | 与目标 DPU 匹配的模型工件 |
| VART / XIR | 板端加载模型、管理张量并调用 DPU 等 | Linux 运行时 |
| XRT | Vitis 集成路线中的加速运行时 | 仅在选定路线需要时使用 |
| Verilog/SystemVerilog | 描述自研硬件逻辑 | 运动、音频 RTL 与测试平台 |
| Python/C++ | 编写板端服务、算法、主机服务和验证程序 | PS 与 Windows 应用 |

当前项目文件采用的历史兼容组合是：

~~~text
Vivado / Vitis / PetaLinux 2022.2
Vitis AI 3.0
DPUCZDX8G IP 4.1
~~~

AMD 的对应版本资料列出了这个组合。它是本项目用于复现的版本基线，不代表其他日期发布的镜像、模型和工具都能混用。[AMD 版本兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)

### 5.3 必须选定一种硬件加载路线

| 路线 | 核心特点 | 需要避免的问题 |
|---|---|---|
| 沿匹配的 Vitis 参考平台集成 | 使用该平台的加速包与运行时，可能包含 xclbin | 不能换成另一路线的驱动后仍按原方式加载 |
| 沿 Vivado DPU 集成路线 | 在硬件设计中集成 DPU，按该路线准备 Linux 与 VART | 不能默认要求一个不存在的 xclbin |
| 使用经过验证的 PYNQ 平台 | 可以使用其 Overlay 和 MMIO 等接口 | 普通 Linux 镜像不会自动成为 PYNQ 平台 |

AMD Vitis AI 3.0 明确区分 Vitis 与 Vivado 路线的 VART/XRT 配置。先重建并运行匹配参考平台，再按该路线加入自研模块。[AMD 集成与运行时说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)

理解文件后缀有助于避免部署混乱：

- 位流描述 FPGA 配置。
- XSA 描述导出的硬件平台信息。
- 设备树让 Linux 知道设备、地址、中断等信息。
- xmodel 是 DPU 模型部署工件。
- xclbin 是特定加速平台路线使用的容器工件。
- hwh 常用于对应平台的硬件元数据解析，不能认为所有路线都必须加载它。

最终交付应列出本工程实际需要的文件与加载顺序，不把所有后缀机械地放在一起。

## 6. USB 摄像头：怎样让所有功能使用同一份现场画面

### 6.1 连接与采集

首版采用 USB UVC 摄像头，连接 KV260 USB。Linux 通过视频设备接口获取画面，采集程序可用 V4L2、经过配置的 OpenCV 或 GStreamer。具体后端依据最终镜像选择。

先检查摄像头实际支持的分辨率、帧率和格式，再确定模式。项目可从 640×480 开始验证，检测网络的输入尺寸另按模型要求处理。摄像头每秒采到 30 帧，不代表 DPU 每秒完成 30 次有效检测。

### 6.2 为什么只开一个采集服务

同一画面将用于人体检测、屏幕预览、人脸识别和看图问答。如果每个程序都独立打开摄像头，容易发生设备争用、缓冲不同步以及“嘴上说当前画面，实际上用了另一张图”的问题。

因此设计一个唯一采集入口：

~~~text
摄像头
  └─ 统一采集服务
       ├─ 最新帧 → 人体检测
       ├─ 当前帧或对应人脸区域 → 身份请求
       ├─ 本轮快照 → VLM 问答
       └─ 降频预览 → 屏幕显示
~~~

每帧附带启动标识、相机代次、帧编号、时间及其来源、图像尺寸和格式。图像与这些信息必须保持配对，不能把第 100 帧的图片与第 101 帧的时间组合起来。

### 6.3 时间与缓存

记录相机或驱动提供的时间、程序出队时间、推理结束时间。驱动时间戳的含义和时钟类型需要核验；它不天然就是准确曝光时刻。Linux V4L2 为缓冲时间戳及其标志提供了定义。[Linux V4L2 缓冲说明](https://www.kernel.org/doc/html/latest/userspace-api/media/v4l/buffer.html)

视觉待处理队列优先只保留最新一帧，避免算法忙碌后连续处理过去的画面。与此同时要检查驱动、解码器和后端自己的缓存；仅把 Python 队列改成 1，并不能消除上游缓存。

“最新一帧”也可能已经很旧。相机冻结或断开时，即使缓存里仍有图片，也必须按原时间判定失效。应用重新发布同一张图不能刷新它的采集时间。

### 6.4 做到什么算通过

先完成固定图片保存，再完成连续采集和重连。最后让检测、预览和快照请求同时使用采集服务，确认它们不会互相阻塞，图像编号可以追溯，摄像头停帧能被发现。

## 7. DPU 人体检测与 PS 跟踪：怎样从图像得到交互对象

### 7.1 检测模型做什么

检测器输入一张经过规定预处理的图片，输出边界框、类别和分数。当前首版候选是 AMD 模型库中的 YOLOX-Nano 相关工件；优先使用与实际参考平台匹配、已经能运行的轻量检测模型。[AMD 模型条目](https://github.com/Xilinx/Vitis-AI/tree/3.0/model_zoo/model-list/pt_yolox-nano_coco_416_416_1G_3.0)

工程顺序是“固定图片 CPU 参考—匹配 DPU 单图推理—相机实时输入”，再根据现场失败样本决定是否需要微调。只筛选 person 类主要减少后处理内容，并不自动减少整个网络主体的计算。

### 7.2 一帧在 PS 和 DPU 之间如何流动

~~~text
USB 采集到 PS
→ 解码/颜色格式整理
→ resize 或 letterbox
→ 按模型要求形成张量
→ VART 提交 DPU 推理
→ 读取网络输出
→ 解码、筛选、按需 NMS
→ 坐标还原到原图
→ 发布带 frame_id 的人体框
~~~

预处理要冻结 RGB/BGR、输入尺寸、数值范围、布局、填充值和量化规则。不要给一个要求原始数值范围的模型额外做错误归一化，也不要把其他模型的后处理直接套上来。

以 640×480 图片按比例放入 416×416 的输入为例：若选择居中 letterbox，缩放后为 416×312，上下各填充 52 像素。检测框还原时必须先减去填充，再除以缩放比例。这个例子解释坐标变换，实际模型可能使用不同预处理，必须跟随工件说明。

板端程序通过运行时分配和提交张量。若以后加入自研图像 DMA，还需要处理连续缓冲、对齐、缓存一致性和所有权，不能假设任意 Python 图像数组都能直接被 PL 正确读取。

### 7.3 量化与编译

量化用有限精度表示数值，以适应目标推理实现。应使用与最终场景有代表性的校准数据，并比较源模型和部署模型在同一批输入上的输出。

编译器需要实际 DPU 架构对应的信息。DPU 配置变化后，原模型工件未必仍然匹配。模型能导出 ONNX，只说明完成了一种格式转换，不能替代目标算子支持检查与 DPU 编译验证。

保存模型来源、版本、哈希、输入输出约定、DPU 配置和编译日志。官方示例能运行后，再使用本项目的数据衡量漏检、误检及实际更新频率。

### 7.4 跟踪为什么放在 PS

检测只说明“这一帧这里有人”；跟踪负责关联“这一帧的人是否对应上一帧的人”。首版可用 IoU，即两个框的交集面积除以并集面积，配合位置变化和连续确认完成关联。

一个可实施的首版跟踪流程是：

1. 对已有轨迹做短时位置预测。
2. 计算新检测框与已有轨迹的关联代价。
3. 执行一对一匹配，避免一个框同时接到两个人。
4. 对可靠匹配更新轨迹；未匹配轨迹短时保留；新目标经过连续确认再建立。
5. 丢失超过条件后释放轨迹，并撤销相关身份和运动依据。

若多人交叉和遮挡的失败率较高，再参考 ByteTrack 的两阶段关联。ByteTrack 与 BoT-SORT 的完整系统有各自前提，采用其中方法时需要注明复用范围。[ByteTrack 原论文](https://www.ecva.net/papers/eccv_2022/papers_ECCV/papers/136820001.pdf)、[BoT-SORT 原论文](https://arxiv.org/abs/2206.14651)

### 7.5 选定当前交互对象

初次选择可以考虑检测可信程度、框大小、位置和交互区域。一旦锁定对象，设置保持和切换条件，避免某个人暂时靠近中心就抢走当前会话。

区分三个编号：

| 编号 | 意义 | 失效或更新时机 |
|---|---|---|
| track_id | 一段视觉轨迹 | 丢轨、重新关联或跟踪重启 |
| presence_session_id | 这次与某位来访者的交互会话 | 确认离场、切换对象或无法可靠接续 |
| person_id | 登记库中的持久身份 | 经身份确认得到，删除或库变更后重新核验 |

摄像头自身转动会改变所有人的图像坐标。可先用背景运动估计补偿整体位移；估计不可靠时降低关联信任，不能只靠舵机命令假定相机已经准确到位。

## 8. 视觉控制与舵机：怎样让人保持在画面中央

### 8.1 先核实是哪种电机

本方案默认有限角度位置舵机：控制信号表达目标位置，舵机内部执行位置调节。

若实际购买的是连续旋转舵机，类似 PWM 常用于表达转速和方向，不能直接套用“目标角度”方案。步进电机、直流电机还需要各自驱动器、反馈和控制设计，必须在编写运动逻辑前确认型号。

### 8.2 从人体框得到转向请求

设原图宽度为 W，目标框中心横坐标为 cx，定义：

~~~text
e = (cx - W/2) / (W/2)
~~~

e 为零表示目标在中心，正负表示图像左右偏差。显示画面可能镜像，因此“误差符号对应哪边转”必须用台架小角度实验标定。

先过滤检测框的微小抖动，再设置中心死区。若死区参数 d 使用上述归一化单位，d=0.1 表示离中心的距离为半画面宽的 10%，即全画面宽的 5%；文档与程序必须使用同一个定义。

一种简单控制形式是：

~~~text
e_dead = sign(e_filtered) × max(abs(e_filtered) - d, 0)
omega_request = direction_sign × Kp × e_dead
omega_request = 限制在允许的指令角速度范围内
theta_request = theta_previous + omega_request × dt
theta_request = 限制在允许的指令角度范围内
~~~

Kp 把图像误差换成转向请求。dt 使用实际有效更新间隔，长时间暂停后先重置控制状态，不能把很大的 dt 直接积分成一次跳转。内部 theta 应依据硬件已接受的受限指令更新，避免软件累计了硬件根本没有执行的目标。

### 8.3 滤波、死区、限速分别解决什么

| 方法 | 解决的问题 | 使用时注意 |
|---|---|---|
| EMA 平滑 | 检测框在相邻帧间跳动 | 平滑过强会带来跟随滞后 |
| One Euro 滤波 | 在静止抖动和快速移动响应之间调整 | 按实际时间间隔更新，换目标需重置 |
| 中心死区 | 居中后仍不停微调 | 明确坐标单位和宽度定义 |
| P 控制 | 偏差大时加快追随、偏差小时减慢 | 方向和增益必须实测 |
| 指令限速 | 一次目标变化太大 | 约束的是指令变化，不等同于测得实际机械速度 |
| 软限位 | 防止指令超出允许范围 | 需与物理机构和线束范围一致 |

首版先比较“无滤波、EMA、One Euro”的效果，再决定最终配置，不需要一开始就叠加复杂 PID。

### 8.4 角度如何变成 PWM

经过标定，可以把允许指令角映射成脉宽：

~~~text
pulse_us = p_min + (theta - theta_min) × (p_max - p_min) / (theta_max - theta_min)
~~~

真实映射可能存在非线性、空回和方向差异，需要时改用标定表。PWM 周期、最小/最大脉宽及中位必须读取舵机手册再测试，不能把常见的 50 Hz、1—2 ms 当作所有舵机的通用规格。

仅解释数字电路的例子：若硬件时钟为 100 MHz、已经确认的 PWM 周期为 20 ms，那么周期约为 2,000,000 个时钟计数；1.5 ms 脉宽约为 150,000 个计数。实际工程还要处理计数范围、减一关系、舍入和参数位宽。这个算例不能直接作为尚未确定型号的舵机参数。

### 8.5 没有编码器时能知道什么

系统可以知道自己接受了什么指令、输出了什么脉宽，以及目标是否在画面中央。若没有外部位置反馈，就不能把指令角显示成实际测得的转轴角。

视觉闭环可以不断修正目标居中，但不能单靠它证明每个机械角都准确到位。上电、断力或机构被手动移动后，应进入需要参考位置确认的状态；直接发送中位并不能消除首个动作突跳的可能。

## 9. 自研运动 FPGA 模块：怎样实现可靠的执行通路

### 9.1 总体模块分解

~~~text
PS 唯一运动服务
→ AXI4-Lite 寄存器
→ 影子命令 + 原子提交
→ 会话/序号/范围/有效期检查
→ 指令变化限制
→ 角度到脉宽映射
→ PWM 发生器
→ 输出门控/执行器接口

停止输入、到期计时器、复位与故障状态
→ 独立影响许可和输出
~~~

| 建议模块 | 具体实现内容 |
|---|---|
| axi_regs.sv | AXI4-Lite 读写握手、地址、写掩码、读回与错误响应 |
| command_guard.sv | 使能、会话、序号、安全代次、范围和租约检查 |
| slew_limiter.sv | 每个控制更新步允许的指令变化 |
| pulse_mapper.sv | 经标定的角度到脉宽转换 |
| pwm_generator.sv | 周期计数和正常更新边界 |
| stop_watchdog.sv | 停止同步、到期检测、故障锁存与恢复条件 |
| timestamp_telemetry.sv | 接受/拒绝记录、计数、状态快照 |
| motion_guard_ip.sv | 模块连接、复位、状态机和输出门控 |
| tb_motion_guard.sv | 自动检查正常、边界及异常行为 |

### 9.2 PS 如何真正写入 FPGA

PS 通过 AXI 访问分配给运动 IP 的寄存器地址。Vivado 中要连接 PS 的相应主接口、互连、时钟与复位，并在地址分配中确定真实范围。Linux 中的设备树和驱动映射必须一致。

应用层只有一个运动服务获得设备访问权。视觉程序提交请求，界面提交启停意图，模型服务没有寄存器写入权限。底层可以使用经验证的 UIO/MMIO 或匹配平台提供的接口，不能仅凭示例里的固定地址访问实际硬件。

### 9.3 为什么需要影子寄存器和 COMMIT

一条运动命令包含角度、序号、会话和有效期等多个字段。PS 分多次总线写入，如果硬件边写边执行，就可能读取到“新角度＋旧会话＋旧有效期”。

因此先把字段写到影子区，最后写一次 COMMIT。硬件在该事件上取得一致的命令快照，统一检查后整体接受或拒绝。总线写成功，只表示总线事务完成；是否接受动作要查看应用级状态和拒绝原因。

AXI 写地址与写数据通道独立，不能假定它们永远同一拍到达。还要处理背压、部分字节写入、非法地址和字段不完整等情况。

### 9.4 寄存器至少表达哪些内容

| 类别 | 典型字段 | 用途 |
|---|---|---|
| 身份与配置 | IP_ID、VERSION、CONFIG_CRC | 防止驱动与硬件版本错配 |
| 控制与状态 | CONTROL、STATUS、FAULT | 禁能、受控使能、故障查询 |
| 命令归属 | MOTION_SESSION、SAFETY_EPOCH | 防止重启和恢复后旧命令生效 |
| 命令内容 | CMD_SEQ、TARGET_MDEG、LEASE_US | 顺序、指令角、剩余许可时间 |
| 提交结果 | COMMIT、APPLIED_SEQ、REJECT_REASON | 确认请求实际是否被接受 |
| 运行回读 | LIMITED_TARGET、PWM_EFFECTIVE、计数快照 | 排查限速、映射和异常行为 |

角度可统一使用有符号整数毫度。每个寄存器仍需规定偏移、位宽、读写属性、复位值和副作用。64 位时间与多字段状态需一致快照，不能任意拼接两次可能跨更新的读取。

### 9.5 有效期怎样与原画面相连

普通“心跳还活着”只能说明某段程序仍在运行，不能说明相机仍在产生新画面。因此命令许可必须受原始证据的截止时间约束。

以下为说明逻辑的算例，数值不是实测配置：

~~~text
某帧的参考时间：1000 ms
允许帧龄：300 ms
该帧固定截止时间：1300 ms
提交前当前时间：1120 ms
预留提交误差：20 ms
硬件最大租约：200 ms

本次剩余租约 = min(200, 1300 - 1120 - 20) = 160 ms
~~~

驱动在真正提交前重新计算，若结果不为正则拒绝。重复命令、逆序命令和错误会话不能刷新已有租约；同一帧改一个新序号也不能获得新的证据截止时间。

采用相对租约时，硬件保证的是“接受后的许可时长”。若要给出严格的采集到执行上界，还必须约束采集时间定义、PS 提交延迟与 PS/PL 时钟映射误差。PL 不能只凭软件传来的数字判断真实曝光时间或图像语义是否正确。

### 9.6 状态与恢复

~~~text
上电/重载 → DISARMED
自检通过但位置未知 → NEEDS_REFERENCE
人工位置确认与配置检查通过 → ARMED
有效目标与许可到达 → TRACKING
到限位 → 保持允许范围内状态
停止、超时或故障 → 撤销许可，进入对应禁能/故障状态
人工核对后 → 清故障、重建会话、位置确认、再次使能
~~~

界面取消播报、网络重新连通、模型恢复，都不能自动清除运动故障或重新使能转轴。

### 9.7 PWM 与停止如何配合

正常脉宽更新在周期边界切换，防止中途改数值形成异常短脉冲。停止路径优先于正常更新，其数字响应通过明确电路测量。

撤销 PWM、保持某个脉宽、切断电源和机械立即停止并不等价。最终选择哪种 SAFE_ACTION，要根据真实舵机、负载和外部使能电路确定。数字波形能证明输出行为，机械响应要另用实物测试。

### 9.8 验证顺序

先用 testbench 检查计数、范围、部分写、背压、重复与逆序、错误会话、超时、停止和复位；再综合实现并检查时序；上板先读版本，再在不连接舵机时测波形，随后轻载、小角度，最后整机负载。

外部停止输入需要同步和已知的检测延迟；释放去抖和人工恢复分开处理。若有多时钟域，单比特和多位数据使用适合的同步方案，多位样本不能逐位各放两个触发器就视为一致传输。

## 10. 双 I2S 麦克风：怎样用 FPGA 判断声音大致方向

### 10.1 它与 USB 对话麦克风的区别

USB 麦克风通常已把声音转换为可供操作系统读取的数字音频，接入对话较方便。I2S 数字麦克风则把音频样本按时钟输出到引脚，团队需要自己实现接收与处理逻辑。

本项目让两个同型号 I2S 麦克风共用时钟，比较同一声音到达两只麦的时间差。输出先限定为 LEFT、CENTER、RIGHT、UNKNOWN，表示前方受控场景下的粗方向与无法判断。

这部分负责声音方向，不识别姓名，也不直接生成用户问题文字。双麦与语音识别可以共享声学场景，但初版的数据链相互独立。

### 10.2 接线与采样

~~~text
PL BCLK ──────> 左麦 BCLK、右麦 BCLK
PL WS   ──────> 左麦 WS、右麦 WS
左麦 SD ──────> PL 左通道数据输入
右麦 SD ──────> PL 右通道数据输入
合适电源与地 ─> 两个麦克风模块
各麦声道选择脚 ─> 按器件手册固定
~~~

优先使用两根独立 SD 降低排查难度。若想把两麦接在同一条数据线上，必须确认其声道选择和非工作槽位的高阻行为，不能直接把两个有源输出并接。

BCLK 是位时钟，WS 区分音频槽位，SD 承载串行数据。标准 I2S 的声道切换与最高有效位存在规定的位时序关系，但实际模块可能采用其他格式；必须核对有效位、槽宽、采样边沿和启动无效数据。[NXP I2S 规范](https://www.nxp.com.cn/docs/en/user-manual/UM11732.pdf)

如果器件使用每帧两个 32 位槽、采样率 48 kHz，则 BCLK 为 48,000×64=3.072 MHz。这个数值只适用于该格式假设。时钟应由经过验证的时钟方案产生，不能随意整数分频后默认采样率已经准确。

### 10.3 在 FPGA 中逐步还原样本

1. 按手册产生时钟并等待麦克风启动稳定。
2. 根据 WS 和位计数定位所需槽位。
3. 在正确边沿依次移入有效位。
4. 对有符号数据进行正确符号扩展。
5. 对齐左右通道，产生一对样本及 sample_valid。
6. 同时递增样本计数，检测缺样与缓冲溢出。
7. 把样本送入窗口缓存，再进行方向计算。

先导出一小段原始音频检查波形和左右通道，确认符号、位序、幅度和实际采样率。若输入本身错位，后面再复杂的算法也不能修复采集错误。

### 10.4 时差为什么能对应方向

当声源偏左或偏右时，到两只麦的路径长度不同。设麦距 d、采样率 fs、声速近似 c，则最大几何时差对应的采样点数约为：

~~~text
最大时差采样点 ≈ d × fs / c
~~~

以 d=0.05 m、fs=48,000 Hz、c≈343 m/s 为算例，结果约 7 个采样点。因此原计划采用小范围延迟搜索有依据，但必须考虑真实通道偏差、安装误差和噪声。

远场、固定几何条件下可以建立时差与方位的近似关系；双麦存在前后歧义，混响、多个同时声源和机身反射也会破坏判断。首版输出粗方向比未经标定就输出“精确角度”更符合当前硬件能力。

### 10.5 短窗互相关怎么计算

记左右样本为 x、y，对多个候选延迟 k 比较：

~~~text
R(k) = sum(x[n] × y[n+k])
~~~

哪一个延迟使两个波形最相似，相关值就可能较大。所有 k 应使用相同长度的有效区间，避免边缘延迟因为参与求和样本数量不同而受到偏置。

例如窗口 N=480、搜索 k=-8…8，可以统一取 n=8…471，得到每个候选 464 个乘累加；17 个候选约 7,888 次乘累加。若窗口每 10 ms 更新一次，理论工作量约每秒 0.79 百万次乘累加，尚未包括预处理与判决。

这个算例说明可以从复用乘法器的时分计算开始，不必一开始布置大量并行乘法器。最终并行度由时钟、窗口截止时间和 DPU 已占资源决定。

### 10.6 为什么不能只找最大峰

静音、削波、噪声或强反射也可能产生一个最大值，所以方向判决需要质量检查：

- 两通道能量是否达到可用范围。
- 是否削波、缺样或缓冲溢出。
- 主峰与其他候选峰的差异是否足够。
- 延迟是否符合标定后的物理范围。
- 连续几个窗口是否支持同一方向。
- 设备是否正在播音或转动，从而受到明显自身干扰。

质量不足返回 UNKNOWN，不能把静音默认解释为 CENTER。左右符号需要用真实左侧、右侧声源标定，不能只凭公式中的 k 正负决定接线方向。

GCC-PHAT 可先作为软件对照：它对频域互相关进行相位相关加权，再恢复时差信息。是否值得加入 FFT 硬件，应由真实录音和资源收益决定；首版时域互相关已经可以构成可验证的自研数据通路。

### 10.7 定点、缓存与结果接口

若输入缩放为有符号 16 位，乘积需正确保留符号和位宽。按 32 位乘积、最多约 480 项求和保守预算，可增加 9 位增长空间；48 位累加器是可评估的设计起点。缩放、舍入、饱和和溢出规则应在 C/C++ 参考与 RTL 中完全一致。

缓存可以采用双缓冲：一个窗口采集、另一个窗口计算。跨时钟域使用一致的握手或异步 FIFO。第一版仅需寄存器输出方向事件和有限长度调试音频，连续音频 DMA 可在确有需求时增加。

建议输出字段为：音频代次、窗口序号、起止样本计数、方向、质量、有效标志、溢出标志。PS 一次读取应对应同一窗口的完整快照。

### 10.8 模块和测试

| 建议模块 | 作用 |
|---|---|
| i2s_clock_ctrl.sv | 产生或管理经过验证的音频时钟 |
| i2s_rx_pair.sv | 双路串行接收与样本配对 |
| audio_window_buffer.sv | 缓冲、窗口切换、计数与溢出 |
| xcorr_engine.sv | 固定延迟范围内的乘累加 |
| doa_decision.sv | 峰值质量、方向映射、连续确认与拒判 |
| audio_regs.sv | 结果快照和调试读取 |
| tb_audio_doa.sv | 延迟、静音、噪声、错位、削波与复位测试 |

先用人工构造的已知延迟向量证明数字实现正确，再用实录验证方向。实录至少覆盖左、中、右、后方、同侧多人、同时说话、设备播音与电机运动。分别统计正确、错误和 UNKNOWN，不能只报告剔除拒判后的准确率。

## 11. 视听融合：声音方向怎样与画面中的人对应

### 11.1 输入是什么

视觉侧提供当前可见的人、图像位置、轨迹稳定性、时间和相机运动状态。音频侧提供粗方向、质量和采样窗口。PS 将它们按时间及几何关系关联，形成当前交互对象。

先标定画面方向与麦克风方向。若预览左右镜像，只改变用户看到的画面时也必须保持算法坐标定义一致。若麦克风固定在底座、相机随轴转动，就需要额外的坐标转换与转角不确定性处理；本文首选二者共同转动。

### 11.2 首版判决过程

1. 检查音频有效且没有过期。
2. 检查附近时间的视觉候选，排除陈旧或关联不可靠的对象。
3. 检查机构是否处于可用的安定状态。
4. 找出与声音方向相符的可见候选。
5. 只有一个可靠候选并持续满足确认条件时，才允许切换交互对象。
6. 同侧多人、声音与画面冲突、目标不可见或质量不足时，输出歧义状态并保留经过核验的原会话或请求用户确认。

“保留原会话”不等于让旧图无限驱动转轴。即使不切换身份，原目标的运动仍需新鲜视觉证据。

### 11.3 三个典型例子

| 场景 | 可用证据 | 合理结果 |
|---|---|---|
| 左右各一人，左侧人讲话 | 音频左侧，左侧只有一个稳定目标 | 连续确认后面向左侧人 |
| 两人都在左侧，其中一人讲话 | 粗方向无法区分两人 | 暂不自动切换，提示或等待更多证据 |
| 设备正在播放回答 | 双麦可能收到自己扬声器 | 抑制声音触发换人，保持当前交互规则 |

普通视觉跟随不应要求用户持续讲话。声音是需要选人或换人时的辅助证据，而安静时的稳定跟随仍依靠视觉链。

### 11.4 USB 音频与 I2S 音频如何对应

两条链的时钟、缓冲和驱动延迟可能不同。共用电脑时间戳并不意味着采样同步。需要测量 USB 录音与 I2S 样本计数的时间偏移、漂移及误差，再规定允许的关联时间范围。

如果以后增加“人脸嘴部运动＋声音”的主动说话人模型，还要为连续人脸片段与音频建立相同时间基准。模型先在主机验证，推理位置和额外延迟单独记录。[Light-ASD](https://arxiv.org/abs/2303.04439)、[流式 ASD 研究](https://machinelearning.apple.com/research/efficient-streaming-audio-visual)

## 12. USB 语音与音响：怎样把一句话收进来再说出去

### 12.1 硬件播放链

~~~text
用户声音
→ USB 麦克风，或模拟麦克风接 USB 声卡
→ KV260 录音程序
→ PCM/WAV 音频
→ Windows 语音识别

Windows 语音合成
→ 网络传输的音频
→ KV260 播放程序
→ USB 声卡/USB 音箱
→ 按需功放
→ 扬声器
~~~

USB 麦克风不一定带播放输出；USB 声卡的线路输出也不一定能直接推动无源喇叭。根据实物选择“带功放的 USB 音箱”或“USB 声卡＋功放＋无源扬声器”等经过核验的组合。

板端应使用稳定设备标识，避免插拔顺序改变后，把另一个设备误当麦克风或输出端。

### 12.2 按键半双工怎么工作

按键按下：取消当前播报、清除旧播放队列、开始录音，UI 显示正在听。  
按键松开：结束录音、检查是否过短或无声、提交识别，UI 显示正在思考。  
回复音频开始实际播放：UI 才切换到说话状态。  
用户再次按键或取消：作废旧轮次，停止旧声音，按新操作进入录音或待机。

录音有最长时长和文件大小限制，避免按键异常导致无界增长。取消需要在板端立即停止播放，不能等待远端模型完成后再处理。

### 12.3 ASR：声音变文字

首版候选是 SenseVoiceSmall 的适用工件，在 Windows 主机上提供 ASR 服务。部署先使用固定音频，再使用实体机实录，确认中文、姓名和常用问题是否识别正确。[SenseVoice 接口说明](https://k2-fsa.github.io/sherpa/onnx/sense-voice/python-api.html)

音频的采样率、声道和编码要符合所选模型。若要把 48 kHz 转成 16 kHz，需要真实重采样，不能只修改 WAV 文件头。识别服务返回文字及本次请求编号；空白、失败和超时要明确表达。

按键结束后识别整段语音不等于逐字流式识别。若以后改成流式，接口、端点检测和取消机制都需要重新验证。

### 12.4 TTS：文字变声音

首版候选是经过验证的中文 VITS 工件，在 Windows 主机上生成音频。需要确认声库、字典、采样率、许可证和中文姓名读音。[VITS 工件说明](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/vits.html)

播放前再次检查轮次是否有效，必要时真实重采样到播放设备支持的格式。音频生成完成、下载完成和扬声器实际出声是三个不同时间点，端到端响应从用户松键计到实际首段出声。

### 12.5 为什么初版暂不依赖全双工

设备播放自己的声音时，麦克风也可能收到它。全双工需要处理回声、缓冲延迟、设备时钟漂移、双人同时说话和误打断，工作量超过“同时打开录音和播放”。

后续增加 AEC 时，回声参考应对应实际送入播放设备的 PCM，并处理延迟与重采样。首版按键半双工先保证听、答、播、取消完整可靠。

## 13. Windows 视觉语言模型：怎样结合真实画面回答

### 13.1 为什么安排在主机上

首版本地视觉语言模型候选是 Qwen2.5-VL-3B-Instruct。它用于图片和文字的联合理解；实际后端、量化方式、视觉组件、显存与延迟要在这台主机上验证。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct)

将它放在 Windows GPU 电脑上，可以让 KV260 的内存和处理预算优先用于持续采集、检测与控制。完整系统通过局域网运行，提前下载全部依赖后再测试断公网冷启动。

“本地运行”在这里指板卡和自带电脑组成的系统。若 Windows 被关闭，首版完整问答会失去必要服务；板端的检测与运动控制应独立保留。

### 13.2 部署顺序

1. 核实 GPU、实际显存、驱动与主机内存。
2. 选择实际支持目标视觉语言模型的推理后端，锁定版本。
3. 准备匹配的语言和视觉组件；某些后端需要额外视觉投影文件。
4. 先验证纯文本，再验证真实图片输入。
5. 从单图片、单并发、有限上下文和较短回答开始测量。
6. 通过应用层封装稳定的 dialogue 接口。
7. 用已下载文件在断公网条件下重新启动并测试。

模型文件能下载或服务端口能打开，不代表图片已经正确输入模型，也不代表实际使用了预期 GPU 后端。

### 13.3 一次请求里有哪些数据

~~~text
请求编号、人员会话编号
本轮问题文字
本轮实际 JPEG 图片
图片编号、来源时间和质量说明
经过核验的当前场景
允许使用的已确认姓名与偏好
回答长度、语言和允许表情范围
~~~

其中，请求编号与图片来源由应用服务管理，不能让模型自由生成这些字段后再把它们当作可信事实。

问题“我手里的物品是什么颜色”需要真实图像。只发送“画面中有一个 person”的文本摘要，不足以证明完成了看图问答。

### 13.4 怎样避免拿旧图回答当前问题

对话编排先请求新鲜快照，检查模糊、曝光和目标可见性，再绑定到本轮请求。回答回来时，重新检查人员会话和取消状态；画面已经变化时，应改为描述“刚才那张画面”，或重新取图。

本轮输入图片可以以缩略图显示，方便用户知道设备回答依据了什么。但展示输入图只能证明来源，不能自动证明模型答案正确。

### 13.5 模型可以影响哪些动作

模型可以提出有限的交互意图，例如请求登记、停止跟随或再观察一次。应用层校验后再进入对应流程。

模型不能直接写 PWM、扩大限位、清除运动故障或重新使能。看图文字和模型回复也不能变成任意命令执行入口。对话推理慢、失败或卡住时，板端停止与视觉链仍需独立工作。

## 14. 人脸与身份记忆：怎样记住并再次识别用户

### 14.1 模型分工

当前首版建议在 Windows 使用 OpenCV 的 YuNet 和 SFace 链路：YuNet 定位人脸和相应关键点，程序完成人脸关联与对齐，SFace 提取用于比较的特征。[OpenCV 官方教程](https://docs.opencv.org/4.x/d0/dd4/tutorial_dnn_face.html)

人体检测告诉系统“这里有人”；人脸特征比较支持“可能是已登记的某个人”。姓名来自用户确认的数据库，不能由人体框或大模型猜测。

### 14.2 登记过程

1. 用户提出“记住我，我叫小林”或通过界面发起登记。
2. ASR 得到的姓名作为候选，界面让用户确认文字。
3. 确认当前只有一个明确登记对象，且其人脸与人体目标可以可靠关联。
4. 检查脸部尺寸、清晰度、姿态、遮挡和图片新鲜度。
5. 在同一会话内采集 3—5 个合格且不过度重复的样本，作为起始设计。
6. 提取特征、检查一致性，原子写入身份库并递增库版本。
7. 确认写入成功后再播报完成。

采集过程中换人、离开或取消，则作废整个登记事务。不能先播报登记完成，再发现数据库其实没有成功写入。

### 14.3 特征比较怎样工作

把特征归一化后，可计算余弦相似度。系统比较最相近的已登记模板，同时检查最高分是否足够、第一与第二候选是否有足够差距，以及连续多帧是否一致。

阈值用本项目的登记、调参和独立测试数据确定。相似度不是身份正确的概率，也不能直接照搬公开演示中的阈值承诺准确率。

不满足条件时返回 unknown 或 ambiguous，允许稍后再确认。轨迹短暂丢失、两个用户交叉后，应重新审查身份关联。

### 14.4 数据库与删除

首版小规模用户库可以使用 SQLite 保存人物、特征、偏好和登记事务。建议记录：

| 数据 | 主要字段 |
|---|---|
| 人物 | person_id、确认姓名、同意状态、创建时间 |
| 模板 | person_id、特征、模型标识、质量记录 |
| 偏好 | person_id、内容、确认来源、版本 |
| 登记事务 | transaction_id、人员会话、当前阶段 |
| 库版本 | gallery_revision |

删除时更新数据库版本，清除模板、偏好与相关缓存，并使正在返回的旧识别结果失效。默认不长期保留原始人脸照片；调试保存应显式启用并有容量与删除规则。

这套小规模交互记忆不能直接宣称具有门禁或支付级身份认证能力。

### 14.5 为什么要检查迟到结果

假设小林离开后小李进入，主机才返回“小林”的识别结果。板端要核对该结果属于哪个启动、相机、帧、轨迹、人员会话和数据库版本；任一关键归属不再匹配，就丢弃结果。

同样的隔离规则用于偏好。未知用户不能读取上一位来访者的偏好，对话上下文也应随人员会话重置或清理。

## 15. 屏幕玩偶：怎样让显示真正反映设备状态

### 15.1 从视频接口到真实界面

屏幕通过匹配的视频输入连接 KV260 HDMI 或 DP，并按自身规格供电。触摸屏如需 USB 触控，则另接数据链。

先用最终镜像验证屏幕输出、分辨率和显示栈，再选择浏览器、Qt/SDL 或其他轻量渲染。板上存在 HDMI 插口，并不意味着当前 DPU 镜像已经支持完整桌面或任意浏览器。

若显示需要特定 PL 模块或设备树，要把它保留在 DPU 与自研 IP 的最终设计中。电脑上打开一个网页只能验证界面原型，不能替代板端实屏验收。

### 15.2 页面建议

主页面显示玩偶、最近一句字幕、录音/思考/播放状态，以及跟随和连接状态。根据屏幕尺寸选择是否显示小幅相机预览，不必让用户一直面对大量工程参数。

工程页面可以显示帧龄、检测频率、方向质量、当前会话、命令是否接受和拒绝原因。没有角度传感器时明确标为“指令角”，不显示成实测机械角。

### 15.3 动画从哪些事件驱动

| 实际事件 | 对应表现 |
|---|---|
| 目标进入并确认 | 玩偶关注、有限问候 |
| 开始真实录音 | 聆听表情、录音提示 |
| 音频提交、模型处理中 | 思考表情 |
| 扬声器开始实际播放 | 说话动画和字幕 |
| 播放取消或结束 | 同步停止口型 |
| 身份正在确认 | 显示登记/识别过程 |
| 主机不可用 | 明确显示当前受限能力 |
| 硬件停止或故障 | 明确显示运动状态与恢复要求 |

首版嘴部动画可以根据实际播放进度或音频能量驱动。整句字幕能够先满足理解需求；如果没有字词时间对齐，就不要承诺逐字同步。

### 15.4 显示不能阻塞控制

界面读取状态并提交受控意图。刷新、浏览器断开、动画卡顿或状态订阅者太慢，都不应阻塞相机和运动服务。界面重连后读取真实状态，而不是继续播放断连前排队的动画。

停止状态、连接状态和说话状态可以同时存在，不能用一个单独动画掩盖其他状态。

## 16. 模块接口、时间和并发怎样统一

### 16.1 两种通信

板内实时链优先使用本地进程通信或受控函数接口，直接连接视觉与运动服务。跨设备的音频、图片和模型结果通过有线局域网传输，首版可用 HTTP 请求与 WebSocket 状态推送。

端口和主机地址写入配置，而不是散落在代码里。模型引擎可以只监听 Windows 本机，由应用服务对板卡提供统一接口。

| 接口或数据 | 提供者 | 使用者 | 关键要求 |
|---|---|---|---|
| health | 各服务 | 启动管理与 UI | 区分加载中、就绪、降级、错误 |
| snapshot | 板端相机服务 | 对话与身份流程 | 图片与元数据对应，有明确帧龄 |
| scene_state | 板端视觉服务 | UI、融合、编排 | 当前目标与不确定原因 |
| request_target | 板端运动服务 | 视觉控制或获批观察任务 | 原始依据、会话、角度与剩余许可 |
| motion_status | 板端运动服务 | 视觉控制与 UI | 接受序号、受限目标、故障 |
| asr | Windows 语音服务 | 板端编排 | 音频格式和本轮编号 |
| dialogue | Windows 模型应用服务 | 板端编排 | 实际图片、问题与场景绑定 |
| tts | Windows 语音服务 | 板端编排 | 输出格式和取消代次 |
| identity | Windows 身份服务 | 板端身份流程 | 目标、事务和库版本 |
| ui_event | 板端编排 | 屏幕界面 | 来自真实事件，有可恢复状态 |

### 16.2 一条消息为什么要有多个编号

不同编号解决不同的旧数据问题：

- boot_id：板端重新启动后，旧启动的结果全部失效。
- camera_epoch：相机重连或重建采集后，旧图像流不能继续沿用。
- frame_id：定位具体图片。
- presence_session_id：定位本次交互对象。
- request_id / utterance_id：定位当前问答与语音轮次。
- audio_generation_id：取消后使旧音频及迟到合成失效。
- motion_session / safety_epoch：使旧运动会话在停止和恢复后失效。
- gallery_revision：使身份删除、修改后的旧结果失效。

这些检查应由公共接口和基础运行时统一实现，避免每个模块各写一套含义不同的编号。

### 16.3 时间基准

板端期限使用单调时钟，避免系统校时导致时间突然跳变。Windows 与 KV260 的时间戳不能直接相减得出单向延迟；首版用请求发起方测往返时间，或建立经过验证的时钟映射。

PL 样本计数、硬件时间与 PS 时间也需建立关系并记录误差。一个音频窗口对应时间区间，而不是凭读取寄存器那一刻就当作刚采到声音。

### 16.4 并发与队列

视觉、运动、对话、身份、显示分别按节奏工作。对话链可以等待网络，运动链不能在等待模型时停顿。身份低频处理，不需要每帧都重复识别。

视觉保留最新数据；语音和事件采用有限队列；日志采用轮转和非阻塞处理。严重故障由独立锁存或高优先级路径处理，不能因为普通遥测队列满而丢失。

至少区分四类状态：交互、运动、连接、健康。网络恢复可以改变连接状态，但不能把运动故障同时清掉。

## 17. 从上电到交互结束：完整过程逐步展开

### 17.1 上电启动

1. 电路保持执行器默认禁能，检查供电与线束。
2. KV260 启动，先通过调试串口确认基本系统状态。
3. 按已冻结的平台路线加载或确认最终硬件配置。
4. 核对 DPU、自研 IP 版本与配置，确认驱动可访问。
5. 启动唯一相机服务和本地 UI，做板端健康检查。
6. Windows 加载语音、视觉语言模型与身份服务，报告实际就绪。
7. 检查声卡、扬声器、屏幕和按键。
8. 人工完成参考位置确认，建立新的运动会话，再允许跟随。
9. 持续记录运行状态，开始接受用户操作。

依赖应分开检查：Windows 尚未就绪时，可以显示问答不可用；在本地控制自检和人工确认通过后，板端跟随可按实际配置独立启用。

### 17.2 用户进入并左右移动

相机产生新帧，DPU 检测人体，PS 关联轨迹并确认进入事件。UI 进入关注状态，视觉控制根据当前目标生成受限请求。驱动检查帧龄和会话后提交，FPGA 接受合法命令，舵机调整朝向，相机再次反馈位置。

目标接近中心时死区减少微动。目标暂时遮挡时可以保留短时轨迹，但失效画面不再续租；目标确实离场后结束会话，清理身份与对话关联。

### 17.3 一次完整看图问答

~~~mermaid

    U->>B: 按住说话键
    B->>O: 取消旧播放并显示聆听
    U->>B: 松开按键
~~~

在这些步骤进行时，板端的视觉和运动链独立运行。若本轮取消，后续迟到结果只能被记录或丢弃，不能重新开始播放。

### 17.4 两人轮流发言

双麦持续生成有效方向事件，PS 与附近时间的视觉候选关联。在当前交互规则允许换人时，唯一候选通过连续确认后切换。切换使旧对话、身份候选和登记事务失效；新对象需要自己的身份确认。

若两人同侧或同时说话，系统可以显示无法确认并等待。正常对话停顿不等于离场，也不应每次静音都清空当前目标。

### 17.5 用户再次回来

系统重新建立视觉轨迹和来访会话，向身份服务提交该对象的合格人脸。主机返回候选身份，板端验证结果归属和多帧一致性后，才进行姓名问候和本人偏好调用。

重识别发生在新的轨迹上，因此不能把“原 track_id 又出现”作为重新认出用户的证明。

### 17.6 断连、停帧与停止

| 事件 | 应观察到的行为 |
|---|---|
| 断公网，但板卡与主机仍连通 | 预下载依赖的本地完整服务继续工作 |
| Windows 服务关闭 | 板端显示问答/身份不可用，保留实际已验证的本地能力 |
| 相机停帧 | 旧视觉依据到期，不再产生持续有效的跟随许可 |
| 运动服务退出 | 硬件租约到期进入已定义输出状态 |
| 按下外部停止键 | 独立停止通路生效，释放后仍等待规定恢复流程 |
| UI 崩溃 | 核心采集与停止不受阻塞，界面重启读取真实状态 |
| 系统重新启动 | 新启动编号与新运动会话，拒绝上一轮缓存命令 |

## 18. DPU 与自研 FPGA 模块怎样放在一起

### 18.1 最终需要一套共同的硬件设计

DPU 是部署在 PL 中的神经网络计算 IP。PWM、双麦采集、相关计算和运动保护也是 PL 中的逻辑。它们需要在最终硬件工程中共同存在，经过统一综合、布局布线和时序检查，生成与软件配套的配置文件。

不能先加载一个只含 DPU 的完整比特流，再加载一个只含 PWM 的完整比特流，就认为二者同时存在。通常第二次完整配置会替换第一次的 PL 设计。动态部分重配置需要专门的平台和分区设计，不应作为本项目的默认方案。

AMD 给出了 DPU 集成路径，但具体平台、DPU 配置和运行时必须相互匹配。参考：[Vitis AI 3.0 系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)。

### 18.2 控制数据和大块数据走不同通道

可以把数据分成两类：

- **小量控制数据**：目标位置、角速度、租约、停止状态、声源方向和错误码。适合通过 AXI-Lite 寄存器读写。
- **大量图像和张量**：需要在 DDR 中存放，由运行时和 DPU 数据接口协同搬运。不能把一幅图像逐像素通过普通控制寄存器送进去。

一帧相机图像的典型路径是：USB 接口进入 Linux 内存，PS 完成约定的预处理，运行时组织输入张量，DPU 读取输入并写回输出，PS 再做解码、筛选和跟踪。某些平台提供 DMA 或额外图像处理模块；只有确认其收益和平台兼容性之后再加入。

双麦音频则可以在 PL 内形成短窗口，直接完成方向计算，把结果和质量指标交给 PS。这样不必为了每个方向结果都把完整双通道音频送往主机。调试期仍可保留原始音频导出能力，用于复现和比对。

### 18.3 集成时需要共同确认的七件事

| 项目 | 具体需要确认什么 | 不匹配时常见现象 |
|---|---|---|
| 资源 | DPU 与其他模块的 LUT、寄存器、BRAM、URAM、DSP 总占用以及布线余量 | 综合能过但布局布线失败，或时序不达标 |
| 地址 | 每个 AXI 外设的地址段唯一，软件访问地址与硬件一致 | 读不到版本号，写入无效，访问异常 |
| 时钟 | DPU、AXI、音频采集、PWM 分别采用合适时钟 | 音频速率错、控制时序异常 |
| 复位 | 每个时钟域有正确复位，启动时输出默认受控 | 上电瞬间乱动，寄存器状态不确定 |
| 跨时钟域 | 状态同步、脉冲传递、音频缓冲交接使用合适机制 | 偶发丢结果，难以重复的错误 |
| Linux 描述 | 设备树、驱动或受控映射方式与最终设计对应 | 外设存在但软件无法访问 |
| 版本 | 硬件文件、运行时、DPU 架构和编译模型形成同一发布包 | 模型加载失败，旧接口写错新寄存器 |

第一次综合成功只能证明设计通过了相应工具步骤。第一次模型推理成功只说明某个输入上的链路能运行。还需要同时打开相机、显示、DPU、音频和转动控制，观察并发负载下的表现。

### 18.4 推荐的集成节奏

1. 先保存一份能稳定启动、显示并运行官方匹配模型的板卡基线。
2. 在同一路线中加入只有版本号、状态寄存器和可控输出的最小自研外设。
3. 验证 Linux 能读取正确版本号，再验证命令提交和看门狗。
4. 先用逻辑分析仪或示波器检查 PWM，再连接轻载机构。
5. 加入双麦采集和方向计算，分别验证时钟、声道和结果。
6. 每次增加模块都保存可回退的硬件、软件、配置和测试记录。

最终交付物是一套一致的系统版本，不能只交一个孤立的 bit 文件。

## 19. 从零到完整系统，应该按什么顺序实现

### 19.1 用阶段验收控制进度

已有材料中的二十天安排可以作为工作拆分参考，但是否进入下一步，应以当前阶段有没有通过验证为依据。特别是工具平台和 DPU 尚未稳定时，不宜同时推进大量依赖它们的功能。

| 阶段 | 主要工作 | 完成标志 |
|---|---|---|
| G0：确认真实器件 | 记录板卡版本、相机、屏幕、舵机、双麦、供电和主机配置；冻结工具路线 | 有实际型号、接线表、供电图和版本表 |
| G1：独立打通硬件 | 板卡启动、相机取图、屏幕显示、网络连通；分别检查麦克风和舵机 | 每个器件有独立运行记录，故障可定位 |
| G2：完成视觉与受控运动 | DPU 检测、轨迹选择、画面坐标控制、硬件租约、停止与恢复 | 单人跟随稳定；停帧、进程退出和停止测试通过 |
| G3：形成完整语音问答 | USB 音频、ASR、带图问答、TTS、板端播放与取消 | 在局域网内完成可重复的整轮交互 |
| G4：加入双麦融合和身份 | PL 声源方向、多人目标选择、人脸登记与重识别 | 能解释每次选择依据；歧义时不乱绑定身份 |
| G5：并发与演示验收 | 多模块同时运行、异常注入、长时间运行、重启和数据整理 | 有实际日志、性能统计、版本包及可复现实验 |

“能在电脑上跑模型”不等于 G2 完成；“播放器能出声”也不等于 G3 完成。阶段验收要覆盖真实的输入、处理、输出和状态转换。

### 19.2 每个阶段内部的实际操作

**先看得见。** 只接相机和屏幕，固定曝光相关设置或至少记录自动设置状态，连续显示真实帧号和时间。确认摄像头断开、重连、缓冲积压时程序的行为。

**再算得出来。** 用相同的保存图片验证模型预处理和后处理；确认框位置还原正确，再切到实时输入。先让检测框稳定显示，再讨论跟随。

**再允许运动。** 仿真命令提交、超时和停止逻辑；空载观察波形；检查机械限位和线缆；最后小范围、低速度地建立“画面偏左—实际向左纠正”的关系。

**再接完整问答。** 用已知语音文件检查 ASR，用固定图片和问题检查视觉语言模型，用固定文本检查 TTS；各自可靠后，再把真实麦克风、拍照时刻和播放状态串起来。

**最后处理多人和记忆。** 双麦方向先在固定位置测试；身份登记先验证输入质量和数据库一致性；两者都通过后，再进入转动、交谈、遮挡同时发生的场景。

### 19.3 三个人如何配合

如果继续采用原计划的三人分工，可按下表执行。接口规格和集成记录需要共同维护。

| 角色 | 主责 | 向其他人交付什么 |
|---|---|---|
| A：板卡、FPGA 与机构 | 工具平台、最终 PL 工程、PWM/保护、双麦、供电与机械 | 地址与寄存器表、时间规则、状态码、接线和标定方法 |
| B：视觉与模型 | 检测、跟踪、目标选择、人脸、主机视觉问答 | 带帧号和有效期的结果、模型版本、质量指标、测试集 |
| C：交互与系统集成 | 音频链路、UI、服务通信、会话取消、日志与发布 | 请求/响应协议、状态流转、错误处理、启动与验收记录 |

例如，B 交付目标中心坐标时，必须同时说明坐标所属的图像尺寸、采集时刻、轨迹编号和质量。A 交付方向结果时，必须同时说明坐标系、质量、采样窗口和有效期。C 才能把它们正确放入同一个会话，而不是仅把几个数拼到一起。

## 20. 如何验证效果，怎样证明系统确实有效

### 20.1 先分清目标值和实测值

已有计划中的帧率、准确率和时延属于待验证指标。本目录尚未提供足以证明这些指标全部实现的板端代码、波形和测试日志。因此，正式报告应分别列出“目标”“测试条件”“实际结果”，没有测量的格子写“未测”。

### 20.2 关键测试清单

| 测试对象 | 怎么测 | 重点记录什么 |
|---|---|---|
| 相机 | 连续采集、遮挡、拔插、模拟处理变慢 | 帧号、实际帧率、积压、恢复行为 |
| 检测 | 固定图片在参考实现和板端实现上运行 | 输入是否一致、框坐标、类别、阈值、误差 |
| 跟踪 | 单人走动、遮挡、两人交叉、相机转动 | 丢失、恢复、ID 切换、错误目标持续时间 |
| 跟随 | 规定距离和左右移动路线，多次重复 | 画面中心误差、稳定时间、振荡、触限位次数 |
| PWM | 测量不同目标值、上下限、复位和超时下的波形 | 周期、脉宽、异常输出和停止延迟 |
| 保护 | 注入重复序号、过期帧、进程退出、停止键和重启 | 是否拒绝、拒绝原因、输出状态、恢复条件 |
| 双麦 | 用同一段 PCM 在软件参考和 RTL 中计算 | 相关值、峰位置、声道方向、溢出和缩放 |
| 声源选择 | 左中右、不同距离、背景噪声、两人同时说话 | 正确率、错误率、UNKNOWN 比例及条件 |
| ASR | 固定语料和真实录音分别测试 | 转写错误、噪声条件、耗时和失败率 |
| 视觉问答 | 固定问题、图片、预期答案和图片时效条件 | 事实正确性、看不清时是否承认、整轮耗时 |
| 播放和取消 | 播放中取消、换会话、主机超时 | 停止耗时、是否串音、旧结果是否被丢弃 |
| 身份 | 登记者、陌生人、多人、离开后返回、删除后返回 | 误认、拒识、会话归属、删除是否立即生效 |
| 整机 | 全模块同时工作、断公网、断主机、长时间运行 | 资源占用、温度、异常次数、自动恢复和日志 |

### 20.3 可以沿用的初始验收方向

以下是便于执行的候选目标，应结合实际器件和现有需求文档最终冻结，不能当作已经实现的结果：

- 视觉控制链路先争取稳定达到约 10 Hz，记录帧率分布和端到端时延；不要只报最快的一帧。
- 图像出队到控制接受可先以 P95 不超过 200 ms 为调优目标，同时单独评估出队前的相机缓存延迟。
- 单人跟随用不少于 20 次规定运动测试，记录目标中心偏离图像宽度的比例；例如把稳定后误差不超过宽度的 10% 作为起始目标。
- 停止输入到规定数字输出变化可用 5 ms 作为初始验证目标。机械停止、惯性和舵机内部行为必须另测。
- 语音问答用不少于 30 轮固定场景统计整轮 P95；例如以 8 秒作为第一轮系统优化目标，但模型、主机和语音长度变化后需要重新测量。
- 取消操作独立测试，例如至少 20 次，目标可先设为 300 ms 内停止当前本地播放并使旧结果失效。
- 完成至少 3 次冷启动和一次 2 小时并发运行，检查启动一致性、内存增长、温度和失效恢复。

准确率必须连同样本条件一起报告。假设声源模块遇到 100 次输入，只对 20 次作出判断，其中 19 次正确，则“已判断样本准确率 95%”不能代表整体覆盖率很高；还应报告 80 次 UNKNOWN。

### 20.4 时延怎样拆开测

建议分别记录：相机帧到达、图像出队、预处理完成、推理完成、跟踪完成、控制候选生成、硬件接受、输出更新。主机侧另记录请求接收、模型开始、模型完成和返回。

板端发起请求到收到响应的往返耗时，可以全部使用板端单调时钟计算。主机内部处理耗时，可以使用主机自己的单调时钟计算。未经同步和误差评估，不能直接拿主机时间减板端时间，作为某段单向网络时延。

如果没有位置传感器或外部测量系统，日志里的“目标角度”只能表示控制意图，不能证明机构实际到达了该角度。可先用外部视频、角度刻度或测量设备验证，再决定是否需要增加编码器。

### 20.5 日志至少留下哪些信息

每条关键事件建议包含：启动编号、会话编号、请求编号、帧号、轨迹编号、单调时间、模块名、状态、模型版本、阈值配置、结果质量、许可截止时间和拒绝原因。

日志既要能回答“模型为什么选这个人”，也要能回答“硬件为什么接受或拒绝这次运动”。录音和人脸图片是否保存应单独配置；日常排查尽量先使用结构化事件，避免无必要地长期保存原始个人数据。

## 22. 在现有广度上，最值得做深的研究方向

### 22.1 推荐聚焦：带时效和质量约束的视听目标选择与运动许可

这个方向直接用到现有相机、双麦、跟踪、PS/PL 和舵机，能够把多个现成功能收束成一个可验证的问题：**当视觉和声音存在延迟、歧义或失效时，系统怎样选择当前交互对象，并决定是否仍有足够依据继续转动？**

可把每份证据统一描述为：来源、对象、采样时段、接收时刻、质量、坐标系以及有效期限。PS 负责融合和生成控制候选，PL 对提交顺序、许可期限和停止条件执行确定规则。

其中，“做了超时保护”本身不足以构成明显学术创新。研究价值取决于能否提出有依据的方法，例如在相同错误目标转向率约束下减少无必要停止，或在相同可用率下减少由过期证据引起的错误动作，并通过消融实验证明。

### 22.2 分三层推进

**第一层：可解释基线。** 使用视觉稳定轨迹、粗粒度声源方向和固定有效期。把没有融合、简单融合、带固定时效约束的融合进行比较。这一层最适合先做成可靠演示。

**第二层：自适应有效期。** 根据测得的速度、跟踪稳定度、遮挡、观测延迟和声音歧义，对证据可用时间作保守调整。质量下降时缩短许可或拒绝；不能仅因为模型置信度高就无上限延长旧画面的效力。即使上层计算出较长期限，PL 仍应执行最大租约上限。

**第三层：流式说话人证据。** 当粗方向无法区分相邻两人时，再引入嘴部运动与音频关联。要明确模型使用多少过去和未来信息，实际决策延迟是多少；非因果离线模型的高准确率不等于它适合直接控制实时机构。

### 22.3 与哪些论文和方法有关

| 资料 | 核心用途 | 对本项目的适配方式 |
|---|---|---|
| [ByteTrack，ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/papers/136820001.pdf) | 利用检测结果进行多目标关联，包括合理利用低分框 | 作为多人跟踪候选基线；跟踪 ID 仍不代表真实身份 |
| [BoT-SORT，2022](https://arxiv.org/abs/2206.14651) | 在多目标跟踪中结合运动、外观等信息，并考虑相机运动 | 参考其相机运动处理思路；先测转头引起的误关联是否真是主要瓶颈 |
| [Light-ASD，CVPR 2023](https://arxiv.org/abs/2303.04439) | 使用视听信息判断画面中的人是否在说话 | 在主机上验证多人选择收益，再评估流式改造与同步成本 |
| [Efficient Streaming Audio-Visual Speech Classification，ICASSP 2025](https://machinelearning.apple.com/research/efficient-streaming-audio-visual) | 面向流式视听语音分类讨论计算与时间上下文 | 参考其流式设计，不能直接假设预训练权重或部署链路适合 KV260 |
| [Age of Information: An Introduction and Survey](https://arxiv.org/abs/2007.08564) | 研究信息随时间变旧的度量与影响 | 为“使用结果时，原始观察已经多旧”提供分析语言 |

这些资料提供可借鉴的方法。它们并不自动证明本项目的新颖性，也不能替代针对“视听跟随、信息时效和执行监督”交叉方向的专项查新。

### 22.4 适合写成论文的实验设计

固定硬件、输入任务和计算预算，比较以下系统：只用视觉；视觉加粗声源方向；加入固定期限；加入自适应期限；最后按需加入流式说话人判断。

主动设置网络延迟、相机积压、遮挡、两人交叉、同时讲话、设备自身播放和短时服务失效，记录：错误对象转向次数、错误持续时间、目标切换时间、正确跟随覆盖率、拒绝率、停止次数、控制时延和资源消耗。

关键是同时报告正确性和可用性。一个始终拒绝转动的系统可能几乎不犯转向错误，却不能完成任务。一个始终保持运动的系统可能体验连续，却把过期信息当作新证据。研究应展示两者之间可重复的改进。

自研监督模块可以验证数字接口和明确的时序规则，但若没有足够的机械状态观测、制动建模和适用范围说明，不应把它表述为已经证明整机物理安全。

## 23. 容易混淆的概念，一次讲清楚

| 常见疑问 | 本项目中的准确理解 |
|---|---|
| KV260 是不是只负责 FPGA？ | 它同时包含运行 Linux 的 PS 与实现硬件逻辑的 PL，两边共同完成系统 |
| DPU 是板上另一块独立 AI 芯片吗？ | 本方案的 DPU 是在 PL 资源中实现的计算 IP，与其他自研逻辑共用资源 |
| 主机跑大模型，板卡还有什么价值？ | 板卡承担实时采集、视觉控制、双麦方向、显示交互及执行监督，主机承担计算较重的语言和身份服务 |
| 两个麦克风就能直接知道谁在说话吗？ | 双麦首先提供方向证据；具体对应哪张脸还需视觉坐标、时间对齐与歧义处理 |
| I2S 双麦能直接替代 USB 对话麦克风吗？ | 原理上可以进一步打通，但现有分工不同；需要补音频导出、格式转换和识别输入链路 |
| 检测到人是不是就认识这个人？ | 检测输出类别和位置；跟踪维持临时对象；身份识别需要人脸特征及登记库 |
| PWM 有输出，舵机就一定到位吗？ | 输出只是控制信号；实际位置还受供电、负载、机械限制和内部控制影响 |
| 断公网是不是整个系统离线？ | 局域网主机仍可工作；如果主机也断开，则只能保留板端已实现的能力 |
| 看见界面很流畅，推理是不是也很快？ | 显示刷新、相机采集和模型推理可以是不同速率，应分别测量 |
| 旧结果补发一个新时间戳能续命吗？ | 不能；有效期必须追溯到产生证据的原始采样时刻或经过明确界定的观测时间 |
| 一个转轴能覆盖任意方向吗？ | 单轴只能改变一个角度，不能独立控制俯仰；视野还受相机安装和遮挡影响 |
| HDMI 线是否同时完成屏幕供电？ | 不能这样默认；应按屏幕规格确认独立供电与接口要求 |
| 直接把 PC 网页展示出来算板端界面吗？ | 应确认画面实际由 KV260 输出到设备屏幕，并由整机真实状态驱动 |

排障时按“供电和线缆—独立器件—单模块—接口—并发”逐层检查。例如舵机动作引起相机掉线，先核查电源压降、回流路径和连接可靠性；不要一开始就调整视觉模型阈值。

整个项目可以概括为：相机提供“人在哪里、画面里有什么”，双麦提供“声音大致来自哪里”，PS 把观察组织成当前交互对象与控制请求，PL 完成有明确时序的采集、计算和执行监督，Windows 主机负责较重的理解与生成，屏幕、扬声器和转轴共同把结果表达出来。工程做成的关键，是每份数据都能说明来源、归属和时效，每次动作都有明确许可，每种失效都有可验证的处理流程。
