# 雾镜 Lite：基于 AMD KV260 的视听融合、板端身份识别与单轴交互系统

## 文档说明与本轮确定的路线

- 版本：V2.0，2026-09-19。
- 用途：队内开发、软硬件分工、联调、论文实验设计及 AMD 赛道申报参考。
- 性质：整合方案与实施基线。描述的能力属于拟实现目标，不能据此认定代码、硬件或性能已经通过验证。
- 产品：固定底座、单轴水平转动的桌面视听交互终端，项目名“雾镜 Lite”。
- 计算平台：一块 AMD Kria KV260，加一台通过局域网连接的 Windows 模型主机；Linux 开发环境用于构建，不额外算作演示所需的一台运行主机。
- 本轮算法一、二、三按此前《算法论文调研与自研路线》的编号整合：① GCC/时差估计方向；② ByteTrack；③ BoT-SORT 中的相机运动补偿思路。YOLO 是人体检测基础，另行明确采用；没有把 Light-ASD 同时纳入必做。
- “人脸识别上板”指将人脸处理、特征比较和身份库迁到 KV260，采用 PS 与 DPU 协同；不表示所有步骤都需要自研 RTL。
- “多机整合”在本版指 KV260 与 Windows 主机协同，以及板内多个软硬件模块整合。当前没有新增第二块 FPGA、多摄像头阵列、多舵机或多机器人集群。

本版依据最新讨论调整部署位置与算法范围。旧文档中“身份识别仅在 Windows 主机运行”的描述不再作为目标架构；旧材料中的电路参数、冻结验收值和任务编号仍需与原始记录核对。本版不重定义旧 W/T 编号，避免把新增板端身份任务错误归入原来的主机任务。

## 1. 项目要解决什么问题

### 1.1 产品定位

设备面向桌面接待、校园展示、展台讲解等近距离交互场景。相机用于发现和跟随来访者；双麦提供粗声源方向；屏幕展示虚拟角色、字幕与状态；扬声器播放回答；水平转轴让设备朝向当前交互对象。

本项目重点研究：多人同框、遮挡、相机自身转动和证据延迟同时存在时，怎样持续选择正确对象，并避免旧结果继续影响转动。人脸识别使设备能够区分已登记用户和陌生人，语音与看图问答使关注对象之后的交互具有实际内容。

### 1.2 预期功能

| 功能 | 用户看到的表现 | 主要技术 |
|---|---|---|
| 人体发现 | 人进入画面后，设备进入关注状态 | YOLO 系列轻量人体检测 |
| 稳定跟踪 | 短暂遮挡或交叉后尽量继续跟随原对象 | ByteTrack 式两阶段关联 |
| 转动下跟踪 | 转头后不轻易把原对象丢掉或换成别人 | 相机运动补偿 |
| 声音辅助选人 | 在可判定场景中朝向发声侧对应人物 | 双麦时差、质量与视听融合 |
| 单轴随动 | 当前对象尽量保持在画面中央 | 视觉误差控制、限速、PWM |
| 板端认人 | 已登记用户返回时显示姓名和问候 | 人脸检测、对齐、特征提取与匹配 |
| 身份记忆 | 调用用户确认过的姓名和偏好 | 板端身份库与会话管理 |
| 语音交互 | 按键说话、回答播放、随时取消 | USB 音频、ASR、TTS |
| 看图问答 | 结合本轮图片回答展示物品等问题 | 主机 VLM |
| 异常降级 | 主机断开时保留板端能力，画面失效时撤销运动许可 | 独立状态机与期限检查 |

### 1.3 本期边界

首版使用一个水平轴，不包含移动底盘、机械臂、俯仰轴或无限旋转。双麦先输出左、中、右和未知，不承诺三维定位，也不能仅凭粗方向区分同侧相邻两人。人脸识别用于交互身份，不作为支付或门禁认证。本地部署包含局域网主机，不宣称所有大模型都在 FPGA 上运行。

## 2. 总体架构与职责

### 2.1 四个执行位置

| 位置 | 负责内容 | 为什么这样安排 |
|---|---|---|
| KV260 PS：ARM/Linux | 采集、图像预后处理、跟踪、补偿、融合、身份管理、控制请求、UI、通信 | 条件判断和业务流程变化多，软件便于修改 |
| KV260 PL：DPU | 匹配模型的人体检测、人脸检测/关键点、身份特征提取 | 神经网络计算重复度高，采用现成加速 IP |
| KV260 PL：自研 RTL | 双麦采集与短窗相关、方向质量、命令监督、PWM、超时和停止 | 需要明确时序、接口行为和可观察的硬件执行过程 |
| Windows 模型主机 | ASR、VLM、TTS | 处理较大语音与图文模型，减少板端负担 |

人脸检测与关键点是否全部由 DPU 执行，需要根据所选模型确认；无法适配的轻量步骤可先放 PS。最终报告必须按实际执行位置描述，不能把整条人脸流程统一标成“全部 DPU 加速”。

### 3.2 已知信息与待核实信息

用户修订稿记录舵机为 DSSERVO 30 kg 级、标签 DC 4.8—6.8 V，并采用 6.0 V 标称支路；本次没有附上原始标签照片或测量记录，按该记录设计时仍需补确切型号、角度版本、输入电平和峰值电流。不得将 7.4 V 或满电 2S 电池直接接入这一标称范围的器件。

双麦采用 INMP441 类器件的方向保留，但“类”不能替代实际芯片型号。目标采样率 48 kHz，32 位双槽时 BCLK 为 3.072 MHz。真实 INMP441 的 SCK 上限为 3.2 MHz；仍须核对模块、接线、供电和实测时序。[TDK INMP441 数据手册](https://invensense.tdk.com/wp-content/uploads/2015/02/INMP441.pdf)

### 3.3 供电原则与电路收敛

KV260 使用规定的板卡电源。官方资料列出 12 V/3 A，Pmod 为 3.3 V/100 mA，USB 单口预算 900 mA、四口合计 2.1 A。舵机不能从 Pmod 取功率，USB 也不作为该大扭矩舵机的供电来源。[AMD 电源预算](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Powering-the-Starter-Kit-and-Power-Budgets)

~~~text
板卡适配器 → KV260 → 预算内的 USB 外设与散热
独立合适电源 → 舵机功率转换/保护 → 默认关闭的高边开关 → 舵机
屏幕规定电源 → 屏幕
音频规定电源 → 功放/有源音箱
PL PWM → 经核对的信号接口 → 舵机控制端
外部停止通路 → 撤销执行器使能，同时向 PL 提供状态
~~~

若共用一条上游电源，须另算板卡、转换效率、舵机峰值和其他外设的总预算，不能把板卡的 12 V/3 A 适配器自动视为整机电源。非隔离信号需要可靠地参考，但舵机大电流回流不应经过细小 Pmod 地线。

修订稿中的 5 A 保险、2200—4700 µF 电容、100 Ω 串阻、BAT54S 钳位与线径均作为待校核候选：保护选值需结合线束、故障电流和启动过程；电容需核算浪涌与断电后的储能；钳位需核查方向、回灌和关机状态。它们不能仅凭出现在文档里就视为验证完成。

高边 P-MOS 应区分 FPGA 逻辑 EN 与器件 GATE。栅极靠近源极电位通常使 P-MOS 关断，栅极拉低通常导通；若设计 EN=0 表示关闭，应通过明确的驱动/反相级实现，不能写成“直接拉低 P-MOS 栅极就关断”。6 V 高边栅极不能默认与 3.3 V FPGA 引脚直连。

### 3.4 机构与引脚

优先让相机、双麦和朝向用户的显示部分保持固定相对关系。双麦与相机共同旋转时，音频左右与画面左右更容易标定；若麦克风留在底座，融合需知道二者的相对朝向，不能靠未测量的舵机命令当作真实角度。

一组 Pmod 的示例信号预算是 BCLK、WS、两路 SD、PWM、停止状态、驱动 EN、预留确认输入，共 8 根。该表不等于最终引脚约束；必须依据载板版本、原理图和所选平台核对。说话键可通过 UI 或 USB 输入实现。

安装前检查承重、惯量、转角、线缆余量和限位。没有编码器时，不能报告真实轴角闭环精度；可以报告画面居中误差和命令输出时序。

## 4. 算法清单、引用与自研边界

| 算法/方法 | 解决的问题 | 采用范围 | 定位 |
|---|---|---|---|
| YOLO 系列轻量检测 | 人体位置与分数 | 优先验证匹配平台的 YOLOX-Nano 工件 | 已选择的基础检测方向 |
| GCC/时差估计 | 双麦声音到达时间差 | 时域相关先行，GCC-PHAT 为软件对照 | 算法一 |
| ByteTrack | 遮挡、低分检测下的轨迹连续性 | 高低分两阶段关联，保留一对一匹配与生命周期 | 算法二 |
| BoT-SORT 的相机运动补偿 | 机身转动导致的全画面位移 | 先做轻量背景运动估计；不承诺完整外观 ReID | 算法三 |
| 人脸检测与特征识别 | 用户持久身份 | 匹配 DPU 的轻量模型，PS 做质量、对齐、比对与登记 | 板端产品能力 |
| 视觉误差控制 | 对象在画面中居中 | 死区、比例速率、平滑和限速 | 基础控制 |
| 视听时效与质量裁决 | 多种证据不一致或变旧 | 可解释规则、拒判、迟滞、有效期 | 拟深化的自研方法 |
| 命令许可监督 | 无效指令不得续期执行 | 范围、顺序、会话、期限、停止 | 自研硬件逻辑 |

ByteTrack 与 BoT-SORT 都属于跟踪方法，不能把两个完整跟踪器简单串联。建议以 ByteTrack 式关联为基础，在其预测/匹配之前引入经过验证的相机运动补偿。普通互相关也不能在报告中直接称为已实现 GCC-PHAT。

前三项是方法基础，自研贡献应落在适配本设备的融合规则、有效期机制、软硬件实现和实验结果。采用现成论文或调几个阈值本身不能证明算法创新。

## 5. YOLO：从相机画面得到人体框

### 5.1 为什么使用 YOLO

跟踪、选人和转动都需要人物位置。轻量 YOLO 系列适合作为人体检测入口，输出边界框、类别与分数。只保留 person 类可以减少后处理和无关对象，但不会自动减少网络主干计算。

首版优先核验 AMD Vitis AI 3.0 模型库中的 YOLOX-Nano 候选，前提是模型、运行时和实际 DPU 匹配；本方案不承诺任意新版本 YOLO 能直接部署。[AMD YOLOX-Nano 模型条目](https://github.com/Xilinx/Vitis-AI/tree/3.0/model_zoo/model-list/pt_yolox-nano_coco_416_416_1G_3.0)

### 5.2 单帧流程

~~~text
UVC 图像 → 唯一采集服务 → 取最新有效帧
→ 格式转换与模型规定的缩放/填充
→ 输入张量 → VART 提交 → DPU 网络计算
→ PS 解码与筛选 → 按需 NMS
→ 框坐标还原 → 带帧号和时间的检测结果
~~~

例如 640×480 图像采用居中 letterbox 放入 416×416：缩放比例 0.65，得到 416×312，上下各补 52 像素。还原框时先去掉偏移，再除以比例。实际工件可能采用直接 resize 或其他预处理，必须跟随其说明。

### 5.3 采集与缓存

只设置一个相机所有者。检测、身份、快照问答和 UI 读取这一服务发布的图像，不能各自打开同一摄像头并假设帧天然一致。图像缓冲采用明确引用计数或只读快照，不能在 DPU 或网络尚未使用完时被下一帧覆盖。

每帧记录 boot_id、camera_epoch、frame_id、图像尺寸、像素格式、单调时间及其来源。V4L2 时间戳需要核对含义；出队时间不是天然的曝光时刻。[Linux V4L2 缓冲说明](https://www.kernel.org/doc/html/latest/userspace-api/media/v4l/buffer.html)

视觉队列优先只保留最新待处理帧，同时检查驱动和解码缓存。重复发布冻结图片不得刷新原始采集时间。相机重启后增加 camera_epoch，拒绝旧代次结果。

### 5.4 模型验证顺序

先用固定图片验证参考模型，再验证量化和目标编译结果，最后接入真实相机。保存原始模型、量化模型、编译产物的版本与校验值。分别观察近远距离、侧身、遮挡和转动模糊。DPU 编译通过后，仍要核对是否存在 CPU 子图和额外后处理耗时。

## 6. ByteTrack 式跟踪：维持当前对象

### 6.1 基本流程

检测结果分为高分集合和较低分集合。已有轨迹先预测当前位置，与高分框执行一对一关联；剩余可续接轨迹再尝试用较低分框补回。新轨迹应由足够可靠的观测建立，低分框不能随意生成新身份。[ByteTrack 原论文，ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/papers/136820001.pdf)

实现至少包括：轨迹状态、预测、代价矩阵、匹配阈值、一对一分配、未匹配处理、连续确认与丢失超时。根据实际时间间隔更新，不默认每帧固定等间距。

### 6.2 需要分开的三个编号

- track_id：本次视觉跟踪中的临时轨迹。
- presence_session_id：当前来访或交互会话。
- person_id：登记库中的真实身份记录。

同一个人可以有多个历史轨迹，一个轨迹也可能发生误关联。只有可靠的人脸确认才能赋予 person_id，不能把重用的 track_id 当作再次认出用户。

### 6.3 遮挡和丢失

短时保留轨迹用于重新关联，但“保留对象记录”和“继续允许运动”分开。看不见人的时候，预测结果的许可应受更严格条件约束；默认不能无限用旧框驱动转轴。

目标切换需要连续证据与迟滞，避免每次检测分数变化都换人。建议固定一批录像回放，比较单阈值 IoU 与两阶段关联的 ID 切换、丢轨、误选和处理耗时。

## 7. 相机运动补偿：设备转头后为什么还能跟住人

### 7.1 问题来源

相机向右转时，静止背景和人物通常整体向画面左侧移动。如果直接用原轨迹位置匹配，就可能把设备自身造成的变化误判为人物快速移动。BoT-SORT 提供了将相机运动补偿结合到多目标跟踪中的参考思路。[BoT-SORT 原论文](https://arxiv.org/abs/2206.14651)

### 7.2 首版实现

1. 对相邻图像适度降采样。
2. 尽量排除人体区域，在背景寻找可跟踪特征。
3. 通过稀疏光流或特征匹配获得位移候选。
4. 用稳健估计剔除异常点，得到水平位移或适当的图像变换。
5. 将已有轨迹预测框变换到当前图像坐标，再进行关联。
6. 输出内点数、残差等质量指标；质量不足时关闭补偿或降低关联信任。

先做小转角条件下的水平位移基线，再按实测决定是否需要仿射或单应变换。相机旋转的精确投影并不总能由一个全局平移表示；近景视差、遮挡和机身振动也可能破坏估计。

### 7.3 不应采用的捷径

舵机目标角度不等于真实镜头角度。没有编码器、标定和机械响应验证时，不能直接用命令角确定补偿量。可将命令作为“正在转动”的辅助状态，把实际图像估计作为主要依据。

此阶段暂不把完整 BoT-SORT 的外观 ReID 网络设为必做，以免在人体检测和人脸模型之外再增加一条重计算链。

## 8. 双麦时差与 FPGA 音频处理

### 8.1 两条音频链各做什么

USB 麦克风负责提问录音，双 I2S 麦克风负责方向研究。两条链不天然同步，不能用 USB 录音的某一时刻直接索引 I2S 样本；粗事件融合先在板端统一时间域中建立对应关系。若以后共享双麦音频用于 ASR，需要补导出、采样率处理与设备接口。

### 8.2 几何与采样率

在远场、固定几何条件下，定义 theta 为相对双麦正前方的水平角，近似有：

~~~text
tau = d × sin(theta) / c
k = tau × fs
|k|max ≈ d × fs / c
~~~

取 c≈343 m/s、fs=48 kHz，40 mm 间距的最大 lag≈5.6 个采样，50 mm 间距≈7.0 个采样。最终以实测声孔中心间距为准；40/50 mm 不能同时作为固件中的冻结参数。

48 kHz 为整数时差估计提供更多可分辨采样位置。16 kHz 会降低分辨率，但不能断言其原理上无法做三档判断。角分辨率随方位而变化，不能把正前方附近的近似数值当成全视野常数。

一般几何使用麦克风基线向量与声源方向的点积建模；只有限定的安装倾斜和声源平面下，才可简化成有效间距 d×cos(alpha)。双麦存在前后歧义，首版应限定受控前方交互区域。

### 8.3 时钟实现

两只麦共用 BCLK、WS，初版采用两路独立 SD。两麦相同声道配置可简化采样对应，实际仍按器件格式确认。标准 I2S 的 WS 切换与最高有效位有规定时序，不能按任意串口读取。

若用 100 MHz 母时钟生成平均 3.072 MHz 的完整 BCLK 周期，平均分频比为 32.552083…；32 与 33 等量交替得到约 3.076923 MHz，不能误写成精确目标。一个平均比示例是每 96 个输出完整周期分配 43 个 32 周期、53 个 33 周期；实际应由相位累加器等机制合理分布，并核对高低电平、边沿和周期抖动。

MMCM/PLL 路线应由实际器件、分数/级联选项、中间频率和工具结果判定，不能仅凭一个分频上限宣布所有路线不可行。[AMD UltraScale MMCM 属性](https://docs.amd.com/r/en-US/ug572-ultrascale-clocking/MMCM-Attributes)

共时钟有助于消除独立采样时钟漂移，但不能保证安装、器件延迟、声道槽位和接收逻辑完全无偏差；仍应做通道同步和交换测试。实测采样率需进入声学参数，不能始终写标称值。

### 8.4 相关与质量判断

先实现参考算法：去直流、可选固定预滤波、窗口缓存，在候选 lag 范围内计算相关值，找峰并判断质量。对不同 lag 使用一致的有效窗口或明确归一化规则，避免因有效样本数量不同造成偏置。

例如 N=480、候选 lag=-8…8，在共同有效索引 n=8…471 上，每个 lag 使用 464 对样本，总计 17×464=7888 次乘加/窗口。若每 10 ms 输出一次，约为 0.79 百万次乘加/秒；这只是设计估算，未计预处理和控制开销。

这种规模未必需要大量并行乘法器。可先用较少乘加单元时分复用，以便给 DPU 留资源，再根据时序和窗口吞吐结果调整。PL 实现价值应以延迟、抖动、CPU 占用与资源代价的对照说明。

输出建议包括 direction、lag、energy、peak_quality、clip_count、sample_start/end、sample_counter 和有效期。能量低、削波严重、峰不明确、多声源或数据丢失时输出 UNKNOWN。

### 8.5 GCC-PHAT 的定位

GCC 是广义互相关的理论框架，PHAT 是其中一种频域加权方式。首版可把 GCC-PHAT 放在软件参考中，与原始互相关比较；只有数据说明其收益值得资源和实现成本时，再考虑 FFT、归一化和逆变换的 PL 路线。[Knapp 与 Carter，1976，原论文 DOI](https://doi.org/10.1109/TASSP.1976.1162830)

### 8.6 定点与缓存

器件输出 24 位不意味着后续计算必须全用 24 位。若取高 16 位，应明确符号、舍入/截断和幅度范围，参考程序与 RTL 一致。16 位乘积为 32 位，约 480 项累加采用至少 41 位的保守口径；保留 24 位时需重新推导更宽累加器。检查极值输入、溢出、饱和和全零情况。

双缓冲将采样和计算分开，跨时钟域使用正确的握手或异步 FIFO。溢出计数和样本计数必须可读，不允许丢样后仍无条件给出高质量方向。

## 9. 人脸识别迁到 KV260 的完整方案

### 9.1 部署目标

目标是板端完成从人脸输入到 person_id/UNKNOWN 的闭环，并在板端持有身份库。Windows 不再是认人的必需节点。初期可以先在 PS 验证流程，再把受支持的网络计算迁到 DPU，但最终必须按实际运行位置如实描述。

### 9.2 处理步骤

~~~text
当前轨迹的人物区域
→ 人脸检测与关键点
→ 尺寸/模糊/姿态/遮挡质量检查
→ PS 人脸对齐、颜色和数值预处理
→ DPU 特征提取
→ PS 归一化及身份库比较
→ 阈值、第一第二候选差距与多帧确认
→ person_id 或 UNKNOWN
→ 绑定当前来访会话，读取已确认偏好
~~~

检测框包含两张脸或身份归属不明确时，不得随意把其中一张绑定到当前轨迹。为请求附带 frame_id、track_id、presence_session_id、gallery_revision 与模型版本，返回时逐项验证。

### 9.3 模型选择

优先评估与现有 Vitis AI 平台匹配的人脸检测和特征模型。AMD 库提供人脸相关接口，但不能据此保证任意模型在当前 DPU 配置上直接可用。[AMD 人脸识别说明](https://docs.amd.com/r/3.0-English/ug1354-xilinx-ai-sdk/Face-Recognition)

YuNet/SFace 可以作为已有软件参考，不能默认原始 ONNX 文件不经核验就能成为 DPU 工件。检查算子支持、量化工具、输入输出、CPU 子图、性能和许可；人脸量化效果要看误认/拒识，不只看平均向量误差。

### 9.4 登记与查询

用户明确确认登记后，采集 3—5 张不同但合格的姿态/光照模板作为起点；过滤重复低质量图片，确认姓名与当前对象一致后再提交事务。使用多个模板时，应固定相似度聚合规则并重新标定阈值，不能随意取最高值而不检查误认变化。

少量用户的特征比较可以在 PS 完成。余弦相似度为向量点积除以模长乘积；若已做单位归一化可简化为点积。阈值根据部署模型和独立标定集确定，不直接照抄其他模型教程。

身份表保存 person_id、姓名、登记状态；特征表保存 person_id、模型版本、向量、质量信息；偏好表只保存经用户确认的内容。SQLite 等轻量数据库可用于首版，写入采用事务，防止断电后出现半条登记记录。

### 9.5 删除、换模型与断网

删除时同时撤销内存缓存并递增库版本，使旧请求不能重新绑定已经删除的身份。更换特征模型后，旧向量通常不能混用，需要依据保留策略重新提取或重新登记。板端服务重启要使用新 boot_id，不能继续接受上一轮请求。

主机断连时，本地身份匹配可继续；若要语音问候，可使用预置音频或已验证的本地方案，不能假设主机 TTS 仍然可用。姓名和状态至少可在屏幕显示。

### 9.6 按需识别，避免抢占跟随

新人进入、身份未知、丢失后重现、主动登记或周期性必要复核时触发人脸任务。只对当前交互对象优先处理，稳定已确认对象不必每帧重识别。模糊、侧脸过大或区域过小时直接跳过，避免把无效输入排进 DPU 队列。

## 10. 视听融合与单轴运动控制

### 10.1 融合输入与输出

输入包括稳定轨迹位置、轨迹质量、声音方向与质量、双方时间、相机是否转动、设备是否正在播音，以及当前会话。输出为保留当前对象、确认新对象、无对象或歧义，不要求每次都强行选人。

先建立声音左右与图像左右的对应标定。候选人的图像位置可映射到角度区间，但相机视场与镜头畸变需核对。声音方向只作为证据，不直接越过融合模块控制舵机。

### 10.2 首版规则

| 场景 | 行为 |
|---|---|
| 唯一稳定可见人，声音证据一致 | 经连续确认后关注该人 |
| 多人但发声方向只对应一个可靠候选 | 按门限与迟滞确认切换 |
| 同侧两人、双人同时讲话或证据冲突 | AMBIGUOUS，保持会话或提示明确交互 |
| 设备自身播放 | 不依据自播音直接切换对象 |
| 转动噪声、模糊或声音质量低 | 降低该证据权重或拒判 |
| 视觉过期或目标丢失 | 撤销依赖旧视觉的运动许可 |

“保持会话”不等于继续运动。人可以仍是对话对象，但没有新的可靠位置时，转动必须受限或停止。

### 10.3 从画面位置到转动请求

设图像宽度 W，目标中心 cx，归一化误差：

~~~text
e = (cx - W/2) / (W/2)
e_dead = sign(e) × max(|e| - deadband, 0)
omega = clamp(direction_sign × Kp × e_dead, -omega_max, omega_max)
theta_next = clamp(theta_command + omega × dt, theta_min, theta_max)
~~~

direction_sign 通过实物小角度测试确定。死区避免中心附近反复抖动，omega_max 限制速度，theta_min/max 来自机械与舵机标定。dt 使用实际时间，但遇到长时间暂停应重置而非积累一次很大的转动。

可先用轻量平滑或 One Euro Filter，目标切换和失效后重置状态；平滑不能刷新旧帧时间。[One Euro Filter 原论文](https://gery.casiez.net/publications/CHI2012-casiez.pdf)

### 10.4 输出和停止

PS 只提交候选角度/速率和许可信息，PL 检查后输出 PWM。具体脉宽、周期、角度映射和电平必须按舵机实测，不把常见 1—2 ms 范围当作所有器件通用值。

仅一个运动服务可以写命令寄存器，UI、音频、身份和模型服务都不能直接修改舵机。停止优先于常规更新，释放后经过人工恢复与位置确认条件才允许再次启动。数字输出停止时间与机械实际停止时间分开测量。

## 11. FPGA 自研模块及命令许可

### 11.1 建议模块划分

| 模块名（建议） | 输入 | 输出 | 要验证的事情 |
|---|---|---|---|
| audio_clock_gen | 基准时钟、配置 | BCLK、WS、位/槽使能 | 频率、高低电平、相位、启动 |
| dual_i2s_rx | 两路 SD 与时序 | 对齐样本、样本序号 | 位序、符号、槽位、丢样 |
| audio_window_buffer | 样本流 | 稳定窗口与交接事件 | 读写所有权、溢出 |
| xcorr_engine | 双通道窗口 | 各 lag 相关值 | 定点结果、窗口长度、吞吐 |
| doa_quality | 相关值与幅度统计 | 方向、质量、UNKNOWN | 峰选取、阈值、迟滞 |
| axi_control_regs | AXI-Lite 访问 | 影子配置、提交事件、状态 | 地址、字节写使能、背压 |
| command_guard | 命令、硬件计时、停止状态 | 接受/拒绝、活动许可 | 顺序、会话、边界、失效 |
| motion_limiter | 已批准目标与当前命令值 | 受限命令值 | 速度限制、范围和复位 |
| servo_pwm | 脉宽与允许状态 | PWM | 周期、更新边界、异常停止 |
| fault_manager | 停止、超时、模块异常 | 故障锁存、使能撤销 | 优先级、恢复条件 |

这不是把所有模块都拆成独立 IP 的要求。可按接口与验证需要组合，避免过度封装。DPU 使用匹配的官方 IP，单独标记来源，不列为本队从零设计的神经网络加速器。

### 11.2 参数必须原子提交

一条运动请求包含目标、许可期限、序号和会话。如果 ARM 逐个写活动寄存器，硬件可能读取到“新角度＋旧期限”。采用影子寄存器：先写完整命令，再写 COMMIT，硬件在提交时整体检查并一次性替换活动状态。

AXI-Lite 的地址与数据通道独立握手，实现不能假定 AW 和 W 必须同拍到达。正确处理 WSTRB、背压、非法地址和重复提交。状态读取也要避免一半属于新窗口、一半属于旧窗口，可提供序号或快照机制。

### 11.3 寄存器内容

建议提供 VERSION、BUILD_ID、STATUS、FAULT、ACTIVE_SESSION、LAST_ACCEPTED_SEQ、REJECT_REASON、SHADOW_TARGET、SHADOW_LEASE、COMMIT、STOP_STATE、DOA_RESULT、DOA_QUALITY、SAMPLE_COUNTER、DROP_COUNT 等类别。

寄存器地址与位宽在接口文件中冻结，软件使用同一份生成定义或严格版本检查。错误码区分过期、重复、会话不符、范围错误、停止未恢复和模块未就绪，便于证明硬件为何拒绝。

### 11.4 有效期怎样传递到硬件

命令来源是某帧图像或一组证据，其有效期限应追溯到原始观察。软件不能重新发送一次就让旧证据无限续期。

例如在同一 PS 单调时间域中：帧时刻 1000 ms，允许证据年龄 300 ms，因此截止为 1300 ms。准备提交时已经 1120 ms，扣除 20 ms 的映射/提交余量，最多再授予 160 ms；若硬件最大租约另有限制，还要取更小值。

~~~text
remaining = evidence_deadline - ps_now - uncertainty_margin
lease = min(remaining, hardware_max_lease)
remaining <= 0 → 不提交运动许可
~~~

PS 与 PL 不是天然共享同一计数器。需要标定计时关系、约束提交耗时，或设计带硬件挑战计数/截止时间的握手。若仅使用“硬件接受后开始倒计时”的相对租约，必须单独界定提交延迟，不能声称它无条件保证曝光到动作的总年龄。

PL 能可靠检查收到的字段和本地时间规则，但没有直接观测相机曝光时不能独立证明软件提供的时间真实。报告应区分数字协议保证与完整感知链保证。

### 11.5 状态机

建议状态为 DISABLED、READY、ACTIVE、EXPIRED、FAULT。上电和 FPGA 未配置时由外部电路维持禁能；软件和硬件自检后可进入 READY；有效命令进入 ACTIVE；许可过期撤销活动输出；停止或关键异常进入锁存故障。

故障清除、位置确认和重新授权分开处理。停止键释放只是输入恢复，不能自动重启舵机。正常 PWM 更新可在周期边界生效，停止通路应具有单独定义、可测量的响应时间。

## 12. DPU 与自研逻辑如何同片整合

### 12.1 一个最终硬件平台

DPU、AXI 互连、音频处理和控制监督共同进入最终硬件工程。分别综合能通过不代表放在一起也能通过；需要检查总资源、布局布线、时钟约束和复位。

不要依次加载“DPU 完整比特流”和“舵机完整比特流”后假定前者仍然存在。正常完整配置会替换设计；本期不采用未经专门设计的动态部分重配置。

更换与同一 DPU 架构匹配的网络工件通常不要求重新配置 PL；运行时可以组织多个网络的执行，但总体能力受资源与负载限制。[AMD DPU 系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)

### 12.2 两类数据通道

- 大块图像和张量在 DDR 与 DPU 之间传递，按平台运行时要求管理缓冲、对齐、缓存一致性和生命周期。
- 控制、质量、方向和状态通过 AXI-Lite 等轻量接口交换，不逐像素写控制寄存器。

音频短窗口优先在 PL 片上缓冲中计算，减少对 DDR 的依赖；调试时保留可控的原始音频导出。PWM、超时计数和停止逻辑不能等待一次长时间的 DPU 或总线事务完成才继续运行。

### 12.3 资源预算方法

| 资源 | 主要使用者 | 需要记录 |
|---|---|---|
| LUT/FF | DPU、状态机、互连、接口 | 综合与实现占用、关键路径 |
| DSP | DPU、相关乘加 | 总量、并行度、复用后的吞吐 |
| BRAM/URAM | DPU、音频窗口、FIFO | 深度、位宽、端口冲突和余量 |
| DDR 容量与带宽 | 图像、模型、UI、PS 程序 | 峰值内存、搬运量、并发延迟 |
| CPU | 跟踪、补偿、预后处理、UI | 各任务耗时、负载与调度等待 |
| IO/时钟 | Pmod、I2S、PWM、AXI | 引脚表、时钟域、CDC 和约束 |

KV260 的 4 GB DDR 是系统共享内存，不等于 PL 拥有 4 GB 片上缓存。[AMD KV260 产品资料](https://docs.amd.com/r/en-US/ds986-kv260-starter-kit/Product-Details)

在 DPU 配置尚未冻结前，不写“资源肯定够”或固定利用率。先用可运行平台测基线，再加入自研逻辑并重新测量。小型音频计算可用时分复用，优先保留时序和布线余量。

### 12.4 工具链与产物

已有材料中的 Vivado/Vitis/PetaLinux 2022.2、Vitis AI 3.0、DPU 4.1 是历史兼容路线。采用时应使用对应参考设计与版本表，不混装未验证的新旧组件。[Vitis AI 3.0 兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)

Vivado 硬件集成与 Vitis 平台集成需要选择明确路线；Vitis AI 3.0 文档对 VART 是否配合 XRT 有不同要求。PYNQ 仅在对应 overlay 和平台已经验证时使用，不能把 hwh、bit、xclbin、xmodel 当作可互换文件。

冻结发布包至少包括硬件构建标识、硬件文件、设备树、系统镜像、驱动/运行时、模型工件、应用版本、配置和文件校验值。模型架构变化或 DPU 变化后重新检查兼容性。

## 13. 多任务调度与避免冲突

### 13.1 三类不同的并发

自研 PL 电路可以在已实现的资源上并行工作；PS 软件由操作系统调度；多个模型共享 DPU 时需要运行时与应用共同组织提交。三者不能用“FPGA 能并行，所以全部模型都不排队”概括。

### 13.2 调度原则

| 任务 | 触发方式 | 排队与降级策略 |
|---|---|---|
| 停止、许可计时、PWM | 硬件时钟持续运行 | 不依赖网络、UI 或推理返回 |
| 双麦采集 | 连续输入 | 缓冲有界，溢出显式报告 |
| 人体检测 | 周期性取最新帧 | 待处理只保留最新候选 |
| 跟踪/融合/控制 | 新结果或定时状态检查 | 不等待主机语言模型 |
| 人脸识别 | 新人、未知、复核、登记 | 限并发、去重、允许跳过 |
| UI 预览 | 显示刷新 | 降频，避免复制完整处理链 |
| VLM/ASR/TTS | 用户发起一轮交互 | 请求超时、可取消、丢弃迟到结果 |
| 数据库与日志 | 事件触发 | 限容量，不阻塞控制回路 |

建议集中设置 inference_scheduler：限制未完成任务数量，保证人体检测有可用服务机会，再在余量内执行人脸检测和特征提取。应用优先级不能默认中断已开始的 DPU 推理，因此必须测单次人脸任务占用时间。

### 13.3 计算预算的直观估算

设人体检测占用 DPU 的时间为 t_det、执行频率为 f_det；每次身份处理需要 t_face+t_embed、频率为 f_id。在近似串行的首版调度中，可先估算：

~~~text
U ≈ f_det × t_det + f_id × (t_face + t_embed)
~~~

时间统一使用秒。U 接近或超过 1，意味着平均需求已接近或超过单服务通道能力；U 小于 1 也不能证明最坏延迟满足要求，还要考虑突发、预后处理、搬运、其他网络和调度等待。

纯示例：若检测占用 25 ms、每秒 10 次，身份完整 DPU 占用 35 ms、每秒 2 次，平均为 0.25+0.07=0.32。这不是本项目测得性能，只用于说明为何“按需识别”比对所有帧重复认人更容易控制负载。

### 13.4 所有权规则

1. 相机只有一个采集所有者。
2. 运动寄存器只有一个软件写入服务。
3. DPU 任务遵守统一提交与缓冲生命周期。
4. 身份登记和删除由身份服务事务处理。
5. 对话取消由板端会话状态立即生效，网络确认不作为前提。
6. UI 读取真实状态，不能用动画结束时间假装硬件动作完成。

服务边界可以通过进程间队列或共享内存实现，具体选择以实际语言、性能和维护成本为准。使用共享内存时必须定义谁申请、谁读、何时释放。

### 13.5 过载时的行为

优先减少 UI 预览和非必要日志，其次限制人脸复核和非当前对象任务，再根据测量调整检测配置。无论负载如何变化，过期结果都不能继续授权运动。无法维持核心感知时宁可明确进入静止/降级，也不能让队列积累几秒的旧画面。

这不是自动保证无故障：电源、温度、驱动、CDC、时序和程序错误都可能导致异常，必须分别验证。

## 14. KV260 与 Windows 的多机通信

### 14.1 两端职责

KV260 是当前对象、身份与运动许可的权威来源；Windows 返回转写、回答和音频。主机模型可以提出受限的语义建议，不能直接提交 PWM、写寄存器或绕过本地控制模块。

局域网传输内容包括音频片段、选定快照、问题文本、必要的场景摘要、回答文本和合成音频。不要持续上传全部相机帧或整个人脸库，除非某个明确功能确实需要。

### 14.2 建议接口

| 接口类别 | 关键输入 | 关键输出 |
|---|---|---|
| health | 协议版本/探测 | 服务状态、模型版本、能力 |
| asr | 音频、格式、采样率、request_id | 转写、错误、耗时 |
| vlm | 本轮快照、问题、允许的上下文 | 回答、错误、模型版本 |
| tts | 回答文本、语音参数、request_id | 音频、格式、采样率 |
| cancel | request_id、会话代次 | 是否收到取消；本地不等待此响应才停止 |

HTTP 适合请求响应，WebSocket 可用于进度和流式结果。二进制图像/音频应使用清楚的类型和长度，避免无必要编码开销。首版不要求为所有数据建立复杂消息中间件。

### 14.3 请求元数据

~~~json
{
  "protocol_version": 1,
  "boot_id": "board-start-example",
  "presence_session_id": "visit-example",
  "conversation_epoch": 3,
  "request_id": "request-example",
  "frame_id": 1250,
  "camera_epoch": 1,
  "image_age_ms_at_send": 85,
  "timeout_ms": 10000
}
~~~

上述是结构示例，不是冻结阈值。用户身份和会话归属以板端保存的请求上下文为准，不能相信模型回答文本里自称的 ID。重试保持请求身份并做去重，防止重复播放或重复登记。

### 14.4 时间与取消

PS 与 Windows 的单调时钟不能直接相减。板端计算请求发出到返回的往返时间，主机报告自身内部耗时。若需要跨机单向时延，必须建立时钟同步并报告误差。

用户取消时：先停止本地播放，递增对话代次并清空该轮待输出，再尽力通知主机。旧请求随后成功返回也必须被丢弃。换人、相机重启或新一轮提问时采用同样的归属检查。

### 14.5 断连与重连

主机断连后，保持板端检测、跟踪、身份、UI 和受约束运动，前提是这些模块自身正常；显示问答暂不可用。重连后重新协商能力和版本，不重播缓存的旧回答，不自动恢复已取消会话。

应用级“没有公网仍能运行”需要预下载模型和依赖，确认无强制在线鉴权或下载步骤；它不等于完全不依赖局域网主机。

## 15. 语音、看图与屏幕如何配合

### 15.1 首版交互方式

采用按键录音的半双工流程：等待 → 录音 → 理解 → 回答生成 → 合成/播放 → 等待。播放期间可取消；不把设备自己的播音立即送回新一轮识别。全双工与回声消除属于后续增强，不作为首版完成条件。

### 15.2 一轮对话

用户按下说话键，板端记录当前对象与对话代次；松开后结束录音，同时选择具有明确时效的图片。音频送主机 ASR，文本与快照送 VLM，结果再送 TTS。板端检查归属后播放音频与字幕。

若 ASR 模型要求不同采样率，应真正重采样，不只修改 WAV 头。SenseVoice、Qwen2.5-VL 和 VITS/sherpa-onnx 是已有方案的候选，最终根据主机硬件、操作系统支持、模型质量和许可冻结；本文不保证具体显存需求或响应速度。

### 15.3 图像时效与回答范围

回答必须关联本轮图像。若生成期间场景已变，可显示“根据刚才的画面”；不能把旧图理解当作当前事实。图像看不清或对象不在视野时，允许明确说明无法确认，不能补造看见的物品。

### 15.4 板端界面

屏幕由 KV260 实际输出，可使用与当前系统匹配的 Qt 或浏览器界面，先冻结一条实现路线。用户界面显示角色、字幕、当前交互状态和必要的降级说明；工程调试页另显示帧龄、方向、DPU 耗时、拒绝原因等。

说话动画由实际播放状态触发；播放失败不能继续装作正在回答。UI 退出或重启不能阻塞停止与运动期限检查。

## 16. 六条完整运行流程

### 16.1 开机

1. 外部使能保持关闭，停止通路有效。
2. Linux 启动，创建新 boot_id。
3. 检查硬件、应用、模型和寄存器版本是否匹配。
4. 启动相机，确认有连续且非过期的新帧。
5. 验证 DPU 单次推理与结果格式。
6. 启动身份库、音频、跟踪、UI 和日志。
7. 读取 PL 状态，核对停止输入、租约和输出默认值。
8. 人工确认机构位置及允许范围，满足条件后进入 READY。
9. 探测主机服务，显示完整模式或本地降级模式。

主机未就绪不应使已经验证的板端身份与停止能力无法工作。

### 16.2 一个人进入并被跟随

新帧到达，YOLO 发现人体；跟踪连续确认后建立轨迹和来访会话；当前对象选择成立；控制模块计算画面误差，提交有期限的请求；PL 检查通过后更新 PWM；新画面再次进入检测与补偿，形成视觉闭环。身份服务在合格图片出现时按需查询，而非挡在每一次转动之前。

### 16.3 两个人出现且其中一人发声

两条视觉轨迹保持独立。双麦产生方向窗口与质量；融合检查同一时间附近的候选、坐标关系和歧义；足够稳定时切换交互对象并更新运动会话。换人后，旧对象的迟到身份和问答结果失效。

如果两个人在同一粗方向，输出歧义，保留合理的会话状态并请求明确交互；不能虚构双麦具有区分相邻嘴部的能力。

### 16.4 登记后离开再返回

用户明确登记，系统获取合格人脸模板并确认姓名，事务提交到板端身份库。离开后释放临时轨迹；返回时创建新轨迹，通过新图片与库比较，多帧确认后恢复 person_id。测试必须真正离开、重新出现，而不是一直沿用未结束的轨迹。

### 16.5 看图问答

板端完成录音和拍照关联，主机完成转写、图文理解与合成，板端校验请求归属后播放。期间视觉跟踪与硬件监督继续运行；主机忙不能让本地停止处理排队。

### 16.6 失效处理

| 事件 | 必须观察到的行为 |
|---|---|
| 相机断开/冻结 | 原始证据不续期，运动许可按规则到期 |
| 身份服务退出 | 当前对象可继续作为匿名对象处理，不凭旧结果冒认 |
| DPU 过慢 | 丢弃过时待处理帧，必要时撤销运动许可 |
| Windows 断连 | 本地能力继续，问答明确降级 |
| 音频溢出 | 错误计数增加，相关方向结果标无效 |
| UI 崩溃 | 硬件停止与控制不依赖 UI 存活 |
| 外部停止 | 执行器使能按电路撤销，状态锁存 |
| 系统重启 | 新代次，不接收旧命令与旧会话回复 |

## 17. 逻辑错误、资源冲突与工程防护

### 17.1 风险矩阵

| 风险 | 典型表现 | 应对与证据 |
|---|---|---|
| PL 资源/时序不足 | 布局失败或关键路径不达标 | 调整 DPU/并行度，保存实现报告 |
| DPU 排队 | 跟随旧画面，认人拖慢检测 | 集中调度、有界队列、测 P95 和最大值 |
| PS/DDR 拥堵 | UI、跟踪和音频一起变慢 | 减复制、降预览、分析各环节耗时 |
| 帧缓冲提前复用 | 结果对应错误图像或偶发异常 | 引用计数、不可变元数据、生命周期测试 |
| 换人后迟到结果 | 名字/回答归到另一个人 | 会话与请求代次校验 |
| 地址或引脚重叠 | 某模块写坏另一个模块 | 统一表、版本检查、约束审核 |
| 跨时钟域错误 | 偶发丢事件或多位撕裂 | 正确 CDC、FIFO、约束与仿真 |
| 命令非原子更新 | 新目标配旧期限 | 影子寄存器和 COMMIT |
| 权限分散 | 多模块争相写舵机 | 唯一运动写入者 |
| 电源和线束问题 | 转头时掉线、重启、音频噪声 | 分支供电、波形、电流和压降实测 |
| 热与存储问题 | 长时间运行后速度变慢或退出 | 温度、内存、磁盘和日志容量监测 |

### 17.2 不能用一次演示证明的事情

综合通过不等于整个运行时正确；模型单独能跑不等于并发时满足时限；数字停止输出不等于机构瞬时静止；一次认出队员不等于低误认率；断公网不等于断主机。

报告对每项结论给出对应测量范围。没有编码器、制动模型和相关验证时，不宣称整机物理安全已被形式化证明。

## 18. 开发顺序与阶段交付

### 18.1 阶段门槛

| 阶段 | 工作内容 | 进入下一阶段的条件 |
|---|---|---|
| G0：冻结平台 | 器件、供电、引脚、工具、DPU、协议 | 有实际信息与可恢复版本 |

| G3：板端身份 | 人脸检测、对齐、特征、身份库、按需调度 | 认人不破坏 G2，误认/拒识有记录 |
| G4：声音与转动跟踪 | 双麦 RTL、参考比对、相机运动补偿、融合 | 噪声、多人、转头和歧义测试通过 |
| G5：完整交互 | 主机模型、录音、问答、播放、取消、UI | 连贯交互和断连降级可复现 |

软件参考和 RTL 仿真可提前进行，但最终集成按门槛推进。不把日历上的“第几天”当作某项已经完成的证据。

### 18.2 三人协作建议

| 角色 | 主责 | 关键交付 |

| A：FPGA 与硬件 | 平台、DPU 集成、双麦 RTL、控制保护、供电机构 | 同片工程、寄存器、约束、波形、标定 |
| B：视觉与身份 | YOLO、跟踪、补偿、人脸、DPU 模型与调度配合 | 模型契约、轨迹/身份接口、回放实验 |
| C：交互与集成 | 主机服务、语音、UI、网络、会话、日志与发布 | 请求协议、取消流程、完整演示与记录 |

A 与 B 共同确认 DPU 架构及模型工件；B 与 C 共同确认身份/会话；A 与 C 共同确认控制命令与停止。每次接口改变都更新版本，不能只在聊天里临时约定。

### 18.3 最先完成的十件事

1. 整理确切器件与主机配置，补高边开关原理图。
2. 选定已验证平台，保存恢复镜像。
3. 打通官方匹配模型单图推理。
4. 建立唯一相机服务和帧元数据。
5. 验证 YOLO 框坐标与人体检测。
6. 完成基础跟踪、命令监督仿真与空载 PWM 测量。
7. 形成小范围单人跟随闭环。
8. 测试板端人脸模型单图流程与登记库。
9. 进行检测＋人脸并发测试，确定调度预算。
10. 再将双麦、补偿和完整问答接入已稳定的主线。

## 19. 验收指标与测量口径

### 19.1 指标表的原则

下表是建议的测试方向，不替代旧需求中已经确认的验收编号和阈值。正式开测前，将旧 T01—T30 的实际条目逐项映射，并新增板端身份与共享 DPU 的测试；本版不声称已完成映射。

| 对象 | 测试方法 | 输出证据 |
|---|---|---|
| 检测 | 相同图片比参考与部署模型 | 漏检/误检、框位置、推理与预后处理耗时 |
| 跟踪 | 遮挡、交叉、出入画面录像 | ID 切换、丢轨、误切人持续时间 |
| 补偿 | 相机静止/转动、背景丰富/单调 | 补偿质量、跟踪收益、额外 CPU 耗时 |
| 双麦 | 固定方向/距离/噪声与同一 PCM 回放 | 混淆矩阵、UNKNOWN、PS/PL 一致性 |
| 人脸 | 已登记与陌生人，换光照和离开返回 | 误认率、拒识率、确认耗时、量化差异 |
| DPU 共享 | 检测单独、身份单独、共同运行 | 服务时间、排队时间、帧龄与性能变化 |
| 控制 | 规定横移路径与重复跟随 | 中心误差、稳定时间、振荡与触限位 |
| 保护 | 停帧、过期、重复、乱序、停止、软件退出 | 拒绝原因、PWM/使能波形与恢复行为 |
| 对话 | 固定语料、图片、问题与取消场景 | 正确性、整轮 P95、取消与迟到丢弃 |
| 整机 | 多模块长时间并发、冷启动和断连 | 温度、内存、错误、恢复与版本 |

### 19.2 可采用的初始目标

以下数值只用于第一轮规划，冻结后以对应正式测试定义为准：

- 人体感知链先争取约 10 Hz 的稳定更新，同时记录端到端时延。
- 图像出队至控制接受的 P95 可先以 200 ms 为调优方向；这不包括未知的曝光至出队缓存，后者需另量化。
- 单人跟随至少执行 20 次规定运动，报告稳定区间的中心误差，例如以图像宽度的 10% 为初始目标。
- 停止输入到定义的数字输出变化可先以 5 ms 为目标；实际功率轨下降与机械停止另测。
- 语音问答至少 30 轮，整轮 P95 可先以 8 s 为调优方向，明确语音长度、主机和模型配置。
- 取消至少 20 次，检查本地播放停止和旧请求失效；例如以 300 ms 为初始目标。
- 至少 3 次冷启动、2 小时全功能运行；双麦另做连续采样与丢样计数检查。

人脸首版不直接承诺一个很高的准确率。需要同时报告登记人数、未知人数、不同会话次数、姿态/距离、误认与拒识。若测试出现 0 次误认，也要给出总样本数，不把小样本的零事件写成普遍零风险。

### 19.3 时延记录

板端记录图像时间、出队、预处理结束、DPU 排队/执行结束、跟踪结束、融合结束、控制提交和硬件接受；音频记录窗口起止与结果发布；主机独立记录服务内部耗时。

帧率不能替代时延：显示每秒刷新 30 次不代表检测 30 次；排队的模型即使吞吐高，也可能处理很旧的图像。报告至少包含中位数、P95、最大值及异常样本解释。

### 19.4 测试数据与可复现性

保存原始或经适当处理的音视频、时间戳、标注、配置和版本。调参集与测试集按人员/会话/场景划分，不能同一批数据调到最好后又当独立测试。图像和身份素材按参与者同意与保存范围管理，公开工程不直接附带未经授权的人脸库。

## 20. 故障注入与并发验证

### 20.1 最小异常集

| 注入动作 | 预期结果 |
|---|---|
| 相机不再产生新帧但缓存保留 | 不刷新证据时间，许可到期 |
| 人脸任务排队期间换人 | 旧身份结果不绑定新对象 |
| 删除身份后旧请求返回 | 库版本检查拒绝恢复已删身份 |
| 重复提交同序号命令 | 不产生重复有效更新 |
| 乱序命令到达 | 拒绝或按明确协议处理，不倒退活动状态 |
| 只写部分影子寄存器 | 不改变活动命令 |
| UI/主机服务被关闭 | 硬件监督继续，明确降级 |
| DPU 推理延长 | 人脸受限流，过期视觉不驱动机构 |
| 双麦输入饱和或溢出 | 标记无效，方向不假装可靠 |
| 外部停止后释放 | 保持锁存，等待人工恢复 |

### 20.2 分层验证

第一层用固定输入验证算法；第二层用仿真验证 RTL 与参考结果；第三层空载测接口和波形；第四层小负载验证动作方向和限位；第五层加入完整软硬件并发；最后执行故障注入与长时间运行。

并发结果必须与同一发布版本的单模块结果比较。若降级配置改变输入分辨率或模型，应单独列出，不能混合成同一组性能。

## 21. 如何形成有深度的算法与工程贡献

### 21.1 推荐的研究题目

**面向单轴视听交互终端的时效与质量约束目标选择及硬件执行监督。**

围绕真实约束展开：小麦距只能提供粗方向；旋转镜头改变轨迹；人脸推理与检测共享计算资源；语言模型和网络响应不确定；旧感知不应持续授权动作。

### 21.2 拟研究的改进

1. 将声音质量、视觉稳定度和观察时间统一为可比较的证据。
2. 在相机运动补偿质量不足、同侧多人或自播音时显式拒判。
3. 根据实测运动与不确定性保守调整证据期限，上限由硬件限制。
4. 将对象选择与执行许可分开，使“仍在与某人对话”不自动变成“继续跟随旧位置”。
5. 将人脸任务按质量和事件触发，研究在身份确认速度与视觉帧龄之间的取舍。

这些都是待实现和验证的设计方向，不能在没有实验前写成“已提出领先算法”。人脸上板主要是系统部署贡献，不默认构成新的识别网络。

### 21.3 消融实验

| 实验组 | 逐步增加的能力 | 回答的问题 |
|---|---|---|
| A0 | YOLO＋单阈值 IoU | 最简单跟踪有何问题 |
| A1 | 改用两阶段关联 | 低分补回是否减少断轨 |
| A2 | 加相机运动补偿 | 转头场景的错关联是否减少 |
| A3 | 加双麦粗方向 | 多人选择是否改善 |
| A4 | 加质量拒判与迟滞 | 噪声和歧义下是否减少错选 |
| A5 | 加证据期限与硬件许可 | 延迟与失效下是否减少错误动作 |
| B0/B1 | 每帧认人与事件触发认人 | 身份速度、帧龄和资源如何变化 |

同时报告错误率、可用覆盖率、拒判率、延迟和资源。全部拒判的系统不能因为“几乎无错误动作”就宣称优秀；始终跟随的系统也不能只凭连续性忽视错误对象转向。

### 21.4 FPGA 价值怎样证明

对同一算法、同一音频窗口比较优化 PS 实现与 PL 实现的耗时、抖动、CPU 占用和资源。对控制监督比较正常与异常输入下的软件/硬件可观察行为。DPU 比较应说明是否采用相同量化模型和前后处理，避免把模型差异误报为加速收益。

本项目的 FPGA 贡献可以体现在接口时序、可复现逻辑、数据流、并发控制与延迟确定性，不必为了制造算力瓶颈而无必要放大网络或上 FFT。
