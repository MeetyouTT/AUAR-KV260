# AURA 三人实施分工与部署位置复核

日期：2026-09-30（用户本地日期）。

本记录依据项目内方案、三份三十天个人计划、第四轮资料与可读取的相关对话重新核对。它重建已有分工，不把本次聊天里的可行性建议当作已经决定的架构变更，也不代表任何功能已在板上通过。

## 1. 核对结论

当前实施分工以三份 `aura_plan_*_30days.md` 为主，并用 2026-09-27 对齐记录解释第四轮资料的冲突：

- A：FPGA、硬件、平台集成和运动执行监督。
- B：视觉、板端身份、人物轨迹及唯一运动请求服务。
- C：视听说话人、目标建议、语音问答、录放音、界面和启动清单。

人员责任与运行位置分开理解。C 负责语音，意味着 C 同时维护板端录放音/界面和主机模型服务。现有三十天计划没有把完整 ASR/TTS 板端迁移列为首版必交。

“Windows 只运行大模型、其余全部板端运行”不是本次核查中已经统一的现行实施方案。旧资料确有 ASR/TTS 板端优先的说法，第四轮回复已明确改成首版主机运行、板端迁移后置的限时验证任务。

人脸识别不同：用户在《介绍项目结构与实现》对话中明确提出室友希望将人脸识别搬到 FPGA 板，后续 B 计划将板端人脸处理、特征比较与身份库列为目标。第四轮资料仍写主机首版身份链，对齐记录处理为“主机可先联调，板端目标保留”，最终正式范围仍有未回填的选择。

## 4. 三人之间的数据流

运动与关注对象的链路：

1. B 的相机服务提供画面、轨迹、人脸连续片段及时间。
2. A 的双麦模块提供方向、质量、采样窗口和异常状态。
3. C 结合说话证据、方向和上下文，发布候选对象建议。
4. B 的唯一运动服务核验轨迹、会话与时效，计算运动请求。
5. A 的 motion_guard_ip 再检查许可、命令、范围、到期和停止状态，输出 PWM。

正式运动寄存器只有 B 的一个运动服务写入；C 的模型服务不直接控制 PWM。

当前首版语音链：

KV260 录音 → Windows ASR → 文字与 B 提供的本轮快照 → Windows VLM → Windows TTS → KV260 校验、播放及显示。

## 6. 四项研究怎么分

| 方向 | 负责人 | 当前月计划的实现深度 |
|---|---|---|
| Light-ASD | C 主导，B 给轨迹/片段 | 跑预训练基线、接实际音视频、记录失败 |
| Streaming ASD | C 主导，B/A 配合时间信息 | 借鉴有限窗口、队列和延迟管理；不默认为完整新网络复现 |
| LoCoNet | B/C 共同 | 轨迹连续性、时间上下文、多人候选与对照；规则不等同于完整网络 |
| Neural Simplex | A 主导，B/C 给失效场景 | 自研运动执行监督；不自动等同论文完整安全证明 |

YOLO 和人脸是产品视觉能力；双麦相关算法及 RTL 归 A/C 协作，不能替代 Light-ASD。

## 8. 当前实测进度来源与下一步分工

用户在本聊天粘贴的 Ubuntu 审查报告确认：官方 PetaLinux 2022.2 镜像已写卡，板端能登录；Vivado/Vitis/PetaLinux 2022.2 已可用；存在 B4096 固件包；DPU 实际加载与正确推理仍待验证。本次没有连接板卡复测。镜像中存在 B4096 文件不等于本次已加载该配置。

- A：解决串口使用冲突，完成本次启动/固件加载身份记录和 DPU 基线；随后建立可重建参考平台。
- B：核对实际 DPU、配套模型及预后处理，验证固定样例；同时准备相机、检测、跟踪与人脸候选。
- C：用已购 USB 音频设备验证板端录放音和界面；在原计划位置验证 ASR/TTS/VLM 及 Light-ASD 样例，准备音频参考与接口。
