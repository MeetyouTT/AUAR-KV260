**KV260 镜像问题综合判断与重建验收方案**

依据：用户提供的 Codex、DeepSeek 两个审计包，工作区项目需求及平台文件，AMD 官方版本兼容、DPU 接口、系统集成和启动文档。整理日期：2026-09-27（用户本地日期）。

**结论：建议保留现状备份，另用一张 SD 卡建立官方配套的干净基线；基线验证通过后，再从同版本、可重建的参考工程制作项目最终镜像。不要原样重刷当前混装产物，也不要仅替换新 bit 就宣布修复。**

用户口述“KV-2000”，但两份审计、项目需求、历史启动日志的 xck26/KV 载板标识均指向 AMD Kria KV260。本文按 KV260 分析；实际写卡前仍须核对板卡丝印与载板 revision。

本文完成的是资料交叉核验和工程决策，没有连接板卡、重新执行 Vivado 查询、下载完整官方系统镜像或实施烧录。附件里的“禁止”“下一步命令”等是当时审计任务的内容，不是本轮用户指令。

**1．现在究竟已经知道什么**

| 事项 | 材料支持的结论 | 不能据此推导的结论 |
|---|---|---|
| 旧系统硬件交付 | 两份报告均记录：PetaLinux 使用的旧 bit 来自 100/100 MHz 实现，XSA 中 HWH 和设备树却描述 200/100 MHz | 尚未证明用户最近那次异常运行实际加载的就是这一组文件 |
| 新 clockfix 重建 | 新 bit 与 XSA 内嵌 bit 哈希一致，报告记录 200/100 MHz 与时序通过 | 时序通过不等于模型结果正确；新 bit 也未完成系统部署与板端验收 |
| DPU reset | 新旧 OOC 查询均见两路端口无负载，内部层级 pin 指向常量；top synth 至 opt 之间外层连接消失 | 不能仅据此证明实际硬件永久复位，也不能证明这种现象功能上无害 |
| 历史启动链 | 一次日志显示 QSPI 2023.2 系列固件、SD 2022.2 内核，并使用禁用 DPU initcall 的参数 | 不代表当前运行仍使用这些参数；跨版本字符串本身也不足以证明固件不兼容 |
| VART/XIR | 本地镜像包清单标为 3.0；报告提到板端库构建日期不同 | 构建日期不同不是 ABI 错配证据，版本号一样也不是集成方式匹配证据 |
| 推理现象 | Codex 报告记录用户反馈：重复输出波动、猫图和全零输入区分不明显 | 本轮没有相应原始运行数据，不能确认单一根因或宣判板卡损坏 |

最有力的结论是“交付链已经失去一致性”，而不是“SD 卡必坏”“Linux 必坏”或“DPU reset 已经确定坏了”。这足以支持更换可信基线，但不足以承诺重刷一次必然解决全部问题。

这里还有一个常被忽略的区别：旧设计被报告为实际 100/100 MHz，不只是 Linux 显示了错误频率。PG338 定义 dpu_2x_clk 为 m_axi_dpu_aclk 的两倍。如果旧实现和运行身份成立，应修正硬件时钟关系及配套交付；只把设备树数字改成 200/100 不会改变 FPGA 内实际时钟。[AMD DPU 端口定义](https://docs.amd.com/r/en-US/pg338-dpu/Port-Descriptions)。

**2．怎样看待两份报告的分歧**

DeepSeek 对“无负载端口在优化阶段被裁剪”的解释有原始查询支持，新旧实现相同也支持“不是此次重建独有的回归”。但旧实现本身就没有被证明功能正常，因此“旧版也这样”不能作为无害证明。把“网表变化机制已解释”继续推导成“内部复位功能已经正确”，证据不够。

Codex 保留复位语义疑问更稳妥：AMD 要求每路复位与对应时钟同步，端口表将这两路定义为低有效。但是层级网表对象和未使用端口的常量显示，也不能直接等同于器件中的功能复位电平。[AMD 复位要求](https://docs.amd.com/r/en-US/pg338-dpu/Reset)。

工程上应做的是：使用来源明确的同版本 DPU IP 和官方参考配置建立对照，比较 IP 参数、相关网表与复位端点；确认时钟复位、实现告警及板级输出条件后，在可恢复的测试环境做功能验收。必要时向 AMD 提交最小复现工程。不要通过强行 KEEP/DONT_TOUCH 或随意给 reset 绑高低电平来“消除告警”。

两份报告所称“不可上板”不应被扩展成“永远不能进行板端验证”。需要区分尚未验证的候选构建与可交付版本：候选构建在检查和恢复准备完成后可安排受控试验；最终交付必须通过功能和稳定性验收。也没有必要把逆向完整 bitstream 或全量 FPGA 配置回读作为唯一放行方式，可使用受控加载记录、文件哈希、可读硬件构建标识和功能测试共同建立身份链。

另有两个需要纠正的推断：

- QSPI 2023.2、Linux 2022.2 说明来源不同，不能单凭此要求降级 QSPI。兼容性要查目标镜像和 Kria 启动固件说明。
- `Loading Environment from nowhere... OK` 不能单独证明 U-Boot 环境损坏或为空；停在提示符还要检查是否人工打断、boot target、分区与启动脚本。历史日志不足以锁定原因。

**3．按照项目要求，应选择什么系统**

项目的《完整工作内容与实施要求》W02 和 FPGA 框架把下列组合列为优先复现路线，Vivado/Vitis 2022.2 已记录为用户确认；平台清单中的实际镜像名和哈希仍为 null。因此不能说项目已经锁定了一个经过实板验证的最终镜像文件。

| 层级 | 本次建议 |
|---|---|
| 板端系统路线 | 与项目硬件匹配的 AArch64 嵌入式 Linux / PetaLinux 2022.2 路线 |
| FPGA/平台工具 | Vivado/Vitis 2022.2，记录具体补丁和构建环境 |
| Linux 构建 | PetaLinux 2022.2，使用该版本支持的 Linux 主机环境 |
| AI 软件 | Vitis AI 3.0；VART、XIR、Library 及驱动按所选集成方式配套 |
| DPU | DPUCZDX8G 4.1，具体架构、核数、接口宽度、fingerprint 由实际平台确定 |
| 初始官方对照镜像 | `xilinx-kv260-dpu-v2022.2-v3.0.0.img.gz` |
| 最终项目镜像 | 基线可重建后，加入自研逻辑、驱动、外设与应用，重新生成并通过验收的完整 SD 镜像 |

AMD 官方兼容表确认 2022.2 / DPU 4.1 / Vitis AI 3.0 的组合；Library 3.0 发布说明明确列出上述 KV260 镜像。[版本兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)、[Library 3.0 发布说明](https://docs.amd.com/r/3.0-English/ug1354-xilinx-ai-sdk/Vitis-AI-Library-v3.0-Release-Notes)。

下载应从 [AMD Vitis AI 3.0 写卡说明的 KV260 入口](https://docs.amd.com/r/3.0-English/ug1414-vitis-ai/Flashing-the-OS-Image-to-the-SD-Card) 进入。本次核实了文档中的名称与入口，没有取得实际镜像或核验其官方校验值，也没有验证下载权限和传输可用性。若发布页提供校验值或签名，按其校验；自行计算 SHA256 可用于后续识别同一文件，但不等于官方真实性认证。AMD 工具安装器的校验值不能用于这个板端镜像。

不建议此时为了“干净”而切换到另一套 Ubuntu/PYNQ 或最新工具链。它们并非天然不适合 KV260，而是切换后需要重新验证驱动、运行时、DPU 和自研逻辑，增加当前排障变量。开发电脑 Ubuntu、模型编译 Docker 和板端 Linux 是三种不同角色；Vitis AI 源码 zip 与 Docker 镜像都不是可直接写入 SD 卡的板级系统。

**4．各种文件分别做什么，哪些能用于写卡**

| 文件 | 用途 | 使用原则 |
|---|---|---|
| 官方 `.img.gz` | 压缩的整卡镜像 | 按官方流程用写卡工具写入整张 SD 卡并校验，不是普通复制到某个分区 |
| 自建 `.wic` / `.img` | 构建系统生成的完整磁盘布局 | 只有确认其包含匹配分区、内核、rootfs、启动资源后才能作为最终整卡交付 |
| `BOOT.BIN` | 启动固件容器，具体成员依平台打包 | KV260 默认主启动设备是 QSPI，复制到 SD 根目录不代表已更新实际启动固件 |
| `image.ub` | FIT 容器，可含内核、设备树和 ramdisk | 不是自动包含全部 SD 分区和持久化数据的整卡镜像，须按实际打包内容判断 |
| `.bit` / `.bit.bin` | FPGA 配置数据 | 要用目标平台支持的格式与加载方式；不等同于 Linux 系统 |
| `.xsa` / `.hwh` | 硬件交接和描述文件 | 用于软件与设备树生成及追溯，不是给写卡工具烧录的 OS 镜像 |
| `.dtb` / `.dtbo` | 设备树 / overlay | 必须匹配实际硬件、地址、中断、时钟与驱动 |
| `.xclbin` | Vitis 加速应用工件 | 只适用于相应的 Vitis/XRT 平台；不能套用于任意 Vivado DPU 工程 |
| `.xmodel` / `arch.json` | 编译模型 / DPU 目标描述 | 必须匹配实际 DPU 配置与工具链 |

KV260 的 QSPI 主启动固件与 SD 上的运行系统是分层的。这意味着 SD 重刷可以替换系统，但不会自动清除 QSPI 中的启动差异；也意味着不必为每次应用修改重写 QSPI。[AMD 启动设备说明](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Boot-Devices-and-Firmware-Overview)、[QSPI 主启动设备](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Primary-Boot-Device)。

**5．一个应提前排除的集成问题：Vivado 与 Vitis/XRT**

当前材料呈现自建 Vivado DPU BD、PetaLinux 和 `xlnx_dpu` 驱动路线，尚未充分证明最终运行时的构建选项。不能因为运行库都叫 3.0 就视为匹配。

AMD Vitis AI 3.0 文档明确：Zynq UltraScale+/Kria 的 Vivado 集成路线，VART 应不带 XRT 构建；Vitis 集成路线则需要 XRT。文档指出默认 recipe 可能启用 Vitis 模式，应根据路线使用对应 recipe，且不要同时放入两套。这个问题值得核查，但目前不是已经确认的故障原因。[AMD 系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)。

本项目的默认决策应为：官方对照卡保持其原配加载方式；最终自研联合平台先原样重建选定的参考设计，再沿同一路线扩展。如果最终选 Vivado 直接集成，就成套构建对应驱动和不带 XRT 的 VART；若选 Vitis 平台，就保留其 XRT、xclbin 与 overlay 配套结构。官方对照卡跑通不意味着把当前自定义 bit 拷进去就能兼容。

**6．推荐执行顺序与每一步的停止条件**

**第一步：冻结故障现场，避免越修越难比较。**

保留现有 SD 卡，备份项目、应用配置和模型；条件允许时对卸载后的卡做完整镜像备份。保存一次当前上电到异常发生的串口日志，并在同一次运行记录系统版本、bootargs、实际 rootfs 挂载方式、DPU 查询、相关日志、模型/输入/应用和运行库哈希。记录启动加载路径及对应工件哈希，区分“卡上有这个文件”和“本次确实加载这个文件”。

历史日志曾使用 `root=/dev/ram0`，所以还必须确认当前系统哪些目录是持久化的。若应用和配置实际写在内存根文件系统而非持久分区，重启丢失可能被误认为安装失败。历史参数只能提示检查方向，不能证明当前仍是 ramdisk 根文件系统。

不把此阶段变成无限期取证。取得一套可复现故障记录后，转入官方对照卡验证。

**第二步：单独准备官方对照卡。**

从官方渠道取得上述完整镜像，核对来源、大小及可用的发布校验信息，使用已验证容量的 SD 卡和可靠读卡器，完成写入及校验。原故障卡保留，用于恢复和对照。

用官方要求的供电和散热条件，先接串口、网络及必要显示，暂不把所有 USB 外设、执行器和业务服务一起带入测试。记录自动启动流程；确认不再依赖手工输入一串临时 U-Boot 命令，也没有沿用用于隔离故障的 DPU 禁用参数。

先记录 QSPI 版本并检查目标镜像要求。仅在确认不兼容或有明确必要时，按 KV260 官方更新/恢复流程处理启动固件；不要为了年份一致直接降级，也不要把自建工程的 BOOT.BIN 当作通用 QSPI 固件。

**第三步：只用官方模型、官方例程和配套输入验收 DPU。**

使用 Vitis AI 3.0 的官方 KV260 模型包及相应示例，例如官方文档给出的 `resnet50-zcu102_zcu104_kv260-r3.0.0.tar.gz`，先保留示例自身的预处理、类别表和运行方式。[官方快速开始](https://xilinx.github.io/Vitis-AI/3.0/html/docs/quickstart/mpsoc.html)。

不要首先运行当前自编译 B2304 模型。官方镜像的 DPU 不能仅凭镜像名称被假定为 B2304 或 fingerprint `0x101000056010405`；应查询实际配置，使用官方配套模型，随后再编译自己的模型。

官方单图推理正确且重复稳定后，再验证多张样本。官方基线仍失败时，优先检查启动身份、镜像完整性、SD/读卡器、供电、散热、板卡与外设条件；不要继续在自研模型上叠加修改。若换卡和供电等对照后仍可稳定复现，再考虑硬件诊断或厂商支持。

**第四步：原样重建参考平台，确认能扩展。**

锁定参考源码 tag/commit、DPU IP 来源、板卡文件、工具补丁、系统构建 recipe。先不加入自研 IP，完整构建一次，并用同类基准验证。预编译官方镜像能运行，只证明其预编译组合在板上可用，不证明自己的构建链已正确。

对当前 clockfix 工程可保留作比对，但不要默认它就是正式起点。需要解释复位差异，核查 DRC 分类和具体对象、时序约束完整性、时钟关系、地址和中断。342 个 warning 的数量本身不能直接判通过或失败，应逐类给出修复或有依据的保留说明。

重建产物不要求与官方预编译 bit 字节相同，因为构建元数据和实现条件可造成差异；要求的是来源明确、配置一致、交付内部自洽、功能通过。

**第五步：逐层加入项目功能，生成最终镜像。**

依次验证：DPU 基线 → 当前项目模型 → 相机与视觉应用 → 显示及音频 → motion/audio 自研逻辑与并发工作。具体顺序可依团队分工调整，但每次只引入可定位的一组变化。

项目最终需要 DPU 与自研逻辑共同存在。加载另一份整片 bit 通常会替换原有 PL 设计；除非平台明确采用并验证局部重配置，不可用“先加载 DPU，再加载 PWM”当作共存方案。

每次改动硬件都检查是否影响设备树、驱动、加载包和模型。最终从同一次受控发布构建导出硬件和 Linux 工件，重建必要软件，完成部署并在冷启动后验收。模型配置改变时按实际 DPU 重新编译，不沿用不明来源的 arch.json。

**第六步：固化可恢复的交付。**

形成带版本号的完整 SD 镜像、发布清单、校验文件、恢复说明及自检结果；在第二张卡上实际恢复一次，再验证启动和推理。只有这样，才具备“以后重新写卡就能回到已知正常状态”的能力。

**7．建议的最低验收标准**

以下次数是针对本项目的工程建议，不是 AMD 官方保证标准，可按交付强度增加。测试数量达到但存在未解释异常，仍不算通过。

| 项目 | 建议方法 | 通过条件 |
|---|---|---|
| 自动启动 | 至少 10 次冷启动、10 次正常重启；冷启动先正常关机再断电上电 | 每次无需临时手工干预，加载身份一致，相关服务正确启动 |
| DPU 重复性 | 固定同一模型和输入 tensor，关闭随机预处理，先单线程同步执行，连续至少 1000 次 | 对确定性的整数 DPU 输出，逐字节一致；若全图含浮点 CPU 算子，另设有依据容差并定位差异来源 |
| 基准正确性 | 官方例程配套样本，加少量已知类别样本 | 与对应模型预期结果一致；不能只看返回码和推理速度 |
| 自研模型正确性 | 固定 RGB/BGR、resize/crop、layout、量化缩放、类别表；比较量化参考与板端原始输出 | 达到模型预先定义的误差/精度门槛，CPU 浮点识别正确不替代量化执行验证 |
| 不同输入对照 | 猫图、其他自然图及构造输入，记录输入哈希和输出 | 响应可复现、与参考一致；不要求零输入必须判某一固定类别 |
| 持续运行 | 最小 DPU 持续至少 2 小时，再用相机/显示/音频/控制的最终组合持续至少 4 小时 | 无未解释的超时、错误输出、重启、文件系统错误或持续资源耗尽 |
| 并发 | 基础测试通过后增加线程和服务，独立核查 buffer 生命周期与同步 | 输出仍正确稳定，不发生输入被覆盖、未完成就读结果等竞态 |
| 持久化 | 正常重启后检查应用、配置、模型和服务 | 安装和配置保留，临时目录不承担关键状态 |
| 恢复复现 | 第二张卡按发布包重新写入并复验 | 不依赖原卡上的未记录补丁或文件 |

`wait=0`、输入读回相同和 DDR/VART 输出相同，只能说明任务返回及特定数据路径的一致性，不证明 DPU 算术正确。验证应同时覆盖身份、确定性和正确性。

**8．用对照结果决定下一步，避免反复重装**

| 对照结果 | 优先方向 |
|---|---|
| 官方系统＋官方模型仍失败 | 查镜像/卡/启动固件兼容与加载方式、供电散热及板级条件；做单变量替换后再判断硬件 |
| 官方组合通过，自己的模型失败 | 查模型目标、预处理、量化、类别映射和应用运行方式 |
