## 2. 分工一：A——硬件平台、FPGA 与实际运动

**适合负责人：你或主攻 Verilog/SystemVerilog 的同学。目标是交付一套可构建、可加载、DPU 与自研运动 IP 同时工作的硬件平台。**

### 现在先做

1. 整理现有 DPU 4.1 工程、测试包和版本清单，与 B 一起完成独立测试卡上的原应用/候选应用对照。核对实际加载身份、架构指纹、运行时选用的 XCLBIN、推理结果和恢复步骤。
2. 对已有报告中的 DRC、时序和 I/O 约束缺口按实际用到的接口处理。离线图片推理通过只验收这条链；相机、显示和新增 PWM 各自补齐验证。
3. 与 B 冻结运动接口行为；先完成最小 AXI-Lite 版本寄存器，让板端可读 IP_ID/VERSION，并证明同一次加载配置中的 DPU 仍能推理。
4. 并行开发 PWM、原子命令提交、范围与速率限制、序号/会话/有效期检查、停止锁存和明确恢复。先仿真及无动力测波形，再接入舵机。

### 全程负责

- 硬件平台、时钟/复位、地址映射、引脚/XDC、设备树和匹配部署包。
- `motion_guard_ip`、AXI 寄存器、PWM、命令监督、停止与恢复逻辑。
- 底层访问库与维护诊断入口；向 B 提供版本读取、提交、禁能、状态读取接口。
- 舵机独立供电、接线、实体停止通路、机构安装、脉宽/范围标定。
- 硬件仿真、综合实现、DRC、资源和时序报告；联合设计每次变更后保存真实结果。
- 汇总硬件发布版本和整机交付清单，协调三人发布冻结。

### 交付与验收

交付 RTL、仿真、约束、构建入口、硬件工件及哈希、驱动、接线/标定记录和实测波形。验收必须包含：**同一配置下 DPU 正确推理且自研寄存器可访问；正常命令产生正确 PWM；停止、到期、错误命令和恢复符合接口合同。**

运行与开发位置：KV260 PL 执行运动逻辑，PS 访问寄存器，Ubuntu 构建硬件与系统。

## 3. 分工二：B——视觉、板端身份与唯一运动服务

**适合负责人：此前希望人脸识别上板的室友，或负责视觉算法的同学。目标是交付“看见人、持续跟踪、识别身份并生成有效运动请求”的板端应用。**

### 现在先做

1. 和 A 完成 DPU 4.1 对照推理：固定图片、模型、预后处理、程序和运行时；正确性与性能分别记录。原测试图若无法找回，就在原应用与候选应用上重新建立同图基线。
2. 验证实际相机格式与稳定采集，建立唯一 `camera_service`，输出帧编号、采集时间和快照，供自己和 C 共用。
3. 选定人体检测模型，针对实际 DPU 完成适配、量化/编译及精度对照，再接跟踪与目标生命周期。新平台待验证期间可使用现有官方卡准备模型和相机链路。
4. 先用模拟运动接口验证目标计算、失跟和过期处理；A 的访问库可用后接真实接口，联合无动力验证，再做小范围视觉随动。

### 全程负责

- 相机采集、人体检测、预后处理、跟踪、目标进入/离开和防串人。
- 人脸检测、对齐、质量筛选、特征匹配、板端 SQLite 身份库、登记、删除和 UNKNOWN。
- 人体与人脸任务共享 DPU 的调度，记录帧龄和队列，防止身份任务持续挤占检测。
- 唯一 `motion_service`：核验 C 的对象建议、当前轨迹、会话与时效，计算目标并通过 A 的接口提交。
- 给 C 提供连续人脸片段、本轮快照、轨迹、身份和时间信息。
- 视觉/身份测试数据、模型来源、正确率、跟踪/身份错误与异常恢复记录。

### 交付与验收

交付板端视觉、身份、运动服务源码，模型与编译记录，配置、数据清单和测试日志。验收必须包含：**真实人体检测和连续跟踪；小范围视觉随动；冻帧/失跟时不续发旧目标；板端登记、重返识别、陌生人 UNKNOWN、删除和防串人。** Windows 人脸对照不能替代板端身份验收。

运行与开发位置：KV260 DPU 推理适配子图，PS 完成采集、预后处理、跟踪、身份库和运动服务，Ubuntu 适配模型及构建板端程序。

## 4. 分工三：C——USB 音频、说话人判断、问答与界面

**适合负责人：Python、模型调用和应用开发较强的同学。目标是交付“听到提问、结合画面回答、播放声音并显示状态”的交互链，以及视觉说话人建议。**

### 现在先做

1. 用 MCP01 在 KV260 上完成设备识别、录音、回放和重插测试，固定可用音频格式；与 B 测相机和 USB 音频并发。
2. Windows 建立常驻 ASR/VLM/TTS 服务，先用固定音频和图片跑通，记录每阶段耗时和模型版本。
3. 接板端按键半双工流程：录音→主机识别/问答/合成→板端校验、播放和字幕；加入取消、超时、断连和迟到结果丢弃。
4. 先跑离线 Light-ASD 基线，随后使用 B 的连续人脸片段和 MCP01 音频做声画对齐、有限窗口及实时说话人判断。

### 全程负责

- 板端 MCP01 录放音、格式转换、稳定设备选择和缓冲管理。
- Windows ASR、VLM、TTS 与 Light-ASD 模型服务。
- 对话会话/请求、听/想/说状态、字幕、对象绑定、取消、超时、失联提示和恢复。
- 将说话证据、上下文和置信度整理成候选轨迹建议交给 B；不确定时返回 UNKNOWN。
- 日常启动、自检、停止、日志采集入口与演示流程；调用 A/B 已交付的接口。
- 问答、说话人、端到端延迟、取消及断连测试，汇总演示视频和答辩材料。

### 交付与验收

交付板端交互/UI 程序、主机模型服务、启动配置、音视频样例、日志和演示流程。验收必须包含：**真实中文语音与看图问答；实际播放和字幕；取消后旧回答不再播出；主机断连有明确状态；多人说话时建议可追溯，不确定时拒绝自动选人。**

运行与开发位置：KV260 PS/Linux 负责 USB 录放音、交互与界面；Windows 首版运行 ASR/VLM/TTS/Light-ASD。

## 5. 三人交接与责任边界

| 交接 | 必须给出的内容 | 接收方确认 |
|---|---|---|
| A→B | 运动 ABI、地址/版本、驱动、提交/禁能/状态示例 | B 能读版本，在无动力状态下提交并核验结果 |
| A→C | 平台版本、自检项、运动状态与故障枚举 | C 显示真实状态，故障恢复走约定流程 |
| B→C | 帧/快照/连续脸片段、轨迹/身份、生命周期和时间域 | C 使用 B 的唯一相机源，输入能够回溯 |
| C→B | 会话、轨迹及生命周期、证据窗口、分数、质量、到期信息 | B 拒绝过期、换会话及目标已消失的建议 |
| B/C→A | 冻帧、进程退出、失联、乱序、迟到和停止场景 | A 提供对应的运动监督与禁能证据 |
| 三人→发布清单 | 自己模块的版本、启动方法、测试结果与限制 | A 汇总版本；C 编排启动演示；缺陷由原负责人修复 |

正式运动命令只由 B 的 `motion_service` 写入；A 的 PL 最终执行监督，C 提供对象建议。A 的诊断写入仅在正式服务停止的维护模式使用。

首次联调先统一协议版本、会话/请求、帧/轨迹编号、生命周期、时间域/单位、过期规则，以及运动的提交/拒绝/禁能/恢复语义。具体寄存器偏移、引脚和脉宽以实际工程与标定冻结。

全项目链路：**B 采集与检测/身份 → C 提供说话人或交互对象建议 → B 核验并提交运动请求 → A 监督并驱动单轴舵机。** 语音链由 C 贯通，问答画面和身份由 B 提供。

三人可立即并行工作。B/C 先用官方卡、固定样例和模拟接口推进；接入实际联合运动平台须等 A 的对应关卡通过。这里是工作顺序，不是假设已经到原三十天计划的某一天，也不重新承诺固定完成日期。

比赛/答辩材料按模块分摊：A 写平台与自研 FPGA；B 写视觉、身份、模型与数据；C 写视听交互、延迟和演示并汇总 PPT。三人各自保存真实的大模型协作过程、第三方来源、失败记录与复现步骤，共同确认最终设计报告。

当前范围为单轴、MCP01 USB 音频、视觉说话人、板端身份及主机问答；双 I2S 麦、声源定位和 `audio_doa_ip` 已删除。
