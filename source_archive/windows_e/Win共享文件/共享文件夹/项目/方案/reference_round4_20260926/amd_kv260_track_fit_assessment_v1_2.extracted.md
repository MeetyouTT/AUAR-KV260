## 1. 结论摘要（先看这一页）

### 1.1 赛道选择

三名大三本科生 → 初级组（报名资格为大一至大三在读本科生；混合队伍按最高学历归组，本队不涉及）。

KV260 的 K26 是 Zynq UltraScale+ MPSoC，落在初级组允许的器件范围内 → 合规。

建议提交材料中直接写明器件型号（如 XCK26 / Zynq UltraScale+ MPSoC），避免评委对组别适用性产生歧义。

### 1.2 三种赛道的门槛（为什么只剩 3.3 可选）

| 赛道 | 硬门槛 | 本队条件 | 结论 |
| --- | --- | --- | --- |
| 3.1 RTL/HLS 本地智能体 | 需 AMD Radeon 显卡 + ROCm 7.14.0+；模型须装入单张 32 GB 卡 | RTX 5090 Laptop（NVIDIA） | 不可行 |
| 3.2 具身智能 | 上位机必须是 AMD Ryzen AI PC，软件栈 ROCm 7.14.0+；借用机器仅 10 台且需 10/9 中期报告评审 | 无 AMD AI PC | 不可行 |
| 3.3 自主选题（初级组） | 器件落在 7 Series / Zynq-7000 / UltraScale(+)；工具 Vivado/Vitis 2026.1（推荐）或 2025.2；对"主机"无任何要求 | K26 合规；主机可用现有 Windows/GPU 机器 | 唯一可行 |

重要推论： 3.3 赛道不规定上位机。因此现有 Windows + GPU 主机在本赛道是合法资源（不违规、不扣分、不需要 ROCm），只需在报告中如实披露算力位置，并把"板卡自身"的性能与功耗数据单独统计。这一条显著降低了成本压力；代价是评委不会为该主机加分，只会盯着 KV260 上做了什么。

### 1.3 切合性的真实图景

本作品与 3.3 初级组的匹配度是"中高"，但当前方案的叙事重心放错了位置：它讲的是一个"AI 应用故事"，而 3.3 初级组要看的是一个"FPGA 作品故事"。改叙事比重构功能便宜得多。

判断依据（指南 3.3 原文口径）：

初级组考察侧重：「逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力」；

选题要求：「应用方向不限…鼓励综合考虑软硬件协同，充分发挥器件整体性能」；

考察重点：「功能是否正确、设计是否经过实测验证、性能与资源数据是否真实完整、他人能否复现」。

含义： 初级组要的不是"加速器多厉害"，而是"基本功扎不扎实、数据真不真、能不能复现"。本队已有的工程资产（10 态状态机、三层校验、173 组正反例、环境标签纪律、md+docx 成对文档、Gate 报告）恰好就是评分要的东西；反而"塞进一个大模型"在初级组并不值钱。

### 3.3 三条必须写进报告的事实

现有全部成果为 PC / SIMULATED，没有任何板端实测；转为板端后必须重新取证，不能沿用。

原方案产品定义为「固定式多模态桌面智能交互终端（无转轴）」；AMD 版计划新增了水平转轴 + 舵机 + 独立供电 + 机构件，属于范围新增（见第 7 节）。

原方案的"两组异构对比"可改造复用为 AMD 版对比：① 同源模型 CPU vs NPU → 改为 CPU vs DPU；② CPU 软件绘框 vs FPGA overlay 画面叠加 → 可保留/扩展为玩偶帧流合成对比。第 ② 项是把"玩偶演示"变成"FPGA 贡献证据"的关键。

## 4. 概念说明（概念词典）

每个概念的写法：白话解释 → 在本项目里的位置 → 为什么影响评分。

### 4.1 评分机制类

完整 FPGA 作品

白话：在 3.3 里，"作品"= 一套能被别人重建的硬件工程，而不只是"一台能演示的机器"。指南要求工程包内含完整源码、仿真/验证结果、综合与实现报告、上板工程与实测输出、可复现构建脚本。

位置：本队需要从零建立 KV260 工程与构建脚本。

影响：很多队伍把机器做出来但工程不可重建，于是"可复现"15 分拿不到、"完整性"20 分只拿一半。

可测量的证据

白话：能被复测的数字，附原始日志、报告分位数与测量条件；"能跑""很流畅""很快"都不算证据。

位置：现有 evidence_shots/、pytest、validator_cases_report.json 是雏形。

影响：直接对应 20 分与 15 分两档。

同源对比（baseline 与增益）

白话：基线是参照组；"同源"指同一模型、同一输入、同一阈值、同一预处理，只换执行后端。只有同源，差异才能归因于硬件。

位置：本队计划中的 detector_cpu.py 与 detector_dpu.py 就是同源双后端设计。

影响：20 分档的命门。若不是同源对比，这 20 分基本作废。指南明确要求"若只能获得不同模型的结果，写成'两个系统配置比较'"，不能写加速比。

证据的环境标签

白话：给每条结论标注它是在什么环境得到的，防止把仿真结果当实测结果。

位置：本队已有 PC / SIMULATED / BOARD_REQUIRED 约定，本文新增 ESTIMATE（估算）。

影响：这是"数据真实完整"的直接体现，属于低成本的加分项。

技能包 Skill

白话：把与 AI 协作沉淀的经验显式写出来供他人复用，指南分四类：提示词工作流、案例模板、校验脚本、踩坑清单。

位置：本队的 tools/ 脚本、技术记录踩坑章节、GPT 提示词包分别对应后三类的前两类。

影响：15 分档 + 通用 PYNQ Skill 额外加分；评价标准只有一条——"一支陌生队伍拿到该目录，能否直接用在自己的题目上"。

通用 PYNQ Skill（加分项）

白话：面向 PYNQ 框架、且不与本队题目绑定（换题目、换板卡仍可用）的技能包，指南单独加分；示例包括"通用的 Overlay 加载与校验流程""寄存器映射使用范式""从接口契约自动生成主机侧调用代码或测试骨架的脚本""黄金参考比对、性能与资源数据自动采集并生成报告的工具"。

位置：本队"契约驱动"的脚本（从合同生成资源表与 C 头文件、从用例集生成校验报告）天然属于这一类。

影响：属于可争取的额外加分，改造成本低于新建。

可复现性

白话：他人从零能够重建并跑出主要结果；这也是"别人能不能相信你"的唯一检验。

位置：本队的文档习惯很好，但作品的硬件复现门槛高（KV260 + 舵机机构 + 面板 + 主机 + 模型权重）。

影响：必须提供无硬件的 mock 运行路径（"没有板卡也能跑通软件链"），本队已有 MockBoard 与 Adapter，属现成优势。

### 4.2 器件与运行位置

PS / PL

白话：Zynq 类芯片内部有两半：PS 是 ARM 处理器（跑 Linux），PL 是可编程逻辑（"FPGA 部分"）。

位置：PS 跑采集 / 跟踪 / UI / 对话编排；PL 放 DPU 与自研 RTL。

SOM / 载板

白话：KV260 = K26 SOM（核心板，含 XCK26 + 4GB DDR4）+ 视觉载板（接口板）。常说的"KV260"指整套。

位置：整机集成、散热、接口、线束都要按实物核对。

DPU（Deep Learning Processing Unit）

白话：AMD 官方定义是"面向深度学习推理的软核加速器"，由 PL 中的 DSP / BlockRAM / UltraRAM / LUT / FF 构成，并拥有自己的指令集；模型由 Vitis AI 编译器编译成 .xmodel 后在 DPU 上执行。

位置：本队的人体检测加速。

影响：关键概念——DPU 是配置在 PL 里的一段电路，不是独立芯片、不是 Versal 的 AI Engine。因此它与自研转轴 IP 共用同一片 PL 资源，LUT / FF / BRAM / DSP / 时钟 / 带宽必须合并核算。

DPUCZDX8G 与配置后缀

白话：DPUCZDX8G 是 Vitis AI 面向 Zynq UltraScale+ 的 DPU 配置名（官方命名表：Zynq UltraScale+ MPSoC → DPUCZDX8G；Versal AI Core → DPUCVDX8G / H）；后缀如 B4096 / B3136 表示并行度等级，等级越高算力越强、占用 DSP / BRAM 越多（具体数值以 DPU IP 产品指南 PG338 为准）。

位置：需选定一个配置档，并写入版本锁文件。

模型 fingerprint

白话：编译模型时会绑定目标 DPU 架构的"指纹"；改了 DPU 配置就必须重编译模型，不能沿用旧 .xmodel。

影响：这是"DPU 与自研 IP 共存"调试中最容易踩的坑之一，也是可写入技能包的踩坑清单。

位流 / Overlay

白话：位流是 PL 的配置数据；Overlay 是 PYNQ 语境下"PL 电路 + 对应软件接口"的封装包。在 KV260 上通常还需要配套的设备树 overlay 与运行包。

位置：本队要产出可重建的工程与加载脚本。

局部重配置（DFX）

白话：只替换 PL 的一部分电路，其余继续运行。

影响：本队不得用"先加载 DPU 位流、再加载转轴位流"来演示共存——那是全片覆盖，等于替换了整个设计。指南要求作品功能同时成立，交替加载不算共存（本队计划文档已明确禁止）。

### 4.3 总线与接口

AXI4-Lite

白话：ARM 访问 PL 里寄存器的总线协议；等价于"CPU 读写某个地址就能配置硬件"。

位置：自研 axi_motion_regs。这直接对应初级组要考的"接口协议"能力。

AXI4-Stream

白话：传数据流（像素、音频）的高速通道，没有地址概念。

位置：若做图像预处理或玩偶帧流搬运会用到。

寄存器映射 register_map

白话：一张"哪个地址偏移是什么含义"的表。

位置：本队已有完整草案（id_version / control / target_angle / command_seq / heartbeat / status / fault_latch / recovery_request / commanded_angle / applied_seq / safety_epoch / 时间戳高低位）。这是极好的 Skill 素材。

影子寄存器 + 原子提交

白话：多个字段先写入"草稿区"，最后写一个 command_seq 才整体生效，避免读到半成品。

位置：本队已设计。

UIO / MMIO

白话：UIO 是 Linux 的"用户态直接访问硬件"机制；MMIO 是把硬件寄存器映射到内存地址。

位置：这是板端软件能调用自研 RTL 的必要通路，必须在平台阶段打通。

### 4.4 时序与资源（初级组明确考察项）

时序约束（XDC）

白话：告诉工具"时钟频率是多少、引脚在哪里、哪些路径可以放松"。约束写错，后面所有结果都不可信。

时序收敛 / WNS / TNS

白话：收敛 = 所有信号都能按时到达。WNS（最差负裕量）为负表示未收敛。综合与实现报告里必须给出。

影响：20 分档的直接证据。

LUT / FF / BRAM / DSP

白话：PL 的四种"原料"：查找表、触发器、片上 RAM、乘法单元。报告要列占用率。

影响：指南 3.3.5.1 点名要求。

跨时钟域（CDC）

白话：两个不同频率时钟之间传信号必须加同步结构，否则偶发错误。

位置：本队"读时间戳低位时锁存高位"的设计就属于这类细节——写进报告就是基本功的证据。

### 4.5 控制与安全（本队差异化强项，建议重点读）

确定性 determinism

白话：同样输入 → 同样时间 → 同样输出。Linux 做不到（会被调度打断），PL 可以。

位置/影响：这是"为什么这件事必须由 FPGA 做"的核心论证，直接支撑 30 分的技术差异化与 20 分的优化效果。

抖动 jitter 与 P99

白话：抖动 = 实际周期与理想周期的偏差；P99 = 把 100 次里的最差 1 次拿出来看。不能只用平均值。

位置：软件定时 GPIO 与 PL PWM 的固有抖动通常相差几个数量级。

影响：这是"性能与资源优化效果"最直观、最易被评委接受的证据。

PWM（脉宽调制）

白话：用方波占空比表达舵机角度的信号，常见 50 Hz、脉宽 1—2 ms。

注意：50 Hz / 1—2 ms / 180° 不是所有舵机的通用参数，必须按实物数据手册标定。

看门狗 watchdog

白话：软件必须定期"喂狗"；一旦不喂（进程死了、卡住了、被调度饿死），硬件自动进安全态。

位置：本队设计阈值 300 ms（初值，需实测冻结）。

租约 lease

白话：命令的"有效期"。过期命令作废，防止用旧画面驱动转轴。

位置：本队设计 200 ms（起点值，提交时租约不得超过该帧的剩余有效期）。

故障锁存 fault latch

白话：一旦出故障就把标志"焊死"，必须人工确认才能恢复，防止自动重启后失控。

安全代次 safety_epoch

白话：每次故障后"代次 +1"，旧代次的命令一律被拒绝。

说明：这是成熟的工业思路，写进报告能显著提升"工程水平"观感。

限幅 / 限速（slew limiter）与死区（deadzone）

白话：限幅限制单步指令变化量，防突跳；死区让目标在画面中心附近时不动作，防左右抖动。

One Euro Filter

白话：自适应低通滤波——目标慢动时强滤波（稳），快动时弱滤波（跟得上），比固定 EMA 更适合"静止时稳、移动时跟得上"的转向任务。

必须澄清的一个误区

"停止 PWM"不等于"舵机断力或立即停止"。如需切断扭矩，必须有经验证的硬件使能或电源门，不能只靠软件假设。急停要分别测量"输入到控制信号安全"与"机械真正停下"两个时间，二者不可等同。

### 4.6 视觉与显示

检测 / 跟踪 / 身份（三个不同层次）

白话：检测 = 找出画面里有人；跟踪 = 连续帧里认出"还是同一个人"（短时，track_id）；身份 = 跨离开返回认出"这是小林"（持久，person_id）。

位置/影响：本队已严格区分三者；track_id 与 person_id 不等价，混用会导致"把姓名错绑到下一个人"，属于必须写清的实现细节。

letterbox

白话：缩放图像时保持长宽比并在空白处补边；算坐标时必须"还原"回原图坐标。

RGB565 / R5G6B5

白话：每像素 16 位的颜色格式（红 5 位、绿 6 位、蓝 5 位），比 RGB888 省一半内存。

位置：本队玩偶帧流即采用大端 R5G6B5。

双缓冲

白话：前后两块画布交替使用，一块给显示、一块给绘制，避免"画一半被看到"。

位置：本队实测双缓冲占用 0.894 MB —— 属极小开销，可作为"设计克制"的证据。

取景 / LOD

白话：取景 = 素材裁切范围（本队锁定"腰部以上"p=0.58）；LOD = 分辨率档位。

位置：avatar_lod.py 与 ui_spec 合同，且取景在入库阶段完成（保证"素材即产物"的可复现性）。

### 4.7 语音

KWS / VAD / ASR / TTS / AEC / 全双工

| 概念 | 白话 | 备注 |
| --- | --- | --- |
| KWS | 关键词唤醒（如"雾镜暂停"），轻量，可放板卡 CPU | 本队已有 3.3M 中文模型 |
| VAD | 判断"人有没有在说话" | 后续阶段 |
| ASR / TTS | 语音转文字 / 文字转语音 | 本队规划 sherpa-onnx 路线 |
| AEC | 回声消除，避免扬声器声音被自己的麦克风听到 | 本队 V2.0 已正确排除，第一版采用"按键说话"是明智取舍 |
| 全双工 | 边说边听、可打断 | USB 声卡"支持同录同放"只是硬件能力，不等于实现了全双工 |

### 4.8 AI 工程

量化（INT8）与校准集

白话：把模型权重从浮点压成 8 位整数，速度快、体积小，但会掉精度；校准集是用于"标定量化范围"的一小批有代表性图像。

影响：指南要求把量化带来的精度损失单独报告，不能混进"硬件加速"的功劳里。

golden 参考

白话：一份"标准答案"（典型输入 + 期望输出），每次改动后自动比对，防止改坏了没发现。

哈希（SHA256）

白话：文件指纹，用来证明"提交的模型与报告里说的是同一个"。

### 5.1 创新性与应用价值（30 分）

评委在看什么： 解决什么真实问题、前人做过什么、有没有完整可展示的场景。

建议论点： 往届与同类作品普遍是"软件闭环 + 执行器直连"；本作品的不同在于把"安全性"和"确定性"做成硬件责任——停止、超时、指令时效、故障锁存全部由 PL 承担，并用故障注入实验证明"PS 进程被杀 / 视频停帧 / 网络断开"时设备仍进入可预测的安全状态；同时用同源对比量化"哪些事必须由 PL 做"。

必须补的三份对比（按优先级）：

| # | 对比 | "同源"的口径 | 产出证据 |

### 9.2 本队材料的日期溯源

思路：遍历项目全部 md / txt 与 docx 正文及表格，检索 10月9日 / 10/9 / 截止 / 报名截止 / 作品提交 / 官方公布 / 赛程。

# 依赖：python-docx

from docx import Document

import os, re

ROOT = r"…\FPGA语音助手开发"

PAT = re.compile(r"10\s*月\s*9\s*日|10/9|截止日|报名截止|作品提交|官方公布|赛程")

for dirpath, _dirs, files in os.walk(ROOT):

    for name in files:

        path = os.path.join(dirpath, name)

        if name.endswith((".md", ".txt")):

            for i, line in enumerate(open(path, encoding="utf-8", errors="ignore"), 1):

                if PAT.search(line):

                    print(os.path.relpath(path, ROOT), i, line.strip()[:120])

        elif name.endswith(".docx") and not name.startswith("~$"):

            doc = Document(path)

            for para in doc.paragraphs:

                if PAT.search(para.text):

                    print(os.path.relpath(path, ROOT), "P", para.text.strip()[:120])

            for table in doc.tables:

                for row in table.rows:

                    joined = " | ".join(c.text.strip() for c in row.cells)

                    if PAT.search(joined):

                        print(os.path.relpath(path, ROOT), "T", joined[:120])

核验结果：10/9 的全部命中均为内部里程碑 GD（板端视觉闭环）；真正截止日相关表述为"竞赛截止/提交在 10 月中下旬或更晚"（属本队推断）；宣讲记录中"作品提交截止时间"为待确认。

### 10.1 头号技术风险：KV260 的 DPU 工具链断档（开工前三天必须处理）

AMD 官方资料确认： 官方 kria-vitis-platforms v1.2 已升级到 Vivado/Vitis 2026.1，但官方明确：KV260 的 smartcam、aibox-reid、defect-detect、nlp-smartvision、benchmark 等 DPU overlays 在 2026.1 中被移除，原因是 DPU IP 不支持该 2026.1 工具链；若要构建这些 KV260 DPU overlays，必须使用以前的 release tag。

含义： "指南推荐 Vivado/Vitis 2026.1（或 2025.2）"与"KV260 上有官方可重建的 DPU 参考设计"不是同一件事。指南允许使用其他版本，只要在报告中说明理由并保证脚本可复现——因此采用历史 AMD 验证过的 DPU 栈是合理且可答辩的选择，而不是"版本落后错误"。

根据资料推断（建议直接采纳）： D1—D3 做一次硬性 Go / No-Go：

优先尝试团队已有、且能证明可重新构建的完整 DPU 栈；

若无，则首选 Vivado/Vitis/PetaLinux 2022.2 + Vitis AI 3.0 + DPUCZDX8G 4.1（KV260 官方应用历史参考更完整的是 2022.1 + Vitis AI 2.5）；

版本一旦 D3 锁定，本轮不得为了"更新"再更换主工具链。

证据等级更正（V1.2）： 本节"KV260 的 DPU overlays 在 2026.1 中被移除、原因是 DPU IP 不支持该工具链"最初被标为"AMD 官方资料确认"，该结论来自《deep-research-report (1).md》的引述。V1.2 做了一手核验后调整如下：

### 10.5 可直接复用的接口、寄存器与状态机定义

根据资料推断 + AMD 官方资料确认： 该报告已给出成体系的设计定义，建议作为 register_map.md 与 common/schemas/ 的初稿（须先按第 11 节第 4、5 条与本队现有合同对齐，再冻结）。

（1）运动控制状态机（6 态）

DISARMED / NEEDS_REFERENCE / ARMED / TRACKING / AT_LIMIT / FAULT（2026-09-26 按 D5 W17-11 统一；原 `RESET_SAFE → NEEDS_REFERENCE → DISARMED → ARMED_HOLD → ACTIVE → FAULT_LATCHED`，其中 `RESET_SAFE` 降为复位行为、`FAULT_LATCHED` 并入 `FAULT`）

## 12. 创新性与 FPGA 必要性论证（团队必读）

本节回答两个必须在答辩中站住的问题："这个作品的创新点是什么" 与 "为什么必须用 FPGA，而不是树莓派加 STM32"。

结论口径已按团队确认：亮点主线选定方案 D —— PL 做麦克风阵列 DOA，实现视听双模随动（谁说话就看向谁）。

### 12.1 先承认一个前提：这个题材的概念本身不新

"会看人、会转头、会说话的桌面玩偶"作为概念不新，同类与往届作品不少，因此在"创新性与应用价值"（30 分）这一档不能靠题材本身得分。同时必须主动放弃三个无效论点：

| 无效论点 | 为什么站不住 |
| --- | --- |
| "我们做了安全控制" | 安全逻辑用一颗 MCU（甚至纯软件加看门狗）就能做，而且 MCU 做舵机 PWM 的抖动通常比 Linux 软件更小、成本更低 |
| "我们用了 AMD DPU" | DPU 是 AMD 的 IP，团队做的是集成。集成能力值得写进报告，但不是"创新" |
| "我们本地部署了 AI" | 树莓派加一个 NPU 棒也能本地部署 AI |

### 12.2 亮点只能来自三个来源

| 来源 | 内容 | 归属 |
| --- | --- | --- |
| 来源一：同一片芯片内完成"像素级并行 + CNN 加速 + 确定性输出" | MCU 结构上做不到（没有像素级并行与 CNN 加速）；树莓派的 CPU/GPU 给不出确定性控制 | 创新性（30 分） |
| 来源二：交互范式差异，而不是性能差异 | 固定摄像头方案永远背对用户；纯语音方案没有"看向你"这一层；视听双模随动（谁说话就看谁）属范式差异 | 创新性（30 分） |
| 来源三：把 AI 输出的不确定性转换成受约束物理动作的完整链 | 帧龄 / 租约 / 会话 / 安全代次 / 看门狗 / 故障锁存 + 故障注入矩阵 | 完整性（20 分）；不可当创新点讲 |

### 12.3 为什么必须用 FPGA：评委若问"为什么不直接用树莓派加 STM32"

用"我们做了安全控制"回答会输。能答过去的只有三类用软件做不到或做不好、且可测量的事实：

| 论据 | 为什么软件吃亏 | 必须拿出的数据 |
| --- | --- | --- |
| 像素级并行吞吐 | CPU 做色彩转换、缩放、ROI、直方图，要么占满核掉帧，要么排队引入延迟 | CPU vs PL 同源：吞吐、单帧延迟、CPU 占用、PL 资源与 WNS |
| 确定性抖动 | Linux 调度与 Python GC 造成毫秒级抖动与长尾 | 软件定时 vs PL：不少于 1000 周期的 P50/P95/P99/max |
| 同片数据通路 | 相机到前处理到推理到显示到执行器跨设备要多拷贝、多排队 | 端到端延迟分布、DDR 带宽、帧龄分布 |

关键判断：三条里只有第一条是结构上别人替代不了的。 因此 FPGA 必要性的最强落点是"PL 承担真实的感知负载（图像与音频流水线加推理）"，而不是"PL 承担 PWM"。

这条判断同时暴露了原方案的结构性问题：把有吞吐压力的活（视觉推理、大模型）放在 PS 与主机，PL 只剩 DPU 集成与 PWM —— 这正是"没亮点"与"为什么用 FPGA 难答"的共同病根。方案 D 正是针对这一点选的。

| 编号 | 亮点 | 为什么算亮点 | 前置条件 | 主要风险 | 工时 |
| --- | --- | --- | --- | --- | --- |
| A | PL 图像前处理流水线 + DPU 同片（色彩转换/缩放/ROI/直方图，AXI4-Stream 串到 DPU） | 本科作品里少见的"像素级并行 + CNN 加速"完整链；能直接回答"为什么不用树莓派" | 板卡；HLS/RTL 工时 | 与 DPU 固定输入尺寸的配合 | 30—50 h |
| B | 玩偶帧流在 PL 实时合成/缩放直出（466×480 RGB565 → 缩放 + 贴合 + 双缓冲 → 显示） | 交互输出端也硬件化，与输入端对称；属实时图形，不依赖"安全"叙事 | 显示路径必须先定 | 显示路径未定可能白做 | 30—50 h |
| C | AI 到物理动作的确定性链 + 故障注入矩阵（帧龄/租约/会话/安全代次/看门狗/停止） | 不算技术前沿亮点，但是 20 分档最强证据，也是"为什么不能只有软件"的实证 | 舵机 + 示波器或逻辑分析仪 | 机械与供电 | 40—60 h |
| D（已选定） | PL 做麦克风阵列 DOA → 视听双模随动（谁说话就看向谁） | 真正的 DSP 硬件设计；体验直观、评委一眼看懂；且天然满足"PL 承担真实感知负载"（多路音频必须进 PL 才能做） | 必须是 I2S/PDM 多麦阵列（见 12.6），需采购 | 采购周期 + 全新开发 | 70—110 h（最小可行版） |

### 12.5 选定方案 D 的理由与"最小可行版"定义

选定理由（三条）：

它把感知负载真正搬进了 PL —— 这正是 12.3 得出的"FPGA 必要性最强落点"；

它是范式差异型亮点（看向说话的人），而不是"参数更好"，评委容易理解与记住；

它与方案 C 共用同一套 PL 基础设施（AXI4-Lite 寄存器、时钟、复位、中断、状态回读），增量成本低于从零做第二套设计。

最小可行版（本轮目标，务必按此收敛）：

| 项 | 最小可行版 | 本轮不做 |
| --- | --- | --- |
| 麦克风数量 | 2 只（左右），必要时 3 只 | 4—8 只环形阵列 |
| 输出 | 左 / 中 / 右 三档方位判断 + 置信度 | 连续方位角与精细 DOA |
| 算法 | 双麦相位差或延时差 + 门限 + 短时平滑 | GCC-PHAT 精化、波束成形、声源分离、混响抑制 |
| 与视觉融合 | 有语音活动且方位可信时朝向说话人；否则回到视觉跟随 | 多人同时说话、说话人身份绑定 |
| 降噪与回声 | 不做（沿用"按键说话"） | AEC、波束成形降噪 |

为什么必须收敛到"三分档"： 答辩需要的是"设备能转向正在说话的人"这个可演示行为，以及"方位判断准确率 / 处理延迟"这一组可测量数据；连续方位角对本轮分数没有额外贡献，却会成倍增加标定与调试工时。

### 12.6 方案 D 的硬件约束与采购要求（最容易踩坑的一条）

硬约束：多路音频必须进入 PL，否则方案 D 不成立。

| 选择 | 数据能否进 PL | 结论 |
| --- | --- | --- |
| USB 麦克风阵列（UAC 多通道） | 不能：数据由 KV260 PS 侧 ALSA 直接取走，PL 看不到 | 不可用于方案 D（可用于普通录音与语音识别） |
| I2S 数字麦阵列（如 INMP441 等 MEMS） | 能：经 Pmod/PL 引脚进 PL，由自研 I2S 接收逻辑取数 | 推荐；标准 BCLK / LRCLK / DIN 三线 |
| PDM 数字麦 | 能进 PL，但需自研 CIC 与抽取滤波 | 备选；PL 侧工作量更大 |

配套必须核对的技术项：

音频主时钟精度：I2S 需要精确的位时钟与帧时钟（如 256×fs）。不得把"用 PL 的 MMCM/PLL 从板载时钟分出"当作可行方案——100 MHz 对该时钟家族无整数比，MMCM/PLL 的 VCO 频段与分频比上限使 3.072 MHz／48 kHz 无法由整数比分频得到；应采用小数分频得到 3.0720 MHz／48 kHz（平均分频比 32.552083…，不是 1:1 的 32.5；推荐 192 周期块＝86×32＋106×33），整数分频仅作降级路径，并实测 BCLK/WS 分频比（依据 D2 第 5.2 节与 D5 W17-07）；

多麦同步：同一 I2S 总线上多麦共享 BCLK/LRCLK，天然同步（这是选 I2S 而不是两路独立采集的关键原因）；

供电：KV260 的 Pmod 供电只有 3.3 V / 100 mA（见 10.3）。MEMS 麦静态电流通常在毫安级，理论上可行，但必须按实际选型核对总电流，且不得从 Pmod 给其他大功率负载供电；

电平与接口：确认所选麦克风的 IO 电压与 PL bank 电压一致，必要时加电平适配或缓冲；

物理布局：两只麦的间距直接决定可分辨的最小角度，须与机身尺寸一起设计；麦克风孔位不能正对扬声器，否则串音。

待采购清单（建议 D1 前确认）： I2S MEMS 麦 ×2—3、杜邦线或排线、必要的电平适配或缓冲、测试用声源（可先用手机播放已知音频）。

### 12.7 结论：PL 与 CPU／主机的重新分工

| 承担者 | 本轮承担内容 | 对应分数档 |
| --- | --- | --- |
| KV260 PL | ① AMD DPU 推理（集成 + 配置 + 与自研 IP 共存于同一位流）；② 自研 motion_guard_ip（PWM、限幅、租约、看门狗、停止、故障锁存、遥测）；③ 自研 I2S 音频采集 + 双麦方位判断（方案 D） | 性能与资源优化 20、功能完整性 20、创新性 30 |
| KV260 PS | 相机采集、后处理、跟踪、目标选择、视觉控制、运动驱动、UI 与录放音客户端、对话编排 | 功能完整性 20 |
| Windows 主机 | VLM、ASR/TTS（若板端实测不达标）、身份服务 | 视情况；须如实披露算力位置 |

与 V1.1 的差别： PL 从"DPU 集成 + PWM"变为"DPU + 自研安全控制 + 自研音频感知"，即 PL 开始承担真实的感知负载。这既是"为什么用 FPGA"这个问题的答案，也是本轮创新点的落点。

### 12.8 人力影响（必须写进 D1 分工）

方案 D 与方案 A、方案 C 都要占 FPGA 负责人的工时。35 天口径下可以做到"C 保底 + D 亮点"；但若要再加 A 或 B，就必须把 HLS 或前处理交给另一位成员。否则会出现"三个亮点都开工、一个都没做完"。这是本轮最需要在 D1 拍板的分工约束。

### 12.9 答辩问答脚本（现场三句话）

问"创新点是什么" → 我们把感知前处理与安全执行放进了同一片 PL：DPU 做人体检测，自研 I2S 采集与方位判断做声源定位，两者与自研安全控制逻辑共存于同一位流；设备因此能"谁说话就看向谁"，这是固定摄像头方案或纯语音方案做不到的交互范式。

问"为什么必须用 FPGA" → 因为这条链上只有 PL 能同时给出三件事：采样与像素级并行处理、确定的控制抖动、以及毫秒级可控的停止响应。我们用同源对比量化了这三项（CPU 与 PL 的吞吐差与 CPU 占用、软件定时与 PL 的 P99 抖动、端到端延迟分布）。

问"安全控制是不是 MCU 也能做" → 先承认：单独看安全控制确实 MCU 可以做。我们的差异在于安全与感知在同一片芯片内闭环：AI 的感知结果与声源方向直接进入硬件约束链，端到端延迟与时序可测，且不经过操作系统调度。
