# 演示剧本（情绪调度与节奏）技术记录

> 日期：2026-10-05 ｜ 项目：AURA（`D:\share、\项目开发\FPGA-amd自主命题赛道\aura`）
> 关联：`docs/跨素材池轮换_播放层改造_技术记录.md`（播放层改造本体，含池轮换数值依据）

## 一、目标与背景

素材池轮换（`StageCore`）此前只有**数值验证**（`tools/verify_pool_rotation.py` 的 P1~P5），
缺"**一次完整演出**"层面的验收：**长短句变速**对不对、**情绪换档**换不换素材、
**换素材的观感**是否自然。

→ 写一个**剧本（cue sheet）** ＋ 一个**无窗口回放器**，把上面三件事编进一条时间轴，
毫秒级跑完并打印"素材切换点"作为**可复核的证据**（不靠肉眼、不靠记忆）。

## 三、剧本设计（对应两项验收重点）

**① 时间长短变化**（测 `avatar_timing.speed_for_state` 按句长变速 + 阶段机 enter/loop/blend/exit）
11 字短句 / 29 字中句 / 92 字长句 / 2 字极短句，外加"倾听→思考"的**刻意停顿**（3 s）与
"说到一半被打断"（8 s 处 `cancel`）。

**② 情绪调度**（`emotion` → `fsm.speaking_state_name`，**单一来源**，与 TTS 语气同档）

| emotion | 档位 | 素材 | 池大小 |
|---|---|---|---|
| `neutral` / `friendly`（**注意 friendly 不在高涨表**） | `SPEAKING_NEUTRAL` | `talking_neutral` | **3** |
| `happy` / `excited` / … | `SPEAKING` | `talking_normal` | **2** |
| `sad` / `low` / … | `SPEAKING_LOW` | `talking_low` | 1 |

**⑨ 之前 8 拍状态清一色是单素材（IDLE/PRESENT/AWAKE/THINKING/ACK_NOD）**，作为"零轮换对照组"，
用来证明**轮换只发生在配了池的状态**里。

## 四、关键修复与踩坑（**最重要的一节**）

1. **`frame_at` 签名是 `(state, now)`，不是 `(now)`** —— 首跑 660 次采样全部
   `TypeError: missing 1 required positional argument: 'now'`，而错误被 `_sample` 的
   try 兜住 → 画面全是"无素材"、切换点为空，**很容易误判成"素材缺失"**。

2. **FSM 合法转换的三条硬约束（实测，非文档）** —— 剧本第一版把 5 轮回复排成
   "reply → stop → reply → stop"，结果**只有第 1 轮进了播报**，后面全被 FSM 拒绝：
   - `dialogue.response_received` **只在 `THINKING` 下合法**；
   - `audio.playback_stopped` 会把状态**打回 `IDLE`**（不是回到 `PRESENT`）；
   - `audio.vad_end` 在 **`IDLE` 下被拒**（`IDLE → THINKING` 非法）→ 光补 `vad_end` 无效；
   - 经验证可用的**重开一轮链**：
     `scene.person_enter`(IDLE→PRESENT) → `audio.kws_detected`(PRESENT→AWAKE)
     → `audio.vad_end`(AWAKE→THINKING) → `dialogue.response_received`(→SPEAKING_*)
   - 代价：每轮重播一次 AWAKE 惊讶 burst（剧本只给它 0.2 s 就切走）。
     ⇒ 已封装成 `_ask(t)`，并在 docstring 里写明约束，避免下次再踩。

3. **报告口径要限定"池内换素材"** —— 首版结论把**跨状态**切换也算进"是否从 enter 起播"，
   而 `AWAKE` 的 `stage` 是上一状态遗留的 `loop`（burst 无阶段语义）→ 结论被误报成"否！"。
   修法：只统计 `len(core.pool(state)) > 1` 的切换点。

4. **本机取输出的可靠姿势** —— `run_commands` 的终端回显经常"命令完成无法观测"；
   Python 输出重定向到文件后**有缓冲**（要等进程结束才可见）。
   ⇒ 固定套路：`... > "%TEMP%\xxx.txt" 2>&1`，再用 `read_files` 读该文件（可能要读 2~3 次）。
   长剧集跑完约 1 分钟（660 次采样 × 每次真算 `_apply_offsets` 的 resize+rotate）。

## 五、验证结果（2026-10-05 实跑）

```
=== ★ 素材切换点（跨素材池轮换的直接证据）===
  状态 SPEAKING_NEUTRAL   池 = ['talking_neutral', 'talking_neutral_b', 'talking_neutral_c']
      15.50s  idle_thinking      → talking_neutral     (idx=0, stage=enter)
      18.00s  talking_neutral    → talking_neutral_b   (idx=0, stage=enter)   +2.50s
      25.20s  talking_neutral_b  → talking_neutral_c   (idx=0, stage=enter)   +7.20s
      32.30s  talking_neutral_c  → talking_neutral     (idx=0, stage=enter)   +7.10s
  状态 SPEAKING           池 = ['talking_normal', 'talking_normal_b']
      51.00s  idle_thinking      → talking_normal      (idx=0, stage=enter)
      58.20s  talking_normal     → talking_normal_b    (idx=0, stage=enter)   +7.20s
```

- **6 长句（23 s）池 3 个全部用到**，稳态间隔 **7.1~7.2 s**（≈`POOL_SWITCH_SECONDS 6.0`
  ＋ 当前素材 `exit` 收尾时间），每次均 `idx=0 / stage=enter` ⇒ **换素材=从帧 0 起播** 成立。
- **7 高涨（8 s，被 ⑩ 打断）池 2 个用到 1 次切换**。
- **零误伤**：`IDLE / PRESENT / AWAKE / THINKING / ACK_NOD` 全程恒定单素材；
  `SPEAKING_LOW` → `talking_low`（素材**存在**，未走回退）。
- 状态段时长与剧本设定**逐拍吻合**（如 `SPEAKING_NEUTRAL 15.50→38.50 = 23.00 s`）。

## 六、真窗口演出（`--window`）

`--realtime` 只在终端按真实时间打印，**不弹窗口**；要"看着它演"用 `--window`：

- 左侧 320×360 舞台 + 右侧 HUD（asset / 池大小 / frame / phase / speed / stage / 虚时）+ 逐条日志；
  渲染口径（`meta["image"]` 等比缩放到 320×360、`ImageTk`）与 `demo_stage.StageApp._tick`
  **完全一致**，因此窗口里看到的就是生产播放层实际会画的东西。
- 与 `ScriptRunner` **共用同一套 `_fire`**（只换时钟：`time.monotonic()` 真实时间；`tick_ms=33`
  只是重排间隔，**实测有效帧率 ≈ 12 fps**，见 §6.1），**没有复制任何剧本逻辑**。
- `F5` 或「重播」按钮重演全剧（`fsm.reset()` + `reset_playback()`，与剧本 ⑪ 同口径；
  **演出结束后同样可重播**，靠 `scheduled` 标志补链，见 §6.2）。

**为什么不直接看 `demo_stage.py`**：那条路的 LLM 是 Mock —— `board/runtime/dialogue_client/mock_adapter.py:37-38`
固定 `emotion="friendly"`、`reply_text=text`（原样回显）⇒ 窗口里**永远演不到**
`happy/excited`（`SPEAKING` 池 2）与 `sad/low`（`SPEAKING_LOW`）两档。
`--window` 直接按剧本注入 emotion，**三档齐全**。

**两条互补的验收路径**：

| 路径 | 能看到 | 看不到 |
|---|---|---|
| `demo_script.py --window` | 三档情绪、半途打断、reset 零残留、池轮换全貌（自动 66 s） | 手工交互、TTS 发声 |
| `demo_stage.py`（手工台） | 真 TTS 发声、麦克风链路、任意时刻手动发事件 | 高涨 / 低落档（Mock 情绪恒为 friendly） |

**手工台看长句轮换的操作**（Mock 原样回显输入）：`F1` 来人 → `F2` 唤醒 → `F3` 说完 →
把 92 字长句粘进输入框 → `F10` ⇒ 落到 `SPEAKING_NEUTRAL`（池 3）⇒ 约 6 s 一次换素材；
对照 `F12`（短句 11 字 / 3.4 s）看不出轮换。

**启动方式**（GUI 会阻塞，必须后台拉起；`.venv` 的 `python.exe` 是转发 stub，故每次启动是 2 个进程）：

```
cd /d "<项目根>"
start "AURA-剧本演出" ".venv\Scripts\python.exe" -s tools\demo_script.py --window
```

⚠ **踩坑**：用 `start` 从 Cline 的 `run_commands` 里拉起的窗口，会在**下一条命令**（旧终端被关闭）
时被**连带杀掉** —— 表现为"窗口不知怎么就没了"。要留给用户看的窗口必须**脱离终端进程树**
（WMI `Win32_Process.Create`），详见 §6.1 末段。

### 6.1 首帧 `NameError: name 'Image' is not defined` —— 窗口打开即"冻结"（复盘）

**症状**：`--window` 窗口能弹出、标题正常，但**画面永远停在空白画布**，右侧日志一条都不出；
重定向的日志里只有**一次** traceback：

```
File "...\tools\demo_script.py", line 553, in tick
    img.thumbnail((stage_w, stage_h), Image.LANCZOS)
NameError: name 'Image' is not defined. Did you mean: 'ImageTk'?
```

**根因**：`run_window` 里只写了 `from PIL import ImageTk`，而第 553 行用了 `Image.LANCZOS`
（重采样常量）。异常抛在 `tick` 内部 ⇒ 函数末尾的 `root.after(tick_ms, tick)`
**永远不会执行** ⇒ `tick` 链**断在第一帧**，窗口只是"开着"，什么都没画、什么也没记。
日志只有 770 B 是**假象**：`stderr` 重定向到文件是**块缓冲**，一次 traceback 不足 8 KB 不刷新。

**修复**：`from PIL import Image, ImageTk`（一行）。

**验证方法（可复用的无窗口冒烟）**：`%TEMP%\zz_window_smoke.py`
—— 真开 Tk，统计 `ImageTk.PhotoImage` 调用次数，用 `report_callback_exception` 捕获回调异常，
N 毫秒后自动 `destroy`：

```
"<PY>" -s "%TEMP%\zz_window_smoke.py" 6000
→ SMOKE: photos=71 wall=6.05s fps=11.7 cb_errors=0 script_errors=0
→ VERDICT: OK
```

两个关键读数：`cb_errors=0`（回调不再抛异常）；`photos` 随时长**线性增长**
（3 s → 36 帧、6 s → 71 帧）⇒ 证明 `tick` 是**连续**在跑，而不是断在第一帧装没事。

**顺带量到的事实**：逐帧 `img.copy() + thumbnail() + PhotoImage`（PIL→Tk 位图转换）约 **50 ms**
开销 ⇒ **有效帧率 ≈ 12 fps**（`demo_stage.py` 同口径、同开销）。66 s 观感验收够用：
池轮换间隔 6 s ≫ 单帧耗时，"换没换素材"的判断不受影响。

**拉窗口的姿势（重要踩坑）**：要留给用户看的窗口必须**脱离终端进程树**，例如：

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
  CommandLine = 'cmd.exe /c <PY> -u -s tools\demo_script.py --window > "%TEMP%\aura_win_script2.txt" 2>&1' }
```

父进程是 `WmiPrvSE` ⇒ 终端关掉也不受影响。排查存活用**窗口标题**
（`Get-Process | Where-Object { $_.MainWindowTitle }`）比按 PID 查可靠：
`.venv` 的 `python.exe` 是转发 stub，报出来的 PID 与真正干活的进程对不上。
命令里加 `-u` 可让 traceback **立即**落盘（否则被块缓冲藏住，看起来"日志是空的"）。

### 6.2 点「重播」没反应 —— 演出结束后 tick 链不自我排期（复盘）

**症状**：`--window` 演完（日志已打「—— 演出结束 ——」）后，点「重播（F5）」按钮或按 `F5`，
**只有一行「—— 重播（F5）——」，画面永远停在终帧、剧本不再重跑**。

**根因**：`tick()` 末尾的续跑条件写成"只在还没演完时续链"：

```python
if t < end + 0.4:
    root.after(tick_ms, tick)     # 演出中：续链
elif not done[0]:
    done[0] = True                # 演出结束：打一行日志，**不再排期** ⇒ tick 链终止
```

而 `replay()` 只重置了 `cursor / seen_mk / seen_ev / done / wall` 这些**状态**，
**没有重新 `root.after(tick_ms, tick)`** ⇒ 演出结束后点重播，**没人再调用 `tick`**：
状态确实全部归零、日志也打了，但画面一动不动 —— 典型的"改了状态、漏了驱动"。

**修复**（`tools/demo_script.py`，3 处）：

1. 新增 `scheduled = [False]`（`tick` 链是否已排进 `after` 队列）：`tick` 入口置 `False`（本次已消费）、
   续链处置 `True`、首轮起链处也置 `True`；
2. `replay()` 末尾**补链**：`if not scheduled[0]: scheduled[0] = True; root.after(tick_ms, tick)`
   —— 用 `scheduled` 做互斥，防止"演出中连点 F5"排出**第二条链**（双倍帧、两个 tick 抢着推状态）；
3. 顺带修"多轮轨迹串一起"：`trace` 是**跨轮复用**的，而 `seen_mk/seen_ev` 重播时归零
   ⇒ 旧 `marks/events` 会被**重放刷屏**、`samples/states/switches` 累积使报告跨轮混。
   新增 `Trace.reset()` 清空全部记录（`replay` 里调用），并复位 `runner._last_state/_last_asset/_last_meta`。

**验证（新·可复用，全自动，无需人工点击）**：`%TEMP%\zz_replay_smoke.py`
—— 把模块级 `SCRIPT` 换成 1.2 s 短剧本（标记用 ASCII，绕开终端编码）、真开 Tk，
`patch tk.Tk.mainloop` 注入两个定时点：2.6 s（演出已结束、链已停）时 `button.invoke()`
**脚本化点击**「重播」，4.8 s 时读 `Text` 日志控件并 `destroy()`：

```
REPLAY SMOKE: wall=4.88s buttons=1 cb_errors=0 marks=3
  button_found   PASS      round1_ended   PASS      trace_not_dup  PASS
  round1_t1      PASS      replay_logged  PASS      no_cb_error    PASS
  round2_t1      PASS      round2_t2      PASS      → VERDICT: OK
```

关键读数 `round2_t1 / round2_t2`：**在「—— 重播（F5）——」之后又出现第 1、2 拍标记**
⇒ 证明确实**重新起链、重跑剧本**；`marks=3` 则证明旧记录没被重复刷屏。

**通用套路**：这类"点了没反应"先看"回调是否只改了状态、却漏了驱动（`after`/事件重排）"；
本机 GUI 无法人工点击验收，一律用 `patch tk.Tk.mainloop + widget.invoke() + 定时读控件` 做脚本化点击。

## 七、已知限制

- **AWAKE burst 每轮只播 0.2 s** 就被切走（重开一轮链的代价），视觉上"刚要惊讶就开始想"。
  演示素材轮换够用；要精细需给 FSM 另配"无声重开"事件。
- `report()` 的"状态段时长"按采样点封口，末段边界受 `--dt` 影响（默认 0.1 s）。
- 拼图是**静态**的：只能确认"池里每个素材都长得出来"，**交替感必须看真窗口**。
