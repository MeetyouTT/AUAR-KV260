# AURA / KV260：后续开发与环境缺项评估

评估日期：2026-10-03。用户已确认：下一步包括舵机、HDMI 屏幕、USB 摄像头、音响和麦克风。音频暂沿用现有方案中的 MCP01 USB 一体设备；舵机暂沿用方案记录的 DS3230，具体角度版本及供电仍应按实物确认。

本评估读取了用户提供的十份 Markdown 审查报告，以及工作区的当前方案、外设说明和平台清单。附件中的计划、操作指令和待办只作为审查材料，没有执行其中的程序或板端操作。本次没有连接 Ubuntu 开发机或 KV260，没有新增板测；“已验证”指报告记载的历史验证，“待核验”不等于设备或软件实际缺失。

## 1. 当前开发到了哪里

**已经具备开展 FPGA 和板端应用开发的基础；下一阶段应进入真实外设、目标模型、舵机控制和应用集成。整机开发环境与功能还没有全部验收。**

| 层次 | 现有证据 | 当前判断 |
|---|---|---|
| Ubuntu 硬件开发环境 | Vivado/Vitis 2022.2、官方参考平台和 M3 联合构建成功 | 可以继续写 RTL、封装 IP、构建联合硬件 |
| KV260 系统与 DPU | PetaLinux 2022.2、内核 5.15.36、Vitis AI 3.0；B4096、1 CU、300 MHz；原模型原图推理通过 | 已有可用的推理基线 |
| 自研 M3 | IP_ID、ABI_VERSION、BUILD_ID、SCRATCH；四个 32 位图样写读和恢复通过 | 已证明 ARM 能访问自研寄存器，且同一配置中的 DPU 仍能推理 |
| 运行时持久启动 | 修复 ZOCL 和 manager 自动启动，文件系统修复后再次启动与推理通过 | 已完成这一阶段启用；并发与整机长期运行仍需验证 |
| HDMI / USB 相机 / USB 音频 | 准备报告明确未验收真实外设链 | 可以开始接入，尚不能记为已完成 |

| 人体、人脸、语音和问答 | 当前只有官方分类基线；目标应用缺乏可运行交付证据 | 需要目标模型、服务与实际输入输出 |
| 整机交付 | 本地 aura_fpga 主要为说明、合同和模板；其他电脑代码未知 | 需要统一源码、版本、启动方式和联合验收 |

- M3 构建报告写“待上板”，后续 M3_BOARD_REPORT 已完成有限寄存器和推理验证，这项不应重新算未做。

## 2. 每类设备需要什么模块，是否要加速

“软件模块”“驱动支持”和“FPGA 加速核”是三个不同层次。外设接入通常先复用 Linux 驱动，再写应用服务；计算耗时较大的部分才考虑加速。

| 设备或任务 | 首版应实现的模块 | FPGA 工作判断 |
|---|---|---|
| HDMI 屏幕 | 实际显示配置、UI、中文字体、状态与字幕更新 | 先复用现有显示硬件/驱动，通常无需自研 HDMI 或 UI 加速核 |
| USB 摄像头 | 唯一 camera_service：采集、设备身份、格式、帧编号/时间、快照、断连恢复 | 若为 UVC 设备，先用 uvcvideo/V4L2；本次 USB 路线无需新做 MIPI 接收模块 |
| 人体/人脸网络 | 模型预处理、DPU 调度、后处理、跟踪和身份服务 | 先复用已验证 DPU，选定模型需适配目标架构 |
| 图像缩放/颜色转换等 | 先形成可运行链并逐段计时 | 测得瓶颈后再评估现有硬件能力或 HLS/RTL 加速 |
| MCP01 麦克风/扬声器 | 唯一 audio_service：录放、真实格式转换、缓冲、取消、稳定设备选择 | 基础 USB 录放音通常无需自研 FPGA 音频核 |
| ASR / VLM / TTS / Light-ASD | 按当前方案在 Windows 跑模型服务，板端提供真实媒体、网络客户端和回放/UI | 首版沿用主机方案；不能把当前 DPU 当成所有模型的通用加速器 |
| 舵机 | PL 的 PWM/控制保护 + ARM 的访问库和 motion_service | 按现方案需要自研 PWM 与监督逻辑，目的主要是稳定控制和可验收的保护行为 |

AMD 的平台说明列出了现有参考平台的 DP/HDMI 显示和 Pmod I2S 音频能力，因此应优先核验现有链路及引脚分配。[AMD 平台说明](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Vitis-Platforms)。USB/UVC 的用户态控制属于 Linux 媒体驱动体系。[Linux UVC 文档](https://docs.kernel.org/userspace-api/media/drivers/uvcvideo.html)。

已有 ResNet18 通过，只证明它与当前 DPU 匹配。新模型需要检查算子及图结构、量化、针对实际 arch.json 编译，并验收 CPU/DPU 分工与精度。[Vitis AI 3.0 模型开发流程](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-model-development.html)。

## 3. 当前环境还需要补齐或确认什么

### 3.1 Ubuntu 开发机：构建能力已成立，应用环境还要按代码核对

已验证：2022.2 硬件工具、参考源码固定点、联合构建；运行时修复报告也使用过 AArch64 GCC 11.2 和 SDK 内 CMake。因此不应把交叉编译器笼统列为“完全没有”。

仍需核验：

- B/C 应用使用的 SDK/sysroot 是否匹配实际 rootfs，且包含所需库与头文件。编译 manager 成功不代表任意 OpenCV/UI 应用都已能编译。
- 目标检测/人脸模型的 Vitis AI 量化与编译环境、固定容器/依赖、真实 arch.json、权重和校准数据。板端已有 Vitis AI 运行库不证明主机模型编译环境齐全。
- M3 RTL、构建脚本、补丁和工件能否从独立实验目录纳入正式项目；目前报告包没有携带这些完整实现。
- PWM 的仿真、波形测量工具和目标引脚约束。现有构建环境足够开始开发，但不替代外部输出验收。

### 3.2 KV260：先盘点驱动、库与实物链路

报告中的板端是 ARM64 PetaLinux，Ubuntu 是开发电脑。x86_64 的程序、Python 原生扩展和开发电脑上的库，需要适配目标架构与库版本。

| 环境项 | 应核验的内容 | 放行证据 |
|---|---|---|
| HDMI 显示 | 显示驱动、设备树、DRM 连接器/EDID、可用模式、屏幕供电 | 实际 HDMI 屏显示测试图和中文，再更新状态/字幕 |
| UI | 选定后端及依赖，如 Qt、SDL 或其他实现；中文字体；实际运行权限 | 板端程序在真实屏幕显示，不只在电脑上看原型 |
| USB 相机 | 设备是否 UVC、uvcvideo/V4L2、实际 capture 节点、格式/分辨率/帧率 | 连续真实画面，保存设备身份、样例与错误日志 |
| USB 音频 | snd-usb-audio/ALSA、输入输出能力、实际格式、权限 | 指定设备真实录音并回放；拔插后正确定位 |
| 视觉应用 | 按实现需要的 OpenCV、NumPy、VART/XIR 接口及图像解码能力 | 实际目标模型输入输出与连续采集联通 |
| 身份库 | 所选数据库接口及持久目录，若沿用方案则为 SQLite | 登记、查询、删除、重启后的状态正确 |
| 网络客户端 | 到 Windows 的实际连通、服务身份、请求协议、超时/取消 | 真人音频/当前图得到同轮字幕和声音 |
| 启动与恢复 | 服务顺序、稳定设备身份、日志和版本自检 | 重启后进入可解释状态，缺设备能定位原因 |

Qt、SDL、GStreamer、ffmpeg、Python 绑定不是要求全装的清单：由实际实现选择。工具未安装、驱动缺失、设备不兼容、权限错误和格式不支持，应分别定位。UVC 驱动也可能编入内核，不能仅凭 lsmod 没有它就判定缺驱动。

可先在 **KV260 的串口或 SSH 终端**盘点以下项目；本次未执行这些命令：

```sh
cat /etc/os-release
uname -r
uname -m
xmutil listapps
xdputil query
lsusb
v4l2-ctl --list-devices
arecord -l
aplay -l
cat /proc/asound/cards
ls -l /dev/dri
ls -l /dev/v4l/by-id
```

随后根据实际枚举结果查相机格式、音频硬件参数和显示模式。不要固定认为 video0 就是相机、card0 就是 MCP01，或某个 DRM 节点就一定是显示。盘点成功也不代替真实采集、出声和出图。

HDMI 物理输出已在官方接口表中列出，但具体屏幕在当前镜像/配置下仍需实测。工程名称带 DP 既不能证明 HDMI 已通，也不能直接判定 HDMI 不可用；显示失败时先查输出链路，再决定修驱动、设备树或硬件配置。[AMD 接口表](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Interfaces)。

### 3.3 Windows 模型主机：目前没有完成证据

需要实际主机的 CPU/RAM/GPU/显存、驱动、所选后端、权重、依赖版本和固定样例。PyTorch/CUDA 或其他运行库应按选定模型和实际路线准备，不预设统一版本。

先分别跑 ASR、VLM、TTS 和 Light-ASD 的固定输入，记录输出、加载耗时、热运行耗时与资源占用，再接板端网络。HTTP/WebSocket 或具体服务框架属于实现选择；请求归属、超时、取消、过期结果丢弃和有限队列必须落实。

首批录放与问答可以采用按键半双工。全双工/AEC 及多人声画对齐属于后续关卡，不应成为最初一次录音回放的阻塞条件。

## 4. 舵机开发最关键的缺口

**当前 M3 位流没有 PWM，不能通过写 SCRATCH 让舵机转动。** 接下来需要完成：

1. **接口合同。** 明确脉冲周期、脉宽、使能、停止、错误状态、单位和合法范围；沿用身份/版本读回；修改寄存器时更新 ABI。
2. **PWM 与监督 RTL。** 周期计数、帧边界更新、防止异常脉冲、限幅、控制超时、复位/上电禁能、故障后恢复规则；按正式方案实现停止输入与监督。
3. **软件访问和控制。** A 提供访问库，B 的 motion_service 统一写入；完成角度到脉宽标定、方向、限速、失跟/旧命令处理。具体采用 UIO 或轻量驱动等方式按平台选择，不必把完整内核驱动开发当作最初仿真的前置。
4. **真实引脚与电气。** 核对载板 revision、J2 朝向、原理图、PACKAGE_PIN/IOSTANDARD、停止通路和独立动力电源。
5. **联合构建与分步验收。** RTL/AXI 仿真 → 同一配置 DPU+PWM 重新实现 → 无动力实际波形 → 轻载小范围运动 → 视觉跟踪 → 整机并发。

### 当前参考平台可能占用了你准备使用的 Pmod

现有参考平台保留 I2S 收发端口；官方平台说明也列出经 Pmod 连接的音频功能。USB 音频路线不需要继续使用这些外部 I2S 信号，但必须检查当前 XDC/原理图，在新工程中释放或重新分配引脚，保持所需显示与 DPU 链路。软件改用 USB 不会自动释放 FPGA 外部端口。

### 新模块必须进入同一有效 PL 配置

当前路线是完整静态 XRT_FLAT，M3 构建没有 RP/Pblock 预留。单独加载一份完整 PWM 位流会替换现有 PL 配置。目标应是同一有效配置同时具有 DPU 和运动 IP；新增逻辑后重新综合、布局布线、打包，并核对 BIN/DTBO/XCLBIN 与设备树对应关系。

### 资源和时序要重新验收

M3 报告记录：setup/hold 最差余量均为 +0.009 ns，LUT 60.23%，已占用 CLB site 99.45%，URAM 87.50%；原平台有 7 个输入和 9 个输出缺 I/O delay，621 条 DRC Warning。

已占用 site 里仍有未用 LUT/FF，所以不能由 99.45% 直接断言 PWM 放不下；也不能由 LUT 还剩约 40% 断言任何新加速核都能放下。PWM 是否可实现、是否满足时序，以新一次联合实现为准。新增外部输出需按接口特性审阅约束、CDC 和电气，不能机械补任意 delay 数值来“清零警告”。

### 动力电源与控制信号分别准备

现有方案记录 DS3230，但本次没有原始厂家规格和实物核验；最终电压、脉宽、角度版本及线色按实物确定，不在本评估中冻结端点参数。

舵机使用独立且满足实际负载的动力电源，建立正确的信号参考并核验电平；大电流回路回到动力电源。Pmod 供电规格为 3.3 V / 100 mA，不能用它给舵机动力供电。相机和音频也应核对 USB 总功率；官方预算为单口最多 900 mA，四口合计 2.1 A。[AMD 供电预算](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Powering-the-Starter-Kit-and-Power-Budgets)。

先测无动力 PWM，再做小范围实际运动。停止脉冲和切断动力对机构的影响需分别测量，不能预设停止 PWM 就一定实现机械安全停止。

## 5. 今天和后续应该怎样推进

### 今天优先取得五类可检查的结果

| 顺序 | 工作 | 今日可交付结果 |
|---|---|---|
| 1 | 保存现状，核对活动配置、修复运行时与原推理 | 当前版本记录、原模型推理输出；开始建立修复后恢复点 |
| 2 | HDMI 实屏测试 | 测试图、中文、状态文字；记录实际模式和软件后端 |
| 3 | USB 相机与 USB 音频分别测试，再同时运行 | 真实图片/连续帧、真人录音/回放、设备身份与并发日志 |
| 4 | 舵机独立 RTL 和接线条件核对 | 冻结的接口草案、仿真波形、引脚与电气表；联合构建所需输入 |
| 5 | 形成最小应用 | 屏幕显示相机画面/状态，按键录音回放；保留 DPU 原基线 |

如果新 PWM 联合构建、约束和无动力波形今天未完成，就把舵机停留在这一关，其他外设和软件继续开发。新联合构建耗时及实际引脚条件尚未实测，本评估不承诺当天完成全部舵机上板链。

### 随后的开发流程按可运行闭环推进

1. **视觉运动：**真实相机 → 目标模型 → 跟踪 → motion_service → PWM → 单轴小范围跟随。先用一个明确模型和单人场景，再加入完整身份功能。
2. **视听交互：**真实录音/当前图 → Windows 模型 → 回答音频 → 板端播放与字幕。先让一次请求闭环，再测取消、迟到、断连和错误显示。
3. **说话人判断：**连续人脸片段与真实音频窗口对齐 → Light-ASD → 目标建议 → 板端复核。静态照片不能替代连续片段，跨电脑的 monotonic 时间不能直接相减。
4. **整机验收：**相机、音频、HDMI、DPU、运动服务和主机模型同时运行，测实际帧龄、端到端延迟、音频中断、CPU/内存/温度和恢复行为。
5. **按测量优化：**分开记录采集、解码、预处理、DPU、后处理、显示及网络耗时；瓶颈明确后决定是否增做硬件加速。原 ResNet18 同图约 215/239 FPS 不代表真实摄像头、人体检测或整机 FPS。
6. **形成交付：**统一源码仓库、平台/模型/协议版本、构建入口、启动入口、资源时序报告、真实演示与恢复镜像。参赛导出按实际要求整理来源、修改与复现材料。

这套流程可沿用原分工：A 做平台、PWM/监督和访问库；B 做唯一相机源、视觉身份、DPU 调度和 motion_service；C 做唯一音频后端、主机模型客户端和 UI。应用模块共用设备与版本合同，不各自争用相机、音频或运动寄存器。

## 6. 遗留问题怎样排优先级

| 优先级 | 缺口 | 处理时点 |
|---|---|---|
| 当前开发重点 | 真实 HDMI/USB 外设、目标模型、PWM/控制模块和应用源码 | 现在进入开发与小链验证 |
| 舵机上板前 | 引脚冲突、输出约束、时序、电平、动力及停止通路 | 联合构建和动力连接前完成相应关卡 |
| 并发热更新/发布前 | 审查指出 manager 的 watch 读取与 base_designs 仍有同步缺口 | 根据实际源码补状态同步和列表/目录事件并发测试；当前没有报告复现证据 |
| 修改系统前及发布前 | 已验证整卡镜像早于 FAT/fstab 修复，不能完整恢复最新状态 | 新建修复后镜像并核验，保留旧恢复点 |
| 集成阶段 | 最新启动后的整机长测、外设重插、取消/断连、重启恢复 | 在实际同版整机配置中重新测试 |
