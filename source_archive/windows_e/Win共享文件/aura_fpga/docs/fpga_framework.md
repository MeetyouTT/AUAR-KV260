# AURA：面向 AMD 自主选题初级组的 FPGA 详细框架

2026-09-27 对齐注记：本框架的当前执行入口为 [第四轮与当前项目对齐记录](../../方案/AURA_第四轮与当前项目对齐_2026-09-27.md)。需求、命名和整体验收原则上引用第四轮 D5；已发现冲突按对齐记录处理。§5.4—5.5、§6.5 的旧接口细节不得直接作为新版冻结 ABI。

日期：2026-09-23。性质：设计建议与提交映射；不是已实现结果。工具基线采用用户确认的 2022.2，系统镜像尚待记录。

## 0. 你现在要完成的任务

你负责的工作是：在 KV260 上形成一套可重建的联合硬件平台，让官方 DPU、自己的运动控制逻辑、自己的双麦音频逻辑共同运行，并向 B/C 提供稳定、可验证的接口。

可以用一句话理解产品：设备看到人、选择交互对象、转向对方、认人并对话；你的硬件负责提供神经网络运行平台、声音方向证据和受监督的实际运动输出。

第一项集成成果应当是“DPU 推理仍正常，同时 Linux 能读到自研 IP 的版本号”。它比一开始写完所有算法更能说明工程路线成立。最终仍需完成个人计划中的运动、音频与验证任务。

### 0.1 五个容易混淆的概念

| 名称 | 在本项目中表示什么 |
|---|---|
| KV260 | 整块开发板，包含 ARM 处理系统和 FPGA 可编程逻辑等 |
| PS | ARM/Linux，运行相机采集、跟踪、控制请求及其他软件 |
| PL | FPGA 电路，运行 DPU、自研运动 IP、自研双麦 IP |
| DPU | 复用的神经网络加速 IP，位于 PL；不是另一块外部处理器，也不是本队自研模型 |
| 位流/硬件配置 | 决定 PL 里有哪些电路；写 Verilog 后需要综合、布局布线并生成部署工件 |

烧好 Linux 系统说明进入了板端开发阶段，并不自动意味着 DPU 可用或可加入自研逻辑。软件镜像、硬件配置、运行时、模型需要配套。

### 0.2 本次采用的文档优先级

1. 官方指南第 3.3 节决定该赛道要求；后续官方评分细则和公告优先。
2. 当前对齐记录处理跨版本冲突；第四轮 D5 提供需求编号、命名与 T01—T30 整体验收基线。包内未闭合的接口仍须合并复核。
3. 三份 `aura_plan_*_30days.md` 保留 A/B/C 责任与目标；2026-09-19 软硬件详解补充历史结构。身份部署按对齐记录分阶段，主机通过不等于板端通过。
4. 旧 20 天计划、早期 Windows 身份方案和通用 Deep Research 报告作为背景，不叠加成新的必做清单。

AURA 个人计划包含 Light-ASD 基线，板端身份目标保留；第四轮 D5 的首版主机身份服务用于阶段联调。最终身份范围待用户选择，不静默取消板端目标。文档描述均不能证明当前板端已实现。

## 2. 系统实际怎么运行

### 2.1 软件和硬件分层

| 层 | 内容 | A/B/C 责任 |
|---|---|---|
| 外设 | USB 相机、双 I2S 麦、屏幕、USB 录放音、舵机、停止输入 | A 负责硬件关系与运动/双麦；B 相机软件；C 显示录放音 |
| PL 官方部分 | DPU 与配套内存/时钟/复位/中断连接 | A 集成，B 模型验证 |
| PL 自研部分 | `motion_guard_ip`、`audio_doa_ip`、必要调试信号 | A |
| PS 软件 | 相机、模型调用、轨迹/身份、运动服务、音向读取、UI/通信 | B 视觉/身份/运动策略，C 视听/交互；A 底层访问库 |
| 主机软件 | ASD、ASR、VLM、TTS 等计划中的主机模型服务 | C；B 提供带归属与时间的人脸片段 |

B/C 的软件不会作为两个 RTL 文件直接塞进 Vivado。全队同时存在软件 API、网络消息和板内 AXI 接口三类边界。

### 2.2 三条主要运行链

```text
视觉与运动：
USB 相机 -> PS 采集/预处理 -> PL DPU -> PS 后处理/跟踪
                                      -> B 的运动服务
                                      -> 你的 motion_guard_ip -> 舵机
                                                             -> 新画面反馈

选人证据：
双 I2S 麦 -> 你的 audio_doa_ip -> 方向/质量/窗口
B 的人脸片段 + 对齐音频 -> C 的 ASD -> 说话证据
两种证据 + 当前视觉轨迹 -> C 的对象建议 -> B 核对后执行

对话：
USB 录音 + 当前图像 -> C 的主机模型服务 -> 回复/音频
                                       -> 板端屏幕与扬声器
```

普通视觉随动不必等待大模型问答。声音用于补充选人依据；双麦“左/右”不直接证明哪一个人正在讲话，也不识别姓名。身份由 B 的人脸链提供。

### 2.3 你与队友的三个交接接口

| 接口 | 方向 | 最小内容 |
|---|---|---|
| 运动请求 | B -> A 的底层库 -> PL | 会话/恢复代次、序号、目标毫度、剩余许可时间、整体提交 |
| 运动状态 | PL -> 底层库 -> B/C | 状态、接受序号、拒绝原因、有效 PWM、故障、剩余许可 |
| 音向结果 | PL -> 底层库 -> C | 窗口序号、样本范围、左中右/未知、质量、有效性、丢样状态 |

正式运行只有 B 的运动服务写运动寄存器。A 的测试程序与它互斥，只在明确测试模式使用；C 通过软件接口请求停止/关注，不另开一条 PWM 写入链。

## 3. 确定工具路线：2022.2 继续使用

用户已确认工具为 2022.2。AMD Vitis AI 3.0 官方兼容表列出 Vivado/Vitis/PetaLinux 2022.2、DPUCZDX8G IP 4.1 与 Vitis AI 3.0 的验证组合。注意：这说明可用组合存在，不说明用户当前镜像已经属于该组合。

### 3.1 当前决定与待核对项

| 项目 | 本框架决定 |
|---|---|
| Vivado/Vitis | 保持 2022.2，记录完整补丁与构建环境 |
| DPU/软件参考 | 优先核对 Vitis AI 3.0 对应 KV260 参考路线，不混入未知新版本 |
| Linux 镜像 | 记录实际名称、来源、校验值、运行时；本次尚未知 |
| 参考硬件源码 | 必须能获取并重建；只有预编译镜像不足以完成自研联合平台 |
| PYNQ | 不为推荐加分项主动迁移当前平台；若已有匹配可重建 PYNQ 基线再单独评估 |
| 加载方式 | 跟随实测通过的参考设计，不猜测 `.bit/.xclbin/.hwh` 的任意组合 |

### 3.2 为什么暂不指定一个“一键构建命令”

AMD 提供 Vitis 和 Vivado 两类 DPU 集成方式，它们的软件运行时配置不同。Vitis 路线通常使用 XRT/xclbin；对应版本的 MPSoC Vivado 路线使用不带 XRT 的 VART 构建。当前镜像和参考工程未知，直接给固定部署命令很可能启动错误平台。

本框架给出的默认决策是：先原样重建与你当前 DPU 镜像配套的参考设计，再沿同一路线扩展。

- 若使用官方 2022.2 KV260 Vitis 参考平台：保留其平台/加速包结构，自研外设的加入位置须结合平台静态区、可重配置区和链接方式核实。最终检查链接后硬件，不能只检查基础平台。
- 若确认已有可重建的 Vivado DPU 工程：保留该硬件设计和对应 Linux/VART 路线，再加两个 AXI-Lite 外设。
- 若只有可运行镜像却找不到可重建平台：把“镜像能用”和“硬件可扩展”分开记录；继续独立 RTL 仿真，同时解决参考工程，不宣布集成完成。

动态部分重配置不是当前新增研究任务。参考平台已有的加载机制应遵循其文档；自研模块必须位于最终会被保留的区域或共同的加速包中。

## 4. 最终 FPGA 顶层应该长什么样

下图是逻辑结构，实例名、AXI 端口、时钟和地址由匹配参考工程决定，不是可以不加核对直接照连的具体 Block Design。

```text
                      KV260 / K26
  +-----------------------------------------------------------+
  | PS：ARM + Linux                                           |
  |  B：模型、跟踪、身份、motion_service                       |
  |  C：交互软件、音向消费、UI、网络                           |
  |  A：受控访问库 / 驱动适配                                  |
  +----------+-----------------------+------------------------+
             | 控制 AXI              | DDR / 高吞吐访问
  +----------v-----------------------v------------------------+
  | PL                                                       |
  |                                                          |
  |  参考设计控制互连              参考设计内存互连            |
  |    |          |          |                  |             |
  |    v          v          v                  v             |
  |  DPU控制   motion IP   audio IP <---双麦    DPU计算         |
  |              |          |                                 |
  |              |          +-- 窗口、相关、质量、结果快照      |
  |              +-- 命令监督、限速、PWM、禁能输出             |
  |                                                          |
  |  配套时钟 / 每域复位 / CDC / 有限 ILA 调试                 |
  +--------------+--------------------------------------------+
                 v
       外部使能/供电链 + 舵机 + 停止通路
```

### 4.1 首版只定义两个自研外设

1. `motion_guard_ip`：一个 AXI4-Lite 从接口，运动状态及命令集中在一个地址窗口。
2. `audio_doa_ip`：一个 AXI4-Lite 从接口，双麦采集和相关在内部完成，结果从寄存器读出。

DPU 保留原有接口与驱动约定。调试状态暂时放在这两个 IP 内，不额外做复杂的统一调度器。

建议每个自研外设预留 4 KiB 地址窗口，实际物理基地址由最终地址分配生成。4 KiB 是设计建议，不是已分配地址。寄存器规格只先冻结窗口内相对偏移。

### 4.2 哪些连接由你负责

| 连接 | 首版处理 |
|---|---|
| PS 到两个自研 IP | 通过参考平台允许的控制 AXI 互连，32 位寄存器读写 |
| DPU 到 DDR | 继承匹配参考设计；先不自己重构数据搬运 |
| 自研控制时钟 | 从参考平台取得已定义时钟；100 MHz 仅为可评估起点，确认后写入参数 |
| PWM 时间基准 | 由控制时钟的计数/使能产生，不把计数器位当任意新时钟 |
| 音频时钟 | 按实际麦克风与参考平台选择受支持方案；与系统时钟关系写进约束 |
| 复位 | 每个时钟域使用匹配的复位电路，默认禁能，释放同步 |
| 中断 | 运动故障/音向更新可预留；初版状态读取可采用有截止时间的轮询，硬件超时独立运行 |
| 引脚 | 建立实物 revision 对应的正式 XDC；此阶段不猜管脚号 |
| ILA | 优先观察提交、接受/拒绝、计时、窗口切换与握手，不探测所有音频位 |

### 4.3 当前不需要你从零写的内容

USB 主控制器、DDR 控制器、DPU 运算阵列、视频显示控制器、YOLO 的 RTL 实现和全套 DMA。需要保留参考平台已有功能；若所选平台缺显示能力，要单独列为平台任务，不能默认 HDMI 接口存在就已能显示。

## 5. 运动 IP：从文件到行为

### 5.1 建议源码划分

|---|---|---|
| `motion_guard_ip.sv` | 自研运动外设顶层，连接各模块 | 整体仿真能启动、提交、到期 |
| `motion_axi_regs.sv` | AXI-Lite 握手、影子参数、命令快照、状态读取 | AW/W 错拍也正确，半条命令不会执行 |
| `motion_guard.sv` | 状态、范围、会话/代次、序号、许可与优先级 | 旧命令拒绝，超时禁能 |
| `motion_profile.sv` | 指令角范围与每步变化上限，角度到脉宽标定 | 输入跳变时输出按约定步长变化 |
| `servo_pwm.sv` | 稳定周期、脉宽和边界更新 | 周期与高电平时长符合仿真预期 |
| `stop_input.sv` | 外部停止输入同步与锁存，释放条件 | 停止能触发，释放不会自动恢复动作 |

这些是职责划分，不要求每项都必须单独一个文件。先采用清晰、可测试的六块，避免几十层空壳封装。

### 5.2 命令的单位先定下来

- `target_mdeg`：有符号 32 位毫度，相对于明确的标定零位。B 将画面像素误差转成目标角，你的硬件不直接接收检测框。
- `lease_us`：无符号剩余许可微秒数，由 B 在实际提交前计算；有硬件最大上限。
- `session_id`：当前运动会话的标识；更换目标/恢复如何建立新会话由 B 和 A 一起定义。
- `safety_epoch`：本次使能代次，用于让停止前排队的命令失效。
- `cmd_seq`：同一会话/代次内严格递增的序号。
- 机械范围、PWM 端点、周期、方向极性、每步变化率：根据真实舵机和机构标定，未标定时不使能。

### 5.3 一条请求如何变成动作

1. B 从仍有效的视觉轨迹产生请求，计算证据截止时间；长时间排队的旧请求丢弃。
2. 访问库检查硬件版本、当前会话和恢复代次。
3. 写影子字段，完成写入排序；最后写 COMMIT。
4. 寄存器模块取得同一份命令快照，给监督逻辑一次请求事件。
5. 监督逻辑检查状态、停止、配置、字段完整、会话/代次、序号、目标范围与租约。
6. 接受时更新活动命令、接受序号与许可计数；拒绝时保留原活动命令的原到期时刻，绝不续期。
7. 指令限制模块生成受限目标，PWM 正常参数在周期边界生效。
8. B 读取“命令接受状态”；它与“PWM 已生效”和“机身已到位”是不同状态。

AXI 写成功只代表总线事务完成，不代表动作已接受。超时发生在等待 PWM 边界期间时也应撤销许可，不能执行已经到期的待更新目标。

### 5.4 简洁而完整的状态机

对齐状态：统一命名采用 `DISARMED / NEEDS_REFERENCE / ARMED / TRACKING / AT_LIMIT / FAULT`。下面是旧版行为草案，保留追溯，不能直接照搬。无位置反馈重启先禁能并要求位置确认；到期作为事件处理。新版完整转移表、是否必须重新 ARM、同拍优先级仍须按对齐记录 §4.1 冻结。

```text
复位 -> DISABLED
配置有效 + 新会话/新代次 + 明确 ARM -> ARMED
ARMED + 有效命令 -> ACTIVE
ACTIVE + 新有效命令 -> ACTIVE（更新目标和许可）
ACTIVE + 许可耗尽 -> EXPIRED（撤销输出许可）
任意状态 + 停止/关键故障 -> FAULT（锁存，撤销许可）
EXPIRED/FAULT -> 清理请求与会话 -> DISABLED -> 显式重新 ARM
```

ARMED 没有有效运动命令时不产生带负载动作。停止释放、网络恢复、模型回复、清故障，均不单独等于重新使能。

同拍事件优先级：复位/外部停止/关键故障 > 到期 > 禁能 > 恢复操作 > 新命令。恢复和 ARM 分两次明确操作；到期同拍的新命令不能悄悄越过恢复要求。该策略是本项目建议，需写入接口和测试。

“无异常窄脉冲”针对正常更新。紧急禁能可能主动截断当前脉冲，这是优先级决定的行为，应在波形中明确标注，不能与正常更新测试混淆。

### 5.6 AXI-Lite 实现必须覆盖的细节

- 地址 AW 与数据 W 分别握手和暂存，凑齐后处理一次写事务；不假定同拍。
- 限制为一笔未完成读和一笔未完成写也可以，必须正确背压。
- BVALID/RVALID 在对方未接受时保持，返回数据稳定。
- 普通 RW 寄存器按 WSTRB 更新；命令字段完整性按实际写入字节记录。
- COMMIT/CONTROL/SNAPSHOT 首版要求对齐的完整 32 位写，其他写法返回明确错误，不执行副作用。
- 非法/未实现地址返回约定错误响应；不静默启动动作。
- 复位丢弃未完成事务，驱动不能在复位后继续当作旧事务已完成。
- 单写入者避免字段交叉；软件 MMIO 使用平台正确的映射属性与写入顺序保障，不能只靠普通指针或 sleep。

### 5.7 许可时效能保证什么

相对租约首版保证：从硬件接受命令开始，在该许可时长耗尽后撤销执行许可，计时不依赖 PS 或主机继续运行。

它不独立证明相机曝光时间，也不能识别软件把旧图谎报成新图。B 必须固定原始证据截止时间，实际提交前重算剩余时间；新序号不能改变原始证据的到期时刻。

若 PS 在算完剩余时间后长时间被调度暂停，再写 COMMIT，仍可能延长实际帧龄。因此：

1. 首版把可验证承诺限定为“接受后硬件租约上界”，记录软件排队/提交延迟。
2. 若要证明严格采集到执行截止，增加 PS/PL 时间映射、误差预算，并让 PL 比较绝对截止时间；这是需要另外验证的增强项。
3. 论文与答辩区分两个保证，不能用相对租约的波形代替曝光总期限证明。

没有编码器时，输出只表示指令角/PWM；机械实际停止时间、是否到位要单独测量。外部停止和默认禁能电路由真实舵机、电源和机构决定。

## 6. 双麦 IP：采集正确后再做算法

### 6.1 模块划分

| 文件 | 作用 | 输入/输出 |

| `audio_doa_ip.sv` | 音频外设顶层 | AXI-Lite、麦克风引脚、结果状态 |
| `i2s_clock_ctrl.sv` | 按实物配置产生音频时钟 | BCLK、WS 与内部采样使能 |
| `i2s_rx_pair.sv` | 位计数、符号扩展、左右对齐 | 两路 SD -> 左右配对样本 |
| `audio_window_buffer.sv` | 窗口缓存、所有权、样本计数和丢样 | 配对样本 -> 不可变计算窗口 |

### 6.2 首版数据通路

```text
两路独立 SD + 共用 BCLK/WS
    -> 左右串行接收
    -> 同一采样时刻的配对样本 + sample_valid
    -> 双缓冲完整窗口
    -> 复用乘加单元逐个 lag 计算
    -> 质量与方向判断
    -> 结果影子快照
    -> PS 读取 -> C 融合
```

保留两路 SD 是项目首版建议，须确认实际麦克风模块。不要在型号未知时固定引脚、I2S 位偏移、有效位宽或工作电压。

### 6.3 算法规格由 A/C 共同冻结

| 参数 | 初始建议 | 冻结依据 |
|---|---|---|
| fs | 48 kHz 作为已有方案目标 | 麦克风、时钟方案及实测 |
| 槽宽/有效位 | 待核对实物 | 数据手册与原始样本 |
| 内部样本 | 有符号 16 位起点 | C 的软件参考采用相同缩放 |
| 窗口 | N=480 可作初始算例 | 方向质量和等待时间 |
| lag 搜索 | -8 到 +8 可作算例 | 麦距、fs、固定声道偏差 |
| 输出 | LEFT/CENTER/RIGHT/UNKNOWN | 首版不承诺精确角度 |
| 质量 | 能量、峰差、多峰、削波、丢样、迟滞 | 标定集定参数，独立测试集评测 |

例如 N=480、k=-8…8，对所有 k 使用 n=8…471 的共同有效范围，每个 k 为 464 次乘累加，合计 7,888 次。若每 10 ms 处理一次，纯相关约每秒 0.79 百万次乘累加。这个规模支持先评估时分复用结构；实际耗时还包括 RAM 访问、调度和质量判断，须由仿真测周期，不能直接承诺加速倍数。

按第四轮 D5 W17-10，采用 16 位有符号输入、32 位完整乘积、48 位有符号累加器；按最坏样本和有效求和数验证余量。符号扩展、截位、舍入、饱和及溢出规则都进入参考规格。

### 6.4 窗口不会“半新半旧”的规则

- 两块缓冲区分别持有 CAPTURING、READY、PROCESSING、FREE 等所有权状态。
- 采集只能写取得的空闲缓冲；计算只能读已经封存的窗口。
- 下游来不及处理时按已定义策略丢窗口并计数，不覆盖正在计算的数据。
- 采样计数继续追踪时间，不因为丢窗口就重新从零假装连续。
- 若跨时钟域，用异步 FIFO 或完整的所有权握手，不逐位同步整段样本。
- USB 音频与 I2S 是两条时钟链。C 的 ASD 输入使用哪条音频、怎样对齐和估计漂移，必须明确；不能仅凭同一电脑时间戳假定同步。

### 6.5 音频寄存器草案

对齐状态：下表为历史草案。D2 §6.4 的候选编码为 `0=中、1=左、2=右、3=无效`，与下表不同；本次引用 D2 为合并起点，保留本框架的代次、窗口、样本范围和快照要求。驱动须同时检查 `dir_valid` 及版本，不得把复位的 0 当作有效方向。新偏移、质量量纲和时延定义待冻结，详见对齐记录 §4.2。

### 6.6 验证顺序

1. 仿真已知 I2S 位流，证明正负数、左右声道、位偏移正确。
2. 上板导出短段双路原始 PCM，确认真实声音、幅度、符号和计数。
3. C 提供人工延迟向量，A 比较各 lag 的相关值与峰位置。
4. 静音/噪声/多峰/削波/丢样应输出拒判或质量标志。
5. 实物左中右标定，确认符号和几何关系。
6. 加入扬声器播音、舵机转动和同侧多人，统计正确、错误、UNKNOWN。

原始 PCM 调试导出首版可用短窗口寄存器/片上存储读出方案，必须定义冻结与所有权。持续高吞吐 PCM 才评估 DMA，不把 DMA 当作比赛必选项。

## 8. 时钟、引脚与硬件约束怎么管理

### 8.1 时钟/CDC 表

| 域 | 处理策略 | 应记录的内容 |
|---|---|---|
| DPU 域 | 保留参考时钟与约束 | 输入频率、关联复位、接口转换 |
| 控制域 | AXI、监督、PWM 尽量同域 | `ctrl_clk_hz`、微秒使能精度、PWM 分辨率 |
| 音频域 | 按具体方案决定是否独立 | BCLK/WS 生成方式、采样边沿、实际 fs |
| 异步外部输入 | 停止等单比特同步 | 同步延迟、锁存与释放行为 |
| 音频到结果/控制域 | FIFO 或所有权握手 | 数据一致性、满/空、复位顺序 |

若 48 kHz、每帧 64 BCLK，目标 BCLK 为 3.072 MHz；100 MHz 简单整数分频不能恰好得到该值。须选合法时钟生成方案并验证波形、频率及接口时序。不要把目标采样率直接写成“已实现”。

### 8.2 引脚预算先于 XDC

按两路 SD 的方案：BCLK、WS、SD_L、SD_R 共四根；PWM、执行使能、外部停止再占三根，共七根逻辑信号。是否真正可用取决于载板、现有平台占用与电平。独立实体确认键若再占一根则需重新核算余量；首版恢复也可通过受控软件操作完成。

`pin_map.csv` 必须记录信号名、载板连接器位置、FPGA 管脚、方向、IOSTANDARD、电压、参考手册页和实测状态。此框架不提供猜测管脚。

舵机功率、默认使能、停止通路和信号地需要独立核对；不得把断 PWM 直接报告成机械立即停止。实际 SAFE_ACTION 取决于舵机和驱动电路。

### 8.3 时序验收

工程内部发布条件建议：实现完成；相关 setup/hold 通过；脉宽要求通过；时钟/外部接口约束完整；无未解释的未约束关键路径、严重 DRC 或不安全 CDC；所有例外约束有依据。

最终报告包括 `report_timing_summary`、`check_timing`、`report_utilization`、`report_drc`、`report_cdc`、`report_clock_interaction` 与必要的约束例外检查。WNS/WHS 非负不是“所有设计问题已排除”的充分条件。这些是团队工程门槛，不是本指南明示的统一数值赛规。

## 9. 队友怎样调用你的功能

建议提供一个小型访问库，隐藏地址、寄存器偏移、快照及提交顺序。C/C++ 或 Python 取决于最终系统，不为统一语言强行重写已可用软件。

```text
hw_open(expected_abi)              -> handle 或明确错误
hw_get_info()                     -> build/abi/config
motion_get_status()               -> 一致状态快照
motion_disarm()                   -> 请求撤销许可并核对状态
motion_begin_session(session)     -> 当前 epoch，只有禁能时允许
motion_clear_fault()              -> 清理结果，不自动 ARM
motion_arm(session, epoch)        -> 就绪结果
motion_submit(command)            -> accepted/rejected + seq + reason
audio_get_latest_snapshot()       -> 完整音向结果与窗口序号
hw_close()                       -> 释放软件资源；不能替代硬件租约
```

B 的视觉误差、死区、目标选择和身份逻辑留在软件。硬件保留最终范围和变化率上限，因此软件正常限速和 PL 最终限速可以同时存在，但二者的单位、限制值和叠加效果要记录。

软件访问按所选平台使用匹配驱动、UIO 或 XRT 方式。不要把未经核验的 `/dev/mem` 物理地址访问作为统一入口。初版可以轮询状态，但必须有明确条件和超时，不能用固定 sleep 认定硬件已完成。

## 13. 怎样证明 FPGA 的作用

### 13.1 运动监督的贡献

展示相同场景下，PS/主机忙、应用退出或命令停止更新时，硬件仍按自己的时基撤销许可。报告接受后超时边界、停止输入到数字输出响应和波形抖动，并注明测量设备。

对比用相同故障输入和相同目标规则。它证明独立监督和确定性输出的效果，不证明“只有 FPGA 才能控制舵机”，也不等于完整形式化机械安全证明。

### 13.2 音频运算的贡献

相同录音、窗口、候选 lag、定点规则和输出判据，在 PS 参考与 PL 上对比。分别记录核心计算和包含数据读取的端到端耗时。

| 版本 | 正确性 | 核心耗时 | 端到端耗时 | LUT/FF/BRAM/DSP | 备注 |
|---|---|---|---|---|---|
| PS 参考 | 待测 | 待测 | 待测 | 不适用 | C 提供参考 |
| PL 串行/复用 MAC | 待测 | 待测 | 待测 | 待测 | 首版结构 |
| PL 优化版（若有） | 待测 | 待测 | 待测 | 待测 | 说明改了什么 |

当前短窗算法运算量不大，PS 可能已经足够快。若没有明显加速，应如实报告同步采样、CPU 卸载、负载隔离或资源效率的实测收益；不制造加速必要性。

### 13.3 系统创新怎样说清楚

围绕“多人交互中的视听证据质量和时效如何约束实际动作”组织实验。对比仅视觉、增加音向、增加说话人证据、增加时效/拒判后的错选、拒判、确认时间和动作行为。B/C 主导感知实验，你提供硬件证据与异常结果。

PYNQ、DPU、AXI 都是工具和基础，不单独作为本队算法创新。Neural Simplex 的借鉴只能写到实际实现的监督范围。

## 14. 构建和发布流程

### 14.1 最终构建脚本应完成的动作

1. 检查工具与外部依赖版本。
2. 按记录的 commit/配置取得参考平台，应用本队修改。
3. 生成或重建 IP/Block Design，加入 RTL 与约束。
4. 运行对应路线的综合、实现或平台链接。
5. 导出报告、硬件部署工件和必要的软件平台描述。
6. 生成发布清单与哈希；需要模型重新编译时明确依赖。

脚本必须在实际平台上运行后才能标“可复现”。当前不伪造一个无输入依赖、看似一键成功的脚本。

### 14.2 发布包至少包含的关联信息

```text
release_id / source_commit
board_revision / firmware / image_hash
tool_versions / reference_commit / integration_flow
hardware_file_hashes / address_map / pin_map
dpu_configuration / matching_model_hashes
driver_abi / software_commit / calibration_crc
test_result_locations / known_limitations
```

XSA 是硬件平台描述，xmodel 是模型工件；实际是否还需要 xclbin、设备树覆盖、bit/bin、hwh，要由最终路线确定，不要求把所有后缀凑齐。

### 14.3 板端启动顺序

系统和参考驱动可用 -> 按路线加载统一硬件 -> 核对 IP/DPU/模型版本 -> 运动默认禁能 -> 开启采集与检测 -> 状态与界面可观察 -> 明确建立运动会话并使能 -> 进入受控运行。

运动不因 UI 启动或主机返回一句话而自动使能。退出程序时主动请求禁能，同时硬件到期路径独立存在。

## 16. 当前最容易卡住的五件事

1. **烧录成功后找不到同版本参考源码。** 优先获取和重建平台，否则自研 IP 无法真正加入。
2. **把 DPU 工程与 PWM 工程各跑一遍当作集成。** 必须验证最终同配置共存。
3. **接口定义过晚。** B/C 在硬件完成前就需要命令、状态和音向样例；先冻结单位、字段与错误语义。
4. **声音采样还错就开始调方向阈值。** 必须先导出真实 PCM，再核对数值和采样。
5. **你被迫接手全部软件和材料。** A 拥有最终硬件，但 B/C 仍分别负责软件正确性、模型部署和相应实验，交付必须共同完成。
