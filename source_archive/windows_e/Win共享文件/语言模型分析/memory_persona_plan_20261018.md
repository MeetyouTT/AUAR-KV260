# 汐蓝：人设与记忆调整方案

日期：2026-10-18。状态：规划稿，尚未修改在线人设、记忆或推理参数。

## 目标与当前证据

希望汐蓝能持续接住对话、跨重启记住明确事实，保持稳定性格，回答长短适合语音交流。当前后端为 Qwen3.8-27B Huihui破甲版 IQ4_XS；单次历史录音完整语音链路实测7.187秒，多轮文字测试预热后约4.2秒。这些小样本用于比较后续改动，不作为稳定耗时承诺。

当前代码存在以下限制：

- `tools/board_model_host.py` 只保留8条历史消息，约4轮，存在进程内字典中，未落盘。
- 历史按 `board_boot_id + session_id` 分隔；设备或界面重启后生成新会话，无法关联到此前用户。当前最多保留32个会话对象，不等于32位已识别用户。
- `tools/dialogue_host_ollama.py` 的在线fast提示通常要求一两句、最多48个中文字；上下文2048 token、输出120 token。部分说明会被迫过短，输出预算也可能造成JSON不完整。
- `board/runtime/character.py` 定义名字“汐蓝”、描述“DeepSeek 鲸鱼娘”；提示里直接拼接该描述，可能让角色形象与后端身份混淆。
- 助手历史在TTS完成后写入，此时尚未确认HTTP是否超时、板端是否接受或实际播放。取消或失败的回答可能被当作“已经说过”。

## 一、人设：先定义稳定角色，再配置表达风格

建议基线：保留汐蓝名字和鲸鱼娘形象，温柔、自然、有一点俏皮，有自己的判断和兴趣；根据谈话内容给具体回应，减少泛泛安慰和固定口头禅。

将配置拆成以下部分：

| 部分 | 建议内容 |
| --- | --- |
| 核心身份 | 桌面陪伴角色汐蓝、形象设定、角色背景；与实际模型后端信息分开记录 |
| 表达风格 | 温柔程度、俏皮程度、主动程度、回复长短、可用称呼，可分别调整 |
| 相处偏好 | 用户喜欢的称呼、是否喜欢玩笑、是否希望被追问；以用户明确选择为准 |
| 当前状态 | 当前话题、用户本轮表达的心情、正在进行的任务，按时间失效 |
| 实际能力 | 只使用已接入并提供有效结果的录音、视觉、工具和运动能力，不编造“看到”“听到”或“已执行” |

角色背景中的虚构设定应作为设定保存；询问真实模型身份时按实际配置回答，避免自称DeepSeek后端。暂不自行新增年龄、恋爱关系、共同经历等设定；亲密程度、称呼方式可由用户单独配置。

示例目标：用户说“今天有点累”时，可以答“今天很耗神吧。想跟我吐槽两句，还是聊点轻松的？”；避免每次都重复“我会一直陪着你”。用户提出技术问题时，先讲清楚内容，再保留少量角色语气。

统一生成在线fast与其他对话入口的人设提示，避免不同入口各维护一套性格。模型权重保持在项目外 `D:/AIModels`，人设配置是项目代码与配置的一部分。

## 二、记忆：分层存储，按相关性取用

| 层级 | 内容与生命周期 |
| --- | --- |
| 最近对话 | 初始目标8轮，按token预算裁剪；短期落盘，重启后可恢复当前话题 |
| 会话摘要 | 超出最近窗口的重要进展、未回答问题、承诺和待办；包含来源，不将猜测写成事实 |
| 用户长期记忆 | 明确告知的名字、稳定偏好、用户要求记住的事实；跨会话保存，可查看、纠正和删除 |
| 临时情景 | “今天有点累”“正在调试”等短时信息，带时间和有效期，不自动变成永久性格标签 |

第一版使用本地SQLite，先采用结构化字段、标签和可用的全文检索能力，不新增常驻向量模型。只将本轮相关的少量记忆放进上下文，不把整份聊天记录全部送给27B。

建议记录字段：用户标识、记忆类型、内容、来源轮次、用户原话、确认状态、更新时间、有效期。机器提取的候选事实与用户明确确认的事实分开。

写入规则：

1. “记住，我喜欢……”等明确指令优先写入；低把握的ASR专名、日期和数字先确认。
2. 用户纠正信息时替换当前有效事实，旧版本不再参与召回；不根据一次情绪表达推断长期特征。
3. 提供“你记住了什么”“忘掉这件事”“清空我的记忆”等入口；删除需同时覆盖摘要、检索索引和可重新提取的来源，或设置明确的删除标记，防止遗忘内容被自动恢复。
4. 分清“待办/承诺”与“已完成”，只根据实际结果更新完成状态。

第一版先支持一个明确选定的常用用户和访客模式。`boot_id`、会话ID不是用户身份；在身份系统接通前，不凭随口报出的名字自动开放另一个用户的长期记忆。

## 三、对话与记忆处理流程

识别文字 → 确认当前用户 → 取近期对话与相关记忆 → 组合人设和实际能力 → 27B回答 → TTS与板端播放 → 更新本轮状态 → 空闲时提取记忆和更新摘要。

摘要和记忆提取采用独立任务队列，与前台推理串行调度。当前16GB显存余量较小，不在用户等待回答时并行启动第二个大模型；维护任务按短批次执行，前台请求优先。

回答需区分生成、传输、播放完成等状态。第一阶段先防止失败/超时轮次写入正常历史；后续增加板端播放确认，取消或未播放的助手回答不应被当成用户已听到的话。记忆写入按请求ID去重，过期generation不得重复提交。

## 四、上下文与回答长短

- 先对4K上下文做独立性能测试，通过后才替代现有2K；8K作为后续候选，不能直接承诺当前显存足够。
- 每轮按实际token预算分配人设、相关记忆、摘要、近期对话、当前输入和输出空间。历史轮数是目标，不是绕过上下文预算的硬要求。
- 闲聊建议20—60字；解释类60—120字；用户要求详细时再展开，可分段说。现有语音合同限制单次1—240字符和最长30秒WAV，不能直接输出任意长回复。
- 输出预算需覆盖完整JSON，不能仅修改提示词字数；超长回复应在自然句界处理或明确分段，不直接截断结构化数据。
- 首轮先保持温度0.6和现有声线/16步合成参数。只改变人设、记忆和长度策略，测清影响后再调采样参数。

## 五、实施顺序

### 第一阶段：先让角色稳定、对话连续

提取统一人设配置；增加回复长度档位；增加有token预算的近期历史与短期落盘；隔离失败/超时轮次；用4K上下文和现有2K进行同题比较。

### 第二阶段：增加可管理的长期记忆

增加SQLite存储、用户档案、明确记住/纠正/遗忘/查看入口和相关记忆召回。先完成单用户与访客隔离，再接身份识别。增加板端播放确认并完善取消流程。

### 第三阶段：摘要与自然互动

增加空闲时摘要、临时状态过期、待办管理和少量相关主动接话；关系风格仍由用户配置，不随聊天内容自动失控变化。

暂不安排模型微调。先用可回退的人设、记忆与上下文方案解决当前程序层限制，再根据真实样例判断是否需要微调。

## 六、验收标准

- 在不少于20轮、包含干扰话题的对话中，正确接回关键事实和未完成话题。
- 服务/界面重启后，已确认的长期事实仍可召回；访客不能读取常用用户的记忆。
- 姓名等ASR错误经过纠正后不再重复错误；“今天累”过期后不再当作当前状态。
- 明确遗忘后，新会话、摘要与检索均不再召回该条信息。
- 用户询问“我叫什么”与“你是什么模型”时分别正确回答；不会编造共同经历或传感器观察。
- 取消、超时、重复请求及播放失败不会制造虚假的“已说过/已完成”记忆。
- 记录真实端到端延迟、上下文token数、显存峰值和JSON成功率；对照现有27B基线测试，未经实测不承诺新延迟。
- 最后用板端新录音听音验证口语自然度、回复长度、声线与口型，不能以文本测试代替。

本次交付仅为上述规划，当前在线人设、记忆策略与模型参数未修改。
