查过 AMD 模型库、OpenCV、目标跟踪和麦克风阵列的开源项目后，我建议你们采用“现成轻量模型＋传统信号处理＋自己设计的融合与控制逻辑”这套组合，首版不从零训练模型。

以下选择针对你们的条件：KV260、三人、约二十天、固定式玩偶、单转轴、视听交互与身份记忆。它覆盖主要适用方案，但不代表穷尽网上所有算法，也不代表这些算法已在你们板卡上验证。

这里有几个选择需要展开说清楚。

1．人体检测：现在可以明确先试 YOLOX-Nano。

之前我只说“选择现有 DPU 兼容模型”，现在查到了具体候选：AMD Vitis AI 3.0 官方模型表中包含：

pt_yolox-nano_coco_416_416_1G

它是输入为 416×416 的轻量检测模型，官方表中列有 KV260 的测试结果；同一模型库中也有 SSDLite-MobileNetV2，可作为另一候选。AMD 模型性能表、YOLOX-Nano 模型条目

我的建议是：

先下载 AMD 适配版本，核对模型包、运行时及实际 DPU 配置。

先用现成权重，只保留 person 类结果。

测试站立、坐姿、半身、近距离、逆光和两人同框。

如果能稳定完成跟随，就不微调。

注意，过滤掉其他类别通常不会减少神经网络主体的计算量，它主要简化输出和后处理。

如果镜头最终只能拍到近距离人脸，人体检测未必是最佳跟随依据，可以优先用人脸位置；但这要由实际安装画面决定。你们目前还包含找人和多人候选选择，因此我仍建议保留人体检测作为首版。

官方成绩也不能直接当成你们整机帧率：摄像头采集、缩放、后处理和其他任务都会消耗时间。

2．跟踪：先做目标保持，多人遮挡成为实际问题时再加 ByteTrack。

检测告诉设备“这一帧哪里有人”，跟踪负责“下一帧是否还是刚才那个人”。

首版可以用检测框重叠程度，也就是 IoU，进行关联，再增加：

连续几帧确认目标；

当前目标优先；

短暂漏检时保留内部轨迹；

超时或关联不可靠时解除目标。

这里要特别区分：**内部保留轨迹，不等于允许转轴一直追着预测位置运动。**没有新鲜视觉证据时，动作仍需到期停止。

如果两个人交叉、短暂遮挡导致频繁换号，再使用 ByteTrack。它会利用较低置信度的检测框辅助关联，原项目也说明可以接入其他检测器输出，不必连它的检测模型一起使用。ByteTrack 原项目

接入时不要提前删光低置信度框，否则会削弱它的作用。摄像头随转轴运动也会影响关联，需要专门测试。ByteTrack 的轨迹编号仍然不是人的永久身份。

3．人脸和记忆：推荐 YuNet＋SFace，不需要为每个人训练一次。

这两个模型的职责不同：

YuNet 找到人脸和关键点

→ 对齐人脸

→ SFace 提取特征向量

→ 与已登记向量比较

→ 匹配某人，或者返回 unknown

OpenCV 官方提供了这一整套检测与识别示例，比较适合你们快速实现。OpenCV 人脸检测与识别教程

登记新用户时，保存经过质量检查的特征向量和姓名即可，通常不需要重新训练网络。

对你们来说，比更换识别模型更值得投入的是：

匹配不足时拒绝认人；

两人靠近或交叉后重新确认；

识别结果必须属于发起请求时的目标会话；

用户删除后，让在途结果和缓存同时失效。

记忆库先用按身份编号读取的结构化记录，例如“张同学希望回答简短”。十几个人的名字和偏好不需要一开始引入复杂的向量检索系统。

此外，只把数据库搬到 KV260，并不能让身份识别独立运行；人脸检测、对齐和特征提取也必须迁移并通过板端测试。

4．声源定位：短时互相关适合先写成 FPGA 模块，GCC-PHAT 适合做对照。

这部分最适合体现你们自己的数字信号处理设计。

| 算法 | 大致思路 | 对你们的判断 |
|---|---|---|
| 两麦音量差 | 哪边声音大，就认为声音在哪边 | 不建议作主要方向依据，容易受增益和反射影响 |
| 短时互相关 | 比较声音到达两个麦克风的时间差 | 首版 PL 首选，结构较直接 |
| GCC-PHAT | 对频域相关结果进行相位加权，再估计时差 | 软件对照首选；是否更好需要实录比较 |
| SRP-PHAT | 对候选方向计算响应，寻找较强方向 | 本期优先级低，扩大阵列后再考虑 |
| MUSIC 等子空间方法 | 根据阵列信号的空间结构估计方向 | 对双麦三级方向需求而言，实施成本偏高 |

ReSpeaker 提供 GCC-PHAT 的开源实现；Pyroomacoustics 提供包括 SRP-PHAT 在内的阵列处理实现，可用于算法研究和模拟。GCC-PHAT 参考代码、Pyroomacoustics

建议先用同一批双麦录音比较短时互相关和 GCC-PHAT，再决定是否增加硬件复杂度。GCC-PHAT 涉及 FFT、归一化等步骤，不能把 Python 示例直接视为现成 RTL。

首版输出四种状态就够：

左 / 中 / 右 / 无法确定

加上能量门限、峰值质量、连续窗口确认和切换迟滞。双麦不能保证识别同时说话的多人，也不能仅凭一个方向判断人的身份。

5．转轴控制：先用比例控制，不必一开始上完整 PID。

我的工程建议是按“人物偏离画面中心多少”产生转动请求：

横向误差 → 平滑 → 中心死区 → 比例控制 → 指令限速 → PL 执行约束

其中：

中心死区：人物只偏一点时不动，减少来回抖动。

平滑：减轻检测框跳动，但不能设置过强，否则跟随迟缓。

比例控制：偏得越多，调整力度越大。

指令限速：约束每次目标角变化，避免突然大幅转动。

先调好这一套，实测仍然超调再考虑微分项。积分项可能在目标丢失或达到限位时积累，需要额外处理，不是加上就更好。

这属于视觉外环控制；没有编码器时，不应把目标角和指令变化率称为实测机械角度、速度。

6．主动观察：用质量检查和状态机，暂时不用新训练的模型。

建议组合：

帧龄检查：图像是否过期；

拉普拉斯方差或 Tenengrad：提供清晰度线索；

亮度检查：是否严重过暗或过曝；

目标是否仍在画面内；

不满足条件时重新取图，或进行一次受限调整。

OpenCV 介绍了包括拉普拉斯方差在内的清晰度评估方法。OpenCV 清晰度指标比较

清晰度数值受纹理、噪声和图像大小影响，要在固定分辨率和目标区域上标定，不能套一个网上阈值就认定“模型一定看得清”。

7．语音与看图回答：优先复用现成模型，把精力放在交互衔接。

中文语音识别先试 SenseVoiceSmall。sherpa-onnx 已有 SenseVoice 与 Silero VAD 的麦克风示例；但这个示例是在检测到停顿后开始识别，不能直接宣称为逐字流式识别。SenseVoice 麦克风示例

你们首版按键录音、松开提交，可以暂时不加 VAD。语音合成先试现成中文 VITS；若音色或发音不满意，再比较 Kokoro 的中文模型。中文 VITS 模型、Kokoro 模型

看图问答可用 Qwen2.5-VL-3B-Instruct 建立基线；最终选择取决于主机显存、量化方式、图片尺寸及回答延迟。目前不知道你们具体显卡，不能保证某个配置一定流畅。Qwen 官方模型卡

语音模型、视觉语言模型和人脸模型的开源实现，都不等于已适配 KV260 DPU。首版让它们运行在主机，DPU 集中完成已验证的检测任务。

你们最值得自己设计和验证的是下面这段融合规则：

声音方向有效、视觉目标唯一、画面足够新、目标会话一致，才确认交互对象并允许动作；证据冲突时保持或询问。

它可以直接用状态机实现，不需要训练一个“多模态融合大模型”。比较“仅视觉选人”和“视听确认选人”的错选率，再测试冻结画面、两人换位和异步结果迟到，才有证据说明这套设计带来了什么改善。

实际开工顺序建议是：**先跑 YOLOX-Nano＋目标跟踪，再完成 YuNet/SFace；同时用录音比较两种时差算法，确认有效后写 PL。**前两三天就能据此决定哪些候选适合你们的实际摄像头、麦克风和板端环境。
