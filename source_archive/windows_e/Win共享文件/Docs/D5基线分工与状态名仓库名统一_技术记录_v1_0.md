## 1 背景与目标

项目内同时存在**两套可下命令的文档**：D5（`amd_kv260_full_work_requirements_v3.md`，唯一带 W00—W17 工作编号与 T01—T30 验收矩阵，并有 §23 收敛任务）与 A 线框架（`fpga_framework.md`，唯一带 G0—G7 关卡、模块划分、寄存器草案、v01—v11 测试矩阵）。框架 §0.2 自列的优先级清单里**没有 D5**，于是出现"同一件事两套权威"。

由此派生的三个问题必须先定，否则每改一处都要重新争论：

1. **谁说了算**——需求/验收的权威文本是谁；
2. **运动状态叫什么**——现场是**三套**状态名并存，D5 §23.5 判据③（状态名集合唯一）永远不成立；
3. **仓库叫什么**——`fogmirror-kv260`（W17-01 第一版目标）与 `aura`（框架与三份 AURA 计划在用）两套并行。

**目标**：三条一次拍定并落地，使"状态名、编号、命名"各只有一处权威；不改任何性能阈值、不动硬件选型、不动排期。

## 3 状态名三套 → 一套：逐名映射与"降级"处理

**改前并存的三套**：

| 来源 | 状态集合 |
|---|---|
| D1 §10.5 | `RESET_SAFE / NEEDS_REFERENCE / DISARMED / ARMED_HOLD / ACTIVE / FAULT_LATCHED` |
| D5 W17-11（裁定） | `DISARMED / NEEDS_REFERENCE / ARMED / TRACKING / AT_LIMIT / FAULT` |
| 框架 §5.4 | `DISABLED / ARMED / ACTIVE / EXPIRED / FAULT` |
| （附带）D3 §9.3 | 四态，含 `STOPPED` |
| （附带）`aura_plan_a` | `DISABLED/READY/ACTIVE/EXPIRED/FAULT` |

**统一后的处理方式（不是"选一个"，而是把多余的名称降级）**：

| 原名 | 统一后 | 处理方式 |
|---|---|---|
| `RESET_SAFE`（D1） | —— | **降为复位行为**：复位完成后稳定态＝`DISARMED`，不单列为状态 |
| `NEEDS_REFERENCE` | `NEEDS_REFERENCE` | 保留。**无编码器时重启必须处于此态，不得显示"实际角度＝0°"** |
| `DISARMED` / `DISABLED` | `DISARMED` | 框架名改为 D5 名 |
| `ARMED_HOLD` / `ARMED` | `ARMED` | "HOLD"语义不丢：用 `STATUS` 的 `armed`＋`output_active` 两位表达（框架 §5.5 已有该字段） |
| `ACTIVE` | `TRACKING` | 表示"有有效命令在执行" |
| `EXPIRED`（框架） | —— | **降为事件**：许可耗尽时撤销输出许可，回到 `ARMED` 或进入 `AT_LIMIT`（按 D5 转移定义） |
| `FAULT_LATCHED` / `FAULT` | `FAULT` | 锁存；由受控 `CLEAR_FAULT` 清理；种类用 `FAULT_FLAGS` 位区分 |
| `AT_LIMIT` | `AT_LIMIT` | 保留（框架原并入 ACTIVE 会丢"限位"信息） |
| `STOPPED`（D3） | —— | 降为**事件/停止通路动作**，不是独立状态 |

**关键判断**：`EXPIRED` 与 `RESET_SAFE` 描述的是**时刻/行为**，不是**持续姿态**，所以把它们从"状态"降为"事件/复位行为"后语义反而更准，同时框架原文的两个词仍可出现在事件日志与注释里。
