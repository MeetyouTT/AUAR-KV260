# AURA 方案 1：USB 一体音频＋视觉说话人定位实施步骤

日期：2026-09-29  
状态：待实施方案；尚未证明 M1A 在本项目 KV260 镜像上可用，也尚未完成实时 Light-ASD 联调。

## 1. 本方案要实现什么

使用一台 EMEET OfficeCore M1A 作为**唯一的对话录音和回答播报设备**，通过一根 USB 数据线连接 KV260。摄像头连续提供人物轨迹；按键录音期间保存与声音对应的视频片段，使用 Light-ASD 基线判断画面里谁在说话，再由现有的唯一运动服务申请转向。舵机仍由项目原定的 FPGA 运动监督和 PWM 控制。

```text
M1A（麦克风＋扬声器） ──USB──> KV260 Linux 录音／播放
                                  │
                                  ├──录音＋视频片段──> Windows：Light-ASD / ASR / VLM / TTS
相机 ──────────────────────────────┘                    │
                                                       └──说话人建议／回答音频──> KV260

KV260 上唯一运动服务 ──有效性检查──> motion_guard_ip（SV）──> 单轴舵机
```

**范围边界：**这条方案通过视频里的说话动作定位人。M1A 的两只内部麦克风没有经核实可分别向 KV260 输出同步原始数据，因此本方案**不完成**原计划中的 `audio_doa_ip`／SV 自研双麦声源方向计算。它可以作为简化版产品路线；如果赛事验收必须包含该项，需要保留或另做原来的双 I2S 麦克风路线，不能用“2 麦阵列”或 Light-ASD 冒充通过。

项目当前基线参见 [第四轮与当前项目对齐记录](AURA_第四轮与当前项目对齐_2026-09-27.md) 和 [C 计划](aura_plan_c_av_interaction_30days.md)。

## 2. 物料和前置条件

| 项目 | 数量 | 用途与条件 |
|---|---:|---|
| EMEET OfficeCore M1A | 1 | USB 录音和播报；厂家标称 USB-C 连接、5 V／0.5 A 输入、16 kHz 麦克风采样；本机 ARM Linux 兼容性须实测 |
| USB-A↔USB-C **数据线** | 1 | KV260 USB-A 主机口到 M1A；不能使用仅充电线。核对包装内线材／转接头 |
| 现有 KV260、相机、屏幕、单轴舵机和舵机独立电源 | 各 1 套 | 沿用项目原有硬件；舵机不由 USB 或 Pmod 供电 |
| 可运行既定 ASR、VLM、TTS 和 Light-ASD 的 Windows 主机 | 1 | 沿用项目的局域网主机方案；模型、依赖和速度仍需实测 |
| 带独立电源的成品 USB Hub | 仅在供电不足时 | 通过正规 Hub 给 USB 外设供电，不制作 USB 电源分线／注入线 |

M1A 是 USB 供电款，没有已核实的独立电源输入。若“USB 数据线＋另一根电源线直接插入 M1A”是硬性要求，**M1A 不符合该接线形式**；用带电源的成品 USB Hub 是可选的外部供电接法。KV260 USB 口额定每口 900 mA、四口合计 2.1 A，必须把相机等 USB 外设一起计入。[EMEET M1A 产品规格](https://emeet.com/en-uk/products/speakerphone-m1a)、[AMD KV260 供电预算](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Powering-the-Starter-Kit-and-Power-Budgets)

## 3. 按顺序实施

### 步骤 0：确定验收口径

1. 在团队需求表里将本路线写为“USB 语音交互＋视觉说话人定位＋SV 运动控制”。
2. 将“SV 双麦声源方向”单列为**未由本方案覆盖**，记录它是否仍为比赛必交项；不要直接删除原需求或把视觉输出改名为声学 DOA。
3. 沿用项目既定职责：A 管 USB／供电与 FPGA 运动部分，B 管相机、轨迹和**唯一**运动请求进程，C 管录放音、Light-ASD、对话与界面。

**完成标志：**一页范围表能区分“已经实现、待实现、不属于本路线”的功能。

### 步骤 1：采购前确认与收到货的首检

1. 向商家确认具体 SKU 为 **M1A USB 有线款**，包装含可传数据的 USB 线或可用的 USB-A 转接头；确认退换条件。
2. 核对商家所称的 Linux 支持指的是**USB 音频录音和播放**。截图中如出现“Linux 需支持 UVC”，不要把它当作音频兼容证据：UVC 通常用于 USB 视频，音频需要查看实际 USB 音频设备是否能被 Linux 识别。
3. 收到后记录型号、USB VID:PID、线材、电流铭牌、设备外观和固件版本（若可读）。
4. 把 M1A 固定在面向来访者的位置，与相机的相对朝向保持不变；麦孔和扬声器孔不要被外壳挡住。转动机构运动范围内要固定 USB 线并留足余量。

**完成标志：**实物与 SKU 一致，USB 线确实能传数据，安装位置与走线照片可复查。

### 步骤 2：在 KV260 上验证 USB 录放音

先不接通舵机动力电源，只启动 KV260、相机和 M1A。

1. 查看 `lsusb`、`arecord -l`、`aplay -l`：同一 M1A 应分别出现录音端和播放端。板端镜像需要启用 Linux USB 音频支持及 ALSA 工具。
2. 按实际声卡编号 `N` 录制约 5 秒普通说话，并回放录音。例如：

   ```bash
   arecord -D plughw:N,0 -f S16_LE -r 16000 -c 1 -d 5 mic_test.wav
   aplay -D plughw:N,0 mic_test.wav
   ```

   `N` 必须从本机设备列表取得，不能照抄固定编号。若设备不接受该格式，先查询实际支持的采样率／声道，再用真实的重采样转换给 ASR，不能只修改 WAV 文件头。
3. 录音时确认没有软件把麦克风声音直接回放到扬声器。检查静音键状态、音量、断开重插和冷启动后的设备识别。
4. 同时连接相机，复测录音与播放；记录 USB 总电流或供电异常。只有出现实际供电不足，才使用带独立电源且不会向上游回灌的成品 Hub。
5. 程序选设备时使用可复核的设备身份，避免声卡编号在重启后变化导致录错设备。

**完成标志：**KV260 实机可录到清晰人声并从 M1A 播放；相机同时工作，至少三次冷启动／重插可复现。

### 步骤 3：先打通一轮按键语音问答

1. 按下 UI 或实体说话键时开始录音；松开时停止并提交。录音期间暂停回答播放。
2. KV260 把录音和 `request_id`、`utterance_id`、会话编号送到 Windows 主机。主机按既定链路完成 ASR、模型回答和 TTS。
3. 回答音频返回 KV260，由**同一台 M1A**播报。播报期间不把扬声器的声音当作新用户提问，也不触发换人或转动。
4. 取消键、主机超时、换会话或用户离开时，使旧请求失效；晚到的回答不得播放。
5. UI 的“听、想、说”状态使用实际录放音事件更新，不仅靠请求发送时间推测。

**完成标志：**真实人声能走完“按键录音→识别→回答→播报”；取消后没有迟到播报。

### 步骤 4：准备连续视频和声音的对应关系

Light-ASD 判断画面中谁在说话，需要**连续的人脸／嘴部片段及对应时间段的声音**，不能把一张照片重复当成视频。

1. 相机采集由 B 的唯一采集进程负责。每帧附单调时钟时间、帧序号、轨迹 ID；保存有限长度的人脸片段。
2. 录音由 C 的采集进程保存采样率、首尾时间、样本数、音频设备身份和会话编号。
3. 用画面能看见、音频能听见的同步事件做数次测试，测出 USB 音频与视频的时间偏移；长时间运行后复测漂移。保存原始片段与对齐记录。
4. 对齐不可靠、缺脸、缺音、画面过旧或说话人不在画面时，结果标为 `UNKNOWN`；此时不根据 ASD 自动换人。

**完成标志：**任意一段用于 ASD 的音频和视频，都能追溯到同一会话、时间窗口和人物轨迹；有实测偏移及失败样例。

### 步骤 5：先离线、再实时接入 Light-ASD

1. 先用已知对齐的视频与声音跑项目选定的 Light-ASD 预训练基线，记录模型版本、权重来源、输入要求和每个人物的分数。
2. 测试一人说话、两人轮流、两人同时、沉默、遮挡和画面外说话；不要把“看见一个人”直接当成“他正在说话”。
3. 离线样例通过后，再将有时间戳的短片段从 KV260 发给 Windows 服务；限制窗口长度、排队数量和候选人数，测量窗口等待、网络、推理、回传的总延迟。
4. 只在当前交互会话内使用结果。结果返回时再次核对轨迹是否仍可见、会话是否改变、证据是否过期。多人分数接近时给出歧义或 `UNKNOWN`。

**完成标志：**至少能提供逐人、逐时间窗的真实 ASD 输出及失败记录；主机变慢时旧结果不会变成新的控制依据。

### 步骤 6：接入唯一运动服务与 SV 控制

1. C 的视听逻辑只提交“候选轨迹 ID＋说话证据＋有效时间”，**不直接写 FPGA 寄存器**。
2. B 的唯一运动服务结合当前相机位置、轨迹新鲜度、候选唯一性、机构安定状态和会话编号，决定是否请求转向。
3. A 的 `motion_guard_ip` 继续检查许可、角度范围、命令序号、超时和停止输入，输出受约束的 PWM。M1A 不参与舵机供电或 PWM。
4. 先在模拟目标／断舵机动力条件下核对寄存器与波形；再在轻载、小角度范围内验证实体转动。实体停止键独立于语音和主机服务。

**完成标志：**真实说话人被确认后，设备可朝对应视觉轨迹转动；过期、歧义、取消、停止和越界场景不发生错误转动。

### 步骤 7：整机回归和演示

至少覆盖以下场景，并保留音频、视频时间戳、轨迹 ID、ASD 输出、运动请求及拒绝原因：

| 场景 | 应看到的结果 |
|---|---|
| 单人按键提问并回答 | 问题被识别，M1A 播报，字幕和状态一致 |
| 两人轮流提问 | 每次回答和当前会话、正确视觉轨迹绑定 |
| 两人同时说话／同屏歧义 | 输出不确定，不盲目切换或转动 |
| 设备正在播报 | 自己的播音不触发新问题或换人 |
| 相机短暂丢人、主机延迟、旧结果返回 | 旧证据被拒绝，不驱动轴 |
| 音频 USB 重插／冷启动 | 设备能重新识别；失败时有提示，不误用别的声卡 |
| 取消和实体停止 | 旧回答不播报；运动停止链独立有效 |
| 连续运行 | 先做 30 分钟联合检查，再按项目最终测试要求做长时间运行并记录故障 |

## 4. 采购和项目决策结论

- **若目标是最少硬件、尽快做出能说话和朝说话人转向的演示：**先按本方案购买并验证 M1A。正式下单前仍以实物可退换和 KV260 Linux 录放音实测为关卡。
- **若必须提交自研 FPGA 双麦声源辨位：**本方案只能承担对话音频与视觉选人，不能替代原 `audio_doa_ip` 验收；最终仍需增加可向 PL 提供两路同步原始声音的麦克风输入路线。
- **没有额外音频 PCB 打样：**本方案的音频硬件只有 M1A 和它的 USB 线；供电不足时才加成品有源 USB Hub。相机、舵机及其电源沿用既有项目配置。
