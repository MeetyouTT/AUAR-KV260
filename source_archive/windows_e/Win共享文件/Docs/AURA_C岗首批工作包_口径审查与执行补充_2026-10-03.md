## 1. 审查结论

原审查的主要方向成立：真实录放、板端实屏、请求归属、模型功能探针、环境锁和真实证据，确实是当前方案要求；ffmpeg、FastAPI或某一个CUDA/PyTorch版本没有被手册直接指定为统一安装标准。

## 3. 对原审查①：C01／C02、MCP01和音频依赖

### 3.1 原判断正确的地方

- MCP01必须有真实实物、数据连接、输入与输出证据；来源不明的WAV文件不能替代板端录放。
- 先区分工具缺失、驱动缺失、设备未枚举、权限错误和格式不支持；不能把它们混成一个“音频坏了”。
- PetaLinux不能直接套用Ubuntu的安装方案；目标包及驱动由A按实际镜像补齐，C提供精确需求与故障信息。
- 原生Windows、WSL或容器需按实际后端支持确定执行路线，不能把不同环境的测试结果拼成一个通过结论。
- 尚未测得的显存、加载时间或推理耗时应保留未知。

本地依据：C01行724—739；C02行745—765；§8.2行1114—1118。

### 3.2 不能把C01整体理解为“等MCP01到场才能做”

| C01中的子项 | 是否必须有MCP01实物 | 当前可以怎样推进 |
|---|---|---|
| MCP01型号、线材、实际输入输出和照片 | 是 | 实物在场后核验 |
| Windows CPU/RAM/GPU/驱动和运行环境 | 否 | 在目标主机盘点，不用开发者另一台电脑的数据代替 |
| 已有代码、模型文件、权重hash及许可证 | 否 | 对实际文件登记来源、版本与状态 |
| 后端参考样例、模型独立功能探针 | 否 | 用可追溯的固定真实音频、图片和中文文本；签收时再接真实MCP01链 |
| C04协议、取消与迟到注入样例 | 否 | 可先用明确标注的fixture实现协议行为 |
| 板端真实录放及设备重插 | 是，还需KV260目标镜像 | 对应C02，不使用其他声卡冒充通过 |

设备阻塞应落实到具体子项。否则C的模型、协议和环境盘点会被不必要地整体停住。多个模型若依赖互不兼容，可以在同一已验证运行路线中采用分开的模型环境和进程；每个环境分别锁定，并验证进程间接口，不能只提供一份与实际部署不符的合并依赖清单。这是实现建议，不是手册已经规定的具体部署。

### 3.3 U01—U05不能全部算在C02一个包里

| 证据 | 对应任务 | 实际证明什么 |
|---|---|---|
| U01 | C02，A协助 | 指定MCP01在板端真实输入与输出、设备身份 |
| U02 | C03 | 实际格式转换、重采样、样本数和时长一致 |
| U03 | C02，B/A配合 | 相机与音频实际并发，不掉设备、不掉音 |
| U04 | C02，A配合 | 冷启动、拔插后稳定定位，不误选其他声卡 |
| U05 | C03 | 半双工、自播音抑制、按键先停旧播报再录 |
| U07 | C10，B共同负责 | 物理声画偏移、长时间漂移、失效后拒判 |

U01—U05是完整基础音频链的硬要求；“第一批先得到一次真实录放”与“上述五项全部完成”不是同一个阶段。U06全双工/AEC仍为后置项，不能追加为当前开工阻塞条件。

### 3.4 ffmpeg需要按选定代码判定

**对MCP01板端USB/ALSA录放而言，手册没有直接要求ffmpeg。** 真实设备格式探测、录放、必要的转换和缓冲行为必须实现，具体采用哪个可用库或工具可由C选定。是否使用ffmpeg，不影响U01—U05是否必须通过。

但**对原样复用的Light-ASD作者演示而言，不能称ffmpeg完全自由**。本次核读作者main分支的`Columbia_test.py`，看到它通过外部命令调用ffmpeg进行抽帧、抽音频、裁剪和音视频合成。当前C09又要求先跑作者demo。因此，采用这条原样路线时，外部ffmpeg程序及实际媒体处理功能就是该路线的运行依赖。[Light-ASD作者演示源码](https://github.com/Junhua-Liao/Light-ASD/blob/main/Columbia_test.py)

C应先固定作者commit，再做以下记录：外部ffmpeg是否需要、实际可执行路径与版本、演示使用的命令功能是否可用、输入输出是否正确。仅安装一个同名Python包不能证明外部命令已经可调用，这是由该源码的调用方式得出的判断。

如果改为直接接受B的连续脸和C的PCM，或用其他媒体处理库替换作者演示流程，ffmpeg可以不再是该部署的依赖；但须记录适配代码版本，并验证预处理、时序、输入张量和模型结果。不要把“依赖可替代”写成“功能可以省略”。外部作者main分支的事实也不能代替对项目实际固定commit的检查。

## 4. 对原审查②：C04字段样例

原审查对字段归属、二进制媒体、取消/目标换代/超期拒绝和重复请求幂等的理解正确。不过，“列出字段”只完成了协议设计的一部分；C04还要求板端客户端、阶段事件、有限队列、网络故障和取消行为。

### 4.1 应补成可执行的协议包

| 部分 | 至少明确的细节 | 验证做法 |
|---|---|---|
| 协议及服务身份 | release、protocol_version、主机项目身份、支持能力、服务重启代次 | 错项目、错版本、主机重启后旧事件分别注入 |
| 请求归属 | board_boot_id、session_id、request_id、generation、utterance_id及各字段作用域 | 两轮交错返回，旧轮音频/字幕不得进入新轮 |
| 目标与图像 | camera_epoch、frame_id、track_id/track_generation、尺寸、编码、hash、源时间语义 | 目标离开或编号复用后，旧结果拒绝 |
| 音频 | 硬件与模型真实格式、声道、sample_count、字节数、media hash、长度限制 | 格式/字节数/时长不符时明确报错；不靠改WAV头伪装重采样 |
| 字段类型 | 字符串/整数、必填/可空、枚举、单位、宽整数的JSON表示 | schema校验正常例与缺字段、非法值例 |
| 媒体载荷 | 小元数据与二进制的对应方式、大小上限、编码/校验及缓冲所有权 | 文件hash不匹配、载荷超限、缓冲释放后使用均拒绝 |
| 期限与时间 | 板端deadline、剩余预算、主机本机耗时、板端回包后再检查 | 禁止直接相减两机monotonic；排队超时与回包迟到分别测 |
| 事件与音频段 | 阶段枚举、段号、顺序、结束、错误、重复丢弃、缺段超时 | 重复/乱序/缺段/DONE提前注入 |
| 幂等 | 相同请求的重复提交处理；相同标识但不同载荷的冲突处理 | 不重复启动或播放已处理的同一请求；冲突返回明确状态 |
| 取消 | 本地generation先失效，清应用及设备队列，异步通知主机 | 不等主机ACK停声；迟到字幕、音频与口型均不能复活 |
| 资源与重连 | 问答与ASD各自队列上限、并发、优先级、有限重试和断连恢复 | 过载不无限积压；重连不重放历史输出 |

这些是依据C04、C07、§6与§8.3整理的交付细化，具体字段拼写、枚举和接口方式仍应在正式I05/I07中冻结；本报告不宣称对应代码已经存在。

### 4.2 首批建议固化的测试样例

1. 一轮合法音频＋当前图请求，收到关联一致的转写、回答、音频和结束事件。
2. 同一request重复提交，收到已知状态或同一结果，不重复播放。
3. 相同请求标识但媒体hash不同，按冻结的冲突规则拒绝。
4. 旧generation回复在新轮已开始后到达，丢弃全部旧输出。
5. 错boot/session、错协议、目标track_generation变化，分别拒绝。
6. 排队超时、执行超时、板端deadline已过，分别记录失败阶段。
7. 重复音频段、乱序、缺段及超大载荷，资源使用有上限。
8. 取消发生在上传、排队、推理、下载、应用播放队列和设备已缓存阶段。
9. Windows退出或网络断开后恢复，只允许新的有效请求恢复交互。
10. 图像/音频格式错误、模型未ready、设备丢失，错误原因可定位。

建议交付目录含schema、正常/异常元数据、独立二进制媒体、预期行为和运行记录。手册中的伪代码明确是逻辑骨架；原审查“骨架字段已就位”若是在描述实际代码，应附该实现版本和样例，不能以手册示例代替完成证据。

## 5. 对原审查③：C08板端实屏

“PC页面不能替代KV260实屏”“先静态中文，再状态，再动画/字幕，最后并发”的顺序正确。但要补充两个层次。

### 5.1 原手册本身的术语应修正

C08行903写“Qt/SDL/DRM等择其一”。这句话把不同技术层次并列，原手册也需要修订。Qt和SDL属于应用界面/绘制路线，DRM/KMS是Linux显示底层接口；Qt可以通过相应平台插件与KMS/DRM组合，不能把三者理解成互斥、同层的框架。[Qt嵌入式Linux文档](https://doc.qt.io/qt-6.8/embedded-linux.html)

建议替换成：

> A提供最终平台的真实显示通路、驱动、模式和权限；C在该目标镜像上冻结一套经过最小出图验证的“界面框架＋平台/显示后端”组合，列明目标库、平台插件、字体资源及所需显示服务器或compositor。候选可包含Qt、SDL或浏览器等，但是否可用及实际版本以目标镜像验证为准。

这里引用Qt文档仅用于核对技术层次，不表示KV260/PetaLinux 2022.2已经具备Qt 6.8，也不推荐直接升级该版本。

### 5.2 静态图只放行显示基础

| 阶段 | 必须证明 | 可以签收什么 |
|---|---|---|
| 显示基础 | 最终屏幕、最终平台、实际驱动/模式/权限、中文资源能出图 | 显示开工前置；不能直接签收完整C08 |
| UI功能 | 真状态、按钮/取消、目标选择、登记/删除结果、字幕及播放器驱动口型 | C08功能部分 |
| 故障及并发 | 显示恢复不呈现旧事件，UI不占相机/运动锁，音频/相机/DPU同时运行 | C08并发与恢复部分 |
| 最终验收 | 实屏事件时延、真实播放与口型、T25及相关J/T证据 | 最终C08与整机对应项目 |

需要冻结的依赖包括目标ARM64应用、与目标rootfs匹配的SDK/库、实际平台插件、字体和资源路径、所需libdrm/EGL等、设备权限及输入路径。所需项按已选组合列出，不要求所有候选依赖都安装。

显示通路未通过时，C可继续协议和原型；实屏签收保留具体阻塞原因。显示或音频与平台相关时，最终必须使用DPU与motion共存的有效配置复测，不能用另一套成功出图的位流替代整机平台。

## 6. 对原审查④：HTTP与主机服务

没有强制FastAPI/Flask/WebSocket，确实意味着传输框架可选择；但API功能、进程结构和并发行为不能留白。

### 6.1 三个路由名不能证明完整服务

`/asr`、`/tts`、`/health`可作为既有单项测试或复用入口。完整问答仍须有可运行的ASR→VLM→TTS路径，并能关联请求、返回阶段/结果、处理取消和错误。VLM可以是内部流水线调用，无需为形式上齐全而额外创建一个叫`/vlm`的路由。

Light-ASD也须有实际可调用的输入/结果通路，是否与问答共用进程或传输方式可以决定。I06负责窗口和对象建议合同；I05/I07负责对应请求、状态和交互。冻结的是功能覆盖和语义，而不只是三个URL的拼写。

### 6.2 READY应按实际能力拆开

- 服务进程存在、监听端口和可通信只证明基础存活。
- 每个必需模型须分别具备工件、加载状态、固定输入探针结果和明确失败原因。
- 问答整体可用要求其所需ASR/VLM/TTS均可运行且实际串联通过；ASD未通过时，问答可以仍可用，但自动说话人建议应显示未就绪。
- 板端音频和实屏的健康状态也要分别展示，不能因Windows模型ready就宣称完整整机ready。
- 健康返回应带当前服务身份、协议、模型/能力状态和错误，避免重启后沿用旧ready。探针不应每次健康查询都完整加载或运行全部大模型。

### 6.3 选择框架还要解决控制响应

重模型任务不能堵住取消、健康、阶段事件和主机握手。建议将接入/控制与有界模型工作队列分开；推理并发、ASD与VLM优先级以及进程数按显存和实际延迟决定。多进程若各自加载模型，也需计入显存预算。

如果选择FastAPI，不能仅写`async def`便认定阻塞模型会自动非阻塞。官方文档区分普通函数的线程池行为与异步函数；实际重模型调用仍要按其执行方式安排工作线程/进程或队列，并测取消、健康响应。这是对本项目的实现建议，不是要求使用FastAPI。[FastAPI异步与并发文档](https://fastapi.tiangolo.com/async/)

## 7. 对原审查⑤：CUDA、PyTorch与模型工件

### 7.1 “是否换CUDA torch”是有约束的决策

手册没有冻结具体PyTorch/CUDA版本，所以不能仅凭方案要求C无条件换包。但是，本次核读的Light-ASD作者`ASD.py`在模型初始化中使用`.cuda()`，其演示对输入也使用`.cuda()`；采用未修改的这条路线时，CPU版PyTorch不是可直接运行的等价环境。[Light-ASD作者模型封装](https://github.com/Junhua-Liao/Light-ASD/blob/main/ASD.py)、[作者演示](https://github.com/Junhua-Liao/Light-ASD/blob/main/Columbia_test.py)

正确的判定顺序是：

1. 固定要复用的源码commit、模型工件和后端。
2. 盘点目标Windows主机的GPU、显存、驱动和实际Python环境。
3. 核对该后端是否要求CUDA、是否有经验证的CPU或其他设备路线。
4. 若原样路线要求CUDA，则核对实际PyTorch构建和GPU可用性，并跑该模型真实固定样例；只成功`import torch`不够。
5. 如果决定做CPU/其他后端适配，记录改动、权重加载、预处理与结果一致性，以及热延迟和资源实测。
6. 选择满足项目功能及冻结性能要求的路线，再固定环境；不以“只记到C01表里”替代通过。

PyTorch官方安装资料分别提供CPU和CUDA路线，并给出`torch.cuda.is_available()`检查；这可以作为基础环境探针，不能代替ASR/VLM/TTS/ASD的实际模型推理。[PyTorch安装与验证](https://pytorch.org/get-started/locally/)

本次未核验目标C岗主机，不提供猜测的torch/CUDA安装版本，也不声称已有GPU足以同时承载四种能力。

### 7.2 C01/C05环境记录至少补这些事实

| 分类 | 记录项 | 成立依据 |
|---|---|---|
| 执行路线 | 原生Windows／WSL／容器及其实际版本、每个模型的环境位置 | 真实运行入口与系统信息 |
| Python环境 | Python版本/路径、环境标识、直接与传递依赖、锁文件 | 该入口实际使用的解释器和包清单；非另一终端的环境 |
| GPU环境 | GPU型号、显存、驱动、后端设备支持、实际模型运行位置 | 环境探针＋真实模型调用；未知项保留未知 |
| PyTorch路线 | 实际torch版本、CPU/CUDA构建信息、相关音视频/处理器依赖 | 后端兼容检查及样例推理，按所选后端填写 |
| 外部程序 | ffmpeg等是否被代码调用、路径/版本、必要功能 | 固定代码依赖扫描＋实际处理样例 |
| 模型 | ASR/VLM/TTS/Light-ASD各自model_id、源码commit和工件manifest | 文件hash、来源、许可证、参考样例 |
| 能力预算 | 冷加载、热推理、峰值RAM/显存、输入上限、并发/队列上限 | 固定样例与真实并发，冷/热分列 |
| 启动及复现 | 启动入口、配置位置、模型加载/失败/退出、功能探针 | 板端真实调用与非作者复现 |

依赖并非都必须是表中示例的包。采用其他后端时，填它的实际依赖；采用PyTorch时，不能因为手册未点名包版本就略过兼容与锁定。

### 7.3 权重hash不能代表完整可运行模型

应将权重、分片及索引、配置、tokenizer/processor、词典、预处理、模型代码/后端版本、许可证和样例共同归档；具体需要哪些工件按所选模型决定。Qwen2.5-VL官方示例同时涉及模型与AutoProcessor及视觉输入处理，说明仅有权重文件不足以描述完整推理环境。[Qwen官方模型卡](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct)

Light-ASD演示还包含额外的人脸处理路径；项目若直接使用B提供的连续脸，须验证替换后的输入一致性，而不能把作者整段离线demo的所有处理假设直接套成实时方案。ASD的窗口、同步、上下文和延迟另由C09—C11闭环。
