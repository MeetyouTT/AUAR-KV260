## 一、项目摘要

本项目研制一台放置在桌面或展台上的固定式智能交互终端。设备通过摄像头感知来访者，通过麦克风接收语音，结合豆包视听服务完成自然对话与现场问答，并以语音、字幕和屏幕玩偶表达交互状态。用户移动时，设备通过有限角度的水平转轴调整朝向，使摄像头及交互正面面向当前用户。经本人确认登记后，系统能够在用户离开并返回时恢复其身份，进行个性化问候。

作品以 AMD Kria KV260 为设备主控。ARM 处理系统负责采集、跟踪、场景状态、对话会话与界面；可编程逻辑中的 DPU 承担经过适配的视觉神经网络推理；团队自研 FPGA 逻辑完成转轴 PWM、指令限幅、看门狗、停止输入、故障锁存与时间戳。豆包服务提供开放式语言与视觉理解，运动执行始终由设备本地控制链决定。

项目的技术价值是形成一条可测量的闭环：**本地视觉感知 → 用户与场景状态 → 交互决策 → FPGA 实体转向 → 新画面反馈**。计划通过同源模型 CPU/DPU 对比、运动控制时序对比、场景问答测试和故障注入，证明软硬件划分的实际效果。

本次调整保持原 V3.4 的产品方向，替换平台相关实现：FMQL30TAI、ICraft 与原 NPU 工程退出新基线，改用 KV260、AMD 工具链和 DPU。视觉身份记忆、场景理解、Windows 开发、动态玩偶和有限角度旋转继续保留。依据用户本次“豆包视听模型”的表述，本文默认正式接入豆包相关云端服务；若实际意图仅为“类似豆包的体验”，可替换对话适配器，上层功能与本地闭环保持一致。

### 1.1 建议申报名称

**正式题目：基于 AMD Kria KV260 的固定式多模态交互与视觉随动系统**

产品名称继续使用“雾镜 Lite”。“固定式豆包视听终端”可作为体验说明；申报中说明豆包为接入服务，不暗示项目与其存在官方合作，也不把云端模型称为在 KV260 上部署的模型。

### 1.2 典型使用过程

1. 来访者进入视野，设备识别人形目标，玩偶进入关注状态。
2. 设备以受限速度转向该用户，保持目标处于画面中心附近。
3. 用户提问，设备结合当前图像、结构化场景和语音内容回答。
4. 用户说“记住我，我叫小林”，设备确认目标唯一且本人同意后登记身份。
5. 用户离开后再次出现，系统通过人脸特征恢复已登记身份并问候。
6. 用户可按键取消播报、关闭跟随或使转轴进入安全状态。
7. 网络断开时，设备保留本地检测、跟踪、转向、界面和基础提示；界面明确显示自然对话暂不可用。

### 3.2 功能优先级

| 层级 | 功能 | 完成含义 |

| P0-I 产品交互 | 自然语音问答、当前画面问答、语音与玩偶同步 | 接入实际服务并通过端到端测试，不能仅以模板播放代替 |
| P0-M 身份记忆 | 知情登记、离场重识别、unknown、删除和纠错 | 不重训目标检测器即可登记；明确推理运行位置 |

### 3.3 三种运行状态

| 状态 | 组成 | 展示口径 |

## 四、总体架构与数据流

### 4.1 软硬件分工

```text
摄像头 ─→ KV260 PS 采集 ─→ 图像预处理 ─→ PL DPU 人员检测
                                         ↓
                             PS 后处理、跟踪、目标选择
                                         ↓
                          SceneState + 人员会话 + 短时记忆
                          ↙              ↓              ↘
                 身份匹配/登记      视觉伺服控制器        带时间戳的图像/场景
                     ↓                  ↓                       ↓
                 IdentityStore    AXI-Lite 自研 motion IP   豆包服务适配器
                     ↓            限幅/PWM/停止/看门狗      ↑             ↓
                 个性化问候              ↓              麦克风       回复/语音
                                  舵机 + 承重转盘          ↓             ↓
                                         ↓                会话管理与输出校验
                                     新画面反馈                  ↓
                                                       扬声器 + 屏幕玩偶
```

| 执行位置 | 分配任务 | 原因 |
|---|---|---|
| KV260 ARM PS | USB 采集、预后处理、跟踪、场景解释、身份数据库、会话、UI、驱动 | 规则与服务适配变化频繁，适合软件实现 |
| KV260 PL 内 DPU | 兼容的人员检测网络推理 | 处理卷积密集运算，以实际速度/精度/资源比较验证收益 |
| KV260 PL 自研 IP | PWM、速度约束、指令时效、看门狗、停止锁存、遥测 | 在 Linux 忙碌或进程故障时仍维持可预测行为 |
| 豆包云端服务 | 通用对话、图像语义理解、所选语音能力 | 保留自然视听体验；具体 API 和模型权限需工程验证 |
| Windows 开发机 | PC 参考、模型验证、数据处理、UI 联调、可选过渡服务 | 缩短迭代时间，性能结果与板端分开记录 |

**架构事实：**K26 的 DPU 是配置在 PL 中的神经网络加速 IP，不是额外的一颗独立 NPU，也不是 Versal AI Engine。DPU 和转轴 IP 的 LUT、FF、BRAM、DSP、时钟与带宽必须合并核算。[R2、R4]

### 4.2 核心接口

| 接口 | 必要字段 | 处理约束 |
|---|---|---|
| frame_packet | frame_id、capture_ts、分辨率、像素格式、有效期 | 保留原始采集时间，不用处理完成时间冒充 |
| detection_packet | frame_id、bbox、class、score、model_id | 跟踪器不能混入不同模型/尺寸下未转换的框 |
| scene_state | scene_seq、capture_ts、tracks、target_id、session_id、motion_state、ttl | “当前画面”与“近期事件”分开；过期不驱动动作 |
| identity_state | person_id、track_id、状态、得分、model_id、revision | track_id 与持久 person_id 不等价 |
| dialogue_request | request_id、audio_generation_id、scene_seq、frame_id、user_text | 图像与场景绑定；发出前检查时效和分享状态 |
| dialogue_result | request_id、scene_seq、文本、有限表情、语义意图 | 只允许白名单意图；不接受角度、PWM 或清故障命令 |
| motion_command | seq、目标角、有效期、预期 safety_epoch | 单写入者；陈旧、重复或不匹配命令被拒绝 |
| board_status | applied_seq、commanded_angle、fault、limit、heartbeat_age、timestamp | 未装角度传感器时只显示指令角 |

摄像头图像是外部输入。画面中的文字、云端返回文本或用户随口给出的参数均不能修改设备配置、调用任意工具或直接写 FPGA 寄存器。

## 五、KV260 硬件与工具链方案

### 5.1 硬件配置

KV260 视觉载板具有 USB、以太网、HDMI/DisplayPort、microSD、Pmod 等接口；实际使用按载板修订版和 UG1089 核对。[R2、R3]

| 部件 | 首版方案 | D1—D3 核验内容 |
|---|---|---|
| 主板 | KV260 + K26 SOM + 原配散热 | 器件型号、载板修订、启动固件、风扇与电源 |
| 存储 | 匹配镜像的 microSD，另备恢复卡 | 卡容量、镜像校验、启动与恢复记录 |
| 摄像头 | USB UVC，初始 640×480/30 fps，按实测提升 | 格式、缓存延迟、曝光、弱光；首版避免额外 MIPI 驱动工作 |
| 音频 | USB UAC 麦克风/声卡与扬声器 | 同录同放、采样率、时钟漂移、扬声器串音 |
| 显示 | 现有屏幕优先，按实际 HDMI/DP 与驱动适配 | 分辨率、供电、线长、板端显示路径、UI 负载 |
| 转轴 | 单水平舵机 + 独立承重轴承/转盘 | 扭矩、空回、堵转电流、转角和线缆阻力 |
| 控制接口 | 经确认的 Pmod/PL IO → 缓冲/电平适配 → 舵机控制 | 管脚约束、IO 电压、输入阈值；未确认前不接负载 |
| 停止/确认 | 外置可触及停止键，另设确认/交互键 | 不复用系统复位或固件更新键作为日常用户按钮 |
| 电源 | 主板按手册供电，舵机独立支路 | 限流、保险、地参考、去耦；禁止从 GPIO/Pmod 电源脚直接供舵机 |
| 网络 | 有线以太网优先 | 不假定板载 Wi-Fi；现场接入方式另记录 |

外壳内优先固定主板和电源，将摄像头、屏幕等需要面向用户的轻量组件放在旋转部件上。若沿用整体旋转设计，先称重、估算惯量与线缆阻力再选舵机。舵机输出轴不承担整机轴向载荷。

现有外壳资产需重新审核安装柱、风道、风扇净空、接口开口、维修空间及转动时的线束路径。本计划不将旧 FMQL 安装空间视为已经适合 KV260。

### 5.2 工具版本：采用可复现的兼容组合

AMD 官方 Vitis AI 3.0 兼容表给出的验证组合是 **Vitis AI 3.0 + DPUCZDX8G IP 4.1 + Vivado/Vitis/PetaLinux 2022.2**。[R5] 竞赛指南允许在说明理由并保证复现的前提下采用其他工具版本，因此首版以该历史验证组合为候选基线，不把最新版 Vivado 与旧 DPU、旧镜像任意混装。

| 环境 | 候选基线与用途 |
|---|---|
| Windows 11 | 既有 Python/视觉参考、HTML UI、数据集与算法开发；GPU 框架单独锁版本 |
| Linux 构建环境 | 符合所选 AMD 版本支持矩阵的 x86_64 Linux；构建 DPU 平台、板端镜像与模型工件 |
| KV260 板端 | 优先与官方 KV260 Vitis AI 3.0 参考设计匹配的镜像、固件、驱动、VART |
| 快速验证备选 | 匹配版本的 Kria/PYNQ 工程，仅在 DPU 与自研 IP 能共同构建后成为正式基线 |

D1—D3 检查历史安装包、IP、许可、示例与模型下载是否可获取。若已拥有一个经验证的新版本 KV260 工程，优先复用该完整组合，记录差异；不为迁移版本本身消耗整月。WSL2 可用于辅助开发，但不预设其等同于 AMD 对完整构建流程的官方支持环境；JTAG、USB 与板端烧写另做验证。

必须输出 `toolchain_lock.json`：工具补丁、OS、镜像来源与校验值、boot firmware、平台 commit、DPU 配置及 fingerprint、编译器、VART、设备树、模型哈希、自研 IP 版本。GPU 训练环境与历史 Vitis AI 量化环境分开，不要求 RTX 5090 在旧量化容器中直接可用。

DPU-PYNQ 官方仓库当前标记归档，其文档给出 PYNQ 3.0 / Vitis AI 2.5 的组合。[R6] 因而 PYNQ 是可选实现方式，不作为“安装最新版就能运行”的假设；通用 PYNQ Skill 加分也不应压过本体交付。

### 5.3 最关键集成项：DPU 与转轴 IP 共存

1. 先运行官方 DPU 单图样例，确认模型和硬件 fingerprint 匹配。
2. 找到该平台可重建的工程源与脚本，确认包含 PS、DDR、时钟、复位、DPU 和软件接口。
3. 在同一可运行硬件设计中加入 motion IP、AXI-Lite 地址空间、停止输入与中断。
4. 共同生成 bitstream、XSA/相关描述、设备树及匹配运行包；不得加载 DPU 后又用另一完整 overlay 覆盖它来演示转轴。
5. 运行 DPU 推理时同时验证转轴控制、停止链和遥测；额外加入 CPU、USB 与显示负载。
6. D7 前完成共存工程的首次实现与上板验证，D14 前完成连续运行。

若资源或时序不足，先去掉可选视频预处理、调低并发并重新选择 DPU 配置。改变 DPU 配置后重编译模型并重新验证，不能沿用架构不匹配的 xmodel。若 D7 仍无法获得可重建 DPU 工程，可短期用 PS CPU 检测 + 自研 PL 控制保持产品联调，同时将“DPU 部署未完成”列为红项；它不自动变为已完成加速的正式版本。

## 六、视觉感知、场景与身份记忆

### 6.1 人员检测与 DPU 模型

首选**所选 Vitis AI 版本 Model Zoo 中提供 KV260 目标工件的轻量检测模型**；候选方向为小型 YOLO 或 SSD 系列，但必须在 D3 前冻结到具体可下载的文件。原 ZG YOLO11 不直接移植，不以“ONNX 能导出”作为 DPU 兼容证明。[R4、R7]

主/备模型分别记录：来源、commit、权重文件、许可、输入尺寸、RGB/BGR、归一化、类别顺序、输出张量、阈值、NMS、量化方式、DPU 架构和 CPU fallback 子图。若所选量化器不直接接收现有 ONNX，应按该版本支持的 PyTorch/TensorFlow 流程导入；禁止预设通用 ONNX 一键转换。

处理链：摄像头 → 缩放/letterbox → DPU → 后处理 → person 框 → 跟踪。检测帧率与摄像头帧率分开报告；忙时丢旧帧，避免排队导致转轴追赶过去的画面。

数据采用有授权的本地室内场景：正面、侧面、多人、遮挡、弱光、转动模糊。建议校准集不少于 200 张，独立测试集不少于 200 张且包含不少于 300 个 person 实例；不同人员/视频片段分组隔离，不能将相邻帧分别作为校准和测试来夸大效果。数量是本项目计划值，不是赛事硬门槛。

### 6.2 跟踪与面向控制

- 沿用 ByteTrack-Lite 高低分两阶段匹配；复杂度或稳定性不满足时使用 SORT 基线。
- 首版一次只跟随一个主目标。按画面位置、框大小和持续存在时间评分，设最小锁定时间与切换裕量，避免多人之间频繁摆头。
- 使用 One Euro 或 EMA 抑制框中心抖动；两者比较后冻结，不预先宣称某种滤波一定更优。
- 横向归一化误差 `e = (cx - W/2)/(W/2)`；经死区后得到受限角速度，再按真实时间间隔积分为角度目标。像素坐标不能直接当作舵机角。
- 初始中心死区取画面宽度的约 10%，PS 指令更新目标为 20—50 Hz；增益、正负方向、最大速度及加速度由实物调试确定。
- 短时丢目标先停止继续追赶，不外推无限运动；较长时间丢失进入待机。回中只在允许、安全且收到新本地指令时缓慢执行。
- `presence_zone` 为画面交互区域，`tracking_deadzone` 为不转动区，`motor_limit` 为机械约束，三者不能混为一谈。

### 6.3 场景理解与时效

SceneInterpreter 汇总目标、左中右位置、进入/离开事件、当前跟随对象与旋转状态，保留 10—30 秒的有限元数据。转动期间按 `presence_session_id` 接续人员会话，避免同一人因画面变化重复触发迎宾。

“我、这个人、左边、刚才那个人”等指代只在目标唯一且有效时解析。多人歧义时请求重新指明。当前物体属性可由豆包视觉理解输出，但姓名只来自已确认的身份库；无法从当前图像验证的陈述不写成确定事实。

向云端发送帧时记录拍摄时间与 frame_id，匹配同一时刻的 scene_seq。初始当前画面有效期取 1 秒，按网络实测调整。若回复返回时场景已变化，允许表达“刚才画面中……”，禁止将旧画面中的目标直接转化为当前运动指令。

### 6.4 身份登记与重识别

保持 V3.4 的分工：人员检测找人；人脸检测与对齐找可用人脸；embedding 模型将人脸转换为特征；数据库负责持久身份。新增人员是登记模板，不是重新训练 YOLO。

**实现顺序：**Windows 已有参考可复用但先审查实际完成度 → 同模型板端 CPU 验证 → 低频、按需身份识别 → 仅在有收益和资源时考虑 DPU 迁移。人脸特征模型采用经许可核验的轻量方案；ArcFace 是特征学习方法，不能代替具体权重的许可说明。

**登记事务：**用户命名 → 确定唯一目标与人脸 → 质量检查 → 明确确认 → 采集多帧模板 → 原子写库 → 返回确认。多脸、模糊、旧目标、超时或取消均不得写入。

**重识别：**阈值与 top1/top2 差距均达标，且多帧一致后显示姓名；否则显示 unknown。持久 person_id 与临时 track_id 分离。初始模板库规模为 5—10 名自愿测试者，满足首版接待演示。

数据库保留 `person_id/name/embedding/model_id/consent/revision`；删除与纠错需要确认并使缓存失效。默认不长期保存原始人脸或连续视频。身份功能定位于交互记忆，不用于门禁或可靠认证；未经活体与攻击测试，不承诺抗照片攻击。

## 七、豆包视听服务、音频与界面

### 7.1 可实施的接入路径

豆包 App 的体验不等于开发接口能力。首版依据团队实际账户可用的官方接口验证以下路径。[R8、R9]

| 路径 | 实现 | 采用条件 |
|---|---|---|
| A：组合式视听链，首版默认 | 语音识别 → 文本 + 当前图像/场景 → 豆包视觉理解 → 流式文字/语音合成 | 各服务已开通，图像输入与板端调用链可验证 |
| B：实时对话式 AI | 使用支持相应语音/视频能力的官方服务，板端负责采集、播放和会话同步 | 账户权限、协议、ARM64 接入及当前版本图像能力均实测通过 |

不把任一“实时语音”接口自动视为同时支持视频输入。若采用 A，应准确描述为“语音加关键帧的多模态交互”；只有完成连续音视频的采集、传输、理解与同步测试后，才描述相应连续视听能力。

D2 前记录 `service_manifest.json`：具体服务名、model_id、版本、区域、协议、音频采样率、图片格式与上限、限流、超时、用量计费单位、认证位置、可用功能及测试日期。当前计划不虚构已获开通的模型版本或实时性指标。

### 7.2 视听同步与带宽策略

默认按需发送关键帧：用户询问现场、目标显著变化或明确触发视觉问答时取新帧，限制采样频率与分辨率。避免将完整 30 fps 视频无条件持续上传。若使用视频流服务，则单列其码率、流控与网络要求。

音频采样格式以真实 API 为准；采集、播放和网络线程独立。系统保存短时必要缓冲，不用无限音频队列填补网络延迟。对话取消时递增 `audio_generation_id`，清理旧文字/PCM 队列，过期返回不能重新播放。

长期 API 密钥保存在设备后端受限配置或已有授权中转服务，不写进 HTML、公开仓库、截图或日志。无需让 Windows 中转的接口优先由 KV260 后端访问；确需中转时声明依赖与故障回退。

### 7.3 打断与本地控制

第一阶段使用轮次式说话和实体键取消；第二阶段再实现 VAD/AEC。USB 同录同放只是硬件能力，不代表已实现可用的全双工对话。

本地 KWS 延续原方案的中文关键词路线，保留“雾镜暂停、雾镜跟随、雾镜待机、雾镜回位”等受控命令；模型来源、许可证和板端延迟另行核验。暂停播报、关闭跟随和硬件停止是三个不同动作，界面与按键说明清晰区分。

扬声器播放期间，只有通过串音误触发验证的 KWS 才能控制运动。未通过 AEC 时使用按键说话、轮次交互或关闭播放期间语音运动指令，不能牺牲停止键和看门狗来追求“全双工”。

### 7.4 云端意图的执行边界

生成式服务只能提出 `focus_target`、`stop_following`、`start_enrollment`、`forget_identity` 等语义请求。PS 校验目标、时间、用户确认和当前状态后才调用本地模块。舵机角度、PWM、速度上限、限位设置、使能和清故障寄存器均不向模型开放。

网络中断或鉴权失败时显示原因，取消等待中的云端回合，继续本地控制；恢复后创建新会话，丢弃旧回复和旧运动请求。联网失败不自动让主轴回中或恢复使能。

### 7.5 动态玩偶与显示

沿用摄像头区、玩偶区和底部状态栏；实际屏幕空间不足时提供“玩偶主视图”和“工程视图”切换。普通用户看到正在听、思考、说话、跟随、停止、离线和身份确认；时间戳、寄存器、模型耗时等放入工程视图。

交互、运动、连接、健康四个状态域并行管理。例如离线时仍可跟随，播报时可能发生停止故障。显示优先级为：停止/故障 → 需要确认 → 当前交互 → 普通动画。嘴部动作跟随实际播放进度，不能只跟随文字到达时间。

HTML UI 优先复用；D3 检查所选板端镜像的显示栈与浏览器可用性。必要时用轻量本地渲染器实现相同状态协议，复杂动画后置。桌面显示器或外接电脑画面不能被标为板端屏幕验收已完成。

## 八、FPGA 转轴控制与机械安全

### 8.1 团队自研逻辑范围

| 模块 | 功能 | 验证方法 |
|---|---|---|
| axi_motion_regs | 指令/配置/状态寄存器与原子提交 | 读写权限、复位值、乱序/重复请求 |
| pwm_generator | 舵机要求的周期与脉宽，初始按常见 50 Hz 方案验证 | 示波器或逻辑分析仪测周期、脉宽和抖动 |
| motion_limiter | 角度边界、速度限制、缓启动 | 边界值、越界值与满幅切换 |
| command_watchdog | 超时与旧指令检测 | 杀进程、停心跳、重放旧序号 |
| stop_fault_latch | 外部停止、故障锁存、人工恢复 | 边沿响应、释放抖动、误恢复注入 |
| telemetry | 单调时间戳、序号、故障原因、计数器 | FIFO 满、状态读取、故障信息不丢失 |

DPU 的贡献准确注明为 AMD IP 的集成、配置、部署和优化；上述控制与安全模块体现团队 RTL 设计。若有额外 HLS 图像核，也必须展示其独立源码、验证及优化收益。

### 8.2 寄存器建议

以下为拟定合同，D4 冻结；寄存器区基地址由实际设计地址分配决定。

| 偏移 | 名称 | 访问 | 用途 |
|---|---|---|---|
| 0x00 | id_version | RO | IP 版本与兼容检查 |
| 0x04 | control | RW | 请求运行/待机；使能受安全状态约束 |
| 0x08 | target_angle | RW | 有符号毫度或统一定点角度 |
| 0x0c | command_seq | RW | 最后写入并触发命令提交 |
| 0x10 | heartbeat | RW | 单调递增心跳，重复值不刷新健康状态 |
| 0x14 | status | RO | 运行、限位、停止、超时状态 |
| 0x18 | fault_latch | RO | 保留故障来源 |
| 0x1c | recovery_request | WO | 请求恢复；输入安全且经过本地确认才有效 |
| 0x20 | commanded_angle | RO | 当前受限指令角，非真实轴角 |
| 0x24 | applied_seq | RO | 最近接受的命令序号 |
| 0x28 | safety_epoch | RO | 安全代次；故障后旧请求失效 |
| 0x2c | expected_epoch | RW | 提交时必须与当前代次一致 |
| 0x30 | timestamp_low | RO | 读取低位时锁存高位，避免跨界读取不一致 |
| 0x34 | timestamp_high | RO | 已锁存的时间戳高位 |

常量限位、最大速度、PWM 标定与超时参数在配置态设定并锁定；运行态与云端不能随意修改。多字段影子寄存器由单一控制进程写入，最后写 command_seq 原子提交；跨时钟域采用握手/同步结构。

### 8.3 安全行为

水平轴采用独立承重且无需持续电机力保持姿态时，首版拟定安全动作为：禁止新运动、硬件使能关闭、PWM 置安全电平并锁存故障。D3 根据实际执行器和机构验证：**停止 PWM 不保证所有舵机断力或立即停止**，如需要切断扭矩须有经过验证的硬件使能/电源门；不得只靠软件假设。

外部停止信号应直接作用于硬件门控并由 PL 锁存，不经 Linux 或网络。急停响应分开测量“输入到控制信号安全”和“机械真正停下”的时间，二者不可等同。释放停止输入后仍需本地人工确认才能重新使能；云端会话恢复不能清除故障。

上电、FPGA 未配置、配置中、复位、应用未启动均保持硬件默认禁用。看门狗初始阈值为 300 ms，须结合更新周期和实测冻结。目标丢失、摄像头停帧及数据过期也必须触发停止追踪策略。

机械需具备限位、防夹间隙、线束固定、旋转余量与外置可触及停止键。具体舵机型号、脉宽范围、速度、扭矩和电流以真实部件标定；初始参数是调试起点，不是通用接线规格。

### 9.3 板卡未到货时

## 十、验收指标与实验方法

本节数值均为**拟定工程目标，未进行本次板端实测，也不是官方评分阈值**。D3 对可测性确认，D14 仅允许基于真实瓶颈修订并保留原因；最终同时列出目标、实测、是否通过和限制。

| 编号 | 项目 | 首版目标 | 测量方法 |
|---|---|---|---|
| vis_01 | 板端检测处理吞吐 | 持续 ≥15 fps；不足则报告实际可用上限 | 最终输入尺寸下采样 ≥1000 帧，统计丢帧与帧龄 |
| vis_02 | 人员检测 | 本地独立集 precision/recall 均 ≥90%，IoU=0.5；量化后 F1 下降 ≤3 个百分点 | 同一标注集/阈值，记录实例数与弱光分组 |

| motion_02 | 面向效果 | 静止目标稳定后中心误差 P95 ≤画面宽度的 10% | 左中右各不少于 20 次，固定距离与光照 |
| motion_03 | PWM 稳定性 | 脉宽误差 P99 ≤2 μs；报告最大值 | 空闲/CPU 忙/视觉音频并行各 ≥1000 周期 |

### 10.1 两组必做对比

**对比 A：视觉 CPU 与 DPU。**使用同源模型、同输入、同测试集、同阈值与预后处理。最好同时给出 CPU FP32、CPU INT8（如支持）、DPU INT8。若只能比较 FP32 与 INT8，单列量化精度影响，不能将全部收益都归因于硬件。固定线程、频率策略、预热和运行时版本，分别报告模型内耗时、搬运、预后处理、总 FPS、帧龄、CPU、内存和功耗。

**对比 B：软件输出时序与 FPGA PWM。**在相同周期和脉宽下，比较 Linux 软件定时 GPIO 与 PL PWM 的分布、P99、最大误差及超时。软件基线只接测量仪器，避免未经验证的抖动驱动实物。若结果显示 FPGA 收益有限，也如实报告，并分析使用成本。

补充对比为滤波前后目标抖动和响应时间，以及固定朝向/视觉随动下的交互目标保持率。项目创新结论必须有任务结果，不能只写“更智能、更稳定”。

### 10.2 功耗和资源

空闲、仅视觉、仅转动、视觉+语音+转动四种工况分别测主板、舵机、屏幕/音频支路或整机总输入；报告测试边界、仪表、平均值、峰值与每次交互能耗。Windows 中转和云端计算不计入“板卡功耗”，但必须明确它们不在该数字覆盖范围内。

实现报告同时列出 DPU 与自研逻辑的 LUT、FF、BRAM、DSP、频率、WNS/TNS 和资源余量。内存指标按 K26 实际配置与系统占用制定，不沿用原板 850 MB 门槛。记录 USB 摄像头、显示、音频与推理共同工作时的带宽和内存峰值。

## 十一、风险与处理顺序

| 风险 | 识别时间 | 处理方案 | 完成口径 |
|---|---|---|---|
| 老 DPU 工具/模型不可获取 | D2—D3 | 使用已验证且可重建的完整组合；归档合法可分发部分与下载脚本 | 不以空版本号视为完成环境 |
| DPU 与运动 IP 冲突 | D7 | 同设计集成；减可选逻辑、调整 DPU 配置后重编模型 | 分时覆盖 overlay 不算共存 |
| DPU 模型适配失败 | D3—D8 | 切换提前锁定的官方适配备用模型 | CPU 临时运行明确标注 |
| 身份模型板端过慢 | D13 | 降频/仅对主目标运行；记录外部主机过渡配置 | 保留身份产品目标，不冒充板端识别 |
| 云服务不可用/网络差 | D2、D19 | 按需关键帧、超时取消、本地提示与闭环 | 离线能力与完整视听分开验收 |
| 无可用音视频一体接口 | D2 | 采用 ASR + 图像模型 + TTS 的组合路径 | 标为关键帧多模态交互 |
| 播放串音导致误唤醒 | D18 | 轮次式交互、实体键、受控 KWS；AEC 后置 | 不宣称任意语音打断 |
| 舵机承重/供电不足 | D3—D7 | 独立承重、缩小旋转质量、重选执行器/电源 | 不降低停止与限位要求 |
| 原外壳放不下/过热 | D3 | 调整安装与风道，先用开放验证支架 | 外观定稿晚于电气和热测试 |

| 记录缺失导致难复现 | 全周期 | 构建、测试、AI 协作同步归档 | 缺原始证据的指标不记已通过 |

处置顺序：先确保供电、停止和平台可构建，再打通视觉转轴闭环，再稳定视听与身份，最后优化与包装。任何硬件控制异常都暂停带载试验，先完成原因定位。

## 十四、最终演示与完成判定

### 14.1 建议 3—5 分钟演示

1. **开场：**展示设备固定在桌面，摄像头、屏幕、音频与转轴组成一体。
2. **感知与随动：**来访者从左侧进入，设备检测并转向；工程视图简短显示板端检测与 PL 状态。
3. **视听问答：**询问“你现在看到什么”，展示实际画面和回复，再完成一轮语音交流。
4. **身份记忆：**演示已授权用户登记或展示登记流程，用户离开并返回后被正确识别；陌生人显示 unknown。
5. **用户控制：**播报中取消，关闭跟随，再通过新指令恢复。
6. **异常：**演示停止锁存与人工恢复；断网后显示本地模式并继续视觉转向。
7. **性能证据：**展示两组对比和资源报告，指出 DPU、PS、自研 PL 与云端各承担的部分。

演示场景与次序可缩短，但不能预录回答冒充现场云端推理，也不能省略外接计算依赖的说明。

### 14.2 完成检查
