# 《「为什么必须用 FPGA」论证与产品定位澄清》编写 · 技术记录

> 版本：V1.0 ｜ 日期：2026-09-15 ｜ 环境标签：`PC` / `ESTIMATE`
> 关联交付物：`plan_d_fpga_necessity_and_positioning_v1_0.md` / `.docx`

## 1. 背景与目标

团队在执行 V1.2 评估文档与方案 D 实施说明的过程中，提出一个根本性质疑：

> **「为什么一定要用 FPGA？如果只是为了实现类似豆包这样的交互功能，是不是用其它板子更好，或者根本不需要 FPGA？」**

这个质疑在答辩中必然被问到（V1.2 第 12.3 节已列为必答问题），但既有文档只给了**结论**（「PL 承担真实感知负载」），没有给出**判据结构**，也没有处理「与豆包比功能」这一层的应对口径。本次目标：把这个质疑变成可复用、可证伪、可直接用于答辩的论证文档，并且**不夸大、不护短**。

## 3. 关键技术决策

| 编号 | 决策 | 理由 |
|---|---|---|
| K1 | **把「FPGA 必要性」拆成三层判据**：性能必要性（不成立）/ 结构必要性（成立且唯一硬的一条）/ 赛道必要性（成立） | 原文档只有「性能」这一种说法，而它恰好是**最容易被证伪**的一种（全链 4.2 MMAC/s）。拆层后，答辩可精确选择支点，且主动承认性能不必要反而增强可信度 |
| K2 | **明确写出「若目标只是豆包式交互，FPGA 不必要」** | 这是事实，也是团队内部犹豫的根源。回避它会让整篇论证变成自证；正面承认后，论证重心自然落到「数据位置」上 |
| K3 | **把结论改写成可证伪形式**（第 4 节三组同源对比实验 + 判读规则） | 不可证伪的必要性论述会被评委当套话。给出「三项都看不出差别 → 该功能无性能必要性」的判读规则，并预判本项目很可能落在后两种结果 |
| K4 | **新增「FPGA 不该碰的清单」**（第 5 节） | 既有文档的边界散落在 V1.2 第 10.7 / 12.7 节与附录 7.5 节，本次合并为一张三层边界表，可直接用于报告撰写 |
| K5 | **产品定位分叉 A / B 并给出推荐，但标注「待团队拍板」** | 这是产品决策，超出文档作者的权限；文档只负责把两条路的代价讲清楚（并指出「技术更优」与「本赛道得分」在本题上是**背离**的） |
| K6 | **不修改任何既有交付物**（V1.2 与方案 D 附录保持原样） | 沿用团队纪律「未擅自改动已交付文档」；待同步项以清单形式列在第 9.2 节，等团队同意后再升版 |

## 4. 纠错与踩坑记录

| 编号 | 问题 | 根因 | 处理 |
|---|---|---|---|
| E1 | 分块写入新文档时，误把 `## 3. FPGA 必要性的三层判据` 这一行用作「插入第 4 节」的锚点，导致**第 3 节的 H2 标题被第 4 节内容整体覆盖**，第 3 节小节悬空挂到第 4 节下 | 分块编辑时用**已有章节标题**作为锚点，锚点文本被新内容替换 | 立即读取实际行号确认事故范围，用一次精确替换恢复标题，再把第 4 节追加到第 3.4 节之后；**教训：追加内容时锚点必须取上一块的末尾文本，且 new_text 必须原样保留该锚点** |
| E2 | 表格单元格内若出现裸竖线会破坏列结构 | Markdown 竖线即列分隔符 | 全文表格一律避免裸竖线（用 `−2.4 < lag < +2.4` 这类写法）；本次用脚本扫描 37 张表，列数不一致 **0** |
| E3 | 既有文档中的话术带有「性能」色彩（如「毫秒级可控的停止响应」） | 早期论证以「确定性抖动」为重点 | 第 6.4 节单列「不要滥用第 2 条」的风险表，并在第 8.5 节给出禁用话术清单（含「我们的延迟是微秒级」这条） |
