## 1. 结论摘要（先看这一页）

### 1.1 三句话结论

| # | 结论 | 性质 |
|---|---|---|
| 1 | **若目标只是「豆包式聊天交互」，用 FPGA 既不必要也不是好选择**——同等功能用 ESP32-S3 或树莓派可更快、更便宜、体验更好 | 技术判断 |
| 2 | **「为什么必须用 FPGA」有三层判据，只有一层是性能判据**，而性能这一层在本项目**尚未证实**（估算并不支持它）（全链约 4.2 MMAC/s，对 PS 侧 A53 也不构成压力，附录 6.6 已写成表述红线） | 事实澄清 |
| 3 | 因此真正要拍板的不是「要不要 FPGA」，而是**这个产品解决什么问题**：做「聊天」→ 问题在选题与叙事；做「端侧、断网、硬实时、数据不出设备的守护」→ FPGA 才有结构位置 | 决策问题 |

### 1.2 三层判据总表

| 判据层 | 内容 | 是否成立 | 依据 |
|---|---|---|---|
| **① 性能必要性** | 「PS 算不过来，所以放进 PL」 | **未证实**（估算不支持，且缺实测数据） | 附录 6.6：全链 ≈ 4.2 MMAC/s；相对 1,248 个 DSP48 占用率约 0.001% 量级；且已写入表述红线「**不得**讲 CPU 算不动」 |
| **② 结构必要性** | 多路音频与视频**无法由 PL 引脚直接采集（USB 类数据必先由 PS 侧控制器接收并入 DDR，再经 DMA/AXI 交给 PL）**，只有 I2S / PDM / MIPI 类接口才能让数据经过 PL 引脚 | **成立（本文最强的结构论据，但不是唯一论据）** | 附录 3.1、V1.2 第 12.6 节：USB 麦克风阵列的数据由 KV260 PS 侧 ALSA 直接取走，PL 引脚上根本看不到（AMD 官方资料确认） |
| **③ 赛道必要性** | 3.3 初级组考察侧重「逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力」 | **成立** | V1.2 第 1.3 节（指南 3.3 原文口径） |

### 1.3 这次质疑的真正价值

**结论：这次质疑修正的是「叙事」，不是「功能」，更不是「选型」。**

| 项 | 是否需要改动 | 说明 |
|---|---|---|
| 技术方案（方案 D：2 × I2S 数字麦 + PL 内 DOA） | **不需要改** | 它恰好落在判据②（本文最强的结构论据）上，这正是 V1.2 第 12.3 节得出「PL 必须承担真实感知负载」后的选型 |
| 赛道的合规性 | **不需要改** | K26 落在初级组允许器件范围内（V1.2 第 1.1 节） |
| **论证方式与答辩话术** | **必须改** | 现话术里仍有「性能」色彩（如「毫秒级可控的停止响应」「确定性抖动」），一旦评委追问「这点延迟对聊天有影响吗」，就会失去支点 |
| **产品定位与功能取舍** | **需要拍板** | 见第 7 节：与豆包比功能必输，必须把叙事重心换成「豆包做不到的约束」 |

> 一句话：**这次质疑是团队自己发现的一个真实软肋，越早修越好；它属于「叙事矫正」，不属于「方案返工」。**

## 2. 「豆包式交互」的算力拆解

### 2.1 这条链究竟谁在算

把一次「豆包式」问答按时间顺序拆开，逐环看算力与数据的真实归属：

| # | 环节 | 实际承载者 | 端侧芯片承担的部分 | 对芯片的要求 |
|---:|---|---|---|---|
| 1 | 多麦拾音（阵列） | 端侧 | 采集（mW 级） | 稳定时钟 + 多路同步 |
| 2 | 唤醒词 / VAD | 端侧 DSP 或低功耗 NPU | 检测（μW—mW 级） | 常开低功耗 |
| 3 | 降噪 / 回声消除 / 波束成形 | 成熟算法库或 NPU | 可做可不做 | 有成熟方案，不必自研 |
| 4 | ASR（语音转文字） | **云端为主**，或端侧 NPU | 送音频 | 带宽与稳定性 |
| 5 | 对话 / LLM 推理 | **云端**（或主机 GPU） | 转发与超时处理 | 网络 |
| 6 | TTS（文字转语音） | **云端为主** | 播放 | 编解码 |
| 7 | 显示 / 表情 / 动作 | 端侧 | 渲染与 PWM | 常规 |

**读表要点：算力密度最高的第 4—6 环全部落在云端或上位机；端侧芯片在这条链上的角色是「可靠的采集器 + 可靠的播放器 + 一个状态机」。**

### 2.2 为什么端侧芯片对交互体验几乎无影响（三条量化理由）

| # | 理由 | 说明 |
|---:|---|---|
| 1 | **端侧算力量级差了两个数量级** | 对话质量由大模型参数量与训练数据决定（云端数十 B 级以上）。端侧芯片就算快十倍，也换不来一次更聪明的回答——**体验的天花板不在端侧** |
| 2 | **端到端时延由网络与云端推理主导** | 一次问答的时延构成里，端侧采集/播放只占数十毫秒量级，网络往返与云端推理占数百毫秒至数秒。**端侧把延迟压到 0 也改变不了用户感受** |
| 3 | **端侧的差异只体现在「稳定性」** | 采集是否丢帧、时钟是否漂移、播放是否断续——这些是工程问题，ESP32 与 KV260 都能做，**没有一个是必须 PL 才能解决的**（唯一例外见判据②） |

**由此得到本文第一条核心判断：把「豆包式交互」作为作品的功能主线时，FPGA 恰好用在了这条链上唯一不需要它的位置。**

### 2.3 反向推论：如果 PL 只做采集与播放，PL 就没有意义

V1.2 第 12.3 节已经把这个结构性问题写得很直白：

> 原方案把有吞吐压力的活（视觉推理、大模型）放在 PS 与主机，PL 只剩 DPU 集成与 PWM——这正是「没亮点」与「为什么用 FPGA 难答」的共同病根。

**用同一把尺子量一遍就清楚了：**

| PL 承担的内容 | 是否构成「必须 PL」的理由 |
|---|---|
| 只做 I2S / UAC 采集与播放 | ❌ 不构成（PS 软件或 ESP32 都能做） |
| 只做 PWM 与舵机 | ❌ 不构成（MCU 做 PWM 的抖动通常比 Linux 软件更小、成本更低——V1.2 第 12.1 节已认定这是无效论点） |
| 只做 DPU 的集成与调用 | ❌ 不构成（DPU 是 AMD 的 IP，团队做的是集成；V1.2 第 12.1 节已排除把「用了 DPU」当创新点） |
| **采样级同步的多通道音频采集 + 在该数据上完成方位判决** | ✅ **构成**：数据只有经 PL 引脚才拿得到，且判定在同一时钟域内完成（方案 D 的立足点） |
| **多路视频的前处理与推理共存于同一位流** | ✅ **构成**：像素级并行吞吐 + DPU 同片（方案 A 的立足点，V1.2 第 12.3 节判定为「结构上别人替代不了」） |

### 2.4 为什么在「竞赛」语境下答案会反转

技术上「不需要 FPGA」与赛道上「必须交 FPGA 作品」并不矛盾，二者回答的是不同问题：

| 提问 | 正确答案 |
|---|---|
| 「这个功能用 FPGA 实现合理吗？」 | **不合理**（第 2.2 节） |
| 「我们要不要用 FPGA？」 | **要**——因为 3.3 赛道的评分口径考察的是 FPGA 设计能力（逻辑设计、状态机、时序约束、接口协议），**用 ESP32 交的作品在这个赛道拿不到分，甚至不满足赛道设定** |
| 「那怎么让两者不打架？」 | **把「必须 PL 才成立的那一段」做成作品主体，把「不需要 PL 的那一段」诚实地交给云端或上位机**（V1.2 第 12.7 节的分工表） |

**这正是本次定位澄清的目的：不是让作品「看起来」需要 FPGA，而是让作品真的有一段落必须由 PL 承担——方案 D 的音频采集链与方案 C 的确定性动作链就是那两段。**

## 3. FPGA 必要性的三层判据

### 3.1 判据一：性能必要性（**未证实**）

这是最常被误用、也最容易被评委一句话击穿的一条。把账算清楚：

| 计算块 | 运算量 | 说明 |
|---|---|---|
| 32 阶对称 FIR × 2 通道 @ 48 kHz | 3.07 MMAC/s | 最大的一项 |
| 互相关 17 lag × 472 样本 × 100 帧/s | 0.80 MMAC/s | 每帧约 8.0 k MAC |
| DC 高通（2 阶 IIR）× 2 通道 | 0.19 MMAC/s | — |
| 能量 / VAD | 0.10 MMAC/s | — |
| **合计** | **≈ 4.2 MMAC/s** | 相对 1,248 个 DSP48，占用率约 **0.001% 量级** |

> 数据来源：`amd_kv260_plan_d_mic_array_implementation_v1_0.md` 第 6.6 节（`ESTIMATE`）。

**结论：4.2 MMAC/s 对 PS 侧的四核 Cortex-A53 也不构成压力。** 因此：

- 若在答辩中说「CPU 算不过来，所以放 PL」→ **会被直接证伪**，且违反附录 6.6 已写死的表述红线；
- 反过来，这条恰恰是**可以主动承认**的诚实点：先承认「这条链总共才 4 MMAC/s」，再给出真正的理由，可信度反而更高。

### 3.2 判据二：结构必要性（**成立；是最强的一条，但不是唯一论据**）

「结构必要性」问的不是「谁更快」，而是「**数据能不能到达某个位置**」。本题的答案是：**不经过 PL 引脚，PL 就永远看不到这份数据。**

| 采集形态 | 数据能否进 PL | 原因 | 对本方案 |
|---|---|---|---|
| **USB 麦克风阵列**（UAC 多通道） | **不能** | 数据由 KV260 PS 侧 ALSA 直接取走，PL 引脚上根本看不到 | **不可用**（可用于普通录音 / ASR 输入） |
| **I2S 数字麦阵列**（INMP441 类 MEMS） | **能** | 经 Pmod 引脚进 PL，由自研 I2S 接收逻辑取数 | **本方案采用** |
| **PDM 数字麦** | 能进 PL | 需自研 CIC + 抽取滤波，PL 工时更大 | 备选 |
| **模拟驻极体麦 + ADC** | 需外挂 ADC | 增加模拟前端风险，与数字麦同为 3 根线却更差 | 不做 |
| **MIPI / RPi Camera 视频** | 能进 PL | 走 PL 引脚进入 | 视觉链同理（方案 A 的立足点） |

> 来源：`amd_kv260_plan_d_mic_array_implementation_v1_0.md` 第 3.1 节、`amd_kv260_track_fit_assessment_v1_2.md` 第 12.6 节（`AMD 官方资料确认`）。

**这条判据的强度还可以再抬一层（**措辞纪律：可讲「数据只有经 PL 引脚才拿得到」，不讲「唯一硬」；结构必要性须与赛道必要性、技能包并列陈述**）：** 结构必要性不只「别的芯片也能做」，而是「**换掉 PL，这份数据就消失**」。任何软件方案都拿不到 PL 引脚上的并行样本流——这是硬件接口位置决定的事实，不是性能权衡。

**附加的次级结构优势（同属判据二，但需数据支撑）：**

| 次级优势 | 说明 | 取证方式（`BOARD_REQUIRED`） |
|---|---|---|
| **采样级同步** | 两只麦共享同一 BCLK / LRCLK，采样时刻由同一个时钟边沿决定，**无漂移、无需重采样**；两路独立 USB 麦做不到这一点 | D1 实测 lag 零点 30 min 漂移 < 0.1 样本 |
| **同一时钟域内完成判决** | 采集、滤波、互相关、判档全部在 PL 内，无需跨设备搬运中间数据 | ILA 抓取帧节拍与判决时刻 |

### 3.3 判据三：赛道必要性（**成立**）

这一条与技术水平无关，但与能否得分直接相关：

| 项 | 内容 |
|---|---|
| 赛道 | 2026 全国大学生嵌入式芯片与系统设计竞赛 · FPGA 创新设计赛道 · **3.3 自主选题（初级组）** |
| 考察侧重（指南原文口径） | 「**逻辑设计、状态机、时序约束、接口协议等基本 FPGA 设计能力**」 |
| 器件合规 | K26（XCK26，Zynq UltraScale+ MPSoC）落在初级组允许范围内（V1.2 第 1.1 节） |
| 上位机 | **3.3 赛道不规定上位机**；现有 Windows + GPU 主机是合法资源，只需如实披露算力位置（V1.2 第 1.2 节） |

**含义：** 赛道并不要求「这件功能非 FPGA 不可」，它要求的是「**你交出一份能体现 FPGA 设计能力的作品**」。所以本作品的正确定位是：

> **主体 = PL 内自研的采集 / DSP / 确定性动作链（体现判据二 + 技能包）；陪体 = 云端或上位机的大模型能力（如实披露，不当作 FPGA 贡献）。**

### 3.4 三层判据的组合用法（答辩答题模板）

| 若评委问 | 用哪一层答 | 一句话答法 |
|---|---|---|
| 「为什么必须 FPGA？树莓派不行吗？」 | **② + ③** | 「这条链的数据只有经 PL 引脚才拿得到——走 USB 会被操作系统的音频栈直接取走；同时赛道考察的是 FPGA 设计能力，我们把自研的采集与 DSP 链做成了主体。」 |
| 「PL 快在哪？」 | **不要答这条** | 不要谈速度。改为谈「同一时钟域内的采样同步」与「不经过 OS 调度」。 |
| 「这点算力 CPU 也能做吧？」 | **主动承认** | 「对，总共约 4.2 MMAC/s，A53 也扛得住，我们在报告里如实写了。我们用 FPGA 不是因为它更快，而是因为数据位置与确定性。」 |
| 「那小模型放板上跑呢？」 | **诚实设界** | 「KV260 上不做 LLM/VLM 推理，这部分交给主机或云端，我们在报告里标明了算力位置。」 |

## 4. 可证伪自检法：三组对比实验

### 4.1 为什么要做这个自检

「为什么必须用 FPGA」最容易变成一句**不可证伪的口号**（一旦不可证伪，评委就会当它是套话）。把它变成可证伪的命题：

> **命题：** 把同一功能从 PL 移到 PS 侧软件实现后，至少有一项可测量指标显著变差。
> **如果三项都看不出差别 → 这个功能上 FPGA 就没有必要性。**

这条自检有两个好处：① 答辩时有数据而不是形容词；② **它对团队自己也有用**——它把「哪些活值得写 RTL」这件事从感觉变成了测量。

### 4.2 实验设计（同源对比，PL 与 PS 各跑同一算法）

| # | 指标 | 做法 | 采集方式 | 环境标签 |
|---:|---|---|---|---|
| 1 | **CPU 占用** | 同一互相关算法分别在 PL（`audio_doa_ip`）与 PS（**合理优化的 C/C++ 实现；Python 循环不得作为基线**）实现，各跑 10 分钟 | `top` / `psutil` 采样 + `metrics/logs/dpu_cpu` | `BOARD_REQUIRED` |
| 2 | **节拍抖动** | 连续不少于 1000 个处理周期，统计**判决时刻**的 P50 / P95 / P99 / max | PL：ILA 或 `LATENCY_US` 时间戳；PS：软件打点 | `BOARD_REQUIRED` |
| 3 | **端到端延迟分布** | 「说话 → `DIR_CODE` 更新」的完整链路分布 | 音频注入 + 逻辑分析仪触发 | `BOARD_REQUIRED` |

### 4.3 判读规则（先写清楚，避免事后找理由）

| 观测结果 | 结论 | 报告中怎么写 |
|---|---|---|
| 三项均有显著差异（如 PL 的 P99 明显低于 PS、CPU 占用由 PS 侧承担转为近零；**须以实测数据为准，不得写「零占用」**） | 必要性**成立且已实测** | 写进「性能与资源优化」档作为核心证据 |
| 只有 CPU 占用与节拍抖动有差异，端到端延迟无差异 | 必要性**部分成立** | 只声称成立的部分；**不要**声称「端到端更快」 |
| **三项都看不出差别** | 该功能上**无性能必要性**，只剩判据二 | **如实写**：定位为「数据位置与结构必需」，并说明「本轮未观测到性能差异」。**诚实报告反而是加分项** |

> **预判（`ESTIMATE`）：** 本项目极可能落在第二种或第三种。原因很简单——交互链的节拍是 10 ms 级、端到端是数百毫秒级，而 PL 与 PS 在 4.2 MMAC/s 这个量级上的差异会被网络与模型推理彻底淹没。
> **因此：实验前就不要预设结论，也不要为了凑差异去挑指标。**

### 5.6 停止事件的四分类（W17-20 ⑨）

「停止」在验收与答辩中必须分成四件事分别取证，**不得混为一谈**：

| 分类 | 含义 | 取证方式 |
|---|---|---|
| ① 数字停止输出 | 安全输出电平按电气要求置为停止态 | 波形测量，标出边沿与目标态（T11 第一段计时） |
| ② 停止 PWM 更新 | 周期边界后 PWM 不再按新目标翻转 | 同一波形上的周期与脉宽（T11 第二段计时） |
| ③ 切断驱动电源 | 高边使能门断开、驱动器失电 | 电源轨与使能门电平同步测量（T11 第三段计时） |
| ④ 机械静止 | 舵机与机构实际停止 | 真实负载录像，明确定义起止判据 |

口径纪律：「同步停止边沿到数字安全输出 ≤5 ms」只覆盖 ①；②③④ 各自单独测量并分别记录起止点与仪器精度。

## 6. FPGA 四类不可替代场景 × 本项目自查

### 6.1 四类场景（只有这四类，逐条自查）

| # | 场景 | 为什么别的方案吃亏 | 取证方式 |
|---:|---|---|---|
| 1 | **多通道严格同步采样** | 多路独立外设（USB 麦、板载声卡）各有自己的采样时钟，需要漂移估计与重采样；同一 I2S 总线上的多麦共享 BCLK/LRCLK，**采样时刻由同一个时钟边沿决定**，天然同步 | 零点漂移实测：30 min 内 < 0.1 样本（`BOARD_REQUIRED`） |
| 2 | **确定性抖动（硬实时）** | Linux 调度、GC、内存交换带来毫秒级抖动与长尾；PL 的节拍由计数器与状态机决定，**抖动在时钟周期量级** | 不少于 1000 个周期的 P50 / P95 / P99 / max 对比（第 4 节实验②） |
| 3 | **数据物理上不出设备** | 云端方案必须上传原始数据；PL 内完成前处理可**只上传摘要**（甚至不上传），隐私与带宽同时受益 | 数据流向图 + 抓包证明（`BOARD_REQUIRED`） |
| 4 | **无 OS 的确定性启动与无人值守** | Linux 冷启动是秒级；PL 可在 PS 启动前就开始工作（按已固化位流开始工作；**这是设计意图**——冷启动到首个有效输出的时间必须实测，取数前不得写为已实现） | 冷启动到首个有效输出的时间测量（`BOARD_REQUIRED`） |

### 6.2 本项目自查表

| # | 场景 | 本项目是否占 | 依据 |
|---:|---|---|---|
| 1 | 多通道严格同步采样 | ✅ **占** | 2 只麦共享 BCLK / LRCLK（方案 D）；采样同步是 DOA 的物理前提 |
| 2 | 确定性抖动 | △ **部分占** | 方案 C 的安全链（看门狗 / 停止 / 故障锁存）确有此性质；**但交互随动是数百毫秒尺度，这条对本项目的主功能不构成必要性** → 必须靠第 4 节实验②的数据说话，不能空讲 |
| 3 | 数据不出设备 | ✅ **可叙，但要诚实** | 音频/视频的本机处理可以只输出摘要（方位码、检测结论）；但本项目仍需要云端做对话，**三层数据边界（W17-20 ⑤）**：① **原始感知数据**（I2S PCM、相机帧）在 PL／板内处理、**不出设备**；② **派生数据**（方向码、检测结论、帧龄、会话）可留板内或送主机；③ **原始图像、人脸图与语音原文**在走 ASR／VLM／问答链时**会发送到 Windows 主机（并可能到云端）**。只可声称「原始感知数据不出设备」，**不得声称「完全不出设备」** |
| 4 | 无 OS 确定性启动 | ○ **可叙但非主线** | 守护型设备的真实需求；本项目未做冷启动计时实验，**在取到数据前只能写为「设计意图」** |

### 6.3 结论

**本项目最硬的两条是第 1 条与第 3 条（同步采样 + 数据位置），它们都不是「性能」论证，而是「结构」论证。** 这正是第 3.2 节判据二的内容，也是答辩中唯一不会被轻易推翻的支点。

### 6.4 一条重要提醒：不要滥用第 2 条

「确定性抖动」讲起来最像技术亮点，但它最容易翻车：

| 说法 | 风险 |
|---|---|
| 「我们的抖动比软件小 100 倍」 | 评委问「这对一个几百毫秒的交互有什么影响？」→ 答不上来就失去支点 |
| 「我们能做到微秒级停止」 | 若机械与舵机本身的响应是数十毫秒，**瓶颈不在 PL**，声称的微秒级就没有意义 |
| 正确写法 | 「PL 侧的判决节拍抖动为 X（实测），相比 PS 软件实现的 Y；**该差异对端到端体验的影响为 Z（如实说明，含『未观测到显著影响』的结论）**」 |

## 8. 答辩话术（可直接使用）

### 8.1 三段核心话术（替代现版本的「性能」表述）

| # | 场景 | 话术 |
|---:|---|---|
| 1 | 被问创新点 | 「我们把感知与执行放进了**同一片 PL**：DPU 做人体检测，自研 I2S 采集与方位判决做声源定位，与自研安全约束链共存于同一位流。设备因此能『谁说话就看向谁』——固定摄像头方案永远背对用户，纯语音方案没有『看向你』这一层。」 |
| 2 | 被问为什么必须 FPGA | 「这条链上有一个**只有 PL 才能拿到**的东西：多路音频与视频的**采样级同步数据流**。走 USB 的话，数据会被操作系统的音频栈直接取走，我们连原始通道都看不见。所以我们把采集与判决做在 PL 里，帧节拍由硬件计数决定，不经过操作系统调度。」 |
| 3 | 被问算力是否必要 | 「**我们不声称 FPGA 算得更快。**这条链总共约 4.2 MMAC/s，A53 也扛得住——这一点写在报告里。我们用 FPGA 的理由是数据位置与确定性，不是速度。」（**主动承认，反而增强可信度**） |

### 8.2 「你和豆包有什么区别」

| 层 | 应答 |
|---|---|
| 先承认 | 「功能上我们比不过云端大模型，这是设计上的取舍，不是缺陷。我们的对话能力也依赖云端或主机，报告里写明了算力位置。」 |
| 再给差异 | 「差别在**约束**：我们断网可用、原始感知数据不出设备；豆包这类云服务做不到第一条。我们的核心是**PS 与 PL 协同的端侧感知-决策-执行**——没人说话的时候它也在看、在判断（响应时间以实测数据为准）。」 |
| 最后回到赛道 | 「本赛道考察的是 FPGA 设计能力，所以作品主体是 PL 内自研的采集、判决与安全链，对话只是它的对外接口。」 |

### 8.3 「为什么不用 ESP32 / 树莓派」

| 层 | 应答 |
|---|---|
| 承认 | 「如果只做语音助手，ESP32 加云端 API 更合适，成本与工时都低一个量级，我们评估过。」 |
| 给理由 | 「但我们要的是：多路音频的采样级同步采集、判决在同一时钟域内完成、以及一枚 SoC 内感知到执行器的闭环；这些在 MCU 或 SBC 上要么拿不到数据，要么无法保证确定性。」 |
| 诚实补充 | 「另外本赛道的评分口径就是考察 FPGA 设计能力，这是赛道设定。」 |

### 8.4 「这点算力 CPU 也能做吧」

标准答法：**先承认，再换支点，最后给数据。**

> 「对，可以。我们的 PS 侧也实现了同一套算法用于对比。区别不在数学，而在数据在哪里：PL 侧拿到的是同步采样的原始通道，PS 侧只能拿到已经经过设备栈的流。第二部分数据是帧节拍与抖动的实测对比（第 4 节实验②）。」

### 8.5 禁用话术清单（红线）

| ❌ 不要说 | 原因 |
|---|---|
| 「CPU 算不动」 | 全链约 4.2 MMAC/s，A53 也扛得住（第 3.1 节） |
| 「我们用了 AMD DPU，所以是创新」 | DPU 是 AMD 的 IP，团队做的是集成（V1.2 第 12.1 节） |
| 「我们本地部署了 AI」 | 树莓派 + NPU 棒也能做到（V1.2 第 12.1 节） |
| 「我们的延迟是微秒级，所以体验更好」 | 端到端由机械与网络主导；**无实测影响数据就是空话**（第 6.4 节） |
| 「数据完全不出设备」 | 对话仍走云端；只能声称「原始感知数据不出设备」；**原始图像与人脸图会发往主机**（W17-20 ⑤） |
| 「CPU 零占用」／「PL 侧 CPU 占用为零」 | 只能声称「CPU 负载由 PS 侧承担、PL 路径无需 CPU 参与」，并给出**同源同参、基线为合理优化实现**的实测对比（W17-20 ③④） |
| 「上电即守护」／「上电即用」 | 只能写为**设计意图**：PL 按已固化位流可先于 PS 起作用；冷启动到首个有效输出的时间须实测（W17-20 ⑦） |
| 「唯一硬的一条」 | 结构必要性是**最强**的论据，不是唯一论据；对外一律讲「数据只有经 PL 引脚才拿得到」（W17-20 ①） |
| 「安全控制也是我们的创新」 | 单看安全控制，MCU 甚至更合适（V1.2 第 12.1 节） |

### 8.6 60 秒完整口头陈述（建议背诵）

> 「这个作品是一颗 SoC 内 **PS 与 PL 协同**的端侧守护系统。摄像头经 PL 进 DPU 做人体检测，两只 I2S 麦克风经 Pmod 进 PL，由我们自研的接收逻辑与互相关模块判断声源在左、中还是右；判断结果进入自研的安全约束链，驱动转轴——所以谁说话，它就看向谁。
> 我们不声称 FPGA 更快：这条链总共约 4.2 MMAC/s，CPU 也扛得住。我们用 FPGA 是因为两件事只有 PL 能做：第一，**采样级同步的多路音频与视频数据只有经 PL 引脚才拿得到**，走 USB 会被操作系统的设备栈取走；第二，从感知到执行器这一段，**帧节拍与判决时刻由硬件决定，不经过操作系统调度**，因此是可测量、可复现的。
> 对话能力用的是云端或主机的模型，我们在报告里如实标明了算力位置——那是陪体，主体是 PL 内自研的采集、判决与安全链。」
