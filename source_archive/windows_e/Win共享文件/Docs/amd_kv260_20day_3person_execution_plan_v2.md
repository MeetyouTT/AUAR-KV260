## 0. 先确定怎么把项目做完

**本轮目标：20 天交付一台能看到人、面向人、听到问题、结合画面回答、用屏幕玩偶和声音反馈，并能登记和再次认出已登记用户的实体设备。**

三人按你指定的方向分工，但必须从 D2 开始用同一套接口，D5 做第一次三方联调，D10 完成第一版完整体验，D15 冻结功能，D16—D20 用于整机验证和交付。

### 0.1 本版采用的实施假设

- 每人每天约 6 小时有效投入，20 天约 360 人时，其中约 270 人时用于前 15 天开发、90 人时用于后 5 天验证交付。每日联调、记录包含在这 6 小时内。
- D1 可以使用 KV260、摄像头、显示屏、麦克风、音箱和单轴执行器；板卡或主要部件延迟到货会影响实体里程碑。
- 延续旧方案中的 Windows GPU 电脑作为**本地模型主机**，通过有线局域网连接 KV260。具体显卡、显存、磁盘和当前环境由 B 在 D1 实查，不能把旧计划中的配置当作当前已验证事实。
- A 能在 D1—D3 获得一套完整、匹配、可以重建的 KV260 参考平台与构建环境。若从零学习 FPGA、从零装完整工具链和从零制作机械件同时发生，20 天不宜视作保证期限。
- 复用已有 UI、外壳和软件的可用部分；只在实际跑通或装配验证后勾选“已完成”。

**“本地”在本计划中表示自带电脑和板卡组成的局域网系统，无需公网推理。完整对话依赖该电脑；板卡独立保留视觉跟随、基本 UI 和停止功能。** 若必须所有模型都运行在 KV260 上，应按第 12 节重新评估，不能把这份双设备排期直接改名为纯板端方案。

### 0.2 20 天内的功能边界

| 层级 | 本轮内容 | 通过条件 |
|---|---|---|
| 完整产品必做 | 单人优先的人体检测、短时跟踪、单水平轴随动 | 人移动时设备平稳调整朝向；丢人后不继续追旧目标 |
| 完整产品必做 | 自研 FPGA 转轴 IP | PWM、指令限幅/限速、超时、停止输入、状态回读均可上板验证 |

| 完整产品必做 | 玩偶、字幕、状态面板 | 实际录音/推理/播放状态驱动 UI；支持取消当前轮 |

首版语音采用**按键说话、松开提交**；按键可以先是 UI 按钮，随后接实体按键。这样仍能完成自然对话和看图问答。自动唤醒、边播边听属于另一个阶段的体验要求。

## 1. 最终系统怎样运行

### 1.1 设备位置与职责

| 运行位置 | 放置内容 | 负责人 |
|---|---|---|
| KV260 的 PS，即 ARM/Linux | 相机采集、视觉后处理、跟踪、目标选择、场景状态、运动驱动；UI 服务、录放音客户端、对话编排 | B 负责视觉；A 负责运动驱动；C 负责 UI/音频/对话编排 |
| KV260 的 PL，即 FPGA 逻辑 | AMD DPU 人体检测；自研 `motion_guard_ip` | A 做硬件平台/IP；B 做模型编译和推理调用 |
| Windows GPU 电脑 | 本地视觉语言模型服务；首版身份服务；ASR/TTS 推理服务 | B 管视觉语言模型与身份；C 管 ASR/TTS |
| 玩偶机身 | 摄像头、显示屏、麦克风、扬声器、停止键和旋转机构 | A 管转轴、供电、线束；C 管屏幕、音频与外壳面板；共同装配 |

KV260 有 4 GB DDR4。把桌面级多模态对话、语音、视觉检测、UI 全塞入这块板，不能仅凭模型权重大小判断可行；还要考虑运行时、缓存和并发负载。因此本计划采用上述分工，这是工程选择而非板卡性能实测结论。[AMD KV260 数据手册](https://docs.amd.com/r/en-US/ds986-kv260-starter-kit/Product-Details)

### 1.2 三条并行链路

```text
链路一：实时视觉与转轴，持续运行，不等待大模型
USB 相机 → KV260 采集 → DPU 检测 → PS 跟踪/选人
          → 视觉误差 → 运动驱动 → 自研 PL IP → 舵机/水平转轴

链路二：本地视听对话，按用户提问触发
机身麦克风 → KV260 录音 → Windows ASR → 用户文字
          + 同一时刻附近的相机快照、场景状态
          → Windows 视觉语言模型 → 回复文字 → Windows TTS
          → KV260 播放 → 机身扬声器 + 玩偶/字幕

链路三：身份记忆，低频或按事件触发
当前目标的人脸图 → Windows 人脸检测/特征匹配 → 身份库
                 → 绑定原目标的结果 → KV260 场景状态 → 个性化问候
```

第一次演示先在电脑上接外设也可以，但 D5 的日志应标明设备位置；最终按上表将摄像头、录放音与屏幕接入实体机。若显示必须由电脑驱动才能完成，要作为实际依赖记录，不能声称是 KV260 本地显示。

### 1.3 一次完整交互的执行顺序

1. 人进入画面，B 的视觉服务发布目标，C 的玩偶看向目标；A 的转轴链收到有效目标角后调整朝向。
2. 用户按住说话键，C 停止当前播报并开始录音，界面显示“正在听”。
3. 松开按键后，C 将音频交给自己的 ASR 服务，并向 B 的板端服务索取带编号的新鲜快照。
4. C 把识别出的文字、快照和场景摘要交给 B 的统一 `/dialogue` 接口。
5. B 返回简短中文回答。C 进行 TTS，收到音频后在板端播放；实际开始播放时才切换到“说话”状态。
6. 用户取消时，C 作废该轮编号，清掉旧音频；迟到的模型或 TTS 回复不能重新播放。
7. 用户要求记住名字时，进入单独的身份确认流程；B 完成登记，C 显示结果并播报。
8. 所有对话步骤运行期间，板端检测、运动控制和停止输入独立运行。

## 3. D1—D2 必须冻结的公共接口

### 3.1 仓库、分支和运行配置

采用一个项目仓库，目录按职责分开；`main` 每天保持可启动，A/B/C 使用各自功能分支，合并前做当天的最小联合演示。不要把三个人各自的目录临时拷贝到同一台电脑当作版本管理。

```text
aura/
  hardware/rtl/             A：转轴 IP
  hardware/sim/             A：仿真
  hardware/platform/        A：KV260 平台与构建脚本
  hardware/constraints/     A：引脚/时钟约束
  board/motion/             A：唯一寄存器写入者、驱动与运动接口
  board/vision/             B：采集、检测、跟踪、场景、视觉控制
  board/interaction/        C：录音、播放、对话编排、按键
  host/vlm/                 B：模型服务与对话适配器
  host/identity/            B：身份服务和数据库
  host/speech/              C：ASR/TTS
  ui/                       C：玩偶和字幕
  common/                   公共消息定义；改动通知全员
  config/                   环境地址、标定与模型锁
  scripts/                  启动、自检、部署、日志导出
  tests/                    各人自己的验证与整机用例
  docs/                     接线、部署、测试与限制
  skill/                    真实开发中沉淀的复用方法
```

以上是需要建立的目录，并非本文已经创建的工程。

### 3.2 通信约定

- **板内实时链：**B 的视觉控制器调用 A 的本地运动接口，优先使用本地进程通信；不经过 Windows、大模型或浏览器。
- **跨设备链：**HTTP 传一次请求，WebSocket 推送 UI/状态事件。先采用普通请求返回完整文本/音频，再增加流式功能。
- **C 维护板端统一服务入口**，建议配置端口 `8000`；B 的 Windows 应用接口建议 `8001`；C 的语音接口建议 `8002`；模型引擎在 Windows `127.0.0.1:8080`，由 B 的应用接口调用。
- 端口均为项目建议值，写入 `config/runtime.yaml` 后统一使用。Windows 入站仅允许所需局域网通信；模型加载和素材下载完成后再做离线验收。
- 公共字段包括 `schema_version`、`request_id`、`boot_id`、`presence_session_id`；视频再带 `frame_id`，音频再带 `utterance_id`。

| 接口/对象 | 谁提供 → 谁调用 | 内容和完成标准 |
|---|---|---|
| `GET /health` | 各服务 → C | 返回 ready/loading/error、版本；进程存在不等于模型可用 |
| `GET /snapshot` | B 板端 → C | 返回 JPEG 与 frame_id、boot_id、采集/出队时间信息；同一回复中的图像与元数据对应 |
| `scene_state` | B → A/C | 目标存在、归一化坐标、跟踪会话、当前姓名或 unknown；只保留最新状态 |
| `motion.request_target()` | A 提供 → B 调用 | 有效角度、依据帧和会话、剩余有效期；A 提交前再次核验 |
| `motion.status()` | A → B/C | 已接受 seq、受限指令角、故障、是否需要位置确认；没有编码器不显示“实测角度” |
| `POST /asr` | C 主机 → C 板端 | 音频及其格式 → text、utterance_id；空白/失败明确返回 |
| `POST /dialogue` | B 主机 → C 板端 | 文字＋JPEG＋场景＋request_id → text、有限表情；不输出 PWM 或寄存器操作 |
| `POST /tts` | C 主机 → C 板端 | text＋utterance_id → 音频及采样率/编码；文件或流均带本轮编号 |
| `identity/enroll, recognize, delete` | B → C | 登记需事务编号和确认；结果绑定原始目标，删除后旧结果失效 |
| `ui_event` | C 编排 → UI | state、subtitle、expression、utterance_id、音频播放进度 |

### 3.3 必须统一的规则

1. 目标坐标以原始画面为准，`cx_norm`、`cy_norm` 范围为 0—1；模型输入缩放/letterbox 必须还原后才能计算。
2. 运动角度用有符号整数毫度，例如 `10000` 表示相对参考位 +10°；A/B 在 D2 用实物确认正方向。
3. 相机只由 B 的采集进程打开一次，UI、身份和视觉语言模型都复用它的帧，避免多个进程抢相机。
4. 视频队列深度默认 1，只处理最新帧；禁止堆积旧帧后继续驱动转轴。
5. PS 帧龄和租约使用板端单调时钟。Windows 的时间戳不能直接减 KV260 的时间戳；跨机延迟用请求发起方计时。
6. 首版建议视觉帧最大允许年龄 300ms、PL 命令最长租约 200ms；这只是 D3—D7 标定的起点。提交时租约不得超过该帧的剩余有效期。
7. A 的驱动是唯一硬件写入者；B 传目标请求，C 只传启停跟随意图。任何模型文本都不能直接控制角度、清故障或重新使能。
8. 多人进入时先锁定当前目标；丢失确认前不随检测框抖动频繁换人。首版不承诺同时辨认发言者并自动转向。

## 4. A：FPGA 与转轴的具体操作

### A1. 先跑通板卡与可重建平台，D1—D3

1. 记录 KV260/K26 型号、载板修订、电源、散热、microSD；按对应镜像指南检查启动固件兼容性，只在确有需要时更新固件。
2. 取得官方 KV260 参考镜像和同版硬件源码，核验下载完整性；保留原始恢复卡。先串口/SSH 登录，再检查网络、剩余磁盘和系统日志。
3. 与 B 跑一张图的官方 DPU 示例，确认加速器、运行时和模型匹配。
4. **同时启动参考硬件重建。** 下载一个可运行镜像只能说明现成例程可用，不能证明能加入自研 IP。
5. D2 和 C 核验最终屏幕输出路径；部分镜像/硬件设计不自带可用桌面，不能假定“插 HDMI 就有网页”。显示相关硬件/设备树需要保留在后续平台中。
6. D3 前输出 `toolchain_lock.json`：OS、Vivado/Vitis、构建环境、平台 commit、镜像 SHA256、固件、运行时、DPU 配置/fingerprint。

候选历史组合为 Vitis AI 3.0 + DPUCZDX8G 4.1 + Vivado/Vitis/PetaLinux 2022.2，AMD 文档给出了该组合的兼容关系；它是候选复现基线，不是要求升级或倒退现有工程。若已有可运行且可重建的其他组合，沿用并完整锁定。完整构建环境按对应版本支持的 Linux 配置准备，Windows 用于编辑与应用开发。[AMD 兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)

### A2. 编写最小自定义 IP，D2—D6

| 待写文件 | 具体功能 |
|---|---|
| `axi_regs.sv` | AXI4-Lite 读写、影子命令、原子提交、IP/配置版本回读 |
| `pwm_generator.sv` | 固定周期计数、脉宽输出；在周期边界更新，避免半个周期改变脉宽 |
| `command_guard.sv` | 角度范围、命令序号/会话、租约和使能校验 |
| `slew_limiter.sv` | 每个控制步长的指令变化限制；这约束指令，不等于实测机械角速度 |
| `stop_watchdog.sv` | 外部停止输入同步、命令超时、锁存与恢复条件 |
| `motion_guard_ip.sv` | 总装与状态机 |
| `tb_motion_guard.sv` | 正常、边界、越界、超时、重复、复位、停止、恢复等自检用例 |
| `servo_calibration.yaml`、生成脚本 | 从同一份标定生成 RTL 参数和软件配置，附配置校验值 |

**首版采用构建时固定标定参数。** A 修改标定后重新构建；软件/硬件校验值不一致时不能使能。这样避免临时设计一套复杂的在线参数修改协议。

寄存器至少包含下列含义；A 在 D2 的 `register_map.md` 中冻结偏移、位宽和复位值：

| 寄存器类别 | 含义 |
|---|---|
| `IP_ID / VERSION / CONFIG_CRC` | 检查加载的硬件和软件标定是否一致 |
| `CONTROL / STATUS / FAULT` | 禁用、受控使能、停止、状态、故障；清故障不等于允许重新运动 |
| `SESSION / CMD_SESSION` | 使能握手后的当前会话；命令必须属于当前会话 |
| `TARGET_MDEG / CMD_SEQ / LEASE_US` | 目标角、新命令号、从硬件接受起计算的剩余租约 |
| `COMMIT / APPLIED_SEQ / REJECT_REASON` | 将影子字段一次提交，查询是否被接受和拒绝原因 |
| `LIMITED_TARGET_MDEG / CMD_AGE_US` | 回读受限指令角和最后有效命令年龄 |

重复、越界、会话错误和无效提交均不续租。PS 服务或 PL 重启后先禁用、清队列并重新握手，用户完成位置确认后才能开始新的跟随。不要用一个持续运行的“心跳线程”掩盖视觉已经停帧。

### A3. 封装和加入 KV260，D4—D8

1. 仿真先通过，再用 Vivado 的 IP Packager 封装现有 RTL；若用 AXI 外设模板，补全有效地址、写掩码和读写响应逻辑。
2. 将 IP 所在目录加入主工程 IP Repository，加入 Block Design。
3. 连接 PS 的 AXI 主接口、互连、时钟、复位；导出 PWM/停止端口。根据该 KV260 载板手册、原理图和实物核对管脚、电平与时钟约束，不沿用复旦微引脚。
4. 给软件建立真实可访问的通路：优先采用受限的 Linux UIO/MMIO 设备映射；设备树/地址范围与 Vivado Address Editor 一致。若选择匹配的 PYNQ 平台，则用其 MMIO，不能假定普通镜像天然安装了 PYNQ。
5. 集成 DPU：沿所选参考工程的构建方式，把 motion IP 放入可重建平台，再链接相应 DPU/应用硬件工件。保留显示、时钟、复位和中断的有效配置。
6. 检查 DRC、资源、时序和未约束路径；生成该流程实际需要的位流、XSA、设备树、`.hwh` 或 `.xclbin` 等工件。不同加载方式不要求把这些文件全部混装。
7. 上板先只读 `IP_ID/CONFIG_CRC`，随后在不接舵机的情况下输出测试 PWM，再进行 DPU 推理与 PWM 同时运行。

**DPU 与 motion IP 必须共同存在。** 普通整片重配置加载第二个位流会替换原设计。只有平台明确设计并验证了局部重配置时，才能讨论分区域加载；本轮不新增局部重配置架构研究。[AMD Kria 平台源码](https://github.com/Xilinx/kria-vitis-platforms)

### A4. 接舵机与装配，D5—D12

1. 核实执行器是位置舵机、连续旋转舵机还是其他电机；本计划默认**有限角度位置舵机**。连续旋转舵机不能靠位置 PWM 直接指定绝对角度，需要反馈和不同控制方案。
2. 先按数据手册配置 PWM，不把 50Hz、1—2ms、180°当作所有舵机通用参数。用示波器/逻辑分析仪看周期、脉宽和停止输出。
3. 舵机使用独立合适的电源支路；与控制信号建立正确地参考及必要的电平适配。不能从 FPGA IO 给电机供电。
4. 用台架、空载或轻载测试中位、小角度和限位，确认停止/超时的实际反应。失去 PWM 后舵机可能保持、放松或有其他表现，不能把“停止 PWM”等同于机械已经停住。
5. 依据重量、惯量和走线验证扭矩，转盘/轴承承担载荷，舵机负责驱动。首版只做水平轴，范围从小角度逐步扩大到实测允许范围。
6. A 负责底座、传动、轴承和线束；C 负责面板、屏幕、麦克风/扬声器位置。优先使用已有结构，局部改支架，不重做整套外观。
7. 无位置反馈时，上电/断力后状态为 `needs_reference`。采用可验证的机械标记、断力人工对齐和受控使能流程；首个脉冲也需要轻载验证。不能自动发送“回中位”就宣称消除了突跳。

**A 对外最终提供：** `selftest()`、`arm_after_reference()`、`request_target()`、`stop()`、`status()`，以及至少一份真实板端波形和故障用例记录。

## 5. B：视觉与本地大模型的具体操作

### B1. 人体检测与目标跟踪，D1—D7

1. 用现有录像或 USB 相机在电脑上建立参考流程：读取帧、检测 person、画框、记录时间和 FPS。
2. 主模型先选所选 KV260/DPU 参考设计已经支持的人体检测模型，D3 前锁定具体权重、输入尺寸、预后处理和类别映射；不要在转换链还没通时启动训练新模型。
3. D2—D3 与 A 完成板端单图推理，检查输入输出和 DPU fingerprint。随后将相机接到板端，由一个进程负责采集。
4. 写 `detector_cpu.py` 与 `detector_dpu.py` 两个相同接口的后端，保证 UI 和跟踪器不依赖某个模型库。
5. 写简化跟踪/目标锁定：首版可用 IoU 匹配与短时保持；只选择一个当前交互目标，编号和持久身份分开。
6. 维护最新帧缓存和 `scene_state`。身份服务、UI 和看图问答取它们的数据，不重复打开相机。
7. 先用模拟运动驱动输出建议角度；A 台架通过后才接实体转轴。

建议初始采集 640×480，推理输入按模型固定尺寸设置。采集帧率与真实推理帧率分开记录；没有实测前不写“达到 30FPS”。

### B2. 视觉随动，D4—D8

实现文件：`tracker.py`、`target_selector.py`、`scene_state.py`、`visual_controller.py`。

控制顺序：

1. 用目标框中心减去画面中心，得到横向误差。
2. 先加小死区，例如半画面宽度的 5% 左右作为起点，在实物上调整，避免居中后持续抖动。
3. 先采用简单比例控制与平滑，不立刻叠加复杂预测或 PID。
4. 依据间隔 `dt` 产生受限的角度增量，方向在小角度台架上核验。
5. PS 和 PL 使用同版限位；到边界后不继续向外累加目标角，避免回转时迟迟不能反向。
6. 使用 A 返回的已接受/受限指令状态更新内部控制状态；切换目标、故障、停顿过久时重置滤波和积分。
7. 帧龄超限不提交，驱动真正写寄存器前再检查一次；旧画面配新 seq 仍然必须被拒绝。

视觉丢失时停止产生新的跟随目标，进入经 A 标定的保持/禁用策略；不自动快速回中或无限搜索。机械停止时间要另测，不能用软件日志代替。

### B3. 本地视觉语言模型，D2—D6

**本轮建议起步模型：Qwen2.5-VL-3B-Instruct 的兼容量化版本，在 Windows GPU 电脑上运行。** 选择它是为了先完成中文图像问答和文本对话，不是声称它是当前最优模型。若已有其他本地视觉语言模型通过相同验收，优先复用。

llama.cpp 官方多模态文档列出了对应模型支持，服务支持带图像的对话接口；视觉版本需要匹配的视觉投影文件，只有语言模型文件不足以看图。[llama.cpp 多模态说明](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md)、[Qwen 原始模型卡](https://huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct)

操作步骤：

1. D1 检查显存/驱动和磁盘，创建独立模型环境；不共用旧版 Vitis AI 量化环境。
2. 从官方 llama.cpp 发布页获取匹配 Windows/GPU 后端的版本，保存版本号；下载兼容 GGUF 模型和匹配 `mmproj`，记录来源、许可证和 SHA256。
3. 在电脑本机先做一次文本问答、一次图片问答，检查后端日志和显存，确认实际使用了预期计算后端。
4. 把已下载的本地文件路径写入启动脚本，避免每次开机再联网找模型。
5. 使用短回答、单张图、单并发，初始输出上限约 128 tokens、上下文约 4096；显存不足时先缩图、减上下文/批量并检查兼容性，不盲目加大模型。
6. 写 B 自己的 `dialogue_service.py`，向 C 暴露稳定 `/dialogue`。内部再调用模型引擎，承担提示词、图像封装、超时与错误处理。
7. 测试“你看见了什么”“我手里的杯子是什么颜色”等需要图像的题目，以及不需要图像的普通对话；不能只把检测出的 person 字段发给纯文本模型就算完成看图问答。

示例启动模板（路径和文件名须替换为实际下载内容；尚未执行）：

```powershell
.\llama-server.exe -m C:\models\vlm\model.gguf --mmproj C:\models\vlm\mmproj.gguf --host 127.0.0.1 --port 8080 --n-gpu-layers 99 -c 4096
```

启动后先检查 `/health`，再通过 B 的服务测文字和图片两类请求。上述服务能力与参数应以锁定版本的官方说明为准。[llama.cpp 服务文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

产品可以描述为“类似豆包的视听交互体验”，这里部署的是所选开源模型。若另接真实豆包服务，必须单独列明云端依赖和模型位置，不能称其权重已经在 KV260 本地运行。

### B4. 视觉身份记忆，D7—D10

优先复用旧项目已经能运行的人脸链；若尚无实现，可从 OpenCV 官方 YuNet 人脸检测和 SFace 特征识别例程开始，在 Windows 上先完成。锁定 OpenCV 与模型文件的匹配版本，避免直接复制不同版本示例。[YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)、[SFace](https://github.com/opencv/opencv_zoo/tree/main/models/face_recognition_sface)

1. 人体目标确定后取对应区域，在其中检测人脸、对齐、提取特征。
2. 登记时要求一个明确目标、足够清晰的人脸、本人确认；采集多个合格样本并保存姓名/特征/模型版本。
3. 用 SQLite 保存身份和样本信息；默认不保存原始人脸照片，示例与发布包中不带真实身份库。
4. 匹配设置 unknown 和时序确认；阈值用本项目独立的已知/未知样本调试，不能照搬论文阈值承诺准确率。
5. `track_id` 只表示这次跟踪，`person_id` 才是持久身份；身份结果携带 `boot_id/frame_id/presence_session_id/track_id/db_revision`。
6. 目标切换、人员离开、跟踪重启或库版本变化后，丢弃旧结果；姓名不能因一次慢请求错绑到下一个人。
7. 支持删除、纠错并清缓存，重启后仍生效。只做演示规模身份识别，不将其作为门禁或付款认证。

完整产品保留身份功能；首版允许它依赖本地主机。迁移到 KV260 CPU 是后续优化，不挤占 B 的 DPU 与对话主线工时。

## 6. C：玩偶 UI、语音和音响的具体操作

### C1. 屏幕和音频外设，D1—D3

1. 在电脑上分别完成录音保存、回放、显示测试页，确认设备本体工作。
2. 接入 KV260，记录相机之外的 USB 音频设备、采样率、声道数和播放设备标识；设备重启后编号可能变化，应优先用稳定标识选择设备。
3. 与 A 验证镜像内可用的显示路径：桌面浏览器、Qt/SDL 等选一种，不默认所有镜像都提供 Chromium/桌面。
4. 能用现成浏览器时沿用 HTML/Canvas 玩偶；否则 D3 前锁定该平台可用的轻量渲染方式或记录电脑驱屏的过渡方案。
5. 看麦克风位置和扬声器朝向，尽量降低扬声器直接灌入麦克风；首版按键录音期间暂停播放。
6. 显示屏、音频和舵机电源合计检查。屏幕/舵机按实际功耗使用适当支路，避免所有负载都从板卡 USB 取电。

### C2. 玩偶与面板，D1—D7

先用已有 2D 资产或简单眼睛/嘴形，做下面 7 个状态，不重新设计复杂 3D 角色：

| 状态 | 出现时机 | UI 内容 |
|---|---|---|
| `idle` | 没有当前目标 | 待机/眨眼 |
| `attending` | 发现目标 | 目光朝向目标、可交流提示 |
| `listening` | 正在录音 | 收音动画和录音指示 |
| `thinking` | 识别/模型/合成处理中 | 简短等待提示 |
| `speaking` | 音频实际开始播放 | 嘴部动画与字幕 |
| `degraded` | 主机或服务不可用 | 明确说明当前功能不可用，保留可用本地界面 |
| `fault` | 转轴故障/停止锁存 | 停止提示和人工恢复指引 |

实现 `index.html`、`avatar.js`、`state_store.js`、`audio_sync.js`，或选定渲染工具下的等价文件。UI 只消费状态事件，不直接访问 FPGA。

口型先按实际播放音频的分段能量开合；音频播放暂停/取消时同步闭嘴。首版字幕整句显示即可，不承诺逐字时间对齐。

### C3. ASR/TTS，D2—D6

ASR 是语音转文字，TTS 是文字转语音。二者的模型选择、服务和测试都归 C，首先在 Windows 上独立运行，再接板端录放音。

建议使用一个离线语音框架减少集成：例如 sherpa-onnx 的 SenseVoice ASR 和该框架文档列出的中文 VITS TTS 模型。它支持离线语音处理，但模型权重和具体平台运行速度仍需自行验证。[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)、[SenseVoice 使用文档](https://k2-fsa.github.io/sherpa/onnx/sense-voice/index.html)、[VITS 模型说明](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/vits.html)

1. 选择中文 ASR/TTS 工件，记录模型文件、词表/字典、采样率和许可证；D3 前冻结能跑的一组。
2. 先给 ASR 一段已录好的中文 WAV，取得正确文字；给 TTS 一句固定中文，生成并播放 WAV。
3. 再接真实麦克风录音，按模型要求转换采样率/声道；不能只改 WAV 头而不做重采样。
4. 实现主机 `speech_service.py`：`/asr`、`/tts`、`/health`，设定一次录音时长和文件大小上限。
5. 在板端写 `capture_audio.py` 和 `playback_audio.py`，用已知测试音频验证端到端采样率、音量、爆音和截断。
6. 单轮先采用完整音频上传/返回；稳定后才考虑分句返回。录音不足、静音、超时和取消均有明确状态。
7. 小词表控制意图如“停止跟随”由明确规则校验后交本地接口；语音识别可能失效，实体停止键仍独立工作。

### C4. 对话编排，D3—D10

核心文件：`dialogue_orchestrator.py`、`session_state.py`、`service_client.py`、`event_gateway.py`。

执行状态机：

```text
idle/attending → listening → thinking → speaking → attending
                     任意状态可取消 → 作废本轮 → attending
                     依赖失败 → degraded（可重试新一轮）
```

具体操作：

1. 每次录音创建新的 `utterance_id`，每次模型请求再建 `request_id`。
2. ASR 成功后取得新鲜快照，再请求 B 的模型服务；无图时明确改成普通文字问答，不声称看到了当前画面。
3. 回复仅允许文字与枚举表情；限制回复长度，交给 TTS。
4. 只播放当前有效轮的 TTS 结果；取消后迟到的 ASR、模型和 TTS 结果统一丢弃。
5. 主机超时不阻塞板端视觉；UI 显示重试提示，不自动执行模型建议的动作。
6. 登记姓名进入单独确认事务，C 负责询问与按钮，B 负责样本/绑定/写库。目标离开或变更时取消事务。
7. 把启动顺序、健康状态、版本、日志目录汇总成统一入口，D5 开始每天使用。

## 7. 20 天唯一权威排期

以下表格是本版唯一排期。其他章节的日期是这张表的展开；旧方案的 30 天日期不再用于本轮派工。

| 日期 | A：FPGA＋转轴 | B：视觉＋本地模型 | C：UI＋语音＋音响 | 当天共同验收 |
|---|---|---|---|---|
| D1 | 盘点板卡/电源/舵机，启动 KV260，确定构建环境 | 盘点现有代码/电脑，跑相机和 CPU 检测样例 | 点亮屏幕，电脑录放音，复用现有 UI | 建仓库和 BOM；列清已完成/待做；确定模型主机和显示位置 |
| D2 | 启动官方平台重建，冻结寄存器/标定格式，写 PWM | 与 A 跑 DPU 单图；定义帧/场景消息；安装本地 VLM | 板端外设试通；UI 七状态；ASR/TTS 单独启动 | API V1 和 mock 数据可用；C 能调用 B 的健康接口 |
| D3 | 完成 PWM/保护基础仿真；检查平台重建结果 | 锁定 DPU 模型与预后处理；电脑文字/图片问答 | 锁定显示方案；录音→ASR、文字→TTS 分别可用 | G1：工具/模型/显示路径冻结；阻塞项当天决策 |
| D4 | 完成 IP 封装、MMIO/设备树初接、空载波形 | 板端采集/后处理/跟踪，CPU 后端保底；接模拟运动 | 写编排状态机；固定句播放驱动玩偶 | 视觉事件能改变 UI，语音文本能请求模型；有完整日志编号 |

## 9. 验收指标与实际测试方法

下表是团队内部目标，不是赛事规定，不是实测结果，也不保证一定达到。D3 用基础测试检查目标是否合理，正式测试记录配置、数量、失败案例，不能用单次最好成绩替代整体表现。

| 项目 | 建议目标 | 怎么测、谁负责 |
|---|---|---|
| 视觉随动 | 展示区域内能稳定跟随；板端有效检测更新力争 ≥10Hz | B 统计至少1000帧；同时报告采集/推理/输出频率，CPU保底达不到时记录差距 |
| 视觉控制时延 | 出队到命令被接受 P95 力争 ≤200ms | B/A 同板单调时钟计时；若无准确相机曝光时间，不命名为“曝光到动作” |
| 实体运动 | 20次左右移动试验，方向正确、不持续振荡、不撞机构边界 | A/B 视频＋命令日志；声明无编码器时测到的是视觉效果和指令角 |
| 指令失效 | 丢帧/旧帧/进程停顿/无效指令不能无限续期 | A/B 故障注入；记录租约到期的硬件输出及真实机械反应 |
| PWM/资源 | 周期和脉宽符合标定；时序收敛、有完整资源报告 | A 用仪器取至少1000周期，报告最大偏差；记录时钟和仪器精度 |
| 实体停止 | 10次按键停止、10次服务异常均进入规定状态 | A 记录停止输入、输出变化和机械状态；不将软件停止等同于断电或零机械位移 |
| 语音识别 | 安静环境30句固定中文测试，任务关键内容 ≥27句正确 | C 保留转写结果与人工判定；不是通用识别准确率声明 |
| 图像问答 | 20题当前画面问题，≥16题内容正确且无关键虚构 | B/C 提问与保存快照绑定、人工判定；错误/不确定分别记录 |
| 对话体验 | 松开按键到首段实际出声 P95 力争 ≤8s；等待时立即反馈 | C 测至少30轮，分开记录 ASR/模型/TTS/传输/播放；图片题另列 |
| 身份记忆 | 3位同意登记者各返回5次，力争 ≥13/15正确；未知者另测至少10次 | B 报正确/拒识/误认，不只报成功比例；调整阈值后用不同测试片段复测 |
| 取消一致性 | 20次取消均不重新播出旧轮音频 | C 在 ASR、模型、TTS、播放各阶段取消；检查编号和日志 |
| 完整流程 | 20轮整机流程力争 ≥18轮成功 | C 主持；主机参与、身份、看图、停止分别纳入记录 |
| 稳定与恢复 | 连续2小时无崩溃；冷启动3次均按文档恢复 | 三人分看硬件、模型、交互；“恢复”包含人工位置确认，不是自动开始转动 |

### 必测异常清单

- A：非中位上电、断力后被人转动、外部停止、PS服务崩溃、PL重新加载、越界/重复命令、标定不匹配。
- B：旧帧排队、检测停帧但程序仍活着、画面无人/多人/遮挡、目标在限位外再返回、身份迟到、删除后旧结果返回。
- C：长时间静音、录放音设备拔插、播放中取消、模型超时、局域网断连与重连、UI 刷新、重复按键、重启后设备编号变化。

CPU/DPU 比较尽可能使用同源模型、相同输入/阈值/预后处理，分别报告量化差异与端到端开销。若只能获得不同模型的结果，写成“两个系统配置比较”，不写成同模型加速倍数。

## 12. 如果坚持所有模型都在 KV260 上

这会改变本计划的工作量和交付能力，不能只把 Windows 地址替换成 localhost。

需要先用 1—2 天做实测：板端操作系统可用内存、检测并发负载、小语言模型首字/生成速度、语音识别/合成时延，以及多模态运行时是否支持 ARM 和所需算子。传统 DPU 人体检测方案不能直接用来运行任意 GGUF 视觉语言模型。

若小文本模型与轻量语音能运行，可建立“检测结构化结果＋本地文本对话”方案；但它理解的是检测摘要，不等价于任意画面语义理解。保留真正图像问答仍需要适用视觉语言模型的单独实测和部署。

因此本版 20 天基线仍采用 Windows 本地主机。纯板端可作为第二阶段目标，或在用户明确其优先级后重新排期；不能预先保证与双设备方案同等体验。

### 14.2 启动顺序

1. 检查机身、线缆、供电与停止键，转轴保持禁用。
2. 启动 KV260 和 Windows，确认局域网及本地配置；检查当前硬件工件与软件版本。
3. 主机启动模型、身份和语音服务，健康检查全部 ready。
4. 板端启动视觉、运动服务、交互服务和 UI；检查相机、音频、显示与IP版本。
5. A或操作者完成实际机构的位置确认，再受控使能跟随。
6. 做一次移动、一次文字/语音、一次看图问答自检，随后进入演示。

服务可自动启动，但自动开机不等于自动允许电机运动。停止/断力后的恢复步骤仍按 A 的标定流程执行。

### 14.3 五分钟演示提纲

1. 展示设备与两台计算节点的职责，说明 FPGA 自研部分。
2. 人进入画面并左右移动，玩偶响应、设备跟随。
3. 按键提问并举起物品，设备结合实时快照回答与播报。
4. 自愿登记姓名，离开后返回，展示身份问候和 unknown 区别。
5. 取消一次播报，显示旧结果不会重新播放。
6. 断开主机链路，展示板端视觉跟随和停止仍可用；恢复后新建对话。
7. 展示停止与人工恢复，最后给出实际性能/资源表，不报未测加速倍数。

## 15. 本版如何修正旧计划的实施缺口

| 旧审查问题 | 本版处理 |
|---|---|
| 断力后不知道真实位置，却承诺缓启动 | 第4节明确 needs_reference、人工对齐/位置确认与首脉冲验证 |
| 新序号可能包装旧视觉指令 | 第3/4/5节规定提交前重新核验帧龄、租约上限、拒绝不续期 |
| 标定文件与硬件参数脱节 | 第4节采用同源生成的构建时参数与版本校验 |
| 限位外继续积分，返回不及时 | 第5节要求PS防止向外累加并跟随硬件接受状态 |
| 混用相机、PS、PL和主机时钟 | 第3/9节规定时钟来源与测量口径，跨机不直接相减 |
| 身份慢结果串到另一个人 | 第3/5/6节增加目标/会话/帧/数据库版本与事务校验 |
| 多份排期互相冲突 | 第7节作为唯一20天排期，所有操作说明引用它 |

本版参考了原项目需求、KV260 V1.1 计划及其审查记录，采用用户此次明确的三人分工和20天目标重新编排。旧文件中的流程建议是参考内容，不构成对本轮已完成开发或已获赛事认可的证明；赛务材料与最新提交时间应另按赛事当期公告核实。
