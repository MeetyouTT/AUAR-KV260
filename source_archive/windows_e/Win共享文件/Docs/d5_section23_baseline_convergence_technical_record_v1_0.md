## 1. 背景与目标

### 1.1 问题

跨文档收敛产生了 16 条"团队已经判定、但尚未落进任何一份文档"的口径，以及 6 步必须执行的收敛动作。这些内容此前只存在于一次 Cline 会话的交接日志（`.cline-handover.md`）里，存在三个风险：

1. **无权威载体**：换设备或换窗口后，这 16 条与 6 步在任何正式文档中都不存在，团队无法据以排期与追踪。
2. **无法挂进需求追踪表**：D5 第 3 节 W00-07 要求建立"任务编号 → 模块 → 验证项目 → 证据文件 → 完成状态"的追踪表，而未编号的口径挂不进去。
3. **两套追踪线互不交汇**：任务清单线（D5 的 W00 至 W16）与会话续接线（交接日志）互不引用，作者与接手者都可能漏项。

### 1.2 目标

在 D5 中新增第 23 章「W17 基线收敛与版本升级」，把 16 条已判定口径登记为 W17-01 至 W17-16，把 6 步收敛动作登记为 W17-17 至 W17-22，使每一项都具备：任务编号、等级、依赖、落点（需修改的文档与章节）、判据。

### 1.3 明确不做的事

- 不修改 D1、D2、D3、D4 的任何正文：第 23 章只登记"某处应改成什么"，实际改写正是 W17-17 至 W17-22 这些任务要做的事。
- 不替团队拍板 5 项跨文档冲突：只在 23.1 节登记其影响面，指向 W00-06 待决事项表。
- 不改动第 1 至 22 章已冻结的验收阈值与既有任务编号。

## 5. 踩坑与纠错

| 编号 | 现象 | 根因 | 处理 |
|---|---|---|---|
| E1 | 首次 dry-run 自检失败："引入了 CRLF" | 文本块由编辑器以 Windows 换行写出，而 D5 为纯 LF（实测 1068 个 LF、0 个 CRLF） | 脚本增加换行规范化，并保留"最终文本不得含 CRLF、不得含 BOM"的自检断言 |
| E2 | 差点写入一个错误的冲突断言：曾判定 D2 第 6.4 节的 `0x05C` 与 D1 第 10.5 节的 `0x05C` 命名冲突 | 只按偏移比对，未先确认两份表属于不同 IP 的地址段 | 回看 D2 第 6.4 节原文，确认其为新建独立 IP 且明确"不复用运动 IP 地址段"，遂改为正确表述：不同地址段，同偏移不构成冲突，软件须按各自基址访问 |
| E3 | 文本块存在两个标题前缺空行、末尾多 3 个空行 | 分块写入时每块末尾各留一个换行 | 脚本增加 `normalize_markdown`：标题前补空行、压缩连续空行、去末尾空行，实测文本块由 106 行规范化为 104 行 |
| E4 | 交接日志内部数字不一致：第 2.2 节标题写"16 条"，第 3 节又写"2.2 的 21 条" | 16 条已判定加 5 项待拍板等于 21，两种计数混用 | 第 23 章只登记 16 条已判定口径，5 项待拍板作为引用条目单列，避免计数含混 |
| E5 | 用 `Get-Content` 统计 D5 行数得到 606，与 `Select-String` 的行号 1068 不符 | PowerShell 的逐行读取与该文件的统计口径差异，容易误判文件被截断 | 以字节级统计为准（PowerShell 逐字节数换行符：CRLF 0、LF 1068），并在脚本内以 Python 计数复核 |
| E6 | 第 23 章两处判据写成"五份文档检索…命中数为 0"，但第 23 章自身为记录该判据必然包含这些字样，按字面永远无法满足 | 判据只写了检索内容，未限定检索范围 | 收尾复核时发现并修正：检索范围限定为"第 1 至 22 章与 D1 至 D4 内"，并注明第 23 章不计入；用 `patch_judgements.py` 对 D5 与文本块源文件同步修正 |
