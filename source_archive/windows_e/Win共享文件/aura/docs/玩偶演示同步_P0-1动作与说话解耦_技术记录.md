> 项目：AURA（`D:\share、\项目开发\FPGA-amd自主命题赛道\aura`）
> 触发：用户实机反馈「**玩偶演示好像没有与模型反馈同步**」
> 依据：`docs\玩偶素材丰富填充_方案设计.md` §3.2（痛点）/ §4.1 P0-1（做法）/ §8（风险）
> 日期：2026-10-04　状态：**已修复**（验收 `RESULT: OK`；静止时长 4.05s → 0.00s）

## 一、问题：玩偶 0.9 秒就不动了，语音还在念

用户反馈的"不同步"**不是显示问题，而是方案里早记录过的设计缺陷**。证据来自实机日志
（`%TEMP%\aura_host.log`，主机侧记录 LLM 实际返回）：

```text
req=stage-… emotion=friendly action=ack_nod  1281ms | 你好呀，我是你的桌面玩偶，可以陪你聊天、玩游戏，想和我做朋友吗？
req=stage-… emotion=friendly action=ack_nod  1330ms | 你好呀！我是你的桌面玩偶…还能给你讲有趣的故事哦～
req=stage-… emotion=neutral  action=-        8968ms | 你好呀，今天过得怎么样？      ← 这一次是同步的
```

- `avatar_action=ack_nod` → FSM 进 `ACK_NOD`，而它是 **burst 一次性动作**（22 帧 / **0.917s**，
  播完**夹在末帧静止**）；
- 同一时刻 TTS 还在念 3~5 秒的回复 → **玩偶 0.9 秒后就不动了**；
- `action` 为空那一次走的是 `SPEAKING_NEUTRAL`（loop 素材），所以"一直在动" → 看起来同步。

即方案 §3.2 的诊断：**`avatar_action` 与 `emotion` 互斥**，一次性动作被当成"终态"，
没有"点头 → 继续说"的续接。

## 二、根因（可量化）

| | 旧行为 | 说明 |
|---|---|---|
| 动作段 | `ACK_NOD` 0.917s（frame 1→22） | 正常 |
| 动作段之后 | **停在 ACK_NOD 末帧**，直到 `AUDIO_PLAYBACK_STOP` | ❌ 语音还剩 ≈4 秒 |
| 语音仍在播但玩偶静止 | **≈4.05s** | 用户观感就是"没同步" |

## 三、修法（P0-1：动作段 → 播报段，零新增事件类型）

| 改动 | 内容 |
|---|---|
| `board/runtime/fsm.py` 转换表 | 对 `ACK_NOD / AWAKE / PUZZLED` 增加 `AUDIO_PLAYBACK_START → SPEAKING`（目标占位） |
| `board/runtime/fsm.py::_route_emotion` | 事件为 `AUDIO_PLAYBACK_START` 时按 `payload.emotion` 分档 → `SPEAKING / SPEAKING_NEUTRAL / SPEAKING_LOW` |
| `tools/demo_stage.py::StageCore` | 新增 `emotion` 记录、`_burst_done` 标记与 `take_burst_finished()`（burst 播完只上报一次） |
| `tools/demo_stage.py::StageApp._tick` | 检测到"动作段播完"**且 TTS 仍在播** → 发 `AUDIO_PLAYBACK_START` 接进播报段；语音已停则保持不动 |

**关键决策：不新增事件类型**（工程红线）。触发事件复用合同里**早已存在但从未被使用**的
`EventType.AUDIO_PLAYBACK_START`（语义 = "播报开始"），因此：

- 对话协议（`DialogueRequest/Response`）零改动；
- `events.py` 事件全集零改动；
- 播放层与 FSM 之间仍然是既有的 EventBus 通道。

**"纯应答"语义也保住了**（方案 §8 第 1 行）：只有"语音还在"才续播（判据 = `tts.is_busy()`），
`ACK_NOD` 若后面没有语音，就停在末帧后由 `AUDIO_PLAYBACK_STOP → IDLE` 收尾 —— 一行可回滚。

   严丝合缝的口型对齐需要 TTS 时长/音素驱动（超出本轮范围）；
