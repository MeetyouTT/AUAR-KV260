# 玩偶素材丰富填充 · 方案设计

> 项目：AURA（`D:\share、\项目开发\FPGA-amd自主命题赛道\aura`）
> 主题：在 v2（14 态 / 12 素材）已落地的基础上，解决三类"素材不够用"的观感问题：
> ① **长句播报**（一句话很长时玩偶怎么演）；② **肯定 / 否定时的说话状态**；
> ③ **素材清单缺口**（摇头缺失、mock 与白名单不一致等）。
> 定位：**方案设计文档**，供拍板；本文件不含代码实现。
> 日期：2026-10-04

## 一、背景与目标

v2 已把状态集扩到 14 态、素材重制为 12 条（10 个 loop 态 39 帧 + 2 个 burst 态 22 帧，
统一 464×480 / 24 fps），并完成验收与演示。相关记录：
`docs\玩偶状态系统v2落地实施_技术记录.md`、演示页 `docs\demo_v2\index.html`。

"状态覆盖够"不等于"演得像"。本轮要解决的是**素材与播放语义的丰富度**问题：

| 编号 | 目标 | 不达标时的具体观感 |
|---|---|---|
| G1 | 长句播报不露"循环节" | 说 10 秒的句子，玩偶把同一段 1.62s 动作原样重复 6 遍 |
| G2 | 肯定 / 否定能"先表态、再说话" | 点完头玩偶就静止了，而语音还在播 |
| G3 | 素材清单与实际用例对齐 | 有"点头"没有"摇头"；mock 送 `wave` 被静默丢弃 |

## 二、现状事实（代码级，可核对）

### 2.1 播放层能力边界（`board/interaction/qt_widgets.py`）

| 位置 | 事实 | 由此可推断 |
|---|---|---|
| `_SpriteSequence`（:36-） | 字段只有 `burst`；方法只有 `duration() / frame_at(t) / finished(t)` | 播放层是**单一映射 t → 帧号**；变速、相位偏移、分段映射**都能在这一层实现** |
| `frame_at`（:48-） | loop 素材对 `t` **取模**无限循环；burst 素材**夹在末帧**停住 | 长句**不需要额外素材**就能撑住时长（问题只是"看得出来在循环"） |
| `finished(t)`（:60-） | 判定 burst 是否播完；loop 恒 `False` | **"一次性动作播完"的判定已经现成** → 两段式演出不必新增机制 |
| `AvatarPanel._state_time`（:666-） | 状态内时间基，**状态一变就归零** | 每次进 SPEAKING 都从第 0 帧起播 → **没有随机相位**，重复感加倍 |
| `_sprite_sequence`（:678-） | `burst = runtime_state in avatar_assets.BURST_STATES` | burst / loop 语义由 `BURST_STATES` **集中决定**，改语义只改一处 |

### 2.2 协议字段（`board/runtime/dialogue_client/adapter.py:59-81`）

`DialogueResponse` = `{protocol_version, request_id, scene_seq_used, reply_text,
emotion, avatar_action, visual_claims, raw}`

- **没有** 时长 / 分句 / 语音包络字段 → 无法直接得知"这句话要说多久"；
- **但有 `reply_text`** → 可按字数估算时长（中文口语 ≈ 4~5 字/秒），
  这是长句方案的关键抓手；
- 请求侧已存在 `allowed_emotions` / `allowed_avatar_actions`（`adapter.py:32-33`）
  → **白名单机制现成**，扩充动作**不需要改协议结构**。

### 2.3 肯定 / 否定的实际路由行为（`board/runtime/fsm.py:352-367`）

```python
if target is not RuntimeState.SPEAKING:        return target
...
if action == "ack_nod":                        return RuntimeState.ACK_NOD
if action in ("emo_surprised", "surprised"):   return RuntimeState.AWAKE
if action in ("emo_puzzled", "puzzled"):       return RuntimeState.PUZZLED
return RuntimeState[speaking_state_name(payload.get("emotion"))]
```

这是**互斥路由**：一旦命中动作，就**不再进 SPEAKING**——即"动作"与"说话"无法并存。

### 2.4 现有素材与状态映射（`board/interaction/avatar_assets.py`）

- **12 条素材**：`idle_normal / idle_present / idle_listening / idle_thinking /
  talking_normal / talking_neutral / talking_low / emo_puzzled / emo_sad /
  idle_offline / emo_surprised(burst) / ack_nod(burst)`
- 三档播报**全部 loop**（`BURST_STATES` 目前只含 `AWAKE`、`ACK_NOD`）
- 体积实测：单条 39 帧 ≈ **12.25 MiB**、22 帧 burst ≈ **6.9 MiB**
  → 12 条合计 ≈ **145 MiB**

## 三、痛点与根因

### 3.1 长句：双重重复

1. **入场一致**：`_state_time` 归零 → 每次都从第 0 帧起播（同一个"入场动作"）；
2. **循环节一致**：素材长 1.625s，长句必然反复回到同一帧。

两者叠加，观众**极易识别出"在放同一段循环"**。
关键认知：问题不是"演不出来"，而是"看得出来在循环"——所以**修法不必加长素材**。

### 3.2 肯否：动作与说话互斥（真设计缺陷）

`avatar_action` 与 `emotion` 只能二选一，导致：

- `ack_nod` 之后若还有话要说 → 玩偶只点头 0.92s，在 `AUDIO_PLAYBACK_STOP` 之前
  **就已经静止**（回到 IDLE），而语音仍在继续；
- **否定连素材都没有**（无摇头态）→ 只能落到 `SPEAKING_*` 或语义不符的 `emo_puzzled`。

### 3.3 一致性隐患：mock 送 `wave`，白名单不认

`board/runtime/dialogue_client/mock_adapter.py:38` 构造的是 `avatar_action="wave"`，
而 `fsm` 只认 `ack_nod / emo_surprised / emo_puzzled`。→ 本地联调时该字段被
**静默忽略**，且 `wave` 素材本身也不存在。**要么补素材并入白名单，要么改 mock。**

## 四、方案

分三层：**P0 零新素材（只改播放层与路由逻辑）** → **P1 少量新素材** → **P2 观感增强（可选）**。
每项均注明"改哪里 / 成本 / 收益 / 风险"。

### 4.1 P0 · 零新素材（推荐先行）

#### P0-1 解耦"一次性动作"与"说话"（两段式演出）★ 核心修复

**问题**：见 §3.2。
**做法**：把 `ACK_NOD / AWAKE / PUZZLED` 从"终态"改成"**开场段**"——
burst 素材播完后**不直接回 IDLE**，而是**接进按 `emotion` 分档的 `SPEAKING_*`**，
直到 `AUDIO_PLAYBACK_STOP` 再回 IDLE，形成"先表态 N 秒、再说话 M 秒"的自然串行。

**落点**（两处，均为小改）：
1. `board/runtime/fsm.py`：在 `ACK_NOD / AWAKE / PUZZLED` 三态上增加一条
   **由播放层上报触发的 auto 迁移**：`burst 播完 → SPEAKING_*`；
   目标档位沿用现有的 `speaking_state_name(emotion)`，与三档素材一一对应。
2. `board/interaction/qt_widgets.py`：`_SpriteSequence.finished()`（:60-）**已能判定
   burst 播完** → 只需在 `_render_avatar` 中把这一事实**作为一次事件上报**给 FSM
   （走现成事件通道，不新增协议字段）。

**成本**：0 条新素材；改动集中在 2 个文件、约十几行。
**收益**：G2 直接达标——"好的，我帮你把灯打开"从"点头就停"变成"点头 → 继续说话"。
**风险**：若 `ACK_NOD` 被用作"纯应答收尾"（其后没有语音了），会多播一段 1.62s 播报循环。
→ **判定条件**：仅当 `AUDIO_PLAYBACK_STOP` **尚未到达**时才续播报（"语音还在就继续演"），
语音已停则直接回 IDLE。这样"应答 + 继续说话"与"纯应答"两种语义都正确。

#### P0-2 长句去重复：相位随机化 + 轻度变速

**做法**（都在播放层 `_sprite_sequence` / `_render_avatar`）：
- **相位随机化**：对 **loop** 素材（说话 / 待机）进入状态时给一个随机起始相位
  （即 `frame_at(t + phase)`，`phase ∈ [0, duration)`），**打破"每次入场都是同一动作"**；
  burst 素材**不加相位**（必须从第 0 帧起播——`_state_time` 归零正是为此）。
- **轻度变速**：按 `len(reply_text)` 估算句长，映射到 `speed ∈ [0.85, 1.15]`
  （长句略慢更耐看、短句略快更利落），播放时用 `frame_at(t * speed)`。
  估算规则：`字数 / 4.5 ≈ 预计秒数`，**仅在 SPEAKING 档生效**。

**成本**：0 条新素材；两处各几行。
**收益**：G1 的"入场一致"被完全消除；"循环节一致"被时间拉伸打散，肉眼基本不再识别为循环。

#### P0-3 长句打断：句中插一次 burst（可选加强）

**做法**：若估算句长超阈值（如 > 6s），在句中随机时刻插播一次短 burst（`ack_nod`，0.92s），
播完回到原播报档。
**成本**：0 条新素材（复用 `ack_nod`）。
**收益**：彻底打断周期感，观感像"说话时点头"的自然小动作。
**风险**：会稀释"点头=肯定"的语义 → **建议默认关闭**，仅对长句（> 6s）启用，
避免与 P0-1 的肯否语义打架。

#### P0-4 一致性收口（必修项）

把 `avatar_action` 取值在一处定义、多处引用，消除 §3.3 的静默忽略：
- `board/runtime/dialogue_client/mock_adapter.py:38`：`"wave"` → 改为白名单内动作
  （或按 P2 补齐 `wave` 素材后再保留）；
- 核对 `fsm` 白名单取值与 `allowed_avatar_actions` 上报值**收敛一致**
  （目标集合：`ack_nod / deny_shake / emo_surprised / emo_puzzled`）。
**成本**：0 素材；纯取值级修改。

### 4.2 P1 · 少量新素材（1~3 条）

#### P1-1 补 `deny_shake`（摇头）★ 最刺眼的缺口

**做法**：与 `ack_nod` **同规格**生成——burst 22 帧 / 24 fps / 464×480 / 绿幕，
时长 0.917s；`BURST_STATES` 加入 `DENY_SHAKE`，`fsm` 白名单加入 `deny_shake`。
**成本**：1 条素材 ≈ **6.9 MiB**，1 次生成。
**收益**：G3 达标，"肯定有、否定没有"的不对称消除；配合 P0-1 即可实现
"摇头 → 继续说明原因"。

#### P1-2 talking 素材"三段化"（重制，不增条数）

**做法**：重制三档 talking 时让素材**语义分三段**——起手（静止 → 进入动作）/
持续（循环主体）/ 收尾（动作 → 静止）。播放长句 = **起手 → 持续循环 N 次 → 收尾**，
**首尾不再硬接**。依据：burst 素材生成时已验证"起于静止、终于静止"能稳定产出，
同一手法可迁移到 talking。
**成本**：0 条新增（3 条重制，体积不变）；播放层需支持"分段映射"
（`frame_at(t)` 内按 `t` 落在起手 / 持续 / 收尾哪一段返回对应帧）。
**收益**：长句观感接近"真的在说话"，是 G1 的最优解。
**风险**：起手 / 收尾帧需与持续段无缝（末帧 ≈ 持续段首帧），否则会看到跳变
→ 沿用 v2 已有的帧差 / 亮度差验收方法把关。

### 4.3 P2 · 可选丰富件（按需）

| 项 | 用途 | 成本 | 说明 |
|---|---|---|---|
| `wave`（挥手） | 打招呼 / 首次见面 | 1 条 loop 39 帧 ≈12.25 MiB | `mock_adapter` 已在用；补齐后 P0-4 可改为保留 `wave` |
| idle 变体（`idle_normal_b`） | 长待机不重复 | 1 条 ≈12.25 MiB | **与长句同源问题**：待机久了同样看出循环；修法同 P0-2（相位+变速），素材变体仅作加强 |
| `sleep`（久待机休眠） | 长时间无人 | 1 条 ≈12.25 MiB | 若 `idle_offline`（离线态）可复用则不急 |
| 组合素材"点头+说话"/"摇头+说话" | 替代 P0-1 的串行拼接 | **4 条 ≈49 MiB** | 观感最好但体积代价大；**建议先用 P0-1 验证观感再决定** |

## 五、素材清单与体积账

| 阶段 | 素材条数 | 增量 | 累计体积（估） |
|---|---|---|---|
| 现状（v2） | 12 | — | ≈145 MiB |
| + P0（无新素材） | 12 | 0 | ≈145 MiB |
| + P1-1（`deny_shake`） | 13 | +6.9 MiB | ≈152 MiB |
| + P1-2（talking 三段化） | 13 | 0（重制） | ≈152 MiB |
| + P2 全量 | 17 | +4 条 | ≈200 MiB |

结论：**P0 + P1 是"低成本高收益"组合**——只增 **1 条素材**即可覆盖 G1 / G2 / G3 三个目标。

## 六、验收方式（可量化）

沿用 v2 的"**先算后看**"原则（不靠肉眼看图，先出数值）：

1. **G1 长句**：构造三档 `reply_text`（≈10 字 / 30 字 / 80 字），
   用 `tools/demo_scenario.py` 的 GIF 合成能力出片；对出片做**自相关分析**，
   检查"循环节"是否被削弱（峰值间隔不再固定等于素材时长 1.625s）。
2. **G2 肯否**：在 `demo_scenario.py` 时间线里加两条步骤——
   `ack_nod + 长文本` 与 `deny_shake + 长文本`，断言时间线出现
   **两段**（表态 → 播报），且播报段结束与 `AUDIO_PLAYBACK_STOP` 对齐。
3. **G3 清单**：断言 `BURST_STATES`、`fsm` 白名单、`mock_adapter` 三者取值**收敛一致**
   （可做成 `tools/verify_v2_amp.py` 同级的静态检查脚本）。
4. **素材规格**：新增 / 重制素材仍须过 v2 的验收门槛
   （464×480 / 24.0 fps / 帧数 / `amp_p90` / `face_p90`，**严格项不放宽**）。

## 七、施工顺序与拍板项

建议顺序（每步一个可验证单元，完成后停下来验收，符合"小步快跑"）：

1. **P0-4 一致性收口**——最小、最安全，先把白名单 / mock 对齐；
2. **P0-2 长句去重复**——纯播放层，可单独出片验收；
3. **P0-1 解耦动作与说话**——动 FSM，收益最大，单独验收；
4. **P1-1 生成 `deny_shake`**——1 次生成 + 入库 + 验收；
5. **P1-2 talking 三段化**——3 条重制，视前 4 步观感决定是否做；
6. P2 各项按需。

**需用户拍板的三点**：

- 是否采用 **P0-1 的"串行拼接"**（点头 → 说话），还是愿意付体积代价做**组合素材**？
- **`ACK_NOD` 的语义边界**：仅"纯应答"，还是"应答 + 继续说话"？
  （决定 P0-1 的续播条件）
- **`wave`** 是**补素材**（P2）还是**从 mock 里移除**（P0-4）？

## 八、风险与回滚

| 风险 | 触发条件 | 缓解 / 回滚 |
|---|---|---|
| 续播报导致"多演一段" | `ACK_NOD` 被用作纯应答收尾 | 以 `AUDIO_PLAYBACK_STOP` 是否到达为条件；不改事件合同，可一行回滚 |
| 相位随机化破坏 burst 语义 | 误对 burst 素材加相位 | 相位只对 `not seq.burst` 生效（与 `_state_time` 归零逻辑一致） |
| 三段化后起手 / 收尾接缝可见 | 生成素材末帧与持续段首帧差异过大 | 用 v2 的帧差 / 亮度差阈值验收；不达标则回退到 P0-2 |
| 变速导致口型 / 节奏怪 | `speed` 越界 | 限幅 `[0.85, 1.15]`，超出即夹紧 |
| 体积超预算 | P2 全量 +4 条 | 仓库只保留最终采用素材；P0 / P1 增量仅 6.9 MiB |
