## 1. 目标

1. 判定各状态素材是否"真的在动"（是否存在"静止贴图"）；
2. 定位运动**发生在哪个部位**（头/身/下），并与状态语义对照；
3. 给出**状态间可辨识度**的量化依据（"演示看不出状态机在干什么"的根因）；
4. 顺带用数值核验历史遗留项：绿边残留、透明区稳定性。

## 3. 方法与三次迭代（本轮最重要的教训）

| 版本 | 前景掩膜 | 结果 | 问题 |
|---|---|---|---|
| v1 | 无（全图 RGB） | `adj` 6.23~13.31，全部"明显运动" | 把**透明区/背景噪声**一并统计，结论偏大 |
| v2 | 亮度>232 判"白底" | `fg=92%` | **素材是 RGBA 透明 PNG**；`convert("RGB")` 会把透明区烤成黑色，于是黑色透明区被判成"前景"。v2 报出的"下部/边缘剧烈运动（热点 `6,94`/`94,94`/`6,81`/`94,81`）"**全部是透明区假象，结论作废** |
| v3 | **`alpha > 100`** | `fg=55%` | ✅ 有效：前景占比 55%，与 `alpha` 均值 139 / 零值 42% 自洽 |

**三条硬教训**：

1. **分析带 alpha 的素材，绝不能用 `convert("RGB")`**：透明区 RGB 是垃圾值（且随帧变化），
   会被统计成"剧烈运动"，进而得出完全错误的部位结论。**必须用 alpha 通道做掩膜**。
2. **不要把"看得见的拼图"当验收依据**：`docs/vision_sheets/` 的网格把 464×480 缩到约 200px 高，
   细微动作（呼吸、口型）在缩略图上不可辨 → 会误判成"素材静止"。缩略图只适合看**崩坏/绿边**这类大故障。
3. **状态 → 素材是静态映射，不是"缺失回退"**：`board/interaction/avatar_assets.py::STATE_ASSET`
   明确写着 `CAMERA_LOST/NETWORK_LOST → idle_offline`、`CANCELLED → idle_normal`、`ERROR → emo_sad`、
   `PUZZLED → emo_puzzled`。所以"指标逐位相同"是设计结果，不是 bug；但**观感上它确实让状态不可辨**（见 §6）。

## 4. 指标定义（v3）

| 指标 | 定义 | 读法 |
|---|---|---|
| `adj_fg` | 前景（alpha>100）内相邻帧 `mean|Δ|`（0~255） | 本体运动幅度；<0.5 不可见 / <1.5 极弱 / <4 可见 / ≥4 明显 |
| `aligned` | 整帧最优整数位移对齐后再算 | 与 `adj_fg` 之差 = "平移贡献"；本轮差≈0 → 无抖动 |
| `head/mid/low` | 前景 bbox 分三段（上30% / 中40% / 下30%） | 判断动的是头、身还是下部 |
| `greenEdge%` | 半透明边缘带（0<alpha<255）内 `g-max(r,b)>10` 的比例 | 绿边残留；<1% 基本不可见 |
| `transDiff` | 完全透明区（alpha<10）的相邻帧差 | 应≈0；偏大 = 掩膜/颜色不稳定 |

## 6. 判读

### 6.1 "待机族"7 个状态在数值上高度重合 → 观感不可辨

`IDLE 4.07 / SPEAKING_NEUTRAL 4.34 / PRESENT 4.45 / THINKING 4.82 / CAMERA_LOST 4.79 / SPEAKING_LOW 5.10 / LISTENING 5.38`，
`head` 段 4.33~7.62，热点几乎都是同一批"画面左右边缘 + 中部"。叠加 §3-3 的映射关系，
**画面上实际只有 5 种待机素材**（`idle_normal` / `idle_present` / `idle_listening` / `idle_thinking` / `idle_offline`），
而它们的帧间差与热点分布彼此差异 < 1.5 灰阶 → **观众无法从动作上分辨状态机当前处于哪个状态**。
这就是"演示效果差"的**第一根因**（不是"没动"，而是"动得都一样"）。

### 6.2 口型尚未被证实

`SPEAKING`：`adj_fg 7.67` 但 `mid 9.88 > head 6.26`，热点第一名 `31,44` 是唯一"非边缘"型热点
→ 说话时**躯干/手部**的运动反而大于脸部；`SPEAKING_NEUTRAL` 的 `head 7.62` 反超 `SPEAKING`（6.26）
却整体更弱（4.34）→ 更像**头部（含发型）小幅漂移**，而不是嘴部开合。
**判定：现有素材的"口型"证据不足**；需按 §7-2 裁脸部局部放大复核后才能下最终结论。

### 6.3 数值与语义**最吻合**的三个素材（质量最好，建议保留）

| 素材 | 数值证据 | 语义 |
|---|---|---|
| `deny_shake` | `head 20.02`（全场最高）；热点 `56,19`（头顶中央=呆毛）+ `19,56`/`81,56`（左右对称=发梢左右摆） | 摇头 ✓ |
| `emo_puzzled` | `head 14.69`；热点 `31,56 / 31,44 / 31,31` 组成**同一竖列**（手抬到头部的高度带） | 困惑（抬手+歪头）✓ |
| `ack_nod` | `head 10.99`；热度出现在 `44,44 / 56,31 / 56,44`（画面中央偏上 = 脸/下巴） | 点头 ✓ |

### 6.4 两处可疑

- **AWAKE（emo_surprised）12.19，且 `low` 段 12.76 最大** → "惊讶"应当集中在头/上半身，
  但下半身（裙摆）动得更多 → 疑似"整身一颤/整体晃动"而非表情与上身反应。
- **ERROR（emo_sad）8.16 → aligned 6.93（差 15%），`shift 0,1`** → 存在 1px 整体位移，
  即"轻微整幅晃动"叠加真实动作；语义上"难过"更应偏"低头、静态"。

### 6.5 loop 收尾：所有素材都是"起→高潮→收"，末段趋于静止

以 IDLE 为例，39 帧的相邻差曲线：`2.08 → 6.94(峰) → 5.2~6.0 → 1.87 → 0.54`（末两对仅 0.56/0.54）。
`SPEAKING_NEUTRAL`：`1.52 → 7.60(峰) → 0.71/0.61`；`PRESENT`：`3.69 → 7.92(峰) → 1.08/1.16`。
→ **素材本身是一条"单次动作"曲线**（i2v 的自然收敛），**不是无缝循环**。
对 loop 播放的 idle 族来说，每轮回到开头都会从"几乎静止"突跳到"开始动"，
**节拍不匀、有停顿感** —— 这是"灵动性差"的**第二根因**，且是**可以只靠处理解决的**（见 §7-3）。

### 6.6 历史遗留项数值核验

- **绿边**：`greenEdge%` = 0.10~0.29（半透明边缘带内偏绿像素占比）→ 与上一轮"强化去绿定稿"一致，肉眼基本不可见 ✓
- **透明区**：`transDiff` = 1.52~4.72 → 完全透明区（alpha<10）的 RGB **仍在逐帧变化**。
  因 alpha=0 不参与显示，暂判**可忽略**；但半透明边缘（alpha 0~255）可能因此出现"边缘闪动"，
### 6.7 看图确认（1 次，`docs\vision_sheets\heat_overlay.png`，958×268）

备料脚本 `zz_heat_overlay.py`：四态（IDLE / SPEAKING_NEUTRAL / SPEAKING / PUZZLED）的
「首帧 × 累计帧间差异热力（红）」叠加，透明区压暗为深灰。观察结论：

| 观察项 | 结论 | 置信度 |
|---|---|---|
| 热点落在哪里 | **人物本体**：两侧长发 + 裙摆下部 + 身体轮廓边缘；**不是**取景留白/透明区 | 高 |
| 为什么热点在 `x=6% / 94%` | 人物**几乎撑满画面宽度**（长发左右延伸到画面边缘）→ 边缘块本就是头发，掩膜判定正确 | 高 |
| 四态姿态 | 四格**姿态几乎完全相同**（同一站姿、双手交叠身前），仅热力分布略有差异 | 高 |
| 面部中央 | 相比头发/裙摆偏"暗"（变化小），但单格仅 232×240，**不足以判定口型** | 中 |
| 绿边 | 未见明显绿边（与 `greenEdge%` 0.10~0.29 一致） | 高 |

→ 由此明确：**当前素材的"运动"主要是"长发/裙摆飘动 + 轮廓边缘抖动"**，
而不是"呼吸时胸廓起伏"或"说话时口型开合"。这解释了为什么"看着像静止/看不出在做什么"——
运动量并不小，**但都发生在观众不注意的地方（头发/裙摆），且无一表达状态语义**。


### 6.8 脸部局部放大复核（第 2 次看图，`docs\vision_sheets\face_zoom.png`）—— **修正 §6.2 / §6.7**

备料脚本 `zz_face_zoom.py`：裁「前景 bbox 相对 y 5%~40%、x 25%~75%」（脸 + 下巴），
IDLE（上行，作对照）与 SPEAKING_NEUTRAL（下行）各 8 帧，等比放大到 220px 高，透明区合成深灰。

| 行 | 观察（清晰可见） |
|---|---|
| **IDLE**（上，对照） | 有**眨眼**（`#5` 闭眼）+ 头部极轻微移动；**嘴基本闭合不动** |
| **SPEAKING_NEUTRAL**（下） | **嘴在开合**：`#0`/`#5` 微张 → **`#11` 明显张开** → **`#16` 张口较大且闭眼** → `#22` 微张 → **`#27` 闭眼且嘴闭合** → `#33`/`#38` 微张；同时有轻微转头 |

**结论修正（重要，以本条为准）**：

1. **说话态是有口型的** ✓。§6.2 依据「`head` 段均值 < `mid` 段均值」推断"口型证据不足"**是错的**，
   根因是**统计尺度问题**：嘴部像素只占头部的极小比例，其开合被"头发/头部摆动"的平均值淹没；
   而**第 1 次看图的缩略图（每格 232×240）根本看不清脸** → **只有放大局部才能判读**。
2. §6.7 中"面部中央变化小"也应修正为**缩略图观感**：放大后可见面部（眼/嘴）确实在动。
3. **方法论教训（比结论更值钱）**：凡涉及「口型 / 眨眼 / 表情」这类小尺度细节，
   **禁止用整图或缩略拼图判断**——必须先按语义裁出局部（脸/手/道具）再放大，或先做分区数值（§6.9）。

### 6.10 修正后的根因排序（结论）

既然素材层面**口型、眨眼都有**，且帧间差并不低（4~12 灰阶），"演示效果差"的原因**更可能在展示环节**：

| 排名 | 根因 | 证据 | 修复成本 |
|---|---|---|---|
| 1 | **状态间差异不足** | §6.1：待机族 7 态 `adj_fg` 4.07~5.38、热点同一批；`STATE_ASSET` 里 4 个状态共用 3 份素材 | 高（需重制素材） |
| 2 | **显示尺度偏小，细节不显眼** | 板端玩偶框 **423×516**（1024×600 界面），`waist-up` 素材在框内显示 **423×436**（占宽 100%，放大 0.59×，见 `avatar_lod.FRAMING_PRESETS` 注释）；按素材中脸占约 50%×33% 推算，**脸部 ≈ 212×144 px → 嘴部开合约 9~18 px**：可见但不抢眼 | 低（改景别/改显示尺寸） |
| 3 | **loop 收尾停顿** | §6.5：所有素材都是"起→高潮→收"，末段降到 0.5~1.2 → 循环回跳 | 低（乒乓播放，零素材改动） |

→ **下一步应先核"演示台里玩偶的实际显示尺寸"**（`tools/demo_stage.py` 与
`board/app/qt_widgets.py::AvatarPanel` 的目标尺寸），据此决定是
**换更近的景别（head-and-shoulders 特写）**、还是**放大显示区域**，
**不要急着重制素材**。



1. **看图确认热点部位（1 次，已备料 `docs\vision_sheets\heat_overlay.png`）**：
   IDLE / SPEAKING_NEUTRAL / SPEAKING / PUZZLED 四态「首帧 + 累计差异热力」叠加，
   确认 `6,81 / 94,81 / 94,94` 这类热点到底落在**人物左右轮廓/袖口/裙摆**，还是"取景留白"。
2. **口型专项复核**：裁"前景 bbox 上 30% 的中央列"（约 x 35%~65%、y 8%~30%）逐帧求差 + 放大网格，
   数值 + 一次看图，判定**有没有嘴部开合**（§6.2 尚未证实）。
3. **loop 闭合修复（最划算：不改素材、只改处理/播放）**，三选一：
   - **A 乒乓播放**（正放+倒放）→ 首尾速度连续，消除"回到开头突跳"；

## 9. 顺带发现（非本轮范围，建议尽快核）

### 9.1 `avatar_lod.py` 存在重复定义 → "保住 24fps"的意图未生效

`board/interaction/avatar_lod.py`：

```python
# v2 调整（状态系统重设计 §10① 拍板 B）：10.0 → 12.5，目的是**保住 24fps**
# ——39 帧 / 480 宽实测 ≈12.2 MiB，按 10.0 会被 --fit-budget 降到 ~19fps 而失去流畅度。
DEFAULT_BUDGET_MB: float = 12.5      # 第 37 行
# （10MiB ≈ 180×320 PNG 约 120 帧；9 态上限 ≈90MiB，属可接受范围）
DEFAULT_BUDGET_MB: float = 10.0      # 第 39 行 ← 旧值未删除
```

Python 里**后定义的赋值覆盖先定义** → **实际生效值仍是 10.0**，注释中"10.0 → 12.5"的调整**没有生效**。
影响面：任何走 `--fit-budget` 的入库都会按 **10.0 MiB** 判定超预算，可能把 24fps 降到 ~19fps
（`FPS_LADDER` 首档 24.0 → 次档 20.0）。（本轮入库素材 `meta.fps` 仍为 24，说明当次入库未触发降档路径
或使用了显式参数 —— **具体路径待核，勿凭此下结论**。）
**建议**：删掉第 39 行，或明确注释"当前以 10.0 为准，12.5 待评估"。
