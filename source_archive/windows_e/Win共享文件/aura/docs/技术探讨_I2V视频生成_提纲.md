## 2. 原理骨架：视频扩散到底在"扩散"什么

**要回答的问题**

1. 为什么不在**像素空间**做扩散，而要在**潜空间**（latent）里做？
2. 视频 latent 长什么样？时间维度是怎么进去的？
3. "运动"是谁产生的 —— 时序注意力？还是光流模块？
4. 提示词是怎么"进去"的，为什么有时听、有时不听？
5. 采样器、步数、CFG 各自改变什么？seed 为什么能保证复现？

**关键概念（建议按此顺序讲透）**

| 概念 | 要点（张量形状用来说明规模） |
|---|---|
| 3D VAE / 因果 VAE | 视频 VAE 对**空间 + 时间**同时压缩：空间常见 8×、时间常见 4×（ⓥ 各家不同，有 16×16×4 这类高压缩变体）→ `T×H×W×3` 变成 `(T/4)×(H/8)×(W/8)×C` |
| Latent 扩散 | 训练目标是"在 latent 上加噪/去噪"；算力与显存按 **latent token 数**增长，而不是像素数 |
| Patchify + DiT | latent 切成 patch（如 1×2×2）成为 token 序列；DiT 用 Transformer 处理长序列，取代早期 U-Net |
| 时序注意力 | 注意力跨帧建立"同一目标在下一帧应该在哪"的关联 —— 运动与一致性的主要来源 |
| 3D 位置编码（RoPE） | 告诉模型 token 在 (t, h, w) 的位置；生成更长/更高分辨率时需要它能外推 |
| 文本条件 | T5（如 umt5-xxl）/ CLIP 编码 → 经 cross-attention 注入每个 DiT block（ⓥ 各模型文本编码器不同） |
| CFG（无分类器引导） | `ε = ε_uncond + s·(ε_cond − ε_uncond)`；s 越大越"听话"，但更易过曝/僵硬、绿边更明显 |
| 采样器 | DDIM / Euler / DPM++ / UniPC —— 把"噪声→数据"的路径离散化方式不同；步数影响细节与耗时 |
| Seed 决定论 | 同 seed + 同参数 + 同**权重版本** → 同结果；**换量化/换框架版本就不保证复现** |

**工程含义（回扣本项目）**

- 我们的素材是"**微动、均匀、无镜头运动**"的 10 s 闭环 → 对"运动能力"要求低，
  但对**时序一致性**（发丝/裙摆不许漂）和**闭环**要求高：属于"难在一致性、不难在动作"的类型；
- 现役素材循环缝 FAIL（mean 19.90 / 差异像素 47.3%）正是**缺闭环约束**的后果，
  与模型强弱无关 —— 是"生成时没人要求它回到起点"。

**待核实 ⓥ**：各候选模型的 VAE 压缩倍率、文本编码器、是否 3D RoPE、默认采样器与步数。

**值得追问**：为什么提高 CFG 会让绿边更明显？时间压缩比翻倍会怎样影响"微动"的可表达范围？

## 3. I2V 是怎么"图生视频"的（首帧/首尾帧的机制）

**要回答的问题**

1. 图像到视频，模型怎么"知道"要用这张图？三种主流做法的差别与代价？
2. **首尾帧（FLF2V）为什么能把片段"逼"成闭环**？它约束了什么？
3. 若模型不支持首尾帧，"生成长一点 + 事后找最接近帧裁剪"为什么能近似闭环？
4. 参考图质量（我们的锚点图：绿幕、人物高 93%）影响在哪？

**三种 I2V 条件方式**

| 做法 | 机制 | 代价/特点 |
|---|---|---|
| 首帧 latent **通道拼接** | 首帧单独编码成 latent，与噪声 latent 在通道维拼接（`in_channels` 翻倍）→ 模型学到"第 0 帧必须等于它" | 直观稳定；需专门的 I2V 权重 |
| **图像嵌入 + cross-attn** | CLIP/视觉编码器出全局嵌入，像文本一样注入 | 省事，但"像不像"控制偏弱，容易身份漂移 |
| **Masked latent（条件帧遮蔽）** | 只在条件帧保留真值、其余待生成；训练时随机遮蔽 | 灵活，可扩展到任意"关键帧条件" |

**首尾帧为什么能闭环**：把**第 0 帧与最后一帧都给成同一张图**，
模型在潜空间里只能走一条"从 A 出发、回到 A"的路径 → 片段天生闭环。
这就是 Seedance 提示词包里"首尾帧上传同一张锚点图"的物理含义。

**不支持首尾帧时的替代**：生成较长连续动作（10–15 s），
在时间轴上找**与第 0 帧最接近的一帧**裁断 —— 等价于"事后补上闭环约束"。
`tools/avatar_keyframes.py --find-loop` 做的就是这件事。现役素材实测"最接近的帧就是 f0 自己"，
说明这条素材**根本没有可用的闭环点**，裁剪救不了，只能重生成。

**工程含义**：走开源路线时**优先选支持首尾帧条件的模型**；否则必须走"事后裁剪闭环"，
并把裁剪点写进素材元数据（可追溯）。

**待核实 ⓥ**：各模型 I2V 的条件方式、是否有 FLF2V/关键帧变体、训练遮蔽策略。

**值得追问**：为什么"通道拼接"的首帧约束比"图像嵌入"更强？首尾帧同图会不会压小中段动作幅度？

## 4. 显存与速度的账：8 GB 到底卡在哪

**要回答的问题**

1. 显存花在哪几块？哪一块随"分辨率 × 帧数"涨得最快？
2. 为什么"缩分辨率"是最有效的省显存手段（而缩步数只省时间不省显存）？
3. fp8 / int8 / GGUF 量化各自省什么、伤什么？
4. offload、block swap、tiled VAE、flash/sage attention 分别解决哪个瓶颈？
5. 我们能不能靠"降低源帧率/分辨率"把 8 GB 的账做平？

**显存构成（四块）**

| 块 | 量级关系 | 说明 |
|---|---|---|
| 权重 | 参数量 × 每参字节（bf16=2 B、fp8=1 B、Q4≈0.5 B） | 静态占用；5B 模型 bf16 ≈ 10 GB → **8 GB 必须先量化**（ⓥ 实际以模型卡为准） |
| 激活（token） | ∝ token 数 ∝ `T_lat × H_lat/2 × W_lat/2` | 随分辨率**面积**与帧数**线性**增长 |
| 注意力矩阵 | ∝ token 数的**平方**（全 3D 注意力） | 最凶的一块；窗口化/分解式注意力就是为它设计 |
| VAE 解码峰值 | ∝ 输出**像素**数 × 帧数 | 5 s 720×1280 解码瞬间峰值很高 → 用 **tiled VAE** 切块解 |

**示意算例（ⓥ 假设 VAE 8×8×4、patch 2×2）**：512×896 × 49 帧 →
latent `13×112×64` → token ≈ `13 × 56 × 32 ≈ 2.3 万`；
若按全 3D 注意力，注意力矩阵规模 ≈ `2.3万² ≈ 5.4 亿` 项 —— 这就是"小显存必须靠注意力优化 + 量化"的原因。

**省显存七件套与各自代价**

| 手段 | 省什么 | 代价 |
|---|---|---|
| bf16 → **fp8（E4M3）** | 权重/激活约减半 | 细节与微动轻微劣化 |
| **int8 / GGUF（Q8→Q5→Q4）** | 权重进一步压缩 | Q4 起易出"糊动/抖/边缘毛刺"，且**破坏复现性** |
| 权重 offload / **block swap** | 峰值显存 | 每步在 CPU↔GPU 搬权重 → 慢 |
| **Tiled VAE 解码** | 解码峰值 | 分块接缝风险（需 overlap），略慢 |
| **Flash / Sage attention** | 注意力显存与时间 | 需装对应 wheel/算子 |
| `torch.compile` / channels_last | 时间 | 首次编译慢、偶发不稳定 |
| 降分辨率 / 降帧数 | 激活 + 注意力 + 时间 | 画面信息量下降 |

**我们场景的三个"省钱杠杆"（重要）**

1. **显示口径极低**：板端最终只显示 **423×436** → 源只要 ≥720×742（腰上裁切后），
   生成 **512×896** 甚至 **480×832** 完全够用（入库仍是缩小采样）；
2. **最终只播 10 fps**：入库会把源抽到 10 fps（现役 24fps×10s → 100 帧）。
   所以**生成侧源帧率可以低于 24 fps**（比如 16 fps）→ 帧数直接砍 1/3，运动连贯度不掉；
3. **动作极简**：微动 + 无镜头运动 → 步数可以压低（20–30 步量级），无需高 CFG。

**待核实 ⓥ**：各模型官方显存门槛、支持的量化格式、ComfyUI 里可用的低显存开关组合、
常见显卡上的实际耗时（分钟/5 秒片段）。

**值得追问**：为什么"投机取巧只降步数"救不了显存？时间压缩比变大会怎样改变"微动"的频率上限？

| **LTX-Video**（2B / 13B） | 以**快**著称 | 参数迭代首选：同显存下能多跑几十条对比 |

| **Mochi-1 / Open-Sora** | 架构研究与开源复现 | 理解 AsymmDiT、开源复现路线与训练成本 |

**开源 vs 闭源（Seedance/可灵）的差距来源**

| 层 | 闭源优势 | 开源可用替代 |
|---|---|---|
| 数据 | 大规模、强筛选的视频-文本对 | 无（只能靠提示词与参数找补） |
| 后处理 | 超分/插帧/时序稳定化流水线 | 可自建（超分 + RIFE 插帧 + 去闪） |
| 约束能力 | 首尾帧、参考图、运动强度的产品化 | 挑支持 FLF2V 的模型 + 事后裁剪闭环 |
| 算力 | 可跑高分辨率长序列 + 大量候选筛选 | 降分辨率/帧率，靠"多候选 + 判据筛" |

**工程含义**：我们的判据（`--check-loop` / `--ref`）本身就是"**用数量换质量**"的筛选器，
无论素材来自哪家，都是同一套验收口径 —— 这也是为什么工程侧**不需要为来源改动任何代码**。

## 6. ComfyUI 的定位：为什么它成了事实标准

**要回答的问题**

1. 节点图到底是什么？它和"跑一个 python 脚本"相比多提供了什么？
2. 采样器 / 调度器 / 条件 / VAE 这几类节点各自在流水线的哪一步？
3. 工作流为什么能保证"可复现"？它和"模型版本 + 参数 + seed"三件套什么关系？
4. 它的低显存开关在底层做了什么？

**核心认知**

- **节点图 = 计算图**：每个节点是一次函数调用（张量进、张量出），连线即数据流。
  这层抽象让"换模型/换采样器/换条件方式"变成**改连线**，而不是改代码；
- **归类节点**：
  - 加载类：checkpoint（DiT 权重）、VAE、文本编码器、LoRA
  - 条件类：CLIP Text Encode（正/负向）、图像编码（I2V 的首帧/首尾帧输入）
  - 采样类：采样器（Euler/DPM++…）× 调度器（normal/karras…）× 步数 × CFG × seed
  - 解码类：VAE Decode（可开 tiled）、后处理（插帧/超分）
  - 输出类：Save Video / 帧序列（正是我们入库工具的入口形态）
- **可复现三件套**：权重文件版本（含量化档）+ 采样参数 + seed 写进产物元数据 —— 这正对应我们
  `meta.json.spec` 里记 `max_side / fps / framing / tool` 的做法；
- **低显存开关的实质**：`--lowvram` / `--novram` 让权重在需要时进出显存（block swap 的粗粒度版），
  代价是每步的 PCIe 搬运。

**与本项目工具的"概念映射"**

| 我们工程里的东西 | 在生成侧对应什么 |
|---|---|
| `--check-loop`（主体 mean ≤2.0、差异像素 ≤2%） | 生成侧没有等价物 → 必须**事后量化核验** |
| `--ref`（mean ≤4.0、差异 ≤5%） | 参考图一致性（身份/构图漂移的度量） |
| `framing.crop_bottom_ratio = 0.42`（只裁纵向） | 生成侧的"构图约束"（93% 人物高、无镜头运动） |
| `meta.json.spec` | 工作流导出的"参数快照"（seed/步数/CFG/量化档） |

**待核实 ⓥ**：ComfyUI 当前版本对各家族模型的支持矩阵、低显存开关的具体语义与推荐组合。

**值得追问**：为什么"两套采样器 × 两套调度器"会产生完全不同的画面风格？工作流里的节点顺序会影响结果吗？

## 7. 失败模式对症：每一种崩法背后的成因

**要回答的问题**

1. 绿溢/绿边/背景不均匀，成因是提示词没听话还是模型本身？怎么两级兜底？
2. 身份漂移、换装、脸变形 —— 应该先动哪个旋钮？
3. 镜头"偷偷推近"、人物变大 —— 训练偏差还是提示词问题？
4. 动作不闭环、发丝漂移 —— 与我们现役素材 FAIL 的病因是否同类？

**对症表（成因 → 对策）**

| 现象 | 主要成因 | 对策（按代价排序） |
|---|---|---|
| **绿溢 / 绿边 / 背景不匀** | 训练数据里"纯色背景"样本少 + CFG 过高放大伪影 | ①降 CFG ②负向词强化 `green spill/rim light/halo` ③抠像端 `despill` ④换深抠 `rembg` 兜底 |
| **身份漂移 / 换装** | 图像条件强度不足（图嵌入路线）或参考图本身模糊 | ①优先用"首帧通道拼接"的 I2V 权重 ②提高条件帧数（首尾帧/多关键帧）③锚点图保证清晰、无遮挡 |
| **镜头推近 / 人物变大** | 训练数据含大量"推镜"片段 → 模型当成默认运动 | ①负向词 `zooming/dolly/character size drift` ②提示词显式写"固定三脚架机位" ③事后几何校验（我们可用首帧 vs 末帧比例检测） |
| **动作不闭环 / 发丝漂移** | 生成目标只是"一段动作"，没有闭环约束 | ①首尾帧同图 ②事后 `--find-loop` 裁剪闭环 ③裁掉动作最剧烈的头尾 |
| **糊动 / 抖动 / 边缘毛刺** | 量化过狠（Q4 级）或步数过低 | ①量化档退到 Q8/fp8 ②步数 +5 ③降低分辨率换取更高精度档 |
| **过度平滑 / 皮肤塑料感** | CFG 过高或 VAE 反复编解码 | ①CFG 降到 4–6 量级 ②避免"抠像后再编码"反复（我们入库是最后一步，天然避免了二次损失） |

**工程含义**：我们能提供**客观判据**（`--check-loop`/`--ref`），
但"哪一种崩法"仍要人眼看一遍关键帧 —— 这就是 `tools/avatar_keyframes.py` 同时输出
"关键帧原图 + 差异热力图"的原因：**人看趋势，机器判阈值**。

**待核实 ⓥ**：各模型对负向词的响应强度差异（有的模型几乎不吃负向词）。

**值得追问**：为什么有的模型"几乎不吃负向词"？CFG 与负向词在数学上是同一个旋钮吗？

## 附录 C · 三条常见误解（先破再立）

1. **"参数量越大越好"** —— 在 8 GB 显存下，能跑起来的 5B + 好参数，胜过跑不动的 14B；
   而且我们的显示口径只有 423×436，14B 的细节优势基本被缩小采样抹平；
2. **"步数越多越清晰"** —— 步数只影响"路径离散化误差"的收敛，超过甜点后是纯耗时；
   **分辨率与量化档**才是画质主因；
3. **"提示词写全了就等于控制住了"** —— 提示词服从度受训练数据支配；
   真正的"控制力"来自**条件机制**（首帧/首尾帧/参考图）与**事后筛选**（多候选 + 判据）。
