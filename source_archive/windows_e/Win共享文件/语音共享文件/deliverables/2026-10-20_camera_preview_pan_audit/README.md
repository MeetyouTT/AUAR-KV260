# 摄像头画面消失：整机界面审查与修复

用户明确本次“卡住”指摄像头画面消失。此前1410µs的普通左步长越界只解释左按钮禁用，不能解释视频消失；本次按相机→帧传输→原生显示→GTK窗口及CPU/设备占用重新核查。

## 已核实的问题

- 实际画面中，原调轴模态窗遮住左侧相机；收起后相机区域仍残留原弹窗内容，但帧号及视频sink入口计数持续增加。新开的放大预览能显示真实相机画面。故障定位到原生预览嵌入窗口，而非相机采集停止。原GTK在帧龄超过250ms时隐藏DrawingArea，恢复后因XID相同跳过重绑；重映射后的旧sink不能据入口计数视为实际屏幕正常。
- 4个连续板测样本相机均READY、约12.5Hz采集、9.93Hz检测、无相机/检测错误；其中1次UI报告frame_visible=false，但sink仍约11.7Hz更新。收起原弹窗后的32个样本均持续送帧，实际屏幕仍有残影，证明仅查HTTP/帧计数不足。
- 原弹窗将按钮注册进主界面的controls，而诊断保存把所有controls坐标转换到主窗口；跨窗口坐标没有定义，存在None被索引的错误路径。新面板放在同一窗口，关闭时清理控件引用。

## 进程、资源和冲突核查

实板相机唯一所有者为106060；同一个进程的两份/dev/video0描述符不等于两个采集程序。只有现有独立转轴进程持有运动锁，UI音频输出唯一拥有pcmC1D0p，未见另一相机或GUI实例争抢设备。相机、UI的NRestarts=0，当前运行日志无Traceback/Error/critical，接口队列为空。boot及相机epoch保持，已采样期间没有USB断连、OOM或内存耗尽证据。

内存可用约2966MiB、根分区剩余20GiB，/run约775MiB可用。2秒CPU差分样本中，GUI约194%、相机108%、音频15%、Xorg12%、转轴7%，合计约3.4核/4核；五分钟负载约6.3。存在CPU压力，不能称性能余量充足；本轮没有修改DPU模型、语音采集节奏或运动时效来掩盖它。

免点击对话当前为PAUSED/enabled=false，录音IDLE，无本地错误；这表示用户暂停状态，不是卡死。Windows回执仍空，UI显示语音主机待接入，本轮没有发起新语音业务，不能据此宣称电脑端语音或真人身份验收通过。
