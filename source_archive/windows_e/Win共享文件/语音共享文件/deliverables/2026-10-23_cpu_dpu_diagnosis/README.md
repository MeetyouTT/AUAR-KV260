## 结论与当前状态

目前最明确的代码问题是可选任务准入与共享相机状态锁耦合，叠加时隙拒绝后的固定退让，造成有图像、有DPU余量却不能及时发布人脸结果。偶发任务占用超过30ms、相机停止出帧和CPU收益未完成评估是另外的事项。

最新已回传版本为 unit `048ee59c…`，相机298571、GUI298601、Xserver1077；YOLO / YuNet均DPU，正式SFace仍Windows CPU。通知等待与独立取消信号修正版已接受保留。60.327秒窗口：YOLO9.962Hz、人脸发布3.763Hz、227次实际DPU人脸完成，busy撤回、TTL缺口、USB告警均0；80次时隙通知等待全部正常唤醒。最终独立审计累计952次YuNet调用、硬超限0、真实native失败0、gap0，当前人脸源帧龄216ms，辅助controller/timer已退出。

这是短窗口与对应审计时点的结果。当前记录仍有1次累计主周期超限，不能写成全链全程零超时；长期稳定性未验证。

## 偶发30ms超限应如何解释

30ms是项目对可选任务占用的墙钟保护，包含包装、观测、等待与线程被调度出去的时间。历史31.340ms故障中execute约30.547ms、调用线程CPU约1.011ms，status0；同期匹配USB告警0。单凭这些数据不能确定GIL、OS调度、native内部等待或硬件中的唯一原因。

最新正常长尾样本进一步显示：optional墙钟26.438ms、调用线程CPU2.137ms；execute API2.648ms、wait API0.119ms，API之外共23.671ms，其中execute返回到wait开始5.818ms，wait结束到optional结束17.609ms。这证明该样本的大部分占用位于两个API之外；它不是历史超限故障的替代证据，也不证明所有长尾都由同一原因造成。

## 两天反复的原因与后续顺序

从记录看，工作在模型迁移、调度稳定性、音频/相机生命周期恢复、正式身份接入和CPU性能评估之间反复切换。多个轮次以短测或10/30分钟运行无故障作为阶段结果，随后罕见故障又触发回退；直到逐发布统计和真实锁争用数据补齐，才把“有DPU调用”和“有效人脸结果持续发布”区分开。GIL/CPU亲和性实验尚未唯一定位等待原因。现有成果主要是迁移与可靠性修复，CPU收益和正式板端身份仍未完成。

接续优先：

1. 保留当前已接受版本，用正常运行累计硬超限、gap和相机重启证据；每次修改用约1～3分钟真实业务短检查反馈，长稳不再阻断独立开发。
2. 对可选占用的API内外分段做原生最小执行对照，定位等待长尾；保留30ms/5ms保护，不将其放宽当作修复。
3. CPU分别剖析GUI渲染和相机预后处理/拷贝，并固定输入、UI状态与后台负载做对照。不同现场的55%和以前70%不能直接当降耗比例。
4. 再完成SFace正式板端身份、独立INT8登记/阈值与真人闭环。当前YOLO+YuNet上DPU不等于SFace正式身份已迁移。

## 摘要中的统计口径纠正

共享入口将旧版60.063秒窗口概括为“6次gap”，但原baseline-report记录窗口开始为6、结束仍为6，实际该窗口新增0次。6是此前累计数。不能以“旧版6次、新版0次”计算本次改善；确认锁争用依靠的是首版候选355次busy及14次新增缺口，与修正版对应记录。现场输入和背景负载也未固定，因此吞吐/CPU数字不构成严格性能A/B。
