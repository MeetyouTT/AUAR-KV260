# 上板准备、历史证据与固定输入对照

本组材料对应工程源码主审版本 9a4f。当前包内保留三个不同日期的真实观察组，其版本关系见 `board/evidence_index.json`。本次在 Ubuntu 完成资料收件和离线复核，新生成的 FPGA 文件仍标记为待目标板验收。

## 1. 查看和回放已有证据

从工程根目录运行，结果目录选择包外的新路径。

~~~sh
export OUT="$HOME/auar-board-check-$(date +%Y%m%d-%H%M%S)"
python3 -B board/verify_evidence.py --out "$OUT/evidence"
python3 -B -m unittest discover -s board/tests -v
python3 -B board/bringup/run_yunet_synthetic.py --describe
~~~

`comparison.json` 和 `comparison.csv` 列出每项实测值、参考值、容差与判定。回放重新计算旧采样中的 CPU、可用内存、DPU 计数率、阶段均值、LLM/TTS 中位数和显存极值，并核验固定输入的量化差异。此入口只读取文件，回执包含 `hardware_executed_now=false`。

## 2. 准备板端文件树

安装器沿用原工程的实际加载路径。`INPUTS` 指向已按来源清单准备好的授权原件目录，`AUDIO_ZIP` 指向独立语音附件。每次操作使用新的输出路径。

~~~sh
sh board/install.sh plan
sh board/install.sh index --input-root "$INPUTS" --out "$OUT/inputs.json"
sh board/install.sh board --index "$OUT/inputs.json" --audio "$AUDIO_ZIP" --out "$OUT/rootfs"
python3 -B board/bringup/check_runtime.py --rootfs "$OUT/rootfs" --out "$OUT/runtime_files.json"
~~~

读回检查覆盖 380 项组件、原启动清单及两个 systemd 单元和 56 份追加配置，共 439 项。它与正式配置中的 SHA 对照，输出目标路径与指纹。`board/system/image_manifest.json` 和 `build/env.json` 给出板卡、器件、镜像、内核与工具 ABI。现场字段及授权素材按 `board/deploy.json` 的模板和外置输入索引准备。

运行目录和服务关系由原 `board/systemd` 定义以及 `board/deploy.json` 的 `systemd_order` 决定。正式启动器为 `board/startup/launcher.py`，其 config 应位于对应 release 的 startup 目录。启动前依次确认系统镜像/内核、FPGA 与模型配套、显示/触摸、文件树、现场私有区和本次启动绑定。实际发布由当前板端服务负责人按目标机现有运维流程实施。

## 3. 使用已导出的成套 FPGA 文件

本扩充工程包的 `board/artifacts_candidate/`，包含本轮新建的 BIT、XSA、BIT.BIN、DTBO、XCLBIN 与 shell.json。`manifest.json` 记录其待实板验证状态和各文件 SHA。可在该目录执行 `sha256sum -c checksums.sha256`。

如重新构建，可用本包已有 `build/reproduce.py`、`build/export_firmware.py` 得到输出，再归集。`HARDWARE_DIR` 为同一次构建的 hardware 目录，`FIRMWARE_DIR` 为固件导出后的应用载荷目录。

~~~sh
python3 -B board/bringup/prepare_artifacts.py \
  --hardware-dir "$HARDWARE_DIR" --firmware-dir "$FIRMWARE_DIR" \
  --out "$OUT/board_artifacts"
~~~

归集先核对本轮冻结文件 SHA、大小及 XSA 内嵌位流配置数据，再复制到新目录。本版 artifact_manifest 固定本次构建。重新生成不同字节的候选产物时，按实际构建回执更新独立清单并重新验证。

固件四件在目标Linux上的目录为 /lib/firmware/xilinx/aura-visual-servo-b4096-wide-v1，manifest中列出逐文件目标。BIT和XSA作为主机侧硬件移交与位流配对输入一并提供。

新候选的逻辑接口为 K26、B4096、指纹 0x101000056010407、BUILD_ID 0x10282601，伺服地址 0x80080000，PWM E10 / LVCMOS33。实际电气接线、机械范围和当前运行窗口由板端负责人确认。历史证据的通过状态对应其原固件与模型，版本表列出与新产物的关系。

## 4. 在目标板核对已安装文件

将源码验证工具放到目标板独立目录后，可运行以下只读检查。目标板需使用与工程相符的 AArch64 环境和对应文件访问权限。

~~~sh
python3 -B board/bringup/check_runtime.py --out /tmp/auar_9a4f_runtime_check.json
~~~

本检查不启动或重启服务、不加载固件、不执行模型推理和转轴命令。当前板端若已切到其他发布版，会据实列出与 9a4f 的差异。文件一致性检查的回执单独标记为部署字节核对。

## 5. 采集新的 YuNet 合成输入实测输出

`data/board_reference/yunet_synthetic` 收录两个确定性输入（全零 BGR 和固定种子随机 BGR）及 8 个宿主量化参考张量，来自历史板测向量的合成部分。输入、输出维度和 SHA 记录在 manifest。原人脸图像及 SFace 身份特征向量按原资料的分发范围留在包外。

由当前板端负责人安排 DPU 验证窗口，在目标板使用对应历史模型文件执行。`YUNET_XMODEL` 必须匹配 `54d348bf...` 完整 SHA，模型清单位于 `data/board_reference/yunet_compiler_manifest.json`。

~~~sh
python3 -B board/bringup/run_yunet_synthetic.py \
  --model "$YUNET_XMODEL" --out /tmp/auar_yunet_synthetic_run
~~~

脚本使用原固定输入运行器相同的进程互斥锁。DPU 被占用时直接失败，保持当前服务归属。该命令保存 8 个实际输出 `.i8` 文件，并在 comparison.json 中逐头比较量化后的整数差，原验证容差为 1 LSB。报告记录模型指纹与执行范围。新编译的其他 xmodel 需配套生成并验证自己的参考。

本轮完成此入口的描述模式、文件校验和主机侧拒绝路径检查，新的板端推理仍待运行。历史完整脚本见 `board/evidence_sources/dpu_20261021`，保留其原参数和实验过程。

## 6. 其他既有验收入口

原 ID/STOP 工具由 `sh board/install.sh bench ...` 生成受控验收目录，缺省入口打印计划。它检查清单、固件、设备本次启动身份及驱动版本，按原操作条件运行。

现有 `src/models/adapt/board_three_model_core.py` 和 `board_fixed_benchmark.py` 对应历史固定输入实验。历史采集源码保存在 evidence_sources，路径、套件及控制窗口均按原实验条件核对后使用。镜像、服务、固件及运动操作遵循当前目标板的控制归属。
