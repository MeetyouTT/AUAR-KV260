# 27B 流式播放与思考提示实测

日期：2026-10-18。当前主机 RTX 5060 Ti 16GB；不是未来 RTX 5090 移动端的性能报告。

## 本次已实现

- 电脑端继续使用 `aura-qwen3.8-27b-abliterated:iq4_xs`、原 IQ4_XS 权重和选定的 OmniVoice16 声线。KV260 只接收音频和控制数据、播放和驱动已有表情口型。
- 27B 增量文字 → 自然分句 → 每个分句用原 OmniVoice16 完整合成 → 20ms PCM 数据包 → 板端常驻 GStreamer/ALSA 播放。它是分句流水线，OmniVoice 本身还不是原生流式 TTS。
- 轻量规则判断普通聊天与复杂问题；复杂问题对同一 27B 请求原生思考，`num_predict=768`。聊天保留原快速模式。没有额外调用一次 27B 来分类。
- 复杂问题立即发送缓存提示；普通聊天在等待 1.5 秒、熟悉的短闲聊在 3.5 秒仍无可播语音时发送兜底提示。缓存台词为“我想一下，再回答你。”，实际选定声线、16 步生成，2.08 秒。提示与模型计算并行，每轮最多一次，不进入聊天历史。
- 音频设备只在进程启动时预热一次；随后用静音流保持打开，保留每个原始语音 PCM 样本。旧的逐段 1 秒启动静音引擎仍可回退。
- 口型依据已播放内容的 sink 时钟推进；音频缓冲空缺时闭嘴，提示播完且正式回答尚未就绪时回到思考状态。
- 网络接收完成不写入记忆；正式回答完整播完后，校验归属、样本数和 PCM SHA256，再提交本轮历史。仍保留原最近四轮记忆范围。
- 取消会关闭当前传输，丢弃旧轮数据和未播完的回答，停止后续播放，保留原口型自然收拢动画。提示缓存下载在后台进行，电脑服务离线不阻止触摸界面初始化。

## 实机证据

两轮输入由 Windows SAPI 生成，通过实际 Paraformer → 实际 27B → 实际 OmniVoice16 → KV260 音响播放；使用真实控制器、FSM、素材与口型。不是用户重新录入的语音，也不是正式 GTK 界面操作录音的验收。

| 测试 | 首次提示/语音进入播放 | 正式回答进入播放 | 播完与记忆确认 |
| --- | ---: | ---: | --- |
| 普通聊天 | 3.810 秒（超时提示） | 9.869 秒 | 通过 |
| 折扣计算、原生思考 | 0.542 秒（思考提示） | 26.658 秒 | 通过；答案 174 元 |

时间从提交测试录音起算，不含录音自身时长；由板端软件与真实音频 sink 时钟观测，不是外部麦克风测得的声学开口时间。均为单次小样本，不能作为稳定延迟承诺。ASR 把“汐蓝”识别成“西兰”，专名准确率没有因此通过验收。

用户在这轮播放中反馈“完整清楚”，记录见 `listening_acceptance.json`。完整串联数据在 `integration_first.json`，便于复核的摘要在 `verification_summary.json`。

常驻引擎独立探针：一次设备预热约 1.099 秒；连续两次播放请求到 sink 内容开始约 121.76ms / 95.34ms，原始 PCM 一致。该结果只说明播放启动开销，不能用作整条对话链路的延迟。证据为 `persistent_board.json`。

实机取消测试覆盖思考提示与正式回答正在播放的两个阶段；没有发送历史确认，没有旧流重新开始。观察到恢复就绪/口型收拢约 89ms / 329ms；采样涉及真实头像渲染，并非精密声学尾音测量。见 `cancellation.json`。首次取消检查未考虑既有 180ms 收拢动画，原始失败记录保存在 `cancellation_initial.json`。

相关回归 **69 项通过，7.28 秒**，覆盖数据归属、序号、损坏音频、HTTP 复用与取消、播放时钟、提示一次性、原生思考请求、播完后提交历史、离线启动和旧模式兼容。见 `tests.log`。

**正式界面新录音已通过。** 用户自行录入 3.625 秒、58000 个 16kHz 样本，正式 GTK 链路自动回答，用户确认“已听到完整回答”。录音 capture、转写归属与本轮 request 一致，正式回答完整播完后主机确认记忆提交。该轮约 3.959 秒开始兜底提示、6.102 秒开始正式回答；首段 PCM 在主机生成链路的 5.656 秒发出，实际两段 TTS 都是新合成（缓存命中 0），原生思考关闭。证据见 `live_turn.json`。这是一轮真实使用验收，不代表长稳或冷启动通过。
