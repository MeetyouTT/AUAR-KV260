# 紧凑JSON与GPU调度对照（2026-10-18）

本轮保留原27B/IQ4_XS、2048上下文、人设与语音容错提示、四轮记忆、OmniVoice16参考声线及板端视觉程序。已部署`compact_grammar`，仅在普通聊天中由同一个已加载的27B后端生成无多余空白的JSON，仍包含台词、表情与空动作三个字段。短聊天保持整段合成，无固定等待插播。

本轮新录音、完整播放ACK及用户听音“正常接话，连续自然”均通过；现场软件请求到正式开口约4.095秒。150项回归与26个子用例通过。尚未达到1秒有效回答，也不把不同台词的前后录音做提速A/B。

## 采用的实现

`tools/native_grammar.py`仅连接本机11435所属Ollama进程的唯一llama-server子进程，不加载或复制权重。每轮核对实际模型路径位于配置中的项目外Ollama blobs目录，模板与Ollama `/api/show`一致，上下文2048、单slot以及已验证build `b1-620d2225c`一致。端口由进程发现，不将本次实验端口51742硬编码进生产逻辑。

使用原模板渲染原system/user/history，显式关闭普通聊天原生思考；采样temperature0.6、top_k20、top_p0.95、min_p0、repeat_penalty1与本次原后端日志一致，输出预算120保持。紧凑GBNF固定字段顺序及空动作，表情仍由27B从原四种枚举选择，台词内容仍自由生成；去掉的是JSON格式空白，没有强制缩短答案。

每次先向Ollama发送不带prompt的保活/加载请求，不产生回复词元，避免绕开其驻留超时；随后校验并请求其已有runner。新增指标记录后端、build及准备耗时。原生SSE还原为原有流式事件，继续经过防复述、连续TTS、音频哈希和播放ACK后记忆提交。

身份、模板、build、发现或准备阶段不符合条件时，在生成前回退原Ollama通道并记录原因。生成开始后的故障由原取消/错误路径处理，不重复发送部分回答。复杂长思考和旧完整WAV接口保持原路径；原生思考768预算不变。新开关也接入启动预热，使进程发现成本尽量发生在服务就绪前。

## 对照实验：采用与拒绝

| 实验 | 结果与决定 |
|---|---|
| 省略固定空动作字段 | 相邻`2026-10-18_static_action/native_profile.json`的8次探针中，台词准备2264.59→2316.82ms，2字段固定seed问候两次复述。拒绝，生产仍保留全部3字段。 |
| 先结束27B再串行TTS | `pipeline_profile.json`同台词、固定seed、未缓存TTS四次ABBA；重叠首PCM中位数4265.42ms，串行4854.68ms。音频一致，但串行更晚，拒绝。含前缀冷暖波动，不用于精确估算收益。 |
| 原生schema与紧凑语法：自由生成 | `grammar_profile.json`8次ABBA，完整JSON3598.52→3138.40ms、生成词元34.5→27；台词准备2190.50→2368.18ms。较短完整JSON不等于更早开口，不能单凭此采用。 |
| 同台词固定输出语法+TTS | `grammar_pipeline_profile.json`4次ABBA，首PCM3350.11→2773.55ms。四次音频哈希一致，但实验固定台词，不能当作生产聊天收益。 |
| 实际通道、自由生成+TTS | `integrated_profile.json`4次ABBA，相同输入与seed42，两路自由生成同一句台词；所有音频缓存未命中，PCM哈希一致。原Ollama首PCM中位数2949.41ms，紧凑通道2826.22ms，约123ms（4.2%）改善。样本仅各2次，单次范围重叠，不能据此保证每轮提速或统计显著。 |

最终以实际通道小样本结果为参考，**不沿用固定台词实验约0.58秒的改善**。这次没有更换或降低TTS参数；与27B后续元数据生成的重叠以及显卡调度波动影响TTS请求耗时，不能把全部差值说成语音模型自身加速。

## 功能验证与现场验收

- `tests.log`：150项回归及26个子用例通过（10.44秒），包含新增12项原生路径测试：SSE解码、同模型/模板/build/上下文检查、发现约束、失败回退、取消、思考原路径和请求参数保持；此前记忆、防复述、播放与路由回归通过。
- `native_validation.json`：真实原27B在新路径四轮后正确记住小林、更新后的绿色和十五；主动要求复述与错字改写正常。仅在测试中约束第一次生成复制问句，原防复述保护实际触发一次纠正后正常回答。该故障注入验证不是现场自然错误发生率测量，也不是板端纠正路径听音验收。
- 首次实际进程发现准备约0.88–1.72秒，后续校验约35–76ms；这些成本实际存在，不把冷启动探针与预热后的对照混用。启动预热已覆盖发现；模型被淘汰、runner重启、版本变化可能再次触发发现或回退。
- `compact_host.json`：两次实际ASR→27B→TTS HTTP测试，后端均为`llama_native_compact`，无纠正、无等待插播、1次整段TTS，音频未命中缓存。主机首PCM3297.33/2917.73ms；不发送播放ACK，不当作现场听音。
- `live_playback.json`与`listening.json`：本轮新录音原始转写“今天比较开心陪我聊聊吧”，回答“好呀，快跟我说说，是遇到什么好事啦？”。request `dd3011e4027542ed9001b3871e6cbb4b`的capture及完整播放ACK匹配，后端确为新路径，无等待提示、复制标记false、纠正0次、整段1次TTS。用户确认“正常接话，连续自然”，相机PID987及原boot保持。

本次现场软件开口4095.29ms：ASR141ms，台词准备2328ms，TTS请求1266ms且缓存未命中；主机通道首PCM3594ms。板端与主机计时起点不同，完整LLM与TTS又有重叠，不能简单相加完整LLM/TTS耗时。未作外部声学起音测量。

## 限制与后续

该实现依赖Ollama内部runner API，属于版本绑定的优化，版本不同会回退原路径。固定build检查是当前兼容边界，不能将本次验证自动扩展到另一台电脑或后端版本。没有引入草稿模型、DFlash或模型量化改变；27B的自由生成仍是主要耗时，后续大幅降延迟需要更高效的推理/原生流式TTS方案及进一步质量对照。

原有防复述只覆盖已知的整句复制模式，其完整根因仍开放。四轮记忆仍是易失会话历史，不是跨重启长期记忆。此次现场是首轮无历史，四轮功能证据来自真实模型测试，不能说现场已重新验收了所有记忆情形。

## 回退、恢复与存储

将`aura/config/voice_latency.json`中的`compact_grammar`改为false，在确认板端与电脑语音空闲时用本目录`restart_host.ps1`重启电脑8792，即回退原Ollama通道，保留此前记忆、防复述、称呼容错和连续播放修复。完整源码回退可恢复`before`的4份文件；新增原生模块/测试可保留为未引用文件。

独占实验脚本`profile_exclusive.ps1`有finally恢复逻辑，只临时停止确认空闲的电脑8792及其TTS子进程；不操作ASR、Ollama权重或板端视觉。实验脚本中的51742仅对应当次runner快照，不应不经发现直接在下一次启动重放。服务当前状态以实时health为准，`host_ready.json`只代表部署时快照。

大语言模型始终在项目外D盘，路径配置保持；所有新增文件为源码、报告、测试音频及小型证据。`verification_summary.json`记录当前源码指纹，`verified_source.zip`仅包含指定源码和小型报告脚本，不复制模型、环境或私钥；此前验收ZIP不覆盖。
