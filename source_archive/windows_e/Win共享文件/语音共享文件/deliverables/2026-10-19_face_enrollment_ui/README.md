# 人脸直接作为登记目标

> 后续[多帧采样与独立验证](../2026-10-19_multiframe_enrollment/README.md)已部署。本目录保留人脸目标修复和当时匹配失败的历史；当前活动路径及真人验收状态以新目录为准。

用户要求登记直接针对人脸，保留0.85匹配门槛。本轮将原先“先选人体，再从人体内部找脸”改为独立人脸检测/轨迹；人体DPU检测与ByteTrack继续独立运行，数值配置和源码保持原样。

## 改动

- `FaceTargetService`直接使用既有YuNet和人脸框跟踪，共享同一相机不可变BGR源帧，不打开第二个摄像头。只在唯一合格人脸连续确认后提供登记目标；多人脸、失脸、目标过期会清除目标，恢复后使用新的绑定代次。
- SFace只提取所选人脸的112×112对齐裁剪。人脸检测与特征提取分属两个CPU任务，检测结果和对应原始帧一起传递，不重复检测或使用人体框定位身份。
- 身份登记合同、语音录音归属检查改为使用人脸轨迹。没有人体检测或没有选中人体目标时，也能完成显式人脸登记。语音登记仍需明确称呼、复述确认与真实COMMITTED后才播成功。
- 登记入口显示人脸专用窗口；语音登记期间自动显示非模态人脸预览。仅传输112×112人脸PNG，预览请求默认关闭，登记窗口开启时才请求。没有人脸、对象改变、库修订或过期后不继续展示旧图。图片字节不进入UI JSON状态或本轮日志，不新增现场照片文件。
- 人工确认绑定的是屏幕展示的人脸目标，不能在用户点击后重新选择一个不同目标。0.85门槛、0.1歧义间隔、现有身份模板、身份库、原27B及OmniVoice16保持。

`preflight.json`、`real_models.log`：用公开Lena图与临时SQLite验证真实CPU模型的人脸直接登记、后续新帧识别和空白图撤销。没有打开用户模板库或相机；这不是用户真人准确率验收。

`bootstrap.log`验证真实素材加载后导入路径和语音任务初始化。`face_dialog_synthetic.png`为真实GTK离屏渲染的合成色块预览，无用户人脸；已核对中文字体、按钮和人脸框。没有在用户屏幕显示该测试窗口。

## 部署与现状

最新真人结果：用户离场回来反馈“仍显示未识别”，识别未通过。`live_reentry_validation.json`的45秒窗口共103次状态采样，103次有人脸目标、101次可登记、0次KNOWN，特征处理计数211→244。该窗口不单独证明实际离场时序，结合用户反馈记录验收失败。

随后`diagnose_face_scores.py`在板端RAM直接读取生产流程的112×112对齐脸PNG，用同一SFace重新提取并与只读库比对；8个有效样本的最高分为0.583234–0.676908，均低于0.85；第一、第二名差距均至少0.181961，大于0.1。这批拒绝发生在分数门槛，不是多身份歧义。该结论只针对这批样本；不把“最高分身份”自动认定为用户本人，也不据此承诺重登即可解决。

库在45秒观测时为4条/修订7，随后分数诊断开始和结束均为5条/修订8，后者文件哈希保持。观测与诊断工具没有任何登记/删除/更新动作，不推断期间库变化的来源，不自动清理记录。最新汇总见`verification_summary.json`。下一步先核对登记样本质量与当前人脸输入的一致性，保留0.85，不反复新增身份。
