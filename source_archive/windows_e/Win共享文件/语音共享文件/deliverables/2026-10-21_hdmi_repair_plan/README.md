# KV260上电HDMI黑闪修复方案 v2

日期：2026-10-21。依据用户“按给出的建议规划修复”及随后“仍然在黑闪”的反馈。状态：修复方案已整理、失败现场已取证；本轮没有部署新补丁或执行显示恢复。目标是板卡重新接电后，HDMI保持连接即可稳定显示，不需要手动拔插。

## 1. 先纠正当前状态

上一轮5秒参数已经在新启动中生效，但没有解决黑闪。UTC12:25实读boot为5cd17bb7-30da-4a4f-bf18-8167508de1f4，cmdline包含 `zynqmp_dpsub.power_on_delay_ms=5000`，sysfs值为5000；EDID仍为0。用户随后明确当前仍黑闪。此前“已安装、等待验收”已更新为“参数生效、本次实屏验收失败”。

当前三服务active、零重启，GUI1063/相机1002/Xserver1062；UI为IDLE、error空。当前扫描1024×600/49MHz/59.85Hz，识别失败后使用保存的时序；启动器报告显示准备27.296秒。业务在运行与物理画面正常是两个结果，不能相互替代。

历史对照：同一boot8817dc71…中，软件输出OFF→等待2.002秒→ON后用户仍见黑闪；物理HDMI重插后用户明确正常，EDID从0恢复128字节。正常EDID SHA为727d3e1893df759c757c35232f9465b670a64d6de2011b586de48c6446e17c35。两种动作效果不同，普通xrandr off/on不再作为已知有效方案。

## 3. 实施顺序及每步判据

### A. 固定失败基线（本轮已完成）

保存本boot的参数、EDID、实际时序、服务状态、启动记录和用户实屏反馈。保留故障态供下一步实验。本轮只读取证，没有发起重启、显示关开、寄存器写入或运动命令。

5秒旧参数仍留在uEnv和当前内核中，本轮没有回退。开始下一项受控启动试验前，先使用已有受校验回退工具停用它，并在下一boot确认回到4ms；这样可以区分新机制的效果，避免叠加两个延时。回退不会即时改变当前驱动，也不能自行消除当前黑闪。

### B. 先验证一个最小的恢复动作（待执行）

在故障可复现、HDMI未重插的条件下，运行独立助手：核对boot/板卡CID、输出为DP-1、无未知force/EDID覆盖；保存状态。通过该内核已实现的DRM连接器status接口请求一次 `detect`，重新读取连接状态和模式。执行前检查本机权限和实际驱动版本；执行有总超时，失败记录后停止。

这一步是主动重新探测；单纯反复读取EDID sysfs通常只读取现有属性，不能称为重新发起总线通信。status detect也不是物理HPD，不保证完成链路重训练或恢复画面。

读取EDID长度/头部/每块校验和/哈希，并记录是否变化。若恢复到本屏已知EDID，才评估是否有必要用本屏原时序重新提交一次模式；若模式没有变化，不能声称它必然触发训练。每个动作之后都记录实屏是否停止黑闪，不把EDID恢复当作实屏恢复。

判定：

- EDID恢复且画面正常：该动作成为可固化候选，下一步验证开机一次执行。
- EDID恢复但仍黑闪：参数获取与实际输出分开处理，进入链路/下游恢复分支。
- EDID仍0：本次重新检测无效，停止这一方法，不写成无限循环或每5秒重启显示。

### C. 按5秒思路修改真正的初始化阶段（B无效时的候选，待实现）

先用完整早期日志明确第一次DP AUX、HPD处理、EDID读取及Xorg启动时刻。启动已经经历数十秒仍失败，不能单凭“设备需要准备时间”断言多等5秒必然解决。必须区分“首次过早通信造成锁定”与“稍后也无法读取”。

若证据支持首次通信过早，在驱动首次启用AUX探测/HPD相关事务之前增加一个可配置的5秒准备窗口；要求覆盖早期DRM framebuffer、HPD工作和Xorg引起的探测，不能只在GUI或Xserver服务前sleep。一次初始化只等待一次，不在每次模式切换都增加5秒。原power_on_delay_ms恢复默认作为对照。

实现前核对实际内核源码、配置与构建版本，审查probe/bind/AUX注册/中断启用的调用顺序和并发；不得简单在中断上下文sleep。必要时采用可取消的延后初始化/工作队列，记录prepare、first_detect、edid_ready、stream_on时间，证明延时实际发生的位置。新增参数名只是待设计接口，当前内核不存在现成“首次全部通信延迟5秒”开关。

本机找到了两处历史linux-xlnx源码树和PetaLinux2022.2目录，但尚未证明与实际Image逐项匹配。若需要重建内核，使用隔离工作目录、保留原Image/DTB/模块及串口启动回退；在候选中核验DPU/XRT/zocl模块兼容、相机和音频USB，不直接覆盖活动镜像。没有完成这些检查前，不把“改源码加sleep”当作可直接部署的补丁。

就绪条件候选：从真实探测取得本屏EDID，校验正确且相隔0.5秒连续两次一致；总准备期限暂设15秒并记录超时。若超时，应保存明确失败状态；保存的原生时序仅作降级显示选择，不能标记链路识别/物理修复成功。EDID检测是否足以代表下游就绪，还需结合实屏结果。

### D. 查明与物理拔插相对应的恢复机制（B/C无效或证据指向下游时）

优先核对本载板版本、实际分配器、原理图、驱动和厂商支持的控制协议。确认是否可通过已有驱动执行源端AUX/PHY重新初始化，或针对分配器HDMI下游进行检测/复位。源端恢复和HDMI接头产生的事件不是同一动作，必须分别验收。

只有得到确切控制接口、寄存器定义和复位范围，才编写一次性恢复候选；保留原状态，核验其他外设影响和退出恢复。设备树关于STDP4320的注释及地址线索不是可直接使用的寄存器手册，不能据此i2cset或devmem盲写，也不能假定HPD由可控GPIO驱动。

若没有软件可控的下游恢复路径，应如实列为硬件/厂商接口限制，继续用屏幕独立供电、先屏幕后板卡上电、已知正常线缆/屏幕分别对照；需要硬件HPD或电源时序控制时单独设计，不用纯软件开关冒充已实现。

## 4. 开机固化的目标行为

仅把已经在故障态证明确实有效的最小动作加入启动流程：显示链路准备 → 一次5秒前置等待（若实验支持） → 真实连接检测/必要的单次恢复 → 有效模式 → 本屏1024×600/49MHz、16位 → 界面就绪。

固定Xorg原生时序和握手恢复分为独立变更，逐项对照；历史固定Xorg候选已被回退，没有最终物理验收，不能直接重装后宣称根治。不强制没有支持证据的1080p，不升级整个系统或分配器固件来替代定位。

重试有总期限和次数限制，每boot最多一次恢复动作；用boot_id标记避免服务重启重复闪黑。显示操作的取消/失败必须进入恢复出口，不能仅依赖可能被杀死的同一进程。需要输出OFF/复位的候选须配独立恢复入口；软件发现失败只负责记录和降级，不因为服务active或像素更新就自动判定物理正常。

## 5. 验收、回退和分工

| 检查 | 通过标准 |
| --- | --- |
| 配置生效 | 新boot、实际参数和日志符合候选，5秒等待发生在设计的阶段 |
| 识别 | 未注入EDID情况下得到本屏有效EDID；若为保存EDID降级，单独记载 |
| 时序与业务 | 原生49MHz/1024×600/约59.85Hz、16位；GUI/相机正常，DPU和USB音频没有新错误 |
| 实屏 | HDMI全程插着；启动完成后观察60秒无黑闪/撕裂，无手动HDMI恢复 |
| 冷启动 | 相同供电接法下先连续3次独立断电重上电筛查；通过后再做10次重复验收并保留每次结果 |
| 回归 | 一次正常软件重启、一次服务重启，检查没有重复恢复动作或新的启动失败 |

3次/10次及60秒是本项目拟定验收门槛，不是厂商可靠性保证。屏幕供电随板卡掉电和屏幕保持供电的情况如都属于日常使用，应分组记录。关机后再切断电源，HDMI全程保持连接；新一轮失败后先保存证据，再按需要物理重插恢复，恢复后的正常画面不计为自动修复成功。

Ubuntu负责显示启动/驱动候选、串口证据与回退；Windows保留业务基线并核对共享版本；现场只需执行供电对照和实屏反馈。同步完成、软件通过、实体显示验收分别记录。

现有5秒参数回退：`python3 /boot/aura-hdmi-delay5-20261021/rollback.py`。它检查uEnv内容与安装版本一致后移动到备份目录，保留原件，下一次启动恢复原参数。本轮没有执行。后续每个候选均需自己的版本/哈希/备份/恢复步骤；本方案未新增板端启动配置。
