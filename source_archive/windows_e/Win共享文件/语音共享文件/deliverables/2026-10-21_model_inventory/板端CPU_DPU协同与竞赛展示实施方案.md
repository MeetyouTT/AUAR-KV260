# 板端CPU/DPU协同与竞赛展示实施方案

日期：2026-10-21 America/Los_Angeles（UTC22日）。性质：用户最新方向下的实施主线与验收设计；不是模型已上线、已提频或已取得加速比的记录。

## 用户目标与本轮决定

用户明确最终展示侧重板卡使用、利用率、提升效果和创新，希望尽可能利用DPU与CPU。后续优先让真实业务计算在KV260上完成，提高板端视觉覆盖、有效吞吐和响应能力，并给出可复现的对照数据。

阶段主线确定为：**现有YOLOX DPU → SFace正式DPU身份链 → YuNet DPU适配 → 三模型共享DPU与CPU流水线 → 有业务需求时提高检测/身份服务能力。** 不以提高无效计算量来替代业务收益；CPU和DPU的占用均与完成任务数、延迟、正确率和掉帧一起解释。

语音模型暂按现有明确配置保留Windows；用户本次要求足以调整优化重心，不自动切换语音后端、启动未验证的实板候选或解除转轴隔离。此前暂停的CPU优化不因本文件自动恢复运行。当前已有前端GTCRN/Silero仍属于Windows CPU路径。

展示中区分四种数据：

1. FPGA静态资源：LUT/FF/BRAM/URAM/DSP、时序，必须来自与实际加载位流匹配的实现报告。
2. DPU动态占用：XRT任务忙时、各模型任务数、排队和调度；不是DSP乘加阵列效率。
3. CPU执行开销：四核总量100%和每进程单核口径分别标明，同时记录有效业务吞吐；降低空转并增加有效工作也属于提升。
4. 系统能力：有效新帧吞吐、源帧龄、身份更新延迟、身份正确率/UNKNOWN表现、稳定性，以及电脑依赖的范围。

## CPU与DPU的目标分工

| 计算单元 | 目标承担内容 | 价值与边界 |
| --- | --- | --- |
| 单个B4096 DPU | YOLOX人体检测、适配的YuNet人脸/关键点网络、通过验收的SFace特征网络 | 同架构下统一调度分时复用；以实际编译分区声明DPU计算范围 |
| ARM CPU | 唯一相机采集、格式/尺寸转换、裁剪对齐、输出解码/NMS、ByteTrack、特征归一化/匹配、身份库、网络与UI/音频协调 | 通过有界队列与共享源帧降低重复采集/复制，控制OpenCV/NumPy等内部线程数，保留交互时效 |
| 已有自研PL逻辑 | 既有运动监督/独立许可路径；后续可选模型任务准入/计时仲裁 | 硬件调度原型需单独综合、同版联合实现、时序及板测；不把PS软件调度计为PL创新已完成 |
| Windows | 当前语音前端、ASR、27B和TTS；开发对照 | 明确重模型仍依赖电脑，同时单独展示板端视觉/身份自治，不能宣称整机完全离线 |

单个DPU支持多个兼容网络；网络切换通常不要求新增DPU核或换位流，但需冻结编译指纹并验证内存和调度。[AMD多网络说明](https://www.xilinx.com/content/dam/xilinx/publications/webinars/vitis-ai-webinar-dpu-ip-faq.pdf)

## 实施顺序与每关交付

### P0：冻结对照和统一测量

回收最新实际相机/界面版本、boot、活动模型/配置/固件SHA和硬件指纹；双方回执区分已同步与实际运行。保存当前混合分工为对照，不覆盖Windows较新的身份业务。采样固定业务场景，并以单调时间标记采集、排队、DPU执行、后处理和结果消费。

本轮已创建[历史实测基线CSV](板端协同_历史实测基线.csv)与[实验矩阵CSV](板端协同_实验矩阵.csv)，未知结果留空，历史固定图和真实相机分开。它们是文档/证据索引，不是运行测量服务。

### P1：完成SFace正式业务DPU接入

复用现有`DpuSFace`及`DpuSchedule`。先在隔离的固定输入对照中重新核验版本，补代表性校准与独立身份评测；保留现有Windows/浮点模板库，用模型版本分离新INT8库，不能直接复用不兼容模板。

定位旧活相机20.11ms预算触发：分别记录CPU对齐/量化、调度等待、VART执行/等待、输出处理与争用；依据真实分布设计准入预算和保护。已提交的DPU任务不可凭软件期限强行抢占或提前释放资源，不能仅增大20ms阈值就写成解决。

随后在现有相机DPU唯一所有者内验证登记、识别、陌生人UNKNOWN、删除、重启持久化与切人失效。交付版本化模型/数据库规则、精度与延迟、同板混跑及可恢复配置；当前固定图候选不直接算这一关完成。

### P2：适配YuNet，补齐第三个板端视觉网络

固定符合当前业务的输入尺寸/预处理，检查图和DPU目标支持、拆分CNN输出与解码/NMS。完成浮点参考、INT8校准/独立人脸评测、B4096编译与板端同图对照，再纳入同一DPU所有者。用相同输入比较ARM与DPU路径的整链耗时、CPU、检测质量和内存搬运，不能只报告DPU核心时间。

如果原YuNet的编译分区或精度/收益不达标，再评估已有目标部署依据的人脸检测网络；本轮不擅自更换模型。兼容判断以本目标编译/实际输出为准。[AMD模型开发流程](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-model-development.html)

### P3：CPU/DPU三模型流水线与有用负载提升

在共享源帧、时间戳和目标代次上建立人体检测、人脸检测、特征提取三类任务；复用现有检测优先机制，扩展目标数量、输入新鲜度、质量门和实际成本统计。相机/CPU可以准备下一帧，DPU执行当前兼容网络；只有输入准备完且有效才提交。

高优先级检测保持业务时效，身份和人脸任务用有界latest-only队列、过期丢弃及反饥饿策略；识别稳定目标可降低重复身份请求，新人/目标切换提高必要采样。每类任务记录接受、完成、跳过、过期和失败原因，以实际消费的结果解释计算价值。

在保持同等正确率与时效后，按业务需求探索更高检测频率/更多目标。10→15→20→30Hz仅是拟探索档位，30Hz也仅为当前采集配置约束，不是承诺。现有相机配置校验明确锁定10Hz；提频需一起复核校验、时间基准、跟踪参数和预后处理，不能只改一个数字。

CPU先分解相机/界面耗时，再做批量/向量化、缓冲复用、线程配额、绘制更新与任务重叠等按收益选择的优化。已有CPU高占用含界面，SFace当前在Windows，迁回不会自动消除这些CPU开销。本轮不直接开启已暂停的生产优化。

### P4：形成有对照的创新展示

优先验证三项工程贡献：

- 同一个DPU内多视觉网络的期限/新鲜度/质量感知调度：对照固定频率和简单先来先服务，展示同样业务下的有效吞吐、帧龄、身份延迟及过期结果拒用。
- CPU/DPU共享帧流水线：对照各模块独立采集/复制或串行处理，测重复搬运、CPU核秒、端到端延迟和稳定性；参考路径须真实存在并可复现，不能编造“旧实现”。
- 板端视觉身份自治：在受控对照中验证电脑身份服务不可用时，本地检测/跟踪/身份库能否继续工作；明确语音仍依赖Windows，网络故障不恢复运动许可。

若软件调度收益与合同已稳定，再按旧计划评估自研PL准入/计时仲裁。先核当前同源资源/时序报告；旧M3 CLB站点高占用不能当作当前报告，也不能假定新增IP一定容得下。不为展示硬件调度而破坏已验证运动监督。标准模型采用、模型数量和忙时升高本身不称为原创算法，创新结论必须来自实现差异和对照证据。

## 提升效果怎么证明

| 对照 | 目的 | 比较原则 |
| --- | --- | --- |
| 同板ARM参考 vs DPU模型 | 模型加速收益 | 同输入尺寸/预后处理与精度要求；尽量增加ARM INT8对照，无法同精度则注明量化因素，避免把FP32→INT8收益全部归给硬件 |
| 当前混合路径 vs 身份本地DPU | 板端独立性和业务延迟 | Windows CPU与KV260 DPU是部署路径对照，不能当作同CPU的硬件加速比；网络成本单列 |
| 双模型 vs 三模型固定频率 | YuNet卸载效果 | 同场景/同采样频率，观察CPU下降或容量增加，并同时报告人脸/身份精度 |
| 固定调度 vs 自适应调度 | 调度策略收益 | 同一任务到达序列、负载、模型、准确率和资源，记录任务完成、帧龄、过期/丢弃、P50/P95和CPU/DPU |
| 相同业务量 vs 最大可持续业务量 | 效率与容量分别比较 | 前者报告成本，后者报告在预先确定的准确率/时效约束下能承担多少有效业务，不混成一个百分比 |

核心展示表至少包含：各模型实际位置/分区；有效检测FPS；身份更新/每人延迟；P50/P95与源帧龄；CPU总体/进程核秒；DPU驱动忙时及各模型任务数；内存；检测/身份正确性；冷启动及持续运行。功耗/能效有可靠传感或外部仪表才填写；DDR带宽有可用接口才实测，不用RSS或帧率代替。

单模型加速比=`同条件ARM整链耗时 / DPU整链耗时`；吞吐提升=`新方案有效吞吐 / 基线有效吞吐 - 1`；CPU优化可用`每个有效结果消耗的CPU核秒`。计算前必须确认任务、输入、准确率与计时边界可比较。

拟议最终验证包括固定图数值、独立精度集、同一录制输入的多目标回放、真实相机混跑、模型超时/断连/旧结果、冷启动和持续运行。小样本只报告观察值，不以几十次请求宣称可靠P99。所有门槛在正式对照前写入实验配置；未知门槛保留待基线确定，不事后挑有利片段。

压力测试可以使用明确标注的回放任务；实际展示统计需同时区分实时新帧、回放、缓存与重复输入，不能把重复跑同一帧得到的高忙时冒充业务提升。

## 双机工作顺序及当前状态

Ubuntu优先负责模型DPU适配、同版板端集成和测量；Windows提供当前实际模型/接口/版本回执及兼容验证，旧身份和语音配置保留可恢复。双方同一文件变更前核对回执，新共享业务版本可能晚于Ubuntu镜像，不用旧源码覆盖它。

本轮完成资料/源码/历史证据核查、实施方案、基线和实验矩阵；未做新推理、量化、编译、调度代码修改、模型上板、提频、服务重启、运动或显示操作。后续按P0→P1→P2→P3推进，P4中的PL扩展按证据决定。此方案记录用户优化重心，不能当成已完成结果或另一个“全模型PL调度已上线”的声明。
