# 相机进程1ms线程切换实验

2026-10-22。目的：验证Python线程竞争/唤醒等待是否影响YuNet偶发墙钟长尾。保留上一轮完全相同的14份模型/计时/轻量上下文源、模型、Windows正式身份配置与30ms/5ms保护；不同时修改CPU核分配。用户后续允许两个终端，主任务仍独占UART/实板，第二任务只准备本地CPU亲和性候选，没有混入本轮测量。

实验用独立`gil_camera_launcher.py`包住原SHA固定的`board_camera_motion.py`，只接受显式1ms或5ms。启动前核对路径和SHA，记录该进程PID、设置前/实际设置后的值，然后转交原入口/参数；退出或异常恢复原解释器设置。原生产源与启动配置不改写，试验服务单元与候选目录独立，结束恢复原单元。短测360秒独立回退/300秒RuntimeMax；长测1200秒独立回退/900秒RuntimeMax。长测复用固定短测helper，AST只扩展窗口并核对恢复finalizer没有变化。

6项本地检查通过：真实设置与参数转交、5ms控制、目标异常恢复、错误SHA拒绝、无效参数拒绝、符号链接拒绝。14份native/调度候选没有变化，因此不重复跑上一轮67＋66项回归；验证依据沿用冻结包SHA与上轮实测。

按[Python3.9官方说明](https://docs.python.org/3.9/library/sys.html#sys.setswitchinterval)，该值为解释器线程切换的目标间隔，不能保证操作系统调度周期、原生函数耗时或硬件期限。本实验只记录启动时的实际设置，不能据此宣称GIL为唯一根因。

开工只读检查发现原保留相机400028在新观测/SFace影子关闭后又35.6121ms触发YuNet保护，已回CPU。保存新失败证据后，正常重启同原相机为410585，原单元/配置保持、GUI215734/Xserver1077保持，YuNet恢复DPU。此后才准备1ms候选，不把原基线故障归于本次设置。

长测1218请求准入/成功、1142请求拒绝（active338、deadline804）；累计请求2360。首次与末次主模型period_overruns均为1，观察窗口没有新增，但不写成从启动全链零超时。轻量观察2436次读取、0失败、7次低CPU墙钟晚返，最大墙钟7.455ms/最大读CPU0.259ms，所有观察开销仍计入原保护。

**时效还有缺口：** 121个约5秒间隔健康样本里，3个人脸结果年龄达到1000ms TTL，最大1138ms；当时原逻辑会隐藏过期目标。此为稀疏健康快照，不能当逐帧延迟分布或失效时间占比。短测25个样本无TTL过期，最大814ms。`assess_results.py`从原始数字证据重新计算此统计和首次/末次计数。脚本原有“通过”没有将每个健康样本年龄小于TTL列为验收项，因此这里只报告10分钟双模型吞吐/占用保护通过，不能写成实时身份或全部业务时效通过。

与此前5ms失败源完全相同的14份native/观测源码SHA已经核对；新旧测试没有固定相同画面/温度/CPU背景、未做交替重复5ms/1ms试验，不能报告严格加速比或归因。CPU69.10%也不是同输入优化收益。本轮没有重新开启XRT忙时统计，不能推导DPU利用率提升。

长测首次启动在切候选之前遇到`journalctl -k -n0 --show-cursor`的5秒超时。保存失败记录后，同命令只读重查0.023秒成功、journald active/NRestarts28保持，再有界启动同一候选一次；未为此重启日志/音频服务。超时原因没有确定，见长测证据的`launch_history`，不要只保留第二次成功。

结束及独立审计均确认恢复原生产：相机425227、GUI215734、Xserver1077；原单元/6源/模型与manifest核验、正式Windows SFace/原数据库路径保持，YOLO＋YuNet在DPU，影子/producer/埋点/相关timer和XRT统计关闭。1ms设置没有常驻。数字证据见`evidence/`，不含真实人像、声音、向量、身份数据库或原始UART；未代表Windows同步接收。
