# 语音触发摄像头身份登记

本功能为 2026-10-18 Ubuntu 软件候选。尚未部署到活动板端；默认 `voice_identity_enrollment=false`。已有 SFace INT8 工程模型通过物理 DPU 固定图测试，但当前相机身份候选仍是 CPU SFace，DPU 正式相机后端、真人精度和实际听音须另验，不把本候选当成完成。

## 用户操作

沿用现有按键录音，不自动开启常听麦克风。

1. 画面中只保留登记者，说“记住我是谁”。
2. 助手询问称呼；说“我叫小明”。
3. 助手重复称呼，说明保存人脸特征并询问确认；说“确认登记”。
4. 已有摄像头自动采样，界面显示正在登记及进度。保持面对摄像头，可轻微自然转头。
5. 身份库真实事务提交后，助手才说“记住了，你是小明。以后看到你，我会尝试认出你。”

也支持“记住我，我叫小明”直接进入确认。确认前可说“我叫小林”修正 ASR 的称呼；“不同意”“取消登记”结束流程。仅在闲聊中说“我叫小明”不会登记，LLM 回复中的指令也不能启动登记。

采样中可用现有“取消本轮”，或开始一轮新录音打断后说“取消登记”。由于仍为按键半双工，不能宣称采样期间始终监听取消口令。若采样已提交，取消不会删除已经登记的身份，删除继续使用身份管理页面。网络失联或进程异常时，以相机服务的最终事务状态为准，不能仅凭没听到语音判定没有写库。

## 链路

```text
MCP01录音 → Windows Paraformer → 板端语音登记控制器
                                    ├─ 普通问题 → 原27B → OmniVoice16
                                    └─ 登记对话 → 相机服务多帧事务 → 真实结果 → OmniVoice16
```

板端先通过既有 `/v1/asr/transcribe` 获取校验过归属的实际转写，再调用新增 `/v1/voice/text-channel`。普通问题走原模型流，登记提示/结果走固定文本 TTS；每轮不重复 ASR。仍使用原流式 PCM、哈希/序号、generation/capture 和播放完成后提交对话记忆的规则。整个阶段受原板端总预算约束，正常对话多一次本地有线 HTTP 往返，真实延迟待测。

`VoiceEnrollment` 绑定初次请求时唯一可见、已确认人物的相机/轨迹代次；确认阶段可自动选择此唯一目标。多人、换人、相机代次改变、服务未就绪或对话超过60秒会中止。未接入 ASD 时，不通过声音猜测多人画面中的“我”。

## 相机事务

- 新操作 `identity_collect` 接收当前目标、称呼和 `confirmed=true`，立即回执仅表示开始采样。`identity_cancel` 必须指定登记请求 ID，旧取消不能中止新请求。
- 只使用相机服务已有的原始同源帧，经过原 YuNet 归属/大小/置信度/清晰度筛选；不新增摄像头所有者、不上传人脸照片给 LLM。
- 确认之后收集5个新帧样本，间隔至少400ms，对齐裁剪的摘要不得重复；样本间初始余弦一致性门槛为0.8。此值尚未经过真人/DPU量化精度标定，不宣称活体检测或可靠准确率。
- 15秒内未完成、人物不唯一、换代或库版本变化则失败；不同人特征不一致则中止。5个特征归一化聚合后一次事务写库，过程中不写半份身份。
- `last_operation` 使用原请求 ID，状态为 `COLLECTING / COMMITTED / FAILED / CANCELLED`。控制器只在匹配请求、操作和库版本的 `COMMITTED` 状态播报成功。
- 原图、裁剪图和采样向量只驻留内存；落盘仅为设备本地、按模型区分的身份模板。当前工程目录与微力共享交付不包含真人照片/身份库。

原按钮 `identity_enroll` 的旧单帧接口保持兼容。本轮语音入口使用新的多帧接口；按钮流程后续统一迁移。采样用来登记个人，不能自动替代独立的量化校准与准确率评测数据。

## 启用和验收顺序

1. Windows先合入并重启新版 `tools/board_model_host.py`、`tools/voice_channel_source.py` 及 `common/voice_text.py`。`/health` 应报告 `voice_text_channel=true`。保留现有27B、OmniVoice16、常驻播放及延迟配置。
2. 基于当前流式板端版本合入本轮源码，确认相机身份服务及多帧接口就绪。用户要求的正式实现需接入同进程 DPU SFace，并使用对应模型 ID 和阈值；不得混用 CPU 模板。
3. 通过板端配置 `config/board_avatar_gtk.json` 启用 `voice_identity_enrollment=true`，与 `streaming_conversation=true` 配套。服务状态必须来自实际相机；仅供软件回归的 fixture 不允许启用真人登记。
4. 真人依次验证登记、离开返回、陌生人 UNKNOWN、多人拒绝、取消、删除及重启。分别记录画面、真实事务和用户听音，不用源码/HTTP通过代替这些验收。

本轮未修改活动板端服务、Windows运行进程或FPGA配置，也未采集/登记真人。Ubuntu候选和Windows同步接收、板端上线、业务验收须分开记录。

## 软件验证

在具备项目 NumPy/Pillow 的环境中，从 `aura` 根运行：

```sh
python -B -m unittest tests.framework.test_voice_identity -q
python -B -m unittest discover -s tests/framework -p 'test_*.py' -q
```

新增测试使用合成人脸特征、ASR/TTS替身、真实SQLite及临时回环HTTP，覆盖四轮分流、单次ASR、确认与提交的区别、重复帧、换人/多人、取消竞态、超时及写库失败。它们不证明真人识别、真实模型声音或DPU相机混跑已通过。证据和哈希见共享交付 `deliverables/2026-10-18_voice_identity/README.md`。
