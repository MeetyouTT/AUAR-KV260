# AURA项目技能包说明、三人安排与参赛交付方案

编制日期：2026-10-07。适用项目：E盘AURA / Kria KV260视听交互玩偶，AMD自主选题初级组。周期沿用三人、20个工作日；D1是实际开工日。

**建议集中做三个技能包：A的FPGA命令监督验证、B的感知时效与调度评测、C的异步结果与取消验证。** 三包共同服务前一份分析选定的“控制误差约束下的可变感知有效期调度与FPGA执行监督”，分别沉淀执行、感知和交互三个环节的可复用方法。

目前项目已经有不少可用于提炼技能包的代码、测试和工程记录，但未发现正式的`skill/`交付目录或`SKILL.md`。本文件交付的是基于项目核查的说明与实施安排，文中拟建的目录、脚本和验收标准均属于后续工作，不能标记成已完成的技能包。

## 1. 项目中的skill究竟指什么

本赛道中的技能包，是把团队与大模型协作时获得、并经工程验证的经验整理成别人可以使用的方法。例如：给出寄存器合同，如何生成边界用例并判断过期命令是否仍会产生输出；给出视频推理日志，如何发现“FPS很高但控制证据已经过期”；给出异步服务，如何验证取消后旧回复不会再次显示或播放。

一项完整技能应回答五个问题：**什么时候使用、需要提供什么、怎样执行、如何判断效果、在哪些条件下会失效。** 再附上真实失败或观察、修正过程和验证证据，才形成有参赛价值的交付物。

需要区分两种含义：

| 类型 | 本项目应如何处理 |
| --- | --- |
| 比赛要求的`skill/`技能包 | 本次安排的重点。可以由说明、经过验证的提示词、模板、校验脚本和踩坑案例组成，别人不安装智能体也能使用 |
| Codex等工具识别的`SKILL.md`技能入口 | 可选的工具适配。若需要让AI自动识别某个工作流，再增加含名称、适用场景和步骤的入口文件；不能用它替代实际工程验证 |

比赛技能包无需先做成插件，也不要求建立新的模型服务。整理技能包时，应尽量复用已经跑通的业务代码与测试，补上参数化入口和独立使用说明。

## 2. 参赛书对技能包的实际要求

依据本项目现有[AMD选题指南](E:/项目/参赛资料/全国大学生嵌入式芯片与系统设计竞赛'2026FPGA赛道选题指南-AMD.pdf)，PDF第24页、正文第21页第3.3.5.2节：技能包置于`skill/`目录，含`README.md`，说明每项的适用范围、使用方法和失效条件；每项还须写明已验证效果，以及从哪些失败或观察中总结而来。

指南认可四类材料：经过验证的提示词工作流、可以套用的工程或报告模板、校验脚本、带触发条件和排查步骤的踩坑清单。评价重点是：**陌生队伍拿到这个目录，能否直接用于自己的题目。** 因此，本项目采用“脚本或模板＋使用流程＋失败案例＋证据”的组合更合适。

第3.3.5.3节还要求设计报告提交提示词、模型回答、自我纠错轨迹，以及技能提炼和验证过程。应保留真实可见的交互记录，不要求、也不应编写不存在的模型内部推理过程。

PDF第25页第3.3.5.5节的权重为：

| 评分项 | 分值 | 本次技能安排的作用 |
| --- | ---: | --- |
| 创新性与应用价值 | 30 | 帮助把研究方法和对照实验写清楚；具体创新仍由方法与实测结果支撑 |
| 性能与资源优化效果 | 20 | B包提供同条件时效、调度和服务质量评测；A提供相关资源与时序记录 |
| 功能正确性与设计完整性 | 20 | A/C包提供边界条件、取消、失效与恢复的验证方法 |
| 大模型协作与技能包 | 15 | 三包及其真实协作、纠错、复用记录直接对应此项 |
| 文档质量与可复现性 | 15 | 参数化入口、环境说明、证据索引和非作者执行帮助支撑此项 |

**官方没有规定做三个包就获得15分，也没有规定必须提交多少个包。** 这15分同时评价大模型协作与技能包，数量无法代替质量。本文的三个包、工作量和验收门槛是项目建议，不是官方新增条款，也不是95分以上的保证。

指南明确通用PYNQ Skill可单独加分，但这里没有给出固定加分数字。当前方案采用Linux板端服务、DPU及自研IP路线；在未完成PYNQ框架内、换题目和换板卡的验证前，按当前技术路线如实命名，不为加分另开平台迁移任务。

正式提交要求英文目录和文件名，正文可以中文。普通新增文件采用小写英文；`README.md`按指南示例保留。可选的`SKILL.md`是工具格式要求，若最终命名细则与之冲突，可以将工具适配入口留在内部使用版，正式提交版仍完整保留人可执行的技能说明和材料。

### 3.3 本次实际验证与环境问题

### 3.4 要在说明中消除的历史口径差异

1. 新版实时对话仍使用WebSocket合同`1.0`；主机服务骨架使用`aura-runtime-1`。二者需要明确的适配映射，不能只改版本字符串就视为接通。
2. 最新玩偶合同是15态；旧架构说明仍存在9态等历史记录。交互状态、目标生命周期、运动状态和玩偶状态属于不同字段域，不能混成一张枚举。
3. 现有SemanticValidator在`valid_until_ms == 0`时跳过有效期判断，轨迹存在性检查也不等于完整的目标代次验证。提炼C包时标明旧版能力，新增严格模式另行验证。
4. 校验执行器的实际位置为`scripts/validator_cases.py`，部分旧说明中的`tools/validator_cases.py`已经不适用。
5. [platform_manifest.json](E:/项目/aura_fpga/contracts/platform_manifest.json)仍有大量空值，并标记设计状态；历史M3板测应单独引用，不能直接把模板改成“全部已验收”。
6. 本期采用USB一体音频，旧双麦I2S、DOA及音频IP主题已从当前方案移除，技能安排不重新引入这些依赖。

## 4. 推荐的三个核心技能包

| 包名 | 人能理解的用途 | 主责 / 复核 | 当前成熟度 | 交付优先级 |
| --- | --- | --- | --- | --- |
| `command-guard-validation` | 验证迟到、重放、旧目标与异常状态的命令不会获得新的执行许可 | A / B | 合同与有限硬件基础已有；完整监督证据待补 | 核心，体现FPGA作用 |
| `perception-freshness-benchmark` | 从真实源帧时间评估感知有效性，并比较固定/可变期限及共享DPU调度 | B / A | 设计方向已有；正式时序日志、评测适配和板端对照待补 | 核心，支撑研究结论 |

### 4.1 A包：FPGA命令监督验证

**适用场景。** Linux/PS提出动作，PL根据寄存器合同决定是否允许输出的系统，例如视觉随动、有限时长PWM控制、外部推理结果驱动执行器。换用其他板卡时，替换寄存器与时钟适配；方法本身不写死KV260地址。

**输入。** 寄存器映射、字段位宽和单位、允许命令范围、源证据期限、序号及会话/目标代次定义、复位与停止行为、仿真或板测轨迹。当前硬件工件的身份、ABI和来源是前置核查材料。

**输出。** 正反例清单、逐项预期/实际结果、拒绝原因、相应波形或回读证据、环境与源版本，以及未覆盖项。数字输出禁能、动力断开、机构实际停止分别记录；数字回读不自动证明机械效果。

**操作流程。**

1. 从真实合同提取可验证性质，例如“过期提交不激活输出”“旧序号不续期”“复位后旧命令失效”。AI可协助生成候选，但A确认实际寄存器语义。
2. 先用仿真注入合法、过期、重放、旧代次、边界和复位序列，保留正例，避免全部拒绝却误判正确。
3. 使用受控适配入口将同一语义用例用于板测。读取当前配置身份后再访问对应地址；不从历史M3报告推断当前配置已加载。
4. 对比提交时间、commit时间和最终输出截止时间，验证通信或总线延迟会消耗剩余时间，迟到提交不会重新获得完整租约。
5. 形成一份“失败触发→定位→修正→同输入复测”的案例，再交B从新目录执行。

**必须覆盖的边界。**

| 条件 | 期望检查 |
| --- | --- |
| 合法且仍有效的命令 | 可执行；读回与输出符合合同 |
| 截止时间前、恰好到期、已经过期 | 严格按合同定义边界；到期后不继续产生获准输出 |
| 延迟提交或重复提交 | 不将旧证据的期限重新计算成“从收到开始” |
| 旧序号、旧会话、旧目标代次 | 明确拒绝或失效，不覆盖当前命令 |
| 多寄存器更新中断、commit前后打断 | 按原子提交合同工作，不执行半更新字段 |
| PS暂停、心跳中断、PL复位 | 独立监督按合同禁能；恢复需要新的有效输入 |
| 时钟epoch变化、计数回绕、单位错误 | 有明确限制和检测方式，不静默接受 |
| 外部停止与恢复 | 记录停止、恢复和重新许可的实际过程 |

源证据期限向PL计数域换算时，应采用已校验的保守映射，并把采样顺序、误差余量、epoch及回绕范围写入合同。该方法不代表PL能够证明USB相机时间戳真实，更不等同于完成了整个机械系统的形式化安全证明。

**已有来源。** A14硬件交付要求、FPGA框架中的命令监督主题、M3构建/板测/恢复报告；旧地址和平台事实只作为特定配置案例，通用模板通过参数读取。

**待补内容。** 实际监督RTL与仿真入口、最终寄存器合同、期限/代次等用例的波形与板测、受控访问适配、与B源帧日志的关联。M3寄存器模块通过不能抵扣这些工作。

**失效条件。** ABI、地址、时钟或加载配置不匹配；日志没有输出状态；源时间无法映射；只有理想仿真而没有目标配置板测。按具体层级报告“待验证/无法判断”，不能统一写通过。

**跨题目复用建议。** 用同一校验流程检查另一个有期限许可的PWM或数字输出模块，替换映射与字段，不依赖人物检测、AURA UI或本队目标名称。换题目实验未执行前只标“建议迁移场景”。

### 4.2 B包：感知时效与共享推理调度评测

**适用场景。** 视频感知结果用于运动或交互，而且检测、身份等任务共享不可抢占推理资源的系统。也可用于其他视觉控制系统的日志评测；适配层注明具体后端。

**输入。** 原始采集时间及其可信范围、源帧编号、相机epoch、目标id与代次、入队/开始/结束/消费/提交时间、任务类型、执行期限、拒绝原因、资源与配置，以及独立参考轨迹。不同机器的时间先完成映射，不能直接相减。

**输出。** 各阶段耗时、消费时证据年龄P50/P95、输出时是否仍有效、控制误差与有效跟随比例、身份任务完成率和等待分布、拒绝与恢复统计、实验条件、失败样本和原始日志路径。

**操作流程。**

1. 从源帧采集建立时间链，明确时间戳来源。`EventEnvelope.created_at_ms`只是事件创建时间，不能直接当作相机曝光或原始采集时间。
2. 配置共同误差标准、任务负载和日志字段；先用小型合成轨迹验证分析器的单位与关联，再用真实输入记录。
3. 做固定有效期与可变有效期对照，结合检测优先、简单限频和期限准入等策略比较。具体G0—G5实验定义沿用前一份创新方向文件，避免重新发明另一套基线。
4. 分别观察快慢运动、遮挡、身份任务突发、主机迟到等条件，保留失败与任务被拒的样本。
5. 将最终源证据期限与A输出许可关联，给出“调度是否减少了错误执行或改善了有效服务”的证据。

**评价的关键约束。** 不能用每个策略自己设定的有效期判断谁更好；采用相同的独立误差判据。全部停止可能让错误执行数下降，但也会损失服务，因此同时报告有效跟随覆盖、停机时间和恢复。关闭身份任务可能提升检测帧率，所以同时报告身份服务质量，不能将它作为无代价优化。

可变期限的误差增长模型必须由数据校准并保留失效范围。预测帧不能冒充新观测来刷新期限，速度估计失真、急变或遮挡时应按策略收缩许可或停止，并报告性能代价。

**已有来源。** B11/B12的共享DPU与视觉控制计划、EventBus有界队列实现、前一份创新方向分析，以及A可提供的提交/输出记录。CPU/DPU同源验证作为测量前置，重点核对预处理、后处理、模型指纹和真实运行后端。

**待补内容。** 板端完整时序日志、字段适配器、误差参考数据、模型校准、各策略真实实现与同条件对照、分析脚本和迁移样例。当前设计中的性能目标均不算已验证效果。

**失效条件。** 只有FPS没有源时间；跨时钟无映射；用接收时间替代采集时间；只剩汇总均值；缺少失败/取消样本；策略间输入或精度标准不同。分析器需要显式报缺项，不能填零掩盖问题。

**跨题目复用建议。** 替换为移动目标或工业视觉的另一组事件日志，只改字段映射和误差参考配置；评测主体无需知道“汐蓝”、用户姓名或特定人脸模型。

### 4.3 C包：异步结果归属、取消与播放验证

**适用场景。** 网络或本机异步任务返回较慢，用户可以取消、重发或换目标，结果又会影响显示、声音或动作的系统，例如语音助手、看图问答和机器人交互。

**输入。** 当前协议版本、请求/会话/启动身份、请求代次、目标归属、源证据和期限、允许的表情/动作，以及可注入乱序、迟到、重复和取消的测试后端。设备播放作为单独验证层接入。

**输出。** 每例允许/拒绝、拒绝原因、显示/FSM/音频消费状态、代次与token变化、失败归因、执行环境、源版本和验证层级。

**操作流程。**

1. 先以现有35项协议/fixture测试建立最小可运行入口，保留其真实源文件和用例关系。
2. 将173例中可复用的结构、语义与策略检查拆成独立子集，声明`jsonschema`等实际依赖，不为了增加用例数导入整个项目环境。
3. 建立以下协议映射表，检查缺失字段；缺少boot/session/目标代次的旧路径不能标为完整覆盖。
4. 注入旧回复、新旧请求交错、相同请求重试、目标换代、超时、分段缺失与设备状态迟到，观察是否有旧结果进入最终消费者。
5. 逻辑层通过后，接真实对话/语音后端和设备，核查取消后旧音频不会重新开始。PC与KV260/MCP01分别保留结果。

| 当前实际路径 | 已有字段或机制 | 技能整理时的处理 |
| --- | --- | --- |
| 旧/当前桌面对话合同`1.0` | 字符串request_id、audio_generation_id、场景序号和白名单 | 原样记录当前合同；补充字段需版本化，不能假定已与板端新协议一致 |
| 主机骨架`aura-runtime-1` | boot/session/request/generation、TargetKey、board_deadline_ns、分段台账 | 作为较完整的归属验证参考；真实后端能力另列 |
| 当前实时播放控制 | talk_gen与异步任务代次 | 验证cancel/new_turn后旧任务不能应用 |
| 音频子进程状态 | 独立token与设备样本时钟 | 音频token不等于业务request_id；明确映射和失效时机，拒绝旧token状态 |

**应提炼的用例。** 合法响应；request不符；旧generation；boot/session不符；目标LOST/换代；到期及缺失期限；取消发生在推理、待播、播放中；重复重试；分段重复/乱序/缺段；旧音频ready/done污染；设备退出后仍能本地取消。仅在具备对应合同字段的适配层主张该项覆盖。

正式实时控制或带视觉执行权限的模式应有严格有效期规则。旧演示允许空场景或未设置期限的行为保留为明确的演示适配，不能成为正式模式的静默默认值。

**已验证起点。** 本次35项新目录协议测试通过。10月6日桌面交付另有真实声音设备暂停/恢复与打断记录。它们分别证明协议子集和特定桌面实现，不合并成“整个板端技能通过”。

**真实失败来源。** 缺段检测曾是恒空结果；取消钩子被健康探针提前触发；取消只改状态不足以停止旧播放；旧音频token可能污染新时钟；拷贝虚拟环境导致移机失败。每个案例保留具体来源，不反向补造原始协作历史。

**待补内容。** 最小依赖入口、协议适配映射、严格模式新增用例、统一机器可读报告、完整技能包的新目录复现、真实模型链及最终板端设备验收。

**跨题目复用建议。** 将另一种异步任务结果接入相同归属校验，例如取消图片生成后旧结果不得覆盖当前画面；这验证方法不依赖特定TTS、角色名和AURA素材。若未实际执行，状态仍是迁移建议。

## 8. 大模型协作记录怎样沉淀成技能

每人每日保留10—15分钟记录，不在最后一天凭记忆重写。一次有价值的记录形成以下链条：

**具体工程问题 → 当时输入/提示词 → 模型可见回答 → 人工检查与修改 → 源码/配置版本 → 执行结果 → 再次定位和修正 → 适用边界。**

现有技术记录可用于证明失败和修正，但若找不到原始提示词/回答，只标“工程记录可追溯，原始AI交互未收集”。不能将本次方案编写改称为早期算法开发协作，也不能请模型编写一段假历史补齐材料。

## 9. 三人、20个工作日如何安排

沿用现有20天计划每人每天约6小时、总计360人时的假设。技能提炼嵌入原工程开发和验证，不另开20天，不重复计算运动RTL、模型调度、整机测试等业务工作。

建议核心三包的**额外整理与复用工时控制在约30人时以内**，包括每日记录：约12人时记录、9人时参数化与说明、6人时交叉复现、3人时总索引与一致性检查。12人时相当于每人每天平均12分钟；30人时占360人时约8.3%。这是预算建议，遇到工具/硬件阻塞需重排。

## 10. 怎样验证“别人真的能复用”

可以将验证证据按下面层级登记；这是项目内部安排，不是官方评分档位：

| 层级 | 能证明什么 | 必须留下的记录 |
| --- | --- | --- |
| 作者在原工程执行 | 方法在当前工程中有效 | 环境、输入、版本、原始结果 |
| 同机新目录执行 | 对本人的绝对路径和偶然缓存依赖较少 | 拷贝清单、依赖步骤、命令、结果与遇到的问题 |
| 队友按说明独立执行 | 说明可被非作者理解 | 操作者、是否参与实现、卡住的步骤、修改后结果 |
| 在另一题目/模块/数据集执行 | 方法有一定迁移能力 | 替换了什么、通用部分是否修改、结果和失效边界 |
| 陌生队伍或外部人员实际执行 | 对指南所述陌生队伍可用性有更直接证据 | 真实使用环境、独立反馈、运行结果和限制 |

本次35项协议新目录测试只属于第二层的**现有源码子集验证**，不是完整C包验证。队友互换也不能自动写成“陌生队伍已用”；另一题目的合成样例不自动代表另一台实体板卡。

如果20天内没有实际外部使用者，就交付可独立使用的包、团队交叉复现与迁移证据，明确缺少外部复用记录；不能为材料完整编造第三方反馈。外部联系不在本次执行范围内。

建议每个核心包最终至少有：一组能成功运行的最小样例、一组可解释的失败/边界样例、真实问题来源、一份非作者执行记录、清楚的迁移参数与失效条件。板端性质仅在实际目标配置完成对应验证后标为板端通过。

## 12. 对项目的最终安排意见

**将skill作为创新方法的可复用验证成果来建设。** A包回答“最终执行是否遵守源证据期限”，B包回答“计算安排怎样改善有效感知与控制”，C包回答“迟到结果如何不再影响新一轮交互”。这样与整机问题一致，别人又可以把验证方法用于自己的系统。

当前最成熟的起点是C包的协议与取消子集；最需要新增真实证据的是A监督与B调度评测。项目下一步应先补业务实现和真实实验，再将成功与失败一同沉淀，不为凑数量扩展到五六个宽泛主题。
