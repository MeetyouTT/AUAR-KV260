# 系统完成后的开工步骤

适用：AURA 的 FPGA 负责人；Vivado/Vitis 2022.2。本文是待执行清单，当前没有读取用户板卡状态。

## 1. 先准备三个记录，不急着写复杂模块

| 记录 | 写什么 | 为什么 |
|---|---|---|
| 系统记录 | 镜像文件名、下载来源、校验值、板卡 revision、启动日志 | 确定目前到底运行什么 |
| DPU 记录 | 已加载硬件、模型、运行时、固定图输出 | 确定 B 能用哪套模型和运行库 |
| 参考工程记录 | 仓库、分支、commit、构建入口、部署方式 | 确定你能否加入自己的电路 |

填写 [平台模板](../contracts/platform_manifest.json)。不知道的字段保留 null，不猜测“应该是 3.0”或“应该是 4.1”。这些版本需要和用户已确认的 2022.2 工具区分。

## 2. 第一轮：确认系统能启动

预期环境：通过串口或 SSH 登录 KV260 Linux。下面是可选的只读诊断命令，不是让你在 Windows PowerShell 里直接执行 Linux 命令。

```sh
cat /etc/os-release
uname -a
```

将输出和串口启动日志保存。用当前镜像说明中的方法检查已加载硬件、驱动和运行时。不要在不清楚镜像类型时先执行网上任意 overlay 加载或固件升级命令。

在安装好工具的开发机，打开能找到工具的命令环境，记录：

```text
vivado -version
vitis -version
```

如果命令不在 PATH，只说明命令环境尚未配置；先使用实际安装入口核对版本，不以此直接判断安装损坏。PetaLinux 或其他 Linux 构建环境另记实际版本和系统，不能因 Vivado 是 2022.2 就自动填写已验证。

此轮完成条件：启动/登录可重复，系统身份和镜像来源可追溯。相机、屏幕和 DPU 可继续逐项检查，但不把它们一起标成已通过。

## 3. 第二轮：与 B 运行匹配的 DPU 示例

1. 根据镜像原始说明确认 DPU 的加载方式与匹配模型。
2. 与 B 选择一张固定图片，不先接复杂实时跟踪。
3. 记录模型文件、预处理、运行命令、硬件/运行时信息和实际输出。
4. 重启或重新按说明启动后，再运行一次确认步骤没有依赖隐藏状态。

如果镜像安装了对应版本的 `xdputil`，可先查看其帮助，再按该版本说明查询 DPU；工具不存在时记录缺失，不能据此直接断言板卡没有 DPU。

此轮完成条件：有真实推理结果和可重复的调用步骤。B 负责模型含义与预后处理；A 负责平台信息和后续硬件可扩展性。

## 4. 第三轮：找到能重建的硬件起点

优先检查当前镜像所用的参考硬件。对于 2022.2 路线，可核对 [官方 KV260 参考仓库](https://github.com/Xilinx/kria-vitis-platforms/tree/xlnx_rel_v2022.2/kv260/overlays/examples/benchmark)，但不能只看名字就认定它与你当前镜像完全一致。

需要明确回答：

- 这是 Vitis 平台/加速包路线，还是 Vivado DPU 工程路线？
- 哪个文件/命令是官方构建入口？依赖和许可是什么？
- 当前硬件配置从哪里加载？是否有静态平台和可重配置区域？
- DPU 的配置、时钟、内存接口、运行时和模型目标是什么？
- 自研控制外设放在哪里，最终加载 DPU 时会不会被替换？

先原样重建，不改 DPU 配置。成功后用新生成的匹配工件重新部署，并复现第二轮测试。只完成综合不等于重建部署通过。

如果这一轮阻塞，你仍可独立仿真 PWM/监督逻辑，B/C 仍可开发软件。但问题应明确写成“参考平台重建阻塞”，不要把新模型训练或换多个工具版本当作默认绕行。

## 5. 第四轮：只加入一个很小的自研外设

第一版可以叫 `platform_probe_ip`，或直接作为 `motion_guard_ip` 的寄存器子集。只有：

| 寄存器 | 作用 |
|---|---|
| IP_ID | 固定常量，证明访问到了正确外设 |
| ABI_VERSION | 固定接口版本 |
| SCRATCH | 普通可读写寄存器，用于确认写通路和字节写 |
| STATUS | 当前复位/运行状态等 |

此时不接舵机动作，不加 DMA，不实现完整音频算法。SCRATCH 仅用于此阶段测试，正式接口如何保留或移除要写明版本变化。

### 在硬件工程中做的事情

1. 在可回退副本中加入模块/IP。
2. 连接参考平台允许使用的控制 AXI、时钟和复位。
3. 分配无冲突的地址段，记录实际地址，不抄教程常量。
4. 使用该参考路线重新构建最终硬件，而不是只导出一个未参与部署的局部设计。
5. 更新所需设备描述、驱动或 XRT 元数据。
6. 在 PS 端通过对应访问方式读取和写入；保存结果。
7. 同时运行原 DPU 示例，确认两者共存。

此轮最有价值的日志长这样，字段值以实测填写：

```text
hardware_release = 实际发布编号
dpu_model = 实际模型及校验值
dpu_inference = 实际输出/状态
custom_ip_id = 实际读回值
custom_abi = 实际读回值
scratch_write = 写入值
scratch_read = 读回值
same_configuration = 经加载记录核对的结论
```

不能事先写 PASS 占位。只有实测后才填通过。

## 6. 第五轮：把寄存器连接到真正的运动逻辑

建议在进入这一轮前，已经独立完成 PWM 与命令监督的基本仿真。

实施顺序：

1. `servo_pwm.sv`：先检查正常周期、高电平长度、边界更新和禁能。
2. `motion_guard.sv`：先检查接受、拒绝、到期、停止和恢复。
3. 接上影子字段和 COMMIT，验证一次完整命令。
4. 加上限幅/每步变化率和标定映射。
5. 综合实现，检查约束、资源和时序。
6. 在不驱动机械负载时测量 PWM 与使能。
7. 核实实际舵机和电路后，小范围固定请求测试。
8. B 接入真实检测，完成视觉随动。

这轮不等待 C 完成大模型问答或 Light-ASD。初次跟随可由 B 选择单个当前目标，之后再接 C 的多人对象建议。

## 7. 第六轮：双麦与全系统

先接收真实 PCM；再按 C 的软件参考验证相关值；然后加方向质量与拒判；最后加入联合平台并让 C 消费真实音向事件。

为了避免软件等待硬件，A 可以提前交付格式正确、明确标为模拟的方向样例。模拟输入只能用于接口开发，不作为真实音频验收。
