## 1. 本版范围与项目目标

### 1.1 一句话描述作品

做一台放在桌面的单轴交互终端：**看到人，选择交互对象，朝对象小范围转动，按授权记住身份，通过 MCP01 录音和播报，并借助局域网 Windows 主机完成中文识别与看图问答。**

KV260 负责真实传感、板端视觉与身份、交互状态和受监督的运动。Windows 负责首版较重的模型服务。Ubuntu 负责把硬件、Linux、模型和程序构建成可复现的部署包。

### 1.2 本次明确删除的部分

用户已经购买麦克风与扬声器一体设备 MCP01，并要求去掉听声辨位。本版删除以下任务，不再把它们列为交付依赖：

1. 两只独立 I2S 麦克风及对应采购、安装和共时钟接线。
2. PL 内 I2S 双路采集、声学相关/时差估计、粗方向计算。
3. `audio_doa_ip`、其寄存器、PCM 调试导出与相关测试向量。
4. 声学左/中/右方向标定，以及方向与视觉融合。
5. 双麦方向延迟、方向准确率、双麦采样稳定性等原验收项。

**USB 录音、USB 播放、中文 ASR、TTS、VLM 看图问答继续保留。**

**Light-ASD 视觉说话人判断继续作为本版目标。** 用户最新补充确认的是 MCP01 型号，没有明确取消这项既定算法，因此沿用原计划。它使用对应时间段的声音和连续人脸画面，判断画面里谁在说话；不输出麦克风测得的空间方向。

优先级采用：**用户最新决定 → 本文的范围调整 → 当前对齐记录与三十天责任 → 第四轮需求/验收 → 历史方案。** 赛事正式规则及后续公告仍决定正式提交要求。

- 用户此前提出的人脸上板目标保留；在 Windows 跑通身份链只能作为阶段对照。
- 采用三人分工。历史助手提出的两人合并建议不视为用户已取消三人计划。
- 旧寄存器草案彼此有地址冲突。本文给出行为合同，最终偏移、基地址和引脚仍由真实联合工程生成并冻结。
- 原第四轮 T13/T14 标记为本版不适用，保留编号便于追溯；不能写成“已通过”。

### 2.2 最重要的纠正

当前这张官方 DPU 卡运行的是 **PetaLinux 2022.2，配套 Vitis AI 3.0 运行环境**，不是 Ubuntu。Ubuntu 是你的开发电脑系统。另一条 Kria Ubuntu/应用管理路线不能直接混入此卡的构建指令。

固件文件在磁盘上、Linux 能启动、工具已安装，分别是三个进度；它们都不自动证明当前 DPU 已加载且计算正确。

`.bashrc` 为空也不等于工具坏了。先在独立开发终端显式加载已核实的设置脚本，后续写启动脚本，不凭记忆恢复一整份历史环境。

### 2.3 仍需冻结的参数

- KV260 SOM/载板具体型号和 revision；QSPI 启动固件版本。
- 当前加载 DPU 的配置、fingerprint、匹配 `arch.json`。
- 相机型号、实际支持格式/分辨率/帧率；屏幕输入和最终显示路径。
- MCP01 VID:PID、稳定声卡身份、硬件音频格式、重插行为。
- 舵机确切 SKU、180°/270°版本、负载、机构范围、供电与停止电路。
- 最终控制时钟、地址窗口、ABI、Pmod 实物针脚和 XDC。
- Windows 实际 GPU/显存、模型版本、热启动推理耗时。

这些未知项要通过日志、实物或构建报告填写，不能从方案目标反推为已知。

### 3.1 系统结构

```text

                        │                └─> 轨迹/身份/新鲜度
                        ├─> 本轮问答快照 ───────────────────┐
                        └─> 连续人脸片段 ───────────────────┤
                                                         │ 有线局域网
MCP01 ─USB─> KV260：录音 ───────────────────────────────────┤
                                                         ▼
                                           Windows 本地模型服务
                                         ASR / VLM / TTS / Light-ASD
                                                         │
                   字幕、有效回答音频、说话人证据 <─────────┘
                       │                   │
```

### 3.3 系统和工具搭配

**KV260：**先继续使用当前官方 PetaLinux DPU 卡；最后形成包含 DPU 和运动 IP、匹配设备树/运行时及全部板端应用的发布系统。

**Ubuntu：**继续使用已安装的 2022.2 工具。核对宿主版本与 AMD 2022.2 支持列表，优先在受支持环境构建；若现有宿主版本不同，先确定具体阻塞及可用隔离环境，不因文档一句话立即重装电脑。[AMD PetaLinux 2022.2 安装要求](https://docs.amd.com/r/2022.2-English/ug1144-petalinux-tools-reference-guide/Installation-Requirements)

**Windows：**保留现有主机环境，建立单独且固定依赖的模型环境。可能使用原生 Windows、WSL 或容器，但应由所选运行库的实际支持决定；最终只保留团队验证过的一条启动路线。

**版本基线：**Vivado/Vitis/PetaLinux 2022.2，DPUCZDX8G 4.1，Vitis AI 3.0。AMD 官方兼容表支持这一组合；不用新版 `latest` 容器替换已存在的 3.0 容器。[官方版本兼容表](https://xilinx.github.io/Vitis-AI/3.0/html/docs/reference/version_compatibility.html)

### 3.4 是否需要云服务

本版采用 **Windows 本地 ASR/VLM/TTS**，网线连接板卡，首版不依赖公网云合成。此前语音里的“GTSU 云合成”在本版按 TTS 语音合成统一命名。

如果将来接云 TTS/VLM，需要另测公网往返、上传、服务排队和断网行为，并明确本地替代能力。不能把“Windows 本地服务”与“公网云服务”的延迟混成一个数字。

## 4. 三人工作分配与交接

### 4.1 A：平台、FPGA、实际运动和电气

A 建议由主攻 Verilog/SV 的同学承担，即你此前所说的硬件负责人。

1. 板卡/工具/固件清单，官方 DPU 对照与参考平台重建。
2. 在同一有效 PL 配置中加入自研运动 IP，保持 DPU 正确推理。
3. AXI-Lite、影子命令、监督状态机、租约、限速、PWM、停止输入。
4. 与 B 冻结单位、恢复代次、提交/读取接口，提供访问库。
5. 时钟、复位、CDC、地址、XDC、设备树和部署包。
6. 独立舵机电源、接线、停止通路、机械标定与线束。
7. 硬件仿真、波形、综合实现、资源/时序、故障覆盖。

**A 本版不再承担双麦采集、相关算法和 `audio_doa_ip`。** 腾出的时间用于联合平台、停止/恢复和长时间验证。

### 4.2 B：视觉、板端身份、唯一运动服务

1. 唯一相机进程；帧时间、帧编号、图像缓冲和片段接口。
2. 适配实际 DPU 的人体检测；预后处理、量化/编译、精度对照。
3. 跟踪、进入/离开、目标生命周期、当前对象和防串人。
4. 板端人脸检测/对齐/特征/质量、匹配及 SQLite 身份库。
5. 共享 DPU 调度，保证人体检测不会被身份任务持续挤占。
6. **唯一 `motion_service`**：校验建议、轨迹、会话和时间，计算受限目标。
7. 给 C 提供本轮快照、连续脸片段、轨迹、身份和明确的 UNKNOWN。

### 4.3 C：MCP01、说话人、问答、UI 与日常启动

1. KV260 MCP01 录放音、格式转换、稳定设备选择和重插处理。
2. 按键半双工、请求/会话、取消、超时、音频缓冲和字幕。
3. Windows ASR、VLM、TTS 的常驻服务与阶段计时。
4. Light-ASD 基线、声画同步、有限窗口、候选分数和 UNKNOWN。
5. 结合上下文给 B 提交选人建议；没有声学方向字段。
6. 板端 UI、模型主机失联提示和恢复；整机启动、自检、日志脚本。
7. 语音/说话人/延迟/取消回归与演示流程。

### 4.4 谁能决定实际运动

```text
B 产生当前视觉轨迹
       ↓
C 产生“建议关注哪个轨迹”及说话证据
       ↓
B 的 motion_service 用最新轨迹复核，并计算目标角
       ↓
A 的 motion_guard_ip 检查许可、序号、范围、租约和停止
       ↓
PWM 与实际舵机
```

正式控制寄存器只有 B 的一个服务写入。A 的诊断程序要在服务明确停止、负载受控的维护模式运行。C、Windows 和 VLM 不能绕过 B 直接写 PWM、ARM 或清故障。

| 实体停止 | 与负载电流和机构匹配 | 数字停止和动力切断分别核对 |
| 网线/串口数据线 | 开发与模型通信 | 链路速度、实际网络/串口身份 |

不默认重新购买音箱、额外 USB 声卡、外置音频功放、双麦或电机 H 桥。先对现有设备实测，实际不符合需求时再补物料。

### 5.2 三线舵机候选接法

以下是此前 DS3230 附件对应的拓扑，正式接线前按实物确认线色：

```text
KV260 原配 12 V 电源 → KV260

舵机独立稳压电源约 6 V正极 → 保护/停止通路 → 舵机红线
舵机独立电源负极 ────────────────────────→ 舵机棕线
已验证 Pmod PWM → 所选信号接口 ──────────→ 舵机黄线
```

采用直接共地接口时，KV260 信号地与舵机电源负极建立参考；舵机大电流通过独立粗线回到电源，不经 Pmod 地线或 USB 回流。

此前附件值为 4.8—6.8 V、约 2.0—2.4 A 堵转电流、500—2500 μs 脉宽、1500 μs 中位、50—330 Hz。它们来自项目已有附件，**不是对手中 SKU 的独立验证**。首测采用 50 Hz、小范围、轻载；正式端点由实物标定。[项目外设规格与附件记录](AURA_KV260_外设控制与采购规格_2026-09-26.md)

6 V/5 A 是可考虑的供电余量，不意味着舵机恒定消耗 5 A。已有降压板能否供电、能否控制断电，必须分别核对。

### 5.3 Pmod 与显示路径不能猜

- J2 有扩展信号，但最终参考平台可能已占用部分针脚。
- 先查实际 revision 原理图、连接器朝向、平台 `pin.xdc` 和实现 IO 报告。
- 列出每根信号的用途、封装脚、IOSTANDARD、连接器针脚、电平和复位行为。
- 本版删除了双麦所需外部信号；这不自动说明参考工程里的旧音频端口已释放。
- 屏幕存在 HDMI 输入不代表最终 PL 已有可用 HDMI 输出。平台若只验证 DP，应先确认显示路线，再判断是否需要方向正确的主动 DP→HDMI 转换器。

AMD 标准载板 USB 每口供电上限 900 mA、四口总预算 2.1 A，Pmod 电源 3.3 V/100 mA。MCP01、相机等一起核算；舵机动力不从 USB/Pmod 取。[AMD 供电预算](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Powering-the-Starter-Kit-and-Power-Budgets)

### 5.4 若采用 ADuM1201 隔离

ADuM1201 可作为信号隔离候选，但不是电机驱动，也不是电源停止模块。两个通道方向相反；若 PWM 与使能都要同向传输，不能直接把它当两个同向通道。其供电及失电输出行为需要按数据手册设计，默认高电平问题必须纳入上电/失电测试。[Analog Devices 数据手册](https://www.analog.com/media/en/technical-documentation/data-sheets/adum1200_1201.pdf)

本版要求选择并画清一种拓扑：直接共地，或按设计保持隔离的双侧供电。不能接完隔离器又用其他控制线跨接两侧地，随后声称保留完整隔离。

### 5.5 机械装配

1. 转台负载由合适轴承/结构支撑，避免全部力矩压在舵机轴上。
2. 重心、线束、相机和屏幕重量形成的阻力先评估；没有必要让所有部件一起转。
3. 先卸载或轻载测方向，再安装最终负载；建立比机械端点更保守的软件范围。
4. USB/相机/电源线固定并留运动余量，最大角度不能扯紧或绕轴。
5. MCP01 放在面向人的稳定位置，麦孔无遮挡；转台噪声和扬声器回声纳入测试。
6. 断 PWM、切动力和真实轴停止分别测。失去动力可能失去保持力，需要机械支持。

## 6. MCP01 应该怎么用、先测什么

### 6.1 型号级结论

用户已提供型号、包装和评测证据：MCP01 是 thinkplus Pocket 便携会议全向麦音箱，USB-C/蓝牙，标称 5 V/500 mA 输入，约 650 mAh 电池。上述电气值由用户取证提供，收到实物后应以铭牌复核。

联想官方 FAQ 明确 Pocket 在系统中名为 MCP01，支持 USB 有线，推荐拾音距离 1.5 m 以内，3 m 是极限距离；首版用 USB 更可靠。因此演示先把人安排在约 1—1.5 m，不用“3 m 宣传值”直接要求高质量 ASR。[联想 Pocket 官方 FAQ](https://meeting.lenovo.com/device_instruction/Q%26A.pdf)

“电脑免驱”支持优先测试 Linux 通用 USB 音频的判断，但不证明当前 PetaLinux 已识别输入输出。降噪、人声增强和全向拾音也不能证明硬件 AEC、双讲或可取得多只麦克风的原始同步通道。

### 6.2 六条板端首检命令

下面在 **KV260 shell** 执行；首检时舵机动力关闭。先确认工具存在，缺工具只补对应工具/内核配置，不整套替换系统。

```bash
lsusb
arecord -l
aplay -l
cat /proc/asound/cards
arecord -L
aplay -L
```

记录接入前后变化，确定 MCP01 的输入和输出端。设备编号可能变化，不能默认声卡 `0` 或 `1`。

进一步查看录音设备的实际能力，`CARD_ID` 和设备号必须替换为上述输出确认的值：

```bash
arecord -D hw:CARD=CARD_ID,DEV=0 --dump-hw-params -d 1 /tmp/mcp01_probe.wav
```

如默认探测格式被拒绝，以输出的能力表选择格式重试。实际项目程序保存硬件采样率、声道和位宽；转换为模型输入时真正重采样，不只改 WAV 文件头。

### 6.3 录音与回放

在设备支持或 ALSA 转换已核实后，可采用以下候选测试：

```bash
arecord -D plughw:CARD=CARD_ID,DEV=0 -f S16_LE -r 16000 -c 1 -d 5 /tmp/mcp01_voice.wav
aplay -D plughw:CARD=CARD_ID,DEV=0 /tmp/mcp01_voice.wav
```

1. 说一句固定中文，听是否清晰、失真、过小或被静音。
2. 回放必须来自 MCP01，避免误用屏幕/其他声卡。
3. 相机同时工作再测，记录 USB 错误、掉线和功耗迹象。
4. 冷启动、拔插和重新连接各测数次，记录稳定选择方式。
5. 若 CARD_ID 不稳定，结合 VID:PID、序列号/USB 路径建立规则；没有序列号时记录这个限制。

**通过：**板端输入和输出均可用、真实语音可听、相机并发正常。只出现在 `lsusb` 不算通过。

### 6.4 首版采用按键半双工

- 按住说话：停止本轮播报并清理播放队列，然后开始录音。
- 松开：结束录音，创建请求，提交一次。
- 思考：显示状态；不把静默等待算作新的讲话。
- 播报：同一 MCP01 播放；暂停自动新问题和 ASD 换人依据。
- 取消：板端立即停播、清缓冲、废止本轮，再通知 Windows。

这样可以先完成完整产品，不以尚未验证的回声消除为首个依赖。保留按键取消/打断；首版不承诺在播放期间仅凭一句“停”就能可靠识别真人。

### 6.5 同时录放和 AEC 是独立进阶测试

后续验证：播放已知音频同时录音，确认设备不互斥；再让真人同时说话，检查回声抑制和近端人声是否保留。保存录音和播放参考，而不是只观察程序没报错。

结果有三种：

1. 只能可靠分时录放：保持半双工，产品仍可交付。
2. 能同时录放但回声大：不启用语音自由打断，继续按键策略。
3. 双讲测试可用：再实现软件播放参考、VAD/打断和相关回归。

MCP01 不提供本版所需的空间方向输出；不能把混合录音中有声音解释为“左边人说话”。多人同时说话允许拒绝并提示轮流。

## 7. 从当前官方镜像建立可用基线

### 7.1 第一步：恢复可靠的板端访问

1. 核对当前串口设备和持有者。报告里的 PID 是历史值，不照抄终止。
2. 请交互终端退出或让记录终端退出，只保留一个串口读写进程；日志由这个进程同时保存。
3. 参数采用已验证的 115200、8N1；保存启动输出和 root 登录。
4. 在板上读取系统、接口、网络地址和路由，不再凭扫描猜 IP。

```bash
uname -a
cat /etc/os-release
ip -br link
ip -br addr
ip route
```

若 `ip` 的简略选项不可用，改用该镜像已有的完整输出或 `ifconfig`。Ubuntu/Windows 和板卡接交换机时优先使用实际 DHCP 地址；直连时双方设置不冲突的同网段地址，且不能覆盖正在使用的默认路由。

**通过：**一个可靠串口，确认的板卡 MAC/IP，SSH 可登录且不会连错机器。

### 7.2 第二步：记录 DPU 是什么、是否在运行

先查看工具和帮助，再做查询：

```bash
command -v xmutil
command -v xdputil
xmutil --help
xdputil --help
```

若当前版本支持 `xmutil listapps`、`xdputil query`，使用它们记录应用状态、DPU 架构/核数/fingerprint。若没有加载所需应用，按本机帮助和此镜像的配套说明执行加载，保存返回结果及内核日志。

不得只因为 `/lib/firmware/xilinx/kv260-benchmark-b4096/` 存在，就把实际运行架构写成 B4096。查询失败要先查应用/驱动状态，不马上重刷卡。

### 7.3 第三步：跑配套官方模型

1. 找到镜像已带的示例、输入图和模型；记录文件路径和 SHA256。
2. 选与当前硬件 fingerprint 配套的模型，不用旧 B2304 的 xmodel。
3. 先用固定输入运行官方例程，核对输出类别/结果，保存完整日志。
4. 连续运行数次，再复核驱动错误、进程状态、温度和运行时版本。
5. 先尽量用已有二进制验证；缺 SDK 不阻止已配套示例运行。

Vitis AI 官方快速开始说明预构建板端镜像含运行时、示例和模型；目标交叉编译环境则是主机后续工作。[Vitis AI 3.0 MPSoC 快速开始](https://xilinx.github.io/Vitis-AI/3.0/html/docs/quickstart/mpsoc.html)

**通过：**明确的已加载 DPU、固定输入及正确结果、模型/运行时/硬件版本可对应。仅 `xdputil` 能执行或显示核数不算完整通过。

### 7.4 基线证据目录

建议在新 Ubuntu 工作目录建立，不复用被删除的旧工程：


## 8. 重建 DPU＋运动联合平台与最终镜像

### 8.1 镜像构建成功后不是马上接舵机

“构建成功”至少分成四级：

1. **文件产生：**构建进程退出正常，工件齐全。
2. **板端启动：**新卡能启动，设备树、驱动和外设正确。
3. **计算共存：**同一配置下 DPU 推理正确、自研 IP 可读写。
4. **完整系统：**受监督 PWM、真实随动、录音问答和恢复全部通过。

每级都有验收日志。下一步按当前未通过的一层继续，不能把一级成功写成四级完成。

### 8.2 第一条构建路线

以固定版本官方 KV260 参考工程为起点，优先研究 `kria-vitis-platforms` 的 `xlnx_rel_v2022.2` 平台和 benchmark overlay。先不修改 DPU，复建原参考，再加入最小运动寄存器。该仓库把平台与 overlay 分开，构建入口应读取所选子目录的说明。[官方 2022.2 KV260 参考目录](https://github.com/Xilinx/kria-vitis-platforms/tree/xlnx_rel_v2022.2/kv260)

必须记录仓库 commit、子模块、下载 IP/依赖及哈希。固定分支名还不够；后续从 commit 重现。

### 8.3 只能采用一个相匹配的集成模式

| 路线 | 硬件/运行时特点 | 本项目处理 |
|---|---|---|
| Vitis 平台/overlay | DPU 核和其他逻辑按平台流程集成，配套 xclbin 与 XRT/VART | 优先沿已用参考路线验证 |
| Vivado 集成 | DPU 与自研 IP 在 Vivado 系统内构建，配套独立 VART 路线 | 仅在确认完整参考和驱动后切换 |

官方文档区分 Vitis 需要的 XRT/VART 与 Vivado 独立 VART 配置。不能拿一条路线的运行时配另一条路线的工件，或者同时引入互相冲突的 VART recipe。[AMD DPU 系统集成说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-system-integration.html)

本版建议先沿官方卡对应路线完成原样复建。若参考不能满足端口/显示/自研 AXI 接入，要写清障碍和切换后的全部依赖，再选另一条；不是把两套教程的命令交错执行。

### 8.4 实施顺序

**阶段 A：复建未修改参考。**

- 获取 2022.2 原始平台与 DPU IP，核对本地工具。
- 阅读依赖、BSP/系统工件、平台构建和 overlay 构建顺序。
- 产生工件、记录报告，在新卡/受控加载路径验证官方固定样例。
- 与现有官方对照卡比较，差异必须可解释。

**阶段 B：最小自研版本寄存器共存。**

- 加入只读 `IP_ID/ABI_VERSION/BUILD_ID` 和一个受控读写测试寄存器。
- 合法连接控制 AXI、时钟和复位；分配独立地址窗口。
- 输出对应设备树/访问路径，Linux 可读到本次构建 ID。
- 同一次启动、同一有效 PL 配置下 DPU 仍正确推理。

**阶段 C：完整运动 IP，但先不接动力。**

- 加入第 9—10 章监督、PWM 与停止。
- 先用仿真和逻辑分析仪测正常更新、超时、停止、复位。
- 用 B 的访问库测试寄存器，而不是任意写物理地址。
- DPU 空闲/高负载时都复测 PWM 和状态。

**阶段 D：真实小范围运动。**

- 核实针脚、电平、电源、机构、停止和默认禁能。
- 小范围、轻载标定，最后加载最终转台。
- 再把 B 的新鲜轨迹接入，而不是先让 VLM 直接给角度。

**阶段 E：完整系统发布。**

- 相机、身份、MCP01、显示和模型主机共同运行。
- 固定内核、设备树、PL 包、模型、应用、配置与恢复流程。
- 新 SD 卡启动，做冷启动和长测，保留官方对照卡。

### 8.5 同片集成必须证明什么

PL 应同时包含/运行本次有效的 DPU 与 `motion_guard_ip`。把 DPU 位流跑一次、再加载独立 PWM 位流跑一次，不算共存；加载完整位流会替换原有逻辑。

如果使用部分重配置，需要明确静态区/可重配置区、匹配 shell 和全套验证。当前不把额外 DFX 设计作为必须新做的功能；遵循所选官方平台已有机制。

### 8.6 时钟、复位、设备树一致性

- 从本次实际设计导出时钟频率与关系，写入清单。
- DPU 的不同计算时钟按其 IP 文档要求配置；自研控制时钟独立记录。
- 不因历史 HWH 写了 200 MHz 就认定实际硬件跑 200 MHz。
- reset 极性、时钟域释放和外部停止同步要与真实设计一致。
- 地址、IRQ、时钟、reserved memory/CMA 和设备树来自同一设计。
- XSA/设备树/PL payload/运行时/模型更改后，重新验证；不混入旧报告。
- 时序通过与 HWH/DT 一致是必要条件，仍需真实推理确认。

### 8.7 SDK 与板端软件

已有官方二进制用于基线。B/C 自己的 C/C++ 程序，之后使用与最终 rootfs 匹配的 SDK/sysroot 交叉编译；纯 Python 也要核对板端依赖、ARM64 二进制和版本。

确认头文件、共享库 ABI、VART/XIR/OpenCV 和目标架构。不能在 Ubuntu 编出 x86 可执行文件后直接复制到 ARM64 板上期待运行。

### 8.8 最终交付工件

```text
release/aura-<release-id>/
  image/             完整 SD 镜像或经过验证的制卡流程
  firmware/          同版 PL payload、dtbo、xclbin 等实际需要的文件
  system/            内核、设备树、rootfs 来源及构建清单
  models/            xmodel、模型来源、量化/编译配置及哈希
  board-apps/        板端程序、服务定义、依赖与配置
  windows-apps/      模型主机程序、环境锁定与模型清单
  contracts/         ABI、消息协议、标定与版本
  evidence/          正常、故障、波形、性能与长测
  docs/              接线、启动、恢复、复现及限制

  SHA256SUMS
```

`.xsa` 是硬件交接描述，`.hwh` 是元数据，`.xmodel` 是编译模型；它们都不是完整可烧录 SD 镜像。`image.ub` 也不等于完整磁盘镜像。

Kria 主启动固件与 SD 系统有不同职责；不要为了“版本号更统一”就更新/降级 QSPI。先查询实际兼容性，只有明确需要时才按官方恢复路径执行。[AMD 启动设备说明](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Boot-Devices-and-Firmware-Overview)

## 9. 板载运动：自研逻辑要实现什么

### 9.1 运动的输入与输出

输入是 B 根据当前轨迹生成的**目标指令角**、会话、序号和有限租约，不是整个图像，也不是 Windows 的自由文本。

输出是受监督的 PWM、执行许可和状态。没有外部编码器时，系统知道的是指令角/脉宽和运行状态，不能声称知道真实轴角、已经物理到位或真实速度。

### 9.2 建议源码职责

| 模块 | 主要责任 | 必须验证 |
|---|---|---|
| `motion_guard_ip.sv` | 自研 IP 顶层与 AXI/状态连接 | 端到端提交、到期、停止 |
| `motion_axi_regs.sv` | AXI-Lite、字节写、影子字段、原子提交、快照 | AW/W 错拍、半写、阻塞、重复提交 |
| `motion_guard.sv` | 许可、会话/代次、序号、租约、范围、恢复优先级 | 无效请求不续租，故障不能自动恢复 |
| `motion_profile.sv` | 指令变化率限制与脉宽标定 | 目标大跳变仍受限，算术不溢出 |
| `servo_pwm.sv` | 固定周期及周期边界更新 | 正常更新无异常窄脉冲 |
| `stop_input.sv` | 停止同步/锁存及受控释放 | 停止有效；松开不能立即动作 |

这是建议文件划分，当前并不代表这些 RTL 已存在。先完成少量清楚模块，不用大量空目录代替可运行工程。

### 9.3 PWM 的时间关系

候选首版 50 Hz，周期 20,000 μs；脉宽按标定。若实际控制时钟恰为 100 MHz，则每 μs 100 个时钟，20 ms 为 2,000,000 个时钟，1500 μs 为 150,000 个时钟。

该计算只是例子，正式常量由 `ctrl_clk_hz` 生成，并验证取整误差及计数位宽。实际不是 100 MHz 时不能沿用例子。

正常目标更新使用影子参数，在周期边界装入，避免半个周期变窄。停止/复位/到期必须能优先禁能，可能主动截断当前高脉冲；这属于故障动作，要与正常 PWM 抖动分开报告。

### 9.4 监督约束

1. 上电、配置/驱动未就绪、复位默认不输出有效运动许可。
2. 标定未加载或与配置摘要不符，不能 ARM。
3. 超范围目标明确拒绝；正常命令再经过变化率限制。
4. 会话、恢复代次、序号不匹配，拒绝且不刷新旧租约。
5. 缺字段/单位错/零租约/超过租约上限，拒绝。
6. 许可到期、外部停止、关键故障，撤销输出许可并要求明确恢复。
7. 迟到或重复请求不能重新开启已关闭的输出。
8. PS/Windows 卡住时，PL 自己的计数器仍执行到期处理。
9. 故障锁存、状态快照和拒绝原因可读，便于 UI/日志说明。

控制租约要依测得的视觉更新间隔冻结。可从约 200—500 ms 的候选范围评估，但不把候选值视为真实配置；既要容忍正常抖动，也要满足失效响应要求。

### 9.5 状态与恢复语义

本版统一状态名；以下是待实现/测试的行为合同：

| 状态 | 允许动作 | 离开条件 |
|---|---|---|
| `DISARMED` | 读状态、加载受控配置，输出禁能 | 启动/恢复检查；必要时转位置确认 |
| `NEEDS_REFERENCE` | 确认真实机构位置与标定，输出禁能 | 明确人工参考确认后进入 DISARMED |
| `ARMED` | 已准备，可接受本代次有效命令；无命令不自行运动 | 有效命令→TRACKING；停止/故障→FAULT |
| `TRACKING` | 接受有效更新，按限制输出 | 到期/禁能→DISARMED；停止/故障→FAULT |
| `AT_LIMIT` | 不继续朝边界外推；仅允许合法方向和范围 | 合法回程→TRACKING；到期/故障同上 |
| `FAULT` | 禁能，读原因和快照 | 故障源消失且明确 ACK→DISARMED/NEEDS_REFERENCE |

`AT_LIMIT` 的使用条件要结合实际标定冻结；若第一版没有可靠边界反馈，它只能表示**指令达到软件边界**，不能假装触碰到真实限位开关。

冷启动/PL 重载/失去位置参考后，先 DISARMED 再进入 NEEDS_REFERENCE。没有编码器，不通过“PWM 写中位”证明真实归零；先在受控状态确认/定位机构，再明确 ARM。

到期是事件，不另创造与旧文档冲突的 `EXPIRED` 常驻状态。到期后不自动恢复；处理残留请求、更新代次、重新检查位置，再显式 ARM。

**同拍优先级建议：**复位/外部停止/关键故障 > 到期 > 禁能 > 恢复操作 > 新命令。清故障与 ARM 分开执行，网络恢复不等于 ARM。

### 9.6 停止链的三个层次

| 层次 | 能证明的内容 | 不能自动推出 |
|---|---|---|
| PL 数字停止 | 停止输入到 PWM/许可撤销的时间 | 舵机轴立即静止 |
| 动力停止 | 外部停止通路实际切除负载供电 | 机构不下垂、不惯性运动 |
| 机械停止 | 最终负载真实停止行为 | 所有负载/故障均安全 |

首先核验外部停止电路，然后测试数字响应和实际机构。实体停止不能依赖 Windows、VLM、网络或普通 UI 线程及时响应。

### 9.7 必须覆盖的硬件故障

- 停止发生在 PWM 高电平、低电平、目标更新边界。
- 到期与新 COMMIT 同拍；停止与清故障同拍。
- AXI 写了一半软件退出；AW/W 分离；部分字节未写。
- 重复序号、倒序、错会话、停止前旧代次和复位前缓存命令。
- 有效命令后连续无效请求，旧许可仍按原时刻结束。
- 新序号重复同一旧视觉证据，软件不允许续租。
- DPU 高负载、UI 卡顿、Windows 断连时监督仍有效。
- PL 复位/重载、板卡断电重启后不自行转动。

### 9.8 标定和闭环调参的实际步骤

**第一轮：只有电路，没有舵机动力。**

1. 确认控制时钟、IO 电平和停止有效极性，逻辑分析仪观察 PWM/许可。
2. 测上电、PL 尚未配置、配置过程、复位和程序退出时的外部输出。
3. PL 未配置时无法依靠 RTL 拉低针脚，外部接口/动力使能必须有经过验证的默认禁能设计。
4. 若用了隔离/缓冲，分别切源侧、负载侧逻辑电源；确认异常电平不会产生有效舵机控制。
5. 冻结正常更新、紧急截断和恢复后的波形定义。

**第二轮：轻载舵机，不接视觉。**

1. 独立电源调到实物支持范围，测输出/极性，确认停止通路有效。
2. 卸下舵盘或解除高负载机构，在受控状态从中位附近试小范围脉宽。
3. 记录脉宽增大时真实转动方向，不先假定画面左就是角度增加。
4. 逐步测可用范围和机构余量；出现顶住、异常电流或线束受拉则停止并修正范围。
5. 保存脉宽—指令角标定表、实际 SKU、电源、负载和测量日期。
6. 限速先设置保守候选，做小跳变；观察停稳时间而不是只看 PWM 已更新。

**第三轮：接入视觉小范围闭环。**

1. 人在中心保持静止，确认死区不造成来回抖动。
2. 人小幅向左/右移动，确认极性正确，不把错误方向通过加大增益掩盖。
3. 缓慢调比例增益和单步变化，分别记录误差、超调、停稳与指令速率。
4. 加入遮挡、丢失和冻帧，核对停止提交/租约到期。
5. 最后安装最终机构，再重复标定和停止；轻载结果不能代替最终负载结果。

无编码器时，外部视频/标记可用于实测机构动作，但软件“真实轴角”仍不能凭 PWM 反推。校准配置变更产生新摘要，A/B/C 同步版本后再 ARM。

## 10. 运动寄存器与软件访问合同

### 10.1 先合并 ABI，再实现

旧框架和第四轮 D1 的寄存器偏移不同，部分同地址承担不同含义。A/B 必须维护**唯一机器可读定义**，生成 RTL 常量、C/Python 定义和文档；不同时保留两张“最终表”。

推荐 `contracts/motion_regs.yaml` 配合生成脚本。地址窗口可评估 4 KiB；物理基地址由最终平台分配。本版不虚构 `0xA...` 地址或针脚。

### 10.2 必需的逻辑字段

| 组 | 字段 | 语义 |
|---|---|---|
| 身份 | IP_ID、ABI_VERSION、BUILD_ID | 验证访问到正确 IP/版本 |
| 配置 | CONFIG_CRC、CTRL_CLK_HZ、校准/范围/速率参数 | 与发布清单相对应 |
| 状态 | STATE、FAULT、STOP_LATCHED、OUTPUT_ENABLED | 状态/故障和真实许可 |
| 恢复 | SAFETY_EPOCH、ARM、DISARM、ACK_FAULT、REFERENCE_CONFIRM | 明确恢复与使能，不能一写全做 |
| 影子命令 | SESSION_ID、EPOCH、CMD_SEQ、TARGET_MDEG、LEASE_US | 一条完整命令的归属、单位与期限 |
| 证据 | FRAME_TOKEN/证据编号（若纳入 ABI） | 用于追溯及同证据重复控制检查 |
| 提交 | COMMIT | 完整字段快照送监督逻辑一次 |
| 结果 | ACCEPTED_SEQ、REJECT_SEQ、REJECT_REASON、LEASE_REMAINING | 总线写入与接受结果区分 |
| 输出 | COMMAND_MDEG、PWM_EFFECTIVE_TICKS | 指令/生效脉宽，不是测得轴角 |
| 快照 | SNAPSHOT_SEQ 与锁存读取接口 | 多寄存器读取的一致性 |

字段位宽、相对偏移、序号回绕、W1C 等细节由 A/B 冻结。首版也必须完整定义恢复、命令有效期和快照，不能只留一个角度寄存器。

### 10.3 正常提交顺序

1. B 获取同一帧/轨迹快照，复核会话、目标、证据截止时间。
2. 读 IP/ABI/配置和当前代次，确认没有停止/故障。
3. 计算剩余许可，非正值或超上限则丢弃。
4. 写完整影子字段；库保证所选驱动/MMIO 的排序语义。
5. 最后写 COMMIT；硬件原子复制，不执行半条命令。
6. 有限时间内读接受/拒绝结果与序号。
7. 接受后仍区分“PWM 生效”和“真实机械到位”。

AXI 写成功只意味着总线事务完成。没有 ACCEPTED 证据时，软件不能显示“运动已经执行”。

### 10.4 防重复、防乱序、防重启缓存

- 同代次/会话序号严格递增，回绕规则明确；接近回绕时建立新会话，不靠整数溢出。
- 停止/到期/明确恢复推进代次，旧请求在硬件和软件两侧失效。
- 板端进程重启采用新的 boot/session 标识，并先禁能、清队列。
- PL 复位后硬件计数可能归零；因此不能只依靠复位内计数当跨重启唯一标识，需要软件启动身份和重新初始化合同。
- Windows 保存的旧任务无权重建运动会话或恢复输出。

### 10.5 证据时效的实际边界

板端在**最后提交前**核对相机帧/轨迹时间，冻结帧不能通过换新命令序号续租。只计命令编号而不检查源帧，是错误实现。

PL 通常从接受命令开始计租约；它并不天然知道 Linux 相机真正曝光时刻。若总线/调度延迟没有实测边界，不能声称硬件已证明“曝光至执行最大年龄”。记录软件复核时间、接受时间及两者差值，必要时为租约扣除已知最坏提交开销。

相机持续重复旧内容但序号增加的异常也要检测；PL 能独立处理租约/停止，但不能识别软件任意伪造的新鲜图像。这是系统验证边界，需要如实写入报告。

### 10.6 底层库最少接口

```text
read_identity()                 检查 IP/ABI/构建
read_status_snapshot()         一致状态
disarm(reason)                 明确禁能
ack_fault(expected_epoch)      受控清故障
confirm_reference(calib_id)    受控位置参考确认
arm(expected_epoch, session)   明确进入准备状态
submit_command(command)       影子写入、排序、提交、有限等待
```

通过匹配驱动、UIO 或所选 XRT 访问方式实现，范围和权限受控。不把未经核验的 `/dev/mem` 地址散落进 B/C 代码。

## 11. 视觉、跟踪与单轴闭环

### 11.1 唯一采集源

B 的 camera_service 独占相机。其他模块读取带时间/编号的共享帧或接口，不各自打开 `/dev/video*`，避免格式竞争、不同延迟和多份目标状态。

每帧至少包含：板端单调时钟时间、frame_id、图像尺寸、格式、相机配置代次和有效性。若没有曝光时钟，只标注采集出队时间。

### 11.2 模型适配顺序

1. 选固定权重与可重现预后处理的人体检测候选，先建立 CPU/浮点输出。
2. 核对 Vitis AI 3.0 算子、输入布局/尺寸和目标 DPU。
3. 使用代表实际相机工况的校准集量化，再用当前平台 `arch.json` 编译。
4. 保存 quant/compile 日志、CPU 子图、输入输出和 xmodel 哈希。
5. 同样图片比较浮点与板端输出，确认坐标缩放、类别、NMS 无误。
6. 再接相机，测有效更新频率、帧龄和 DPU 时间。

不能保证任意 YOLO 版本/ONNX 一次导出即可上 DPU。若候选算子不适配，优先使用经当前版本验证的较小检测网络；模型选择变化要记录精度与延迟理由，不无限期改网络。

### 11.3 跟踪和目标管理

可采用现有 ByteTrack 思路或已经验证的跟踪实现；身份姓名不能代替 track_id。track_id 可能复用，必须带生命周期/创建代次。

状态至少有：新进入、稳定可见、暂时遮挡、丢失、离开。建立进入/离开去抖，防止每帧重复问候；失去当前轨迹后不继续沿旧方向追。

### 11.4 目标选择优先级

1. 实体停止/维护/故障时，所有自动动作暂停。
2. 已明确选定且仍有效的当前交互目标，保持连续性。
3. 同一会话内可靠的新说话证据可以申请切换，需 B 再确认。
4. 单人可见且无歧义时，可按产品策略选择。
5. 多人、遮挡、画面外声音、分数接近时，保持或 UNKNOWN，并提供手动选人。

目标切换需稳定窗口与滞回；窗口长短由错选/延迟实验决定，不能每帧选分数最大的脸。

### 11.5 首版随动控制建议

归一化水平误差：

```text
e = (target_center_x - image_center_x) / image_width
if abs(e) <= deadband: 不新增目标变化
else: delta_angle = clamp(Kp * e, -max_step, +max_step)
new_target = clamp(last_command_angle + delta_angle, calibrated_min, calibrated_max)
```

相机/轴方向极性由实物标定。先用比例＋死区＋变化率限制，减少不必要控制复杂度。PS 控制限幅与 PL 独立约束共同验证。

`last_command_angle` 是上次指令角，不是编码器读数。画面稳定可以作为视觉稳定判断，不能直接报告轴角误差。

人在死区内意味着不改变目标角，不意味着永久关闭有效期检查。只有新的有效视觉帧仍确认目标时，才允许按合同续租同一目标角；纯定时心跳、重复旧帧或主机回复不能续租。

### 11.6 调度与新鲜度

- 检测/跟踪优先，队列保留最新帧；过期帧丢弃，不 FIFO 无限追赶。
- 身份可按目标/质量/间隔触发，不每个人每帧都推理。
- 相机转动后，旧画面里“左边/右边”的解释需要更新；旧坐标不驱动当前运动。
- ASR/VLM/ASD 等待期间，视觉和 motion_service 继续独立运行。
- UI 或模型异常不占用运动锁；没有有效新视觉时租约自然结束。

## 12. 板端人脸身份与记忆

### 12.1 目标链

```text
人体轨迹→人脸候选→质量/唯一性→关键点对齐→特征
       →板端相似度比较→KNOWN / UNKNOWN / AMBIGUOUS
       →授权登记、数据库事务、重返问候或删除
```

板端身份目标保留。可先用板端 CPU 基线证明完整链和数据库，再把**适配成功的**模型部分交给 DPU；最后报告每步实际运行位置，不能把 CPU 通过写成全部 DPU 加速。

本版继续推进原计划中可适配的人脸 DPU 模型任务。若最终只有 CPU 身份链，应单列“板端身份已通过、计划 DPU 子任务未通过”，不能默认用 CPU 基线取消原加速目标；具体模型/子图边界在可用性评审中冻结。

### 12.2 DPU 与模型限制

人脸检测、关键点、特征网络各自核对当前 DPU 算子与量化精度。常见 OpenCV/ONNX 模型可用于 CPU 参考，但不自动具有本版 DPU xmodel。

选取模型时保存来源、许可证、输入对齐和归一化规则；阈值在独立样本上冻结。不能拿某篇材料的相似度阈值直接当本项目可靠身份阈值。

### 12.3 数据库建议

```text
person(person_id, display_name, consent_version, created_at, updated_at, deleted)
face_template(template_id, person_id, model_id, embedding, quality, created_at)
preference(person_id, key, value, updated_at)
identity_event(event_id, session_id, track_generation, decision, reason, db_version)
```

采用 SQLite 等板端可持久化实现；数据库 schema、embedding 维度/模型版本和迁移策略固定。模型变化导致旧模板不可比较时，重新登记或明确转换，不混用特征空间。

### 12.4 登记流程

1. 用户明确同意登记，输入/确认称呼；录音中的偶然姓名不是自动授权。
2. 只绑定当前唯一有效轨迹，不能多脸同屏时随便挑一张。
3. 收集数个合格且不重复的样本，覆盖少量自然姿态。
4. 每个样本检查模糊、遮挡、大小、角度和同一轨迹连续性。
5. 换人、取消、离开或质量不足，事务中止，不留下半份身份。
6. 事务提交后更新 db_version，显示成功；保存必要质量统计。

### 12.5 识别与删除

- 匹配第一名达到阈值且相对第二名有足够间隔，才 KNOWN；否则 UNKNOWN/AMBIGUOUS。
- 重返问候采用多帧证据和去抖，不因一次相似立即叫名。
- 每轮结果带轨迹生命周期、模板模型和数据库版本，防止串到后来的同编号轨迹。
- 删除立即废止模板、姓名、偏好及缓存；在途旧识别结果因 db_version 不符被拒绝。
- 重启后不复活已删除记录；删除功能和回归证据作为交付项。
- 默认不长期保存全部原始录音/人脸视频，调试样本按团队明确同意、测试用途和保留时间管理。

### 12.6 当前必须达到的区别

“看到脸”“判断他在说话”“识别这个人的身份”是三项不同结果。只有身份链通过才能显示姓名；ASD 输出高分不能证明姓名，姓名匹配也不能证明当前正在说话。

## 13. 无声源定位后，怎么判断谁在说话

### 13.1 MCP01 可以提供的输入

首版只依赖已测试的 USB 人声录音，不依赖独立麦克风通道或厂商方向算法。即使内部有多只麦克风，USB 可能只输出混合后的音频；本版不对内部通道做空间定位。

画面里两个人轮流说话时，Light-ASD 结合音频和每个人连续嘴部/人脸变化给出逐人说话分数。需要对齐的真实片段，不能反复复制同一张照片当视频。[Light-ASD 作者仓库](https://github.com/Junhua-Liao/Light-ASD)

### 13.2 开发顺序

1. C 在主机上跑作者提供的预训练基线，保存模型/依赖版本。
2. B/C 制作真实相机＋MCP01 的同步样本：单人、轮流、同时、沉默、遮挡、画面外讲话。
3. 用可见可听同步事件测声画偏移；长时间复测漂移。
4. 根据基线真实输入要求裁剪、采样和处理；不能只修改帧率元数据。
5. 离线正确后，再发送有限窗口实时推理。
6. 测窗口等待、传输、解码、推理和回传，设置最新优先队列。
7. C 给建议；B 根据最新轨迹再确认后才控制。

### 13.3 有限窗口怎么落实

可先评估 1—2 s 窗口、约 0.5 s 更新间隔等候选值，但模型输入和实际推理决定可用配置。短窗口不保证准确，长窗口会增加等待。

每个窗口包含 audio/video 首尾时间、轨迹生命周期、采样/帧率、缺帧/缺样、对齐校准版本、session_id 和到期时间。窗口不完整、误差超过冻结阈值则 UNKNOWN。

Windows 队列不无限保存历史片段；实时选人宁可丢弃旧窗口，也不能几秒后把已经离开的说话人选回来。

### 13.4 上下文和多人的判定

- 在同一人的连续片段上平滑分数，避免单帧噪声。
- 当前交互对象获得合理连续性，但不能无视明显的新说话证据。
- 两人接近、同时讲话、嘴被挡住或画面外声音，返回 AMBIGUOUS/UNKNOWN。
- 播放回答期间不以设备自己的音频触发自动换人。
- 按键/手动选人保留为可演示路径；ASD 不可用时 UI 明确提示。

### 13.5 研究内容的真实边界

| 原选择方向 | 本版实践 | 报告应怎么写 |
|---|---|---|
| Light-ASD | 预训练基线＋真实声画输入＋系统评估 | 复用模型与工程适配 |
| Streaming ASD | 有限窗口、时效、队列、延迟管理 | 借鉴流式处理思想；不是完整论文网络复现 |
| LoCoNet | 轨迹连续性、多人上下文、拒绝/滞回对照 | 当前规则/上下文方案；不冒称训练了 LoCoNet |
| Neural Simplex | PL 独立运动监督、故障和恢复实验 | 借鉴监督结构；不声称取得完整形式安全证明 |

YOLO、身份、USB 录放音是产品功能。删去声源定位后，本版仍有实际自研运动 RTL 和可测视听选人，但不能保留“硬件声学定位创新已完成”的表述。

## 14. ASR、VLM、TTS 与板端录放音

### 14.1 ASR 服务

首版在 Windows 模型环境运行一个固定中文识别候选。若使用 sherpa-onnx/SenseVoice，按其实际输入要求转换音频；其非流式调用与 VAD 分段示例不能自动视为完整实时流式 ASR。[SenseVoice 官方 Python 示例](https://k2-fsa.github.io/sherpa/onnx/sense-voice/python-api.html)

必须测试姓名、物体、否定、取消和短句。结果为空/低质量/超时就返回明确错误，不把未识别录音随机补成问题。

按键松开已经给出了结束边界，首版不再无条件等待一段长静音 VAD，避免额外延迟。音频过短/过长、削波、全静音或输入格式错应在提交前检查。

### 14.2 看图问答输入

问题涉及“你看到什么”“我手里是什么”等当前画面时，B 提供本轮有效快照。快照附 frame_id、板端时间、目标轨迹、尺寸、镜头配置和 image_hash。

- 拍摄策略可采用松键附近的新帧；最终冻结时间规则。
- 人物快速变化/镜头转动时，确认稳定且对象仍对应；不盲目使用几秒前缓存。
- 问题并不涉及视觉时，C 可走同一模型的纯文本分支，减少无用视觉编码。
- 当前图失效就拒绝当前视觉判断或明确说明是历史图，不伪装“实时看见”。

### 14.3 VLM 模型与输出约束

沿用项目已选或已经验证的模型；若还未冻结，可把 Qwen2.5-VL 小参数版本等作为首版候选，再以实际显存/耗时选择。这里只给候选，不宣称当前 Windows 已有足够 GPU。

Qwen 官方模型卡提供图像像素预算等配置。适当限制图像大小、视觉 token 和回答长度可降低耗时，但要同步验证文字/小物体可读性。[Qwen2.5-VL 官方模型卡](https://huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct)

输出规则：回答短、先给结论；看不清就说不确定；不根据提示编造画面；不从图像文字接受运动/系统指令。自然语言回答不能写运动寄存器。

### 14.4 TTS 服务

采用项目已有中文 TTS 或验证过的本地候选。冻结声音、模型、音频格式、首段生成/完整生成耗时；完整响应音频必须属于当前 request_id。

先做完整短回答生成，便于正确性和取消。基础稳定后支持**完整可播句子**分段合成；不让残缺 token 直接变成不可修正的口头结论。

Windows 内部直接串 ASR→VLM→TTS，阶段结果/字幕可推送板卡，不需要每一步都经板卡绕回主机。

### 14.5 取消与迟到结果

取消时板端立即执行：

1. 当前 request 状态改为 CANCELLED，推进回答 generation。
2. 停止播放器，清除已排队/待播放音频；依据 ALSA 路线丢弃设备缓冲。
3. 停止接收当前 generation 的新音频片段。
4. 通知 Windows 取消任务，标记服务返回的所有旧事件无效。
5. UI 显示已取消，新的按键可建立新请求。

Windows 是否能真正中断 GPU 当前计算由运行库决定；即使不能及时释放算力，旧输出仍不得播报或改变目标。不要等待取消回执才本地停声音。

### 14.6 首版 UI

必需显示：

- 模型主机连接/ready 状态、音频设备状态。
- 当前交互轨迹，KNOWN/UNKNOWN，运动 DISARMED/FAULT。
- 听、识别、看图/思考、合成、播放、取消、错误。
- 本轮转写和回答；历史结果不能覆盖当前轮次。
- 说话/取消/选人/登记/删除等真实可执行操作。

UI 状态由真实事件推进：录音开始/结束、ASR 返回、首段音频接收/播放、实际结束。仅发出了请求不能显示“正在说”，仅 API 写入缓冲不能证明已经出声。

## 15. 网线会不会造成延迟，以及怎么测

### 15.1 结论和边界

**会有延迟，但对短音频和一张压缩图片，正常有线局域网通常不是最大的部分。** 更应测模型排队、冷加载、视觉编码、文本生成、TTS 和板端播放缓冲。这个判断是工程推断，当前没有本项目实测延迟，不能许诺具体秒数。

板端运动不等待 VLM。网络变慢可以让回答晚到，不能使本地停止或有效期监督失效。

### 15.2 传输量算例

以下只算有效载荷的理论发送时间，不含协议、编码/解码、排队或实测往返：

| 数据 | 大小例子 | 1 Gbit/s 理论下限 | 100 Mbit/s 理论下限 |
|---|---:|---:|---:|
| 5 s，16 kHz，16 bit，单声道录音 | 160 kB | 1.28 ms | 12.8 ms |
| 一张压缩问答图 | 300 kB | 2.40 ms | 24.0 ms |
| 5 s，24 kHz，16 bit，单声道回答 | 240 kB | 1.92 ms | 19.2 ms |

1920×1080×3 的 RGB 原始帧约 6.22 MB，30 帧/s 约 1.49 Gbit/s，尚未计算协议开销，不能通过千兆链路持续原样传全视频。

本版网络策略：每轮 VLM 只传必要快照；ASD 只传有界、按输入要求采样的脸片段/音频。压缩减少流量也会增加编解码负担，需要一起实测。

### 15.3 时延拆解

```text
松键→提交前检查/图片编码→上传
    →Windows 排队→ASR→VLM 首 token/首完整句→TTS 首段
    →音频下传→板端校验/播放缓冲→实际出声
```

按键开始到结束的用户讲话时长另列，不混进“松键到首声”。Light-ASD 窗口等待与选人延迟也单列，不以问答总耗时替代。

### 15.4 计时表

| 事件 | 推荐采集位置 | 可计算指标 |
|---|---|---|
| 按键释放/录音结束 | 板端单调时钟 | 首声总延迟起点 |
| 请求发送/音频首包回来 | 板端单调时钟 | 板端通信与处理区间 |
| 入队/出队/ASR 起止 | Windows 单调时钟 | 队列和 ASR |
| VLM 开始/首 token/首句/结束 | Windows 单调时钟 | 模型首输出与全部生成 |
| TTS 开始/首段/结束 | Windows 单调时钟 | 合成响应 |
| 播放 API/缓冲/实际声音 | 板端＋录音或回环测量 | 播放等待与真实首声 |
| 相机出队/命令被接受 | 同板时间及硬件测量映射 | 视觉控制时延 |

不同电脑的原始 monotonic 数值不能直接相减；跨端分段使用各端本地时长，或先建立经过验证的时钟映射。板端到首声端到端指标使用同一板端时基，实际声输出需外部录音/回环或同步采集验证。

### 15.5 优化顺序

1. 模型常驻并预热，避免每轮加载。
2. 单轮主机内流水线，去除多余来回传输。
3. 松键立即结束分段，不重复等静音。
4. 限制图片、上下文、回答长度，先保证关键问题正确。
5. 推送首完整句并生成首段音频；字幕先显示状态。
6. VLM 首版并发 1，限制队列；新轮次按取消策略替换旧任务。
7. ASD 与 VLM 竞争 GPU 时，给 ASD 有限预算，必要时降低频率或在经测试的其他执行设备运行。
8. 调整播放缓冲，同时验证不卡音、取消可停。
9. 最后再评估模型替换或 ASR/TTS 板端迁移。

把 ASR 搬到板上是否更快，要比较 `板端 CPU 推理` 与 `主机推理＋实际传输`，不能只看到网线就认定迁移能降时延。

### 15.6 延迟预算如何冻结

先完成 30 轮热启动测量，记录 P50/P95/max，普通文字问题与当前图像问题分别统计。原第四轮 T18 建议目标是松键到首段实际出声 P95≤8 s；这是内部验收上限，不是已经达到的成绩，也不等于理想体验。

测出各段后把总预算分给排队、ASR、VLM、TTS、通信和播放。若 VLM 已占多数，先优化模型和输入，不反复更换网线。

## 16. 整机流程与状态机

### 16.1 必须分开的状态

- **交互状态：**IDLE、LISTENING、PROCESSING、SPEAKING、CANCELLED、ERROR。
- **目标状态：**NONE、CANDIDATE、CONFIRMED、LOST、AMBIGUOUS。
- **身份状态：**UNKNOWN、KNOWN、ENROLLING、DELETED。
- **运动状态：**第 9 章的六类硬件状态。
- **主机状态：**OFFLINE、CONNECTING、READY、DEGRADED。

这些状态有关联，但不能混成一个“忙”变量：问答忙时视觉仍运行，身份未知时可以对话，停止后仍可显示错误。

### 16.2 上电流程

1. 舵机动力/输出保持受控默认禁能，板卡启动。
2. 检查系统/PL/ABI/模型/标定版本；读取停止状态。
3. 检查相机、MCP01、显示、网络与数据库。
4. Windows 模型预热并报告实际 ready，而不是只开了端口。
5. 进入 UI；缺模型时明确降级，硬件问题不能掩盖。
6. 无位置反馈的机构要求位置参考确认；建立新会话/代次。
7. 人工明确 ARM 后才允许有效视觉请求，不能开机自动扫轴。

### 16.3 一个人走近

1. B 稳定检测/跟踪，建立轨迹生命周期。
2. 当前无目标且策略允许时，确认唯一对象。
3. B 计算小范围随动请求；PL 接受后约束 PWM。
4. 身份链按质量运行，未知显示 UNKNOWN；已知经过连续证据才问候。
5. UI 提示按键说话，不根据全向麦的一次声响盲转。

### 16.4 一次看图问答

1. 按键：必要时取消旧回答，保存新 utterance/session/target。
2. 录音：MCP01 采集，B 维持有限的对应脸片段与轨迹。
3. 松键：停止录音；冻结本轮输入和新鲜快照，生成 request_id。
4. 板端检查输入和主机 ready，发送音频/图像及归属元数据。
5. Windows 完成 ASR；需要视觉时将本轮图交 VLM；输出短回答。
6. 如启用 ASD，独立形成有时限的候选；不阻塞整轮问答等待无限窗口。
7. TTS 返回有效音频片段和顺序，字幕随实际有效事件更新。
8. 板端再次核对 request/session/generation/取消状态和目标策略。
9. 播放 MCP01；完成后回 IDLE，清理本轮临时数据。

### 16.5 两个人轮流说话

1. B 持续维护两条轨迹和连续脸片段。
2. C 在按键窗口中接音频，ASD 判定逐人分数。
3. 证据唯一且有效时，C 请求选中对应轨迹。
4. B 用当前画面验证对象仍在、会话匹配，经过切换滞回再接受。
5. B 按当前坐标产生运动请求，旧说话窗口坐标不直接控制。
6. 同时说话/歧义时提示轮流或手动选人；不为了显示成功强选一个人。

### 16.6 目标离开或遮挡

- 进入 LOST，停止新的跟随提交；待现有短租约到期或主动禁能。
- 当前回答按冻结策略处理：首版建议丢弃尚未播报的目标绑定回答，已经播放则停止并提示对象离开。
- 暂时遮挡后回来也复核轨迹生命周期，不能按同编号自动继承身份/会话。
- 需要重启运动许可时走明确恢复；不会凭模型迟到回复再次使能。

### 16.7 取消与实体停止

普通取消控制问答和播报；实体停止撤销运动并作用于已设计的动力停止通路。两者分别有测试，不互相冒充。

实体停止后：输出禁能、故障/停止锁存、废止旧命令、UI 提示。释放按钮只消除物理停止源；仍需检查机构、ACK、参考确认和显式 ARM。

### 16.8 三类断连

| 故障 | 应保留/停止的能力 | 恢复 |
|---|---|---|
| 断公网但 LAN 正常 | 本地 Windows 模型已完整准备时继续问答；不依赖在线下载 | 不用重新 ARM |
| Windows 失联 | 本地视觉/身份可继续；语音显示主机不可用；本版暂停自动视听换人 | 主机 ready 后建立新请求，不复播旧轮 |
| 板端视觉/运动服务退出 | PL 租约独立到期，停止更新，UI/日志记录 | 新进程先禁能、自检和明确恢复 |

USB 拔出、相机失效、屏幕失效、数据库失败分别显示具体故障；录音设备不在时不能误选系统别的麦克风继续悄悄运行。

## 17. 服务划分、消息协议和日志

### 17.1 首版建议进程

| 服务 | 负责人/位置 | 独占资源与责任 |
|---|---|---|
| camera_service | B，板端 | 唯一相机采集；帧/快照/片段 |
| vision_identity_service | B，板端 | DPU 调度、跟踪、身份与数据库 |
| motion_service | B，板端 | 唯一正式运动命令写入 |
| interaction_service | C，板端 | 会话、录放音、UI、取消和主机通信 |
| model_service | C，Windows | ASR/VLM/TTS 编排、ready/取消/阶段日志 |
| asd_worker | C，Windows | 有限窗口说话证据；可与模型服务同进程但隔离队列 |

进程数量可以根据实现合并，但相机/运动唯一所有者、有限队列和状态责任不能因此消失。

### 17.2 接口先用可调试实现

可采用 LAN HTTP 提交＋WebSocket/流式事件，板端模块间用本地 IPC/共享缓冲。首次实现不必引入复杂消息集群。

模型端口、IP、设备身份和超时放配置；主机只开放项目需要的服务。连接握手核对协议版本和项目身份，防止连错服务。

### 17.3 一轮请求的建议元数据

```json
{
  "protocol_version": "aura-draft-1",
  "board_boot_id": "boot-unique-id",
  "session_id": "session-unique-id",
  "request_id": "request-unique-id",
  "generation": 3,
  "utterance_id": "utterance-unique-id",
  "target": {"track_id": 7, "track_generation": 2},
  "audio": {"format": "pcm_s16le", "sample_rate": 16000, "channels": 1},
  "image": {"frame_id": 1820, "image_hash": "sha256-value"},
  "source_time_domain": "board_monotonic",
  "source_start_us": 1000000,
  "source_end_us": 5000000,
  "deadline_us": 13000000
}
```

这是协议草案和格式例子，数字不代表实际设备支持或已冻结参数。大音频/图片用二进制载荷，避免把整段媒体作为巨量 JSON 字符串。

Windows 返回相同归属 ID、阶段、顺序号、model_id、错误/时长。板端使用自身时间核对 deadline；Windows 不直接拿板端 monotonic 值减主机时钟。

### 17.4 选人建议格式

至少包括 session_id、track_id/生命周期、audio/video 窗口、score、质量、对齐版本、expire_time 和 UNKNOWN 原因。**不含声学 DOA/方位角。**

B 接收后使用最新轨迹位置；同分/超时/目标消失明确拒绝并记录原因。

### 17.5 队列与资源上限

| 队列 | 首版策略 |
|---|---|
| 相机/检测 | 小有界队列，优先最新有效帧 |
| 运动请求 | 不积压历史目标，最后复核后才提交 |
| VLM 请求 | 并发 1；取消/替换策略明确 |
| ASD 窗口 | 有界，过期直接丢弃 |
| 播放片段 | 有界、按 generation/sequence 校验 |
| 身份任务 | 质量/间隔触发，不阻塞人体检测 |

上限由基础测量后冻结；不能把上述“有界”写在方案里但实现仍是无限列表。

### 17.6 日志最低字段

日期/发布版本、boot/session/request、frame/track_generation、事件名、本地时钟/时长、模型/配置版本、接受/拒绝、错误和队列长度。敏感原始媒体与一般状态日志分开存储。

整机可用一次 request_id 查出：谁、哪段音、哪张图、ASR 文本、回答、音频、取消状态；一次 motion seq 查出：源帧、有效期、接受结果、PWM 和停止原因。

### 20.6 故障注入清单

- **硬件：**停止、高电平中断、复位、PL 重载、供电切换及恢复。
- **控制：**半写、重复/倒序、错会话/代次、零/超租约、源帧冻结。
- **视觉：**拔相机、遮挡、弱光、两人交叉、快转镜头、目标离开。
- **模型：**冷启动、长请求、队列满、超时、不能中断的旧 GPU 任务。
- **音频：**静音、录音格式错、USB 拔插、播放缓冲迟到、按键连续取消。
- **身份：**登记时换人、多脸、数据库写失败、删除后在途旧匹配。
- **网络：**断公网、拔 LAN、Windows 服务退出、连错主机/协议版本。

### 20.7 建议对照实验

1. 固定样本浮点 vs INT8：性能和精度代价。
2. 只视觉选人 vs Light-ASD＋上下文：正确/错选/拒绝/耗时。
3. 有限最新队列 vs 保留历史队列的回放实验：过期率和时延；正式系统仍使用受控策略。
4. 无目标滞回 vs 有滞回的离线回放：频繁切换与响应速度。
5. 在无动力仿真/受控台架比较带监督与对照逻辑：停止、超时和乱序；不为对照让真实负载失去必要保护。

消融报告同时写收益、代价和未解决问题，不只挑成功样例。

### 21.2 配置冻结

至少维护：

- platform_manifest：来源、版本、工具、OS、DPU、驱动、实际时钟/地址。
- calibration：舵机范围、方向、脉宽映射、速率、机构/电源标识。
- vision：相机格式、模型/输入、预后处理、更新策略、阈值。
- identity：特征模型、质量/匹配阈值、库版本。
- audio：设备身份、录放格式、转换、缓冲和半双工。
- interaction：主机地址、模型 ID、限流、窗口、超时/取消策略。

每份发布包用统一 release-id，所有文件有哈希。仓库现有 `platform_manifest.json` 的空项/false 不自动改成通过；应附真实证据后逐项更新。

### 21.3 日常启动顺序

1. 检查接线/机构/停止，运动默认禁能。
2. 板卡启动，核对系统、PL 和 ABI。
3. Windows 启动模型并预热，确认 ready。
4. 板端启动唯一相机、视觉/身份、运动服务，运动仍 DISARMED。
5. 启动音频/交互/UI，完成输入输出与主机健康检查。
6. 确认位置参考和配置，显式 ARM。
7. 做一轮短语音和小范围目标测试，再开始演示。

C 维护“一次启动＋自检＋日志”入口；A/B 提供真实检测函数。避免启动脚本不检查退出码就一律打印成功。

### 21.4 停机和恢复

- 停机先禁能运动，停止录音/播报并废止请求，再退出服务。
- 备份数据库与版本，正常关闭系统后断电。
- 新卡或坏卡恢复使用已验证发布包；保留官方对照卡和接线照片。
- 服务异常恢复先清队列/新会话；机构可能失去位置时重新确认。
- 不以重启全部机器替代具体故障定位，记录根因和复测。

### 21.5 应交给评审/队友的内容

1. 实际可构建工程、RTL、约束、平台来源/补丁和构建入口。
2. 正常/故障仿真、实际波形、资源/时序与同片推理证据。
3. 板端应用、主机服务、模型/依赖清单和配置。
4. 数据与许可说明、测试方法、结果、失败/限制。
5. 接线/启动/停止/恢复/独立复现手册。
6. 产品演示视频：启动自检→随动→身份→问答→取消→停止/恢复。
7. 大模型协作记录：有效提示词、回答、自我纠错和采用/未采用理由。
8. 经本项目验证的可复用 Skill，例如命令监督验证流程；写清适用和失效条件。
9. 正式规则要求的开源/授权/提交资料，检查具体公告和截止日期。

已有框架对用户提供的赛事原件做过提交映射，本版沿用其工程材料要求，但不重新断言当前公告/截止日。[现有提交映射与框架](../aura_fpga/docs/fpga_framework.md)

### 21.6 什么才叫“项目完成”

不是只有镜像，不是只有舵机转动，也不是只有主机聊天。完成意味着：

- 同版板卡能启动，DPU 和自研运动 IP 共存并正确运行。
- 当前人物检测/身份/目标和真实运动绑定，有有效期和恢复合同。
- MCP01 实机录放音，语音/当前图问答、字幕与取消闭环。
- 视觉说话人目标有实际证据及失败/拒绝统计。
- 停止、失联、冻帧、迟到、删除与重启不造成旧动作/旧回答复活。
- 最终配置通过规定测试，新卡/非作者可复现，未通过项明确。
