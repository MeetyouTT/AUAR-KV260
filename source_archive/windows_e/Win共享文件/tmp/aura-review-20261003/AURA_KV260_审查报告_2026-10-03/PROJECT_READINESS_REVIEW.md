# AURA 项目：KV260 环境与三人开工条件核对

核对日期：2026-10-03。依据 `/home/ghmd/下载/项目.zip` 的项目入口、2026-10-02 最新分工/联调文件、B/C 手册相关章节、参赛指南 3.3，以及已有构建与最新板端验收记录。

## 结论

三个人现在可以并行开发各自模块。已验证的共同基础包括：KV260 2022.2 硬件工具与器件支持、官方参考平台完整构建、板端 Linux 与修复运行时启动、官方 B4096 原模型/原图片推理、整卡恢复点。

屏幕、相机、MCP01 录放音、人体/人脸模型、语音服务和联合 PWM 各有自己的依赖与验收。当前证据没有覆盖这些完整链路，因此仍需按具体设备和代码补齐。核心 FPGA 环境可用，不能据此将应用依赖或所有外设记为已完成。

本轮是资料核对，没有连接或测试新外设、安装应用依赖、运行室友代码、切换位流或修改板端。屏幕型号/接口尚未提供；室友在其他电脑上的代码和模型环境未盘点。

## 方案当前采用的结构

- **KV260 PL（可编程逻辑）**：DPU 及自研运动控制、AXI-Lite/PWM、命令监督。联合设计尚待实现及验收。
- **KV260 PS（ARM 处理器运行的 Linux）**：相机采集、视觉预后处理、跟踪与身份数据库、运动服务、USB 录放音、网络客户端、屏幕 UI。
- **Windows 首版模型服务**：ASR（语音识别）、VLM（看图问答）、TTS（语音合成）、Light-ASD（结合声音和连续人脸片段判断说话人）。
- **Ubuntu 开发机**：硬件构建、模型适配/编译、匹配板端环境的软件构建、产物和证据管理。

最新版采用 MCP01 USB 音频、单水平轴和视觉说话人判断。历史双 I2S 麦克风、声学方向计算和 `audio_doa_ip` 已从当前范围删除。旧框架中仍出现这些项目，使用时应以最新版范围为准。

## 按模块判断当前能做什么

| 模块 | 当前可以推进 | 还需要确认/交付 |
|---|---|---|
| 屏幕与 UI | 界面原型、字幕、听/想/说状态、事件接口 | 实际屏幕型号/输入、显示驱动和节点、分辨率、字体/UI 后端、真实显示及并发 |
| USB 相机 | 采集程序与唯一 camera_service 的开发 | 实际相机枚举、驱动、格式/帧率、连续真实画面、热插拔及音频并发 |
| MIPI 相机 | 按实际传感器确定硬件和驱动需求 | 传感器驱动、设备树、MIPI/ISP 链路和约束；当前离线分类没有验收该链路 |
| 人体检测/人脸身份 | 在已有官方 DPU 上适配模型；开发预后处理、跟踪、身份库 | 模型来源、量化/编译、DPU 架构匹配、CPU/DPU 分工、真实数据精度和调度 |
| MCP01 麦克风/扬声器 | 开发板端音频后端、录放流程和设备配置 | 实际 USB/ALSA 识别、驱动、原生音频格式、真实录音和出声、重插/并发 |
| ASR/VLM/TTS | Windows 用固定音频/图片跑模型样例和服务 | Windows GPU/显存/依赖/权重、耗时、网络协议、板端回放和取消/断连行为 |
| Light-ASD | Windows 离线样例和服务开发 | B 提供同轨迹连续脸片段、板端真实音频、声画对齐、多人/不确定场景 |
| AXI-Lite/PWM | 独立 RTL 与接口设计、仿真准备 | 与 DPU 集成、地址/时钟/复位/引脚/ABI、重新综合实现、同配置推理与寄存器访问、无动力波形 |

KV260 官方接口表列出 J5 HDMI 输出、J6 DisplayPort 输出及 USB 接口，支持按相应物理接口组织显示和 USB 外设。当前系统对某个具体屏幕的实际可用性仍须实测。SPI/RGB/MIPI 裸屏需按其控制器与接口另做适配，不能把显示器输出接口的可用性直接套用到裸屏。[AMD UG1089 接口说明](https://docs.amd.com/r/en-US/ug1089-kv260-starter-kit/Interfaces)

新的视觉模型需要核对 DPU 支持的算子和图结构，完成针对目标架构的模型部署准备。已有 ResNet18 通过不能代表任意人体检测、人脸网络或语音模型都能直接使用 DPU。[AMD Vitis AI 3.0 模型开发说明](https://xilinx.github.io/Vitis-AI/3.0/html/docs/workflow-model-development.html)

## 共用平台时必须落实的接口

1. **统一一套有效 PL 配置。** 当前参考路线是完整静态 XRT_FLAT，已有审阅未发现 RP/Pblock 预留。DPU 与 PWM 要进入同一份联合设计；加载另一份完整 PWM 位流会替换当前 PL 配置。新增设计需重新实现，不能仅凭全芯片剩余 LUT 比例保证成功。
2. **B 提供唯一相机源和 DPU 业务调度。** C 从约定接口取得快照和连续脸片段，避免各自争用同一相机；人体检测和身份任务共同分配 DPU。
3. **C 提供唯一 MCP01 录放控制。** 不依赖固定 card 0/1 索引；确认真实输入输出格式后再确定 ASR/TTS 转换。
4. **运动正式写入由 B 的 motion_service 负责。** C 提供目标建议，A 提供访问库和 PL 监督；三方共同冻结 ABI、单位、时效、停止与恢复语义。
5. **统一发布身份与消息接口。** 固定平台版本、模型指纹、消息版本、帧/轨迹编号、会话与取消规则。PL 更新时协调应用停止与恢复，保存原可用版本。

最新手册中这些条目是设计合同。寄存器地址、屏幕参数、音频参数及标为 null 的配置还需取得实际值，不能把文档模板当成已经可运行的软件包。

## 软件环境的实际边界

- 当前板卡是 ARM64 PetaLinux；Ubuntu/Windows x86_64 的程序和二进制包不能按路径拷过去即视为可运行。
- 板端 Python3 已在本轮证据采集中实际使用，systemd 也已实测。OpenCV、NumPy、SQLite、UI 库、媒体库和应用所需原生扩展，应按各模块实际依赖核查；不预设都已齐全。
- C++ 板端构建应使用匹配目标 rootfs 的 SDK/sysroot；Python 原生扩展也需核对 ARM64 与库版本。
- 新增缺项先定位是工具、驱动、用户态库还是硬件连接；是否需要调整 rootfs/设备树由实际缺项决定，不先重做整个系统。
- Windows 的模型环境和 KV260 的音频/UI 客户端分别准备。最新版方案没有承诺将完整 ASR/VLM/TTS/Light-ASD 模型全部迁入 FPGA。

## 三个人的第一批可交付结果

| 人员 | 先提交的可运行小链 | 后续联合关卡 |
|---|---|---|
| A：FPGA/硬件 | 最小 AXI-Lite IP 的独立工程和访问合同 | 同一 PL 配置中 DPU 推理正确，同时读回 IP_ID/VERSION；再扩展 PWM |
| B：视觉/身份 | 真实相机连续采集，选定模型在当前 DPU 上有真实输出 | 唯一相机服务、跟踪/身份、运动服务接 A 的访问库 |
| C：屏幕/视听 | MCP01 真实录放、实际屏幕静态中文/状态显示，Windows 固定音频问答样例 | 板端录音→Windows 处理→板端播放/字幕，测试取消/断连与音视频并发 |

B/C 可先用现有官方环境及模拟运动接口推进，联合平台就绪后再接真实运动 IP。第一批成功输出应分别存日志/图片/音频/模型哈希；最终需同时运行相机、音频、显示、DPU 和运动服务验证资源与接口。
