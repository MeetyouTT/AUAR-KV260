# 2026-10-03：AURA / KV260 项目大审查

## 结论

KV260 平台底座、DPU 基线、最小 AXI-Lite M3 样机和修复版运行时都有较强的构建与板端证据；备用卡上的修复版运行时已持久化，并在文件系统修复后的新启动中通过服务、DPU 查询和原图分类核验。AURA 应用整机尚未完成：当前能确认的自研硬件只有身份/版本/SCRATCH 寄存器 IP，没有 PWM、运动监督、相机/身份、音频、UI 或主机模型服务的实现与联合验收。

审查发现一项运行时并发缺口：DFX manager 修复给 watch 表的部分写/删路径加了锁，但服务器请求线程和后台 inotify 线程之间仍有未同步的 watch 读取，以及 `base_designs` 并发访问。此问题是静态审查发现，没有证据显示它已经在板端触发。另有硬件时序余量、恢复镜像落后于当前 SD 状态、本地 Codex 会话数据库权限、审查证据重跑覆盖等风险。

## 已完成且有证据的部分

- **平台与 DPU 基线：**固定在 PetaLinux/Vivado/Vitis 2022.2；官方 B4096 DPU 为 1 CU、300 MHz、基址 `0xa0010000`，fingerprint `0x101000056010407`。原 ResNet18 模型与原图片多轮推理 Top-5 一致，Samoyed 分数为 `0.949879`。
- **M3 最小自研硬件：**在同一静态 PL 配置中加入 `0x80080000` 窗口的 `IP_ID`、`ABI_VERSION`、`BUILD_ID`、`SCRATCH`。DPU 与该寄存器块已做有限板测；四个 32 位 SCRATCH 图样写读后恢复原值。RTL 没有 PWM 或外部控制输出。
- **运行时修复：**修复版 ZOCL 和 DFX manager 曾进行约 30 分钟、30 轮应用卸载/重载和 DPU 复核；证据报告说明使用的是固定哈希候选，并保留了失败尝试和原始基线。修复版随后已安装到备用 SD，systemd 启动顺序至少经过持久化冷启动核验。
- **文件系统：**备用 SD 的 FAT 脏标志已离线修复；`/etc/fstab` 只删除了一条重复 `/boot` 项。新启动日志没有再出现这两类警告。
- **证据管理：**多份板端命令、stdout/stderr、return code、原始 UART、归档成员哈希及原基线哈希均保留。最新文件系统修复冷启动有 15 项板端检查和 27 项主机核对通过，归档 53 项成员一致。

以上只证明平台和有限功能链，不证明完整 AURA 应用、长期部署、全部外设或运动安全已经通过。

## 问题清单

### P0：AURA 核心功能尚未形成可交付实现

当前提交包中的 `项目/aura_fpga/` 主要是说明、合同和清单；主 ZIP 共 435 个条目，其中 346 个路径条目位于 `项目/tmp/`，有构建/排错材料，但没有可交付的 AURA 完整 RTL/板端/主机应用源码。M3 RTL 是单独实验目录中的孤立最小 IP。项目准备报告也记录了摄像头、人体/人脸模型、板端身份、MCP01 录放音、ASR/VLM/TTS/Light-ASD、UI 和 PWM 联合链路仍未验证。

因此目前可称“开发底座和最小寄存器共存样机可用”，不能称 AURA 整机已完成。提交风险包括无法从项目包独立复现、没有完整演示链、也无法证明三人各模块的来源与集成关系。

### P1：DFX manager 的锁没有覆盖共享状态的完整并发访问

修复补丁在 `add_to_watch()` 与 `remove_watch()` 上使用 `watch_lock`，但 `get_watch()`、`path_to_watch()`、`wd_to_pathname()` 仍直接返回共享数组内的裸指针；`listAccelerators()` 会调用 `firmware_dir_walk()` 并同时遍历/更新包信息。`dfx-mgrd` 启动 inotify 后台线程，而 LIST_PACKAGE 在服务器请求线程中调用 `listAccelerators()`。两个线程可并发读写 watch 项和 `base_designs`；后者没有新增同步。当前回归测试中的 8 线程用例只并发调用 `add_to_watch()`，没有覆盖 API 列表与 inotify 创建/删除/重扫同时发生。

影响是热更新或并发列包时可能出现不一致路径、丢失监视项或读取正在变化的结构体。建议让共享状态拥有单一锁和明确快照边界，不把解锁后的内部指针交给调用者；补充“LIST_PACKAGE 与目录创建/删除/重命名并发”的测试。此项为潜在竞态，现有板测未报告复现。

### P1：现有硬件实现余量太小，外部 I/O 约束仍不完整

M3 联合实现报告记录 setup/hold 最差余量各 `+0.009 ns`，脉宽 `+0.071 ns`；7 个输入和 9 个输出仍缺 I/O delay 约束，外部约束覆盖未通过；另有 621 个 DRC Warning（报告列出主要来自 DPU/参考平台），没有 Error/Fatal/Critical Warning。已占用 CLB site 为 99.45%，只有 81 个完全空闲 site。最小 AXI-Lite 样机内部路径虽过了该次检查，这些指标不足以作为新增 PWM、引脚和电气接口的发布签核；每次加入控制逻辑都必须重做实现、I/O 约束、时序和 DRC/CDC 审阅。

### P1：项目目录内存在 Codex 凭据/会话状态边界风险

`start_codex.sh` 将 `CODEX_HOME` 指向项目内 `.codex-home/`，并把交互终端输出写入 `logs/codex/`。只检查了文件名和权限，没有读取 `auth.json` 或数据库内容：`auth.json` 为 `0600`，但 `.codex-home/` 目录为 `0775`，`thread_history_1.sqlite` 为 `0644`。会话数据库可能包含提示、命令输出或个人内容；同机其他用户可能读取该数据库。当前检查的 `项目.zip` 没有包含此目录，但它位于项目工作目录下，后续归档/分享时容易误带。

建议把 Codex 状态和交互日志移出交付树；至少收紧目录和数据库权限，并在归档清单中明确排除 `.codex-home/`、`logs/codex/`。不要把认证信息放入 CLI 参数，因为启动脚本会记录传入参数构成的命令行。

### P2：可验证恢复镜像与当前备用卡状态不一致

目前验证过的整卡镜像是在本次 FAT/fstab 修复之前制作的。恢复报告明确指出，写回该镜像会恢复 FAT 脏标志和重复 `/boot` 条目；修复后的新启动虽通过，但没有新的修复后整卡镜像。因此现有镜像不能单独恢复到当前已验收状态。应建立一个新名称的修复后镜像，验证卡身份、大小、整卡回读摘要和启动结果，并保留旧镜像为历史恢复点。

### P2：文件系统验收采集器允许重跑覆盖旧证据

`collect_post_repair.py` 使用固定板端输出目录并 `mkdir(..., exist_ok=True)`，多个证据文件以覆盖模式写入。若在同一目录再次运行，可能替换旧启动日志、命令结果和状态 JSON，削弱失败轮次可追溯性。一次性证据采集器应在目录已存在时拒绝执行，或自动创建不可复用的唯一 run ID；新结果完成后再封存。

### P2：M3 测试的“无客户端”门槛只检测少数进程名

`m3_board_check.py` 以 root 通过 BusyBox `devmem` 访问物理寄存器。其 `clients()` 只从 `/proc/*/cmdline` 前两个参数中查找四个固定进程名（分类、性能、`xdputil`、`dpu_runner`）；用 Python/VART、自定义二进制或包装器运行的其他设备客户端可能不在此名单内。当前测试对象是 SCRATCH 寄存器，且候选应用身份有多重门控，但该进程名单不足以证明整个设备已空闲。若保留该检查，应明确它是已知客户端检查；需要严格静默时，还应核查相关 DRM 设备 fd/驱动引用或由应用侧显式取得独占测试许可。

### P2：项目状态来源分散且存在过时记录

项目规则指定 `plan/active/` 为当前执行依据，但该目录为空；仅有的 `plan/reference/` 是较早的雾镜 Lite 计划，当前 AURA 三人计划则位于 ZIP 和单独证据目录。`logs/daily/2026-10-03-RUNTIME-LIVE.md` 在持久化/文件系统后续修复前写有“fstab 两条保留、未修复”的状态；最新 `POST_REPAIR_BOOT_REPORT.md` 已证明重复项和 FAT 状态后来处理。应建立一份当前 AURA 基线/状态索引，并把本次之后的状态增补至项目日志，清楚标记被后续证据替代的记录。

本地参赛指南核对记录写明指南建议 Vivado/Vitis 2026.1 或 2025.2，而当前构建固定在 2022.2。这本身不等于违反规则，但最终报告需说明沿用板卡/BSP/运行时兼容版本的理由、适用赛题要求，以及在固定环境下从源码重建的步骤。

### P2：持久化后新启动的负载验证短于此前在线长测

约 30 分钟和 30 轮复验使用了相同修复候选，但发生在持久化启动配置之前；持久化安装后完成过一次冷启动，文件系统修复后又完成一次冷启动和单图推理。最新修复后启动日志覆盖约 517.6 秒，没有新的 30 分钟 soak、断电恢复、PWM 或执行器验收。系统日志仍有 `proc-fs-nfsd.mount` 失败；本次还观察到与旧基线筛查不同的 TPM self-test error 256，原因未查明。性能、健康或长期无泄漏结论应限定到已实际测量范围。
