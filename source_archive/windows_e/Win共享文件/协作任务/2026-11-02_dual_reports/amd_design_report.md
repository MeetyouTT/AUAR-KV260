# AUAR·雪妃

基于 KV260 的多模型视觉、语音交互与执行监督系统

AMD 自主选题设计报告｜审阅稿 V1｜2026年11月2日

本文按 AMD 指南 3.3.5.3 的七项要求组织。作品名称采用用户确认的“AUAR·雪妃”；源码中的 aura 为工程内部标识。文中测试结果来自各自注明的已保存版本，本轮文档编写未重新运行模型、连接板卡或进行机构试验。

## 摘要

AUAR·雪妃面向桌面交互场景，将视觉感知、身份管理、语音交互、角色显示和单轴执行组织为一个软硬件协同系统。系统以 AMD KV260 为感知与业务节点，PS 侧承担相机采集、模型预后处理、任务调度、音频前端、语音识别、记忆存储与显示；PL 侧集成单个 B4096 DPU 和自研运动监督逻辑；Windows 主机承担现有 27B 语言模型与 OmniVoice 语音合成，Ubuntu 用于平台构建、模型适配与证据归档。

项目在同一 DPU 上组织 YOLOX-Nano、YuNet 和 SFace，围绕模型算子适配、INT8 量化、主任务优先与结果时效开展工程优化；通过会话、代次、序号、租约及限速机制约束运动命令；将有效回答、完整播放确认和有来源的记忆提交相衔接。历史固定输入对照中，YuNet 路径中位耗时由 ARM FP32 的 124.02 ms 降为 DPU INT8 的 61.41 ms，SFace 由 520.86 ms 降为 13.56 ms。宽版联合平台布局布线后使用 66,960 个 LUT、710 个 DSP，WNS 为 0.001 ns。另一个 30.004 s 正常业务观察窗口记录整板 CPU 平均 78.65%、DPU 任务忙时平均 6.27%。这些结果分别属于模型短测、静态实现和运行观察，具有不同统计口径。

项目还形成了接口合同驱动的 PYNQ 代码与测试生成 Skill 离线初版，已有 15 项单元测试和两例共 73 个模拟用例通过记录。当前阶段成果覆盖联合硬件、视觉移植、交互软件及验证方法；最终统一版本的整机验收、机械行程标定、完整历史 AI 问答和跨板复用仍需补齐。

关键词：KV260；软硬件协同；多模型推理；执行监督；语音交互；可复现验证

## 1 选题背景与创新点

### 1.1 应用问题与设计目标

桌面交互终端需要同时处理“用户在哪里、面对谁交互、当前说什么、何时执行动作”等问题。单独运行视觉或语音演示时，模块容易各自成立；合入同一嵌入式平台后，相机与音频争用 CPU、模型任务相互等待、旧帧与旧回答迟到、显示与播放状态不同步等问题会直接影响使用体验。

本作品选择将较重的语言模型与语音合成留在局域网主机，把真实采集、视觉推理、业务状态、记忆和受监督执行放在 KV260。设计目标是形成可解释、可验证的交互链，并明确每个动作和每项性能数据所依赖的版本与条件。应用定位是桌面交互原型及教学研究平台。

| 需求 | 设计响应 | 验证关注点 |
| --- | --- | --- |
| 连续感知交互对象 | 唯一相机源、目标轨迹与人脸身份链 | 有效输出频率、帧龄、未知人拒识 |
| 多个视觉任务共存 | 单 DPU 共享、主任务优先、可选任务准入 | 等待、超限、恢复与业务覆盖 |
| 交互与动作保持一致 | PS 校验目标及时效，PL 独立管理执行许可 | 旧会话、乱序、超时及停止 |
| 自然语音与可追溯记忆 | 流式交付、完整播放确认、摘要校验与回收 | 内容正确性、取消、存储与召回 |
| 可交接与复用 | 配套工件、证据索引、Skill 与复现说明 | 新目录复现、依赖闭包及第三方执行 |

### 1.2 前人工作与本项目定位

YOLOX 提供目标检测的公开模型基础，ByteTrack 提供通过检测框关联维持目标轨迹的方法；OpenCV Zoo 提供 YuNet 人脸检测和 SFace 特征模型。本项目使用这些已有算法与模型，工作重点是目标平台适配、任务组织、接口与系统验证。[1–4]

AMD Vitis AI 提供 DPU 模型量化、编译和运行基础；官方 3.0 兼容说明列出与 2022.2 工具链的配套关系。PYNQ 提供 Overlay、DefaultIP 和寄存器访问机制，可作为接口合同生成工具的目标环境。[5–6]

| 既有基础 | 本项目实际工作 | 应用边界 |
| --- | --- | --- |
| YOLOX / ByteTrack | 复用模型与关联方法，接入板端采集及目标状态 | 轨迹编号不等于真实身份 |
| YuNet / SFace | 等价改写、校准、DPU 编译、模板版本隔离与质量评估 | 公开配对结果不代替现场识别率 |
| Vitis AI / DPU | 同一 B4096 上组织三模型及 CPU 预后处理 | 调度逻辑位于 PS，未实现多 DPU 核仲裁 |
| PYNQ 接口机制 | 从合同与 HWH 生成访问及测试骨架 | 当前只完成离线生成和模拟验证 |

### 1.3 主要设计特点与创新价值

第一，围绕交互任务组织计算资源。视觉主任务与按需人脸任务共享同一 DPU；数据准备、推理和业务接受分别检查，关注有效结果与等待，而不只统计模型调用次数。当前已有混合运行及恢复记录，调度策略的严格同输入收益仍需单独实验。

第二，把运动接口设计为带独立许可的事务。上层提供目标脉宽和有限租约，PL 检查会话、代次与连续序号，并在帧边界限速推进。停止和许可失效优先关闭输出。设计将感知和策略计算的波动与底层 PWM 时序分开约束。

第三，将回答交付与记忆提交相衔接。回答文本、播放确认、摘要校验和原文回收使用可追溯状态，便于检查迟到、取消与更正。已有自然到期存储证据，真实同会话摘要召回仍待完成验收。

第四，把实际失败转化为复用方法。PYNQ Skill 将“有地址窗口但缺寄存器元数据”“完成标志迟于超时”等问题固化为检查、反例和独立示例，形成可交给其他工程使用的离线工具。

## 2 设计原理与功能框图

### 2.1 系统总体结构

![图1 系统总体功能框图；实线表示数据或控制关系，Ubuntu 属于开发链](figures/system_overview.png)

相机与 MCP01 接入 KV260。PS 负责唯一采集、预后处理、视觉业务、音频前端和语音识别，通过局域网请求 Windows 的语言模型与 TTS，再在板端完成字幕、角色状态和播放。PL 中的 DPU 计算视觉网络子图，自研监督 IP 接受经 PS 检查的运动事务。

系统具有两条相互配合的路径：感知交互路径将图像、语音和身份状态转为有效回答；执行路径将当前目标转为有边界的运动请求。开发链使用 Ubuntu 完成 RTL/平台构建、模型编译与文件校验，不参与日常交互推理。

### 2.2 视觉、跟踪与身份原理

![图2 视觉处理与身份链；蓝色为 DPU 网络计算，灰色为 PS 处理](figures/vision_pipeline.png)

相机采集后保留源帧序号和时间信息。YOLOX-Nano 提供目标检测结果，跟踪过程维持目标轨迹；YuNet 提供人脸框及关键点，PS 完成解码、NMS 和对齐，SFace 输出身份特征，再由 PS 归一化、匹配并更新业务状态。身份模板按特征模型版本隔离，匹配不足或歧义时保留 UNKNOWN。

部署记录中的三个网络均为 INT8 DPU 工件，每个网络包含一个 DPU 计算分区；板上共享的是单个 B4096。图像编码、后处理、对齐和身份匹配仍消耗 CPU。模型与预处理、输出端口顺序及缩放因子需要配套。[V04–V07、V19]

### 2.3 语音交互与记忆原理

![图3 板端语音、主机回答、播放确认与记忆处理流程](figures/dialogue_memory.png)

较新的板端业务记录采用板端音频前端与 ASR，Windows 保持现有 27B 语言模型和 OmniVoice 推理。板端将转写、身份及会话上下文组织为请求，主机返回有效回答和音频；板端负责播放、字幕及角色状态。较早 Windows ASR 结果只用于对应历史链路比较。

一次请求应关联会话及请求标识。取消、会话切换和迟到返回需要在结果接受处检查；被取消或未完整交付的回答不直接作为完整已播历史提交。记忆处理将原文保存、摘要任务、有效摘要与回收状态分开，便于追溯来源与失败重试。[V10–V11、V15]

### 2.4 单轴执行监督原理

![图4 运动协议与输出许可；停止/租约失效可以独立终止输出](figures/motion_protocol.png)

PS 根据当前目标及帧龄计算请求；PL 侧使用影子字段接收会话、代次、序号、目标脉宽和租约，再在 COMMIT 时进行一致性判断。BIND 建立上下文，REFERENCE 写入经外部确认的控制参考，ARM 开放命令接受，COMMIT 更新目标与租约，STOP 关闭输出许可。REFERENCE 是控制参考，不提供实际角度测量。

宽版 RTL 使用 100 MHz 控制时钟和共享约 1 µs 时钟使能，PWM 帧周期为 20,000 µs，目标范围为 500–2500 µs，12 位字段保存脉宽，帧边界每次最多推进 4 µs。上述值来自对应实现，实际机构零点、角度、负载及允许行程另行标定。[V20–V23]

## 3 软硬件划分依据与接口设计

### 3.1 平台选择与工具版本

目标平台为 KV260，宽版实现报告声明器件为 xck26-sfvc784-2LV-c。项目沿用已有 Vivado/Vitis/PetaLinux 2022.2 与 Vitis AI 3.0 环境，原因是已有参考平台、系统和模型编译链围绕这一组合验证，官方兼容说明也给出该组合。依据 AMD 指南，采用其他工具版本应说明原因并提供可复现脚本。[5、7、V01–V03]

该选择不表示任意同名镜像或 DPU 文件均可互换。最终 release 需要固定源码、实际 DPU fingerprint、模型目标、运行时、BIT/XSA/DTBO/XCLBIN 及设备树映射。

### 3.2 任务划分及判断依据

| 任务 | 执行位置 | 划分依据 | 主要代价与约束 |
| --- | --- | --- | --- |
| 网络卷积等子图 | PL / B4096 DPU | 使用现有 INT8 推理硬件 | 受算子、形状和目标指纹约束 |
| 采集、预后处理及身份匹配 | PS / Linux | 与设备、动态目标和业务状态关联 | CPU 调度及内存访问影响长尾 |
| 多模型准入与等待 | PS 调度器 / 原生运行层 | 单 DPU 统一所有权，主任务优先 | 提交前估计无法给出全局硬实时保证 |
| PWM 与命令许可 | 自研 PL 监督 IP | 需要独立租约、帧时序和停止逻辑 | 需同时验证 RTL、约束及真实电气输出 |
| 音频前端、ASR、存储和显示 | PS / Linux | 保持板端真实输入与业务一致 | 正常业务短窗 CPU 已接近满载 |
| 27B LLM 与 OmniVoice | Windows GPU 主机 | 保留现有模型质量与主机运行环境 | 网络、模型排队、显存与取消需配套 |
| 构建、量化与证据整理 | Ubuntu 开发机 | 工具链及已有工程位于开发端 | 需消除历史绝对路径依赖 |

### 3.3 硬件与外设接口

![图5 外设与执行信号关系示意；用于解释模块关系，不替代最终电气原理图](figures/hardware_connections.png)

相机和 MCP01 通过板端外设接口接入；显示通过现有显示转换链连接屏幕；网口连接 Windows 主机。运动信号在宽版 XDC 中约束为 E10、LVCMOS33，对应项目记录中的 J2.3 连接路径。现有方案记录使用 ADuM1201 和独立舵机供电，最终接线、两侧电源/地及实际隔离关系仍须用实物原理图核对。[V20–V22]

控制器读回的 PWM 脉宽表示指令状态。它不能代替角度传感器、示波器测量或机构行程验证。最终材料需要补正面与45°整机照片、开发板高清特写、线序/供电图及机械装配图。

### 3.4 PS—PL 寄存器接口

宽版准备脚本将自研 IP 的 AXI4-Lite 地址窗口设为 0x80080000，范围 0x1000。下表为 VSRV/2、build 0x10282601 对应 RTL 的相对偏移；使用前必须核对真实映射与版本，不能套用于其他固件。[V20–V21]

| 偏移 | 字段 | 访问与语义 |
| --- | --- | --- |
| 0x000 / 0x004 / 0x008 | ID / ABI / BUILD_ID | 只读；ID=0x56535256，ABI=2，BUILD_ID=0x10282601 |
| 0x00c | flags / reason | 只读；active、armed、referenced、bound 及拒绝原因 |
| 0x010 / 0x014 / 0x018 | shadow session / epoch / seq | 影子上下文；提交时共同校验 |
| 0x01c / 0x020 | shadow width / lease | 目标脉宽 µs；租约 ms |
| 0x024 | command | BIND、REFERENCE、ARM、COMMIT、STOP、QUIESCE |
| 0x028 / 0x02c / 0x030 | ack_seq / width / lease_left | 接受序号、当前指令脉宽和剩余租约 |
| 0x034 / 0x038 | session / epoch | 当前绑定上下文 |
| 0x03c / 0x040 / 0x044 | shadow reference / reference / target | 控制参考、已接受参考及目标脉宽 |

有效 COMMIT 要求已绑定、已参考、已 ARM，影子会话/代次匹配，序号恰为 ack_seq+1，脉宽在允许范围内，租约满足 4–500 ms。命令写入得到 AXI 应答后，软件还须检查业务 reason 和 ack_seq；AXI 总线成功不等于命令已生效。

STOP、租约失效及完成 QUIESCE 会关闭许可并使原绑定失效。QUIESCE 允许正在输出的脉冲自然结束；显式 STOP 具有直接关闭语义。源帧时效由 PS 检查，当前 PL 租约从接受命令起计时，PL 并未验证源帧的绝对截止时间。

### 3.5 视觉与交互数据合同

| 接口 | 关键输入 | 关键输出 | 接受条件 |
| --- | --- | --- | --- |
| 相机→视觉 | 图像、源序号与时间 | 检测框、轨迹及人脸候选 | 保持同源关联，旧结果不覆盖新状态 |
| 人脸→身份 | 对齐图、特征模型版本 | 特征、匹配分数、KNOWN/UNKNOWN | 模板版本及阈值配套，歧义保留未知 |
| 视觉→运动服务 | 有效目标、图像位置及时效 | 有限目标脉宽与租约 | 上下文有效、单写入者、未过期 |
| 板端→Windows | 转写、会话与请求上下文 | 回答、音频及状态 | 当前请求可接受，取消与版本匹配 |
| 播放→记忆 | 完整播放确认、回答来源 | 历史提交和摘要任务 | 确认交付后提交，失败保留可追溯状态 |

### 3.6 时钟、复位与异常处理

监督逻辑在对应 AXI 时钟域运行，采用时钟使能生成时间基准，避免另造低频门控时钟。复位时输出与许可关闭。平台还有 DPU、视频及显示时钟，应随最终 clocks、timing、CDC 和 DRC 报告一并提交。

独立审查已记录 setup/hold 失败端点为0、路由错误为0，同时保留六类 DRC warning 和 6 个 no_input_delay、2 个 no_output_delay 端点。WNS 接近0，当前结果只覆盖已声明约束；板外 PWM、电源及机械测试仍需相应证据。[V03]

## 4 优化过程与性能、资源对比

### 4.1 测量口径

本章将固定输入模型对照、模型任务质量、静态实现资源和正常业务观察分开。每张表注明输入、样本量或版本；正文的中位数与 P95 使用历史原始结果中的定义，本轮未重新采样。已有结果不混合成“最终整机平均性能”。

对完整视觉路径，可把耗时分解为采集/排队、预处理、DPU 等待与执行、后处理和业务接受。对语音路径，可分别记录发言结束、ASR 完成、首正文、台词就绪、首 PCM 和板端播放开始。软件事件与扬声器真实首声属于不同测量量。

### 4.2 模型迁移：从 ARM FP32 到 DPU INT8

迁移先检查算子与数值，再完成代表性校准、目标编译和固定输入板测。模型外处理保留 PS，运行器以 VART 返回的端口顺序组织缓冲区。早期曾因 XIR 集合顺序与 VART 端口顺序不一致发生错误，修正后增加了顺序互换回归。[V04–V07]

| 路径与样本 | ARM FP32 中位 / P95 | DPU INT8 中位 / P95 | 中位加速比 |
| --- | --- | --- | --- |
| YuNet，40 次固定输入，含预后处理 | 124.02 / 147.60 ms | 61.41 / 64.75 ms | 约2.02倍 |

### 4.3 量化质量及参考结果

SFace 使用256个身份的公开样本校准，校准与评测身份分离；2,200对用于选阈值，独立测试为1,000对，含500正对与500负对。两个精度路径各自在训练配对上选阈值，测试结果如下。[V06]

| 指标 | FP32 | INT8 量化模拟 |
| --- | --- | --- |
| 独立测试准确率 | 98.8% | 98.8% |
| 误接收 / 500负对 | 0 | 1 |
| 误拒绝 / 500正对 | 12 | 11 |

总体准确率相同的同时，错误类型发生变化。该1,000对评测在主机上进行，另有4组实板向量与量化参考逐整数一致。现场身份阈值与公开评测阈值不同，因此不能把98.8%直接写成整机现场身份准确率。

YOLOX-Nano 当前使用既有INT8工件。项目场景的独立标注集、FP32/INT8 mAP及误检/漏检对照仍待补，不从约10Hz业务频率推断检测准确率。[V19]

### 6.2 从失败到规则

第一次观察是元数据不完整。真实工程HWH中自研模块的REGISTER元素数为0，表明地址窗口与完整寄存器描述不是同一种信息。工具因此区分MATCHED、INCOMPLETE和冲突；缺少定义时不能凭空生成register_map字段，已知冲突不能绕过。

第二次观察是完成判定顺序。软件需要先判断观察时刻是否超时，再接受完成标志，防止“最终完成”覆盖“已错过期限”。对应反例和修正保留在包中。

第三次观察是单个示例不足以证明复用。加法例与CRC例更换实例、寄存器偏移、完成位和读清除语义；算法分别放在独立模拟和黄金参考中，生成器核心不按算法分支。

| 项目 | 保存的结果 | 层级 |
| --- | --- | --- |
