# AURA：200 MB 工程包与可复现脚本做法

日期：2026-11-02。本文件是材料整理和脚本改造说明，不是最终工程包，也不是已通过复现的脚本。此次只读检查既有文件、字节数及脚本依赖，没有构建、量化、部署、模型请求或板卡操作。

## 1. 大小约束与材料边界

按用户本轮提供的“压缩文件小于 200M”要求整理，内部采用严格小于 200,000,000 字节的检查，建议控制在 180,000,000 字节以内。该预算是项目建议，不是额外的官方评分条件。本次没有登录后台确认 200M 是单附件还是总附件限制，也没有确认外链附件是否被接受。

提交包应保留：自研完整源码、接口与约束、构建脚本、必要 IP 输入或固定来源、依赖锁定、配套上板固件、必要测试样例与参考、原始指标和报告、Skill、真实 AI 协作记录、许可与复现说明。

采用独立的 `aura_release/` 暂存目录，按最终清单收集。排除开发树中的无关缓存、虚拟环境、工具安装、Docker 镜像、历史重复包和可重新生成的中间输出；不删除或修改原目录。

Vivado 的 `.runs/`、`.gen/`、`.cache/`、`.Xil/` 等目录需要先确认输入闭包，再决定是否收录。不能仅凭后缀排除所有 `.dcp`：脚本仍引用的 DCP 就是构建输入。自定义 IP、初始化文件、约束和必需的预综合网表也不能误当缓存。

大型第三方权重、官方系统镜像和工具安装，可规划为固定版本依赖：登记来源、版本或 commit、SHA256、许可、准备命令和预期安装位置。外部补充材料的提交方式仍按后台要求；不假定只放网盘链接就满足完整交付。项目的大语言模型权重继续保存在共享目录之外。

## 3. 可复现脚本具体做什么

把已经成功执行的命令，整理为能在新目录运行、能发现缺失输入、能判断失败、能保存结果的一套入口。

建议按下列职责编写，文件名是拟定接口，尚未在本目录实现：

| 入口 | 负责事项 | 通过标准 |
| --- | --- | --- |
| `scripts/check_env.py` | 检查 Vivado/Vitis、Python、编译器、运行库、模型工具版本及所需许可 | 版本满足锁定条件；缺项明确报错 |
| `scripts/prepare_deps.py` | 按清单准备公开依赖、板卡定义、DPU IP、模型及数据 | 文件来源与 hash 符合清单；支持已有文件离线校验 |
| `build/scripts/create_project.tcl` | 在新输出目录创建工程，加入 RTL、BD、IP、XDC，固定器件及参数 | 工程验证通过，所有输入可定位 |
| `build/scripts/build_fpga.tcl` | 生成 IP、综合、实现、检查时序/DRC，导出固件与报告 | 运行成功，报告与工件存在；时序/错误满足明确标准 |
| `scripts/build_software.py` | 按实际源码入口构建板端 C/C++ 库等，安装固定软件依赖 | 目标架构和依赖正确，构建输出齐全 |
| `scripts/check_results.py` | 对照黄金参考、容差及性能/资源约束，生成汇总 | 失败返回非零，不把日志生成成功当功能成功 |
| `scripts/reproduce.sh` | 依次调用本地准备、验证和构建步骤，保存日志 | 前一步失败即停止，留下失败位置和原因 |
| `board/scripts/` 与 Windows `.ps1` | 按对应系统准备配置、部署、启停与运行验证 | 独立记录本机成功、同步收件及板端验收 |

FPGA 完整重建和加载已编译固件分别提供入口。完整重建必须真的执行综合/实现；快速演示入口用于部署已配对的工件。单次构建脚本不顺带驱动转轴动作。

根目录 readme 应说明先决环境、准备方法、每个入口在哪台机器运行、输入和输出位置、正常结果、失败说明、已知限制，以及哪些步骤需要板卡/Windows 服务。

## 4. 当前脚本要改的具体地方

`build_joint.py` 写死了 Vivado 安装位置，并要求旧工程中的固定 SHA 参考 DCP；`prepare.tcl` 读取的 `platform/repos.txt` 也含多条个人绝对路径。`package_wide.py` 另依赖旧包、工具路径和历史 DTB。只复制几个脚本还不能让陌生机器从零复现。

路径改造示例（说明用片段，未替换原脚本）：

```python
ROOT = Path(__file__).resolve().parent
VIVADO = os.environ.get("VIVADO_BIN", "vivado")
# 保留增量参考路线时，显式提供这个输入并继续检查其固定 SHA。
REFERENCE = Path(os.environ["AURA_REFERENCE_DCP"]).resolve()
```

工程输入相对于包根目录定位；工具安装、模型库等机器相关位置由环境变量或本地配置传入。环境变量只解决路径配置，固定版本与 hash 校验仍须保留。

旧参考 DCP 有两条可选处理路线，尚未选定或验证：

1. 保留当前增量路线：将该 DCP 纳入输入清单，并按允许的交付方式提供固定文件或可验证的再生成方法；预算必须算入约 125.1 MB。
2. 改为不依赖该历史 DCP 的完整实现：先改脚本，再在干净目录重跑，并重新核对时序、资源、功能与板端配套。仅删除引用不能称为通过。

旧 IP 仓库也要逐个追溯：源码和必要生成输入随包或固定来源；工具自带 IP 由锁定工具版本提供；可再生成缓存由脚本生成。当前不能认定 60.3 MB ipcache 全部可省略。

## 5. 从现有 Vivado 工程导出脚本

打开已经核验的工程后，可在 Tcl Console 执行：

```tcl
write_project_tcl recreate_project.tcl
```

它生成重建工程、添加源文件、设置属性与运行配置的 Tcl。随后仍需整理源码和自定义 IP、修正包根目录和输出位置，并追加或保留实际综合/实现/导出流程。路径选项和 origin_dir 行为参见 [AMD UG835 2022.2](https://docs.amd.com/r/2022.2-English/ug835-vivado-tcl-commands/write_project_tcl)。导出 Tcl 不等于已经完成陌生环境复现。

## 6. 打包与验收

1. 从已确定的源码/固件/模型/配置清单收集到全新的暂存目录，保留原始文件。核心源码和必要输入均可追溯。
2. 从暂存目录复制或解压到另一个新位置，在不借用历史工作目录和构建缓存的条件下执行复现，记录工具版本、命令、退出码、报告和输出。
3. 核对 FPGA 接口/器件、时序资源、模型输出和板端业务。现成工件按发布 SHA 核验；重新构建的位流可能受生成元数据等影响，不直接把整文件 SHA 相同作为唯一正确性条件。
4. 生成文件校验清单，创建全新的 ZIP；对 ZIP 做 CRC 和实际字节数检查。超过 180,000,000 字节开始复核，达到 200,000,000 字节则不提交该包。大权重、镜像等依赖的取得方式按允许规则写入 readme。
5. 保留所交 ZIP 的 SHA256、对应公开仓库 commit/tag 和提交回执。
