# AUAR·雪妃：AMD 技术报告目录与写作、配图方案

版本：V1，2026-11-03。本文交付的是目录、写作任务和图表安排；不是新增实测报告。

建议正式题名：**《AUAR·雪妃——基于 AMD KV260 的多模型视觉感知与语音交互终端技术报告》**。沿用现有材料中的作品名“AUAR·雪妃”，历史工程名和代码路径中的 `AURA`、`aura` 保持原样。

本方案依据用户提供的参考设计报告、`项目.zip` 内 AMD 指南第 3.3.5.3 节、最新共享记录及 11 月 2 日两份报告审阅稿制定。原参考 PDF 共 16 页，可借鉴其“约束—设计—实现—实验”的叙述方式。本项目增加软硬件接口、完整交互链、AI 协作、Skill 和复现章节。

## 一、整体组织与版式

### 1. 报告的主线

全文围绕三个问题展开：桌面交互终端遇到什么实际问题；KV260 的 PS、PL 和 Windows 主机怎样协作解决；有哪些数据、原始记录和复现步骤支持结论。

技术重点放在同一 KV260 上的多模型视觉、PS 调度和自研 PL 执行监督，以及语音、记忆与交互状态的一致性。FPGA 章节要说明 AMD DPU 与团队自研 IP 各自承担的工作。模型改写、量化、接口、调度及验证属于团队工程贡献；所复用的模型和算法单列来源。

## 三、逐章怎么写、插什么图

### 前置部分：封面、摘要和目录

封面列作品名、技术报告题名、版本和日期。摘要用约 400–600 字说明问题、系统方案、关键贡献、已测结果与验证范围。摘要中的数字必须能在第 5 章找到对应原始记录。关键词建议选 KV260、软硬件协同、多模型推理、执行监督、语音交互等 4–6 个。

摘要可以保留一张小型技术路线图，但它应与图 2-1 共用信息源，避免两套架构表述。完整架构图在正文展开。

### 第 1 章：选题背景、需求与创新点，建议 2–3 页

**要回答：为什么值得做，现有方法解决到哪里，本项目增加了什么。**

1.1 从桌面交互中的具体困难入手，例如对象发生变化、多任务争用计算资源、网络回答迟到、动作与画面状态不一致。用“使用者行为—现有困难—系统应有行为”写出 2–3 个真实场景。陪伴和人机交互可作为应用动机；医疗效果、心理疗效等不作为未经验证的结论。

1.2 按目标检测与跟踪、身份识别、边缘推理部署、交互终端与执行监督四类整理相关工作。制作**表 1-1 相关工作与本项目关系**，列“来源/方法、已解决问题、本项目复用部分、仍需解决的问题”。文献优先引用原论文、作者仓库和 AMD 官方文档，正式成稿时核对来源和版本。

1.3 制作**表 1-2 需求与评价指标**，把功能要求转为可验收条件，例如有效结果频率、帧龄、未知身份拒识、旧请求丢弃、租约到期停止、复现完整性。目标值与实测值分列。

1.4 建议围绕三项贡献组织：受资源限制的多模型视觉集成；PS 上下文校验与 PL 独立执行许可协同；交付确认、记忆和界面状态的一致性。每项按“问题—机制—证据—边界”写。严格比较或消融尚不足的部分，表述为设计特点或工程贡献。

**插图：图 1-1 应用场景与整机实物。** 建议左侧整机正面、右侧 45° 和关键部件标注。用实际装配照片，角色渲染图另作软件显示示例。

### 第 2 章：系统设计原理与总体架构，建议 2–3 页

**要回答：整个系统怎样工作，各条数据路径怎样闭环。**

2.1 说明相机、MCP01、用户触控等输入，以及屏幕、语音、单轴 PWM 等输出。给出模块职责和数据流向。

2.2 以 KV260 为核心画图：PS 负责采集、预后处理、任务调度和业务；PL 放 DPU 与自研运动监督 IP；Windows 承担实际保留在主机的 LLM/TTS；Ubuntu 作为构建与开发工具节点。依据最新版本确认 ASR 所在位置，不能沿用早期方案将其一律写在 Windows。

2.3 写一个完整例子：“采集到人→形成目标/身份状态→受限跟随→用户发言→回答生成→有效结果接受→播放与字幕→结束/记忆更新”。只把最终实际启用的路径画成有效业务链。

2.4 说明正常、等待、取消、失联、失源及恢复状态。旧会话结果为什么不能重新进入播放或运动，应在这里先解释原则。

2.5 用一张简表冻结最终范围。VLM、视觉说话人、声纹 DPU 等只有方案或候选材料的能力，按其实际状态列出。

**插图：图 2-1 系统总体功能框图；图 2-2 一轮完整交互与取消/异常分支。** 现有 `system_overview` 可改绘为图 2-1。图 2-2 用流程图，节点控制在约 10–14 个，详细状态留给第 4 章。

### 第 3 章：软硬件划分依据与接口设计，建议 3–4 页

**要回答：为什么这样划分，以及各模块究竟如何通信。**

3.1 写实际 KV260 平台、PS/PL 配置、外设与工具版本。现有工程使用 2022.2 等版本，应说明平台兼容与已有构建依据；指南允许其他版本时须说明并保证脚本复现，不能为迎合推荐版本而改写历史环境。

3.2 制作**表 3-1 任务划分与权衡**：列任务、执行位置、划分理由、数据搬运/时延代价、验证证据。说明卷积子图采用 DPU，动态调度与状态管理放 PS，PWM 和执行许可放自研 PL，较大语音生成模型使用 Windows GPU 的原因。比较时依据本项目实际约束。

3.3 制作**表 3-2 外设与电气接口**，覆盖相机、MCP01、显示、J2.3/E10 信号链、隔离器件和舵机动力侧；写清引脚、电压域、供电、地和连接关系。示意图之外，应保留最终实物接线证据和原理图原件。

3.4 正文列关键寄存器组和事务，附录 A 放完整地址表。重点解释影子字段、COMMIT、会话/代次/序号、脉宽单位、租约、ACK、STOP 与复位后的状态。寄存器偏移、时钟和范围从最终 RTL/ABI/约束读取。

3.5 写相机图像到张量的布局、尺寸、颜色通道、量化尺度，以及模型输出到 PS 后处理的边界。现有部署材料可支撑 YOLOX-Nano、YuNet、SFace 的输入与 SHA 表，最终以冻结版本为准。

3.6 网络与进程接口按“生产者—字段—单位—时效—接受条件—错误处理”整理。会话号、请求号、帧号、时间戳、取消和播放确认等字段必须与实际实现一致。涉及超时的时间戳应注明时钟域；跨机比较需解释同步或往返测量方式。

3.7 解释时钟、复位和超时，不把 Linux 普通线程时延写成硬实时保证。区分软件检查源数据时效、PL 检查命令许可，以及舵机实际机械反馈能力。

**插图：图 3-1 PS/PL 联合硬件结构；图 3-2 最终接线和供电图；图 3-3 PS—PL 命令提交时序。** 图 3-1 可使用真实 Vivado BD 配合简化标注；图 3-3 至少表现影子写入、COMMIT、ACK、输出许可及到期。

### 第 4 章：关键模块的设计与实现，建议 4–5 页

**要回答：关键机制如何落到算法、RTL 和软件。**

4.1 按同一图像源说明检测、轨迹、人脸对齐、特征和身份匹配链。明确轨迹编号与真实身份的区别；陌生人或歧义结果如何保留 UNKNOWN。

4.2 说明原始模型、算子适配或等价改写、校准、量化、编译和板端向量校验。明确 CPU/DPU 子图边界，把“编译成功、数值一致、任务质量、现场有效”作为不同验证环节。

4.3 说明单个 B4096 DPU 的共享策略、主任务优先、可选任务准入、等待、背压与旧结果处理。实际调度逻辑位于 PS；PL DPU 是执行推理的硬件。用真实执行事件画时间线，解释不同任务的等待与可用输出。

4.4 重点展开自研监督 IP 的状态、输入条件、原子接受/拒绝、步进限速、租约和输出关闭。用正常命令、旧序号、租约到期和 STOP 四个例子解释行为。指令脉宽不等于实测轴角；无轴角传感器时说明闭环反馈来源。

4.5 说明板端录放音/ASR与主机 LLM/TTS 的分工、首段交付、取消、完整播放确认、记忆提交、摘要校验与原文回收。将自然到期存储检查和同会话真实召回分开描述。

4.6 展示实际界面如何对应听、想、说、暂停/异常等业务状态，避免旧字幕、旧嘴型或迟到事件跨轮次出现。截图只选最终可确认的状态；历史截图标明版本。

**插图：图 4-1 视觉处理流水线；图 4-2 单 DPU 任务时间线；图 4-3 PL 状态机与关键输出条件；图 4-4 语音交付—播放确认—记忆链；图 4-5 界面状态组图。**

第 4 章说明机制，第 5 章评价效果。算法参数和函数清单按需要进入附录，不用大段代码占据正文。

### 第 5 章：优化过程、实验结果与资源分析，建议 5–6 页

**要回答：哪里有问题，为什么改，改后得到什么，付出了什么代价。**

每项优化采用相同结构：原始瓶颈或失败现象→定位方法→候选方案及取舍→实际改动→对照结果→质量/资源代价→有效范围。保留被否决尝试，使优化过程可追溯。

5.1 先列板卡、FPGA/软件/模型 SHA、主机、输入、分辨率、人数、后台负载、冷暖态、预热、重复次数和计时起止。P50/P95 的算法及样本数写清；样本很少的统计不当成长尾保证。

5.2 用**表 5-1 模型性能对照**和**表 5-2 模型质量对照**同时报告速度与质量。现有 YuNet/SFace 固定输入结果可以引用；量化模拟精度、DPU 数值一致和真人识别结果分列。

5.3 用**表 5-3 调度与整机路径对照**列有效结果频率、等待、帧龄、丢弃、期限未满足次数、CPU 和 DPU 忙时。严格收益需同输入、同任务集和同背景负载；已有不同现场窗口只作阶段观察。暂时缺少配对数据时保留实验设计，不填写提升百分比。

5.4 用**表 5-4 FPGA 功能迭代与资源/时序对照**列 LUT、FF、BRAM、URAM、DSP、已配置时钟、WNS/WHS 和失败端点。全平台报告与自研 IP 层次报告分开。窄版到宽版是功能能力扩展，应解释资源成本，不把减少 9 个 LUT 写成显著压缩成果。

5.5 语音拆成 ASR、模型首正文、可交付台词、首 PCM、板端准备、软件播放等阶段。必须先统一时间起点和相邻区间，才能画可相加的瀑布图。真实扬声器首声需要声学测量；软件事件沿用软件名称。不同回答长度、不同主机或冷暖态不能直接算整体加速比。
