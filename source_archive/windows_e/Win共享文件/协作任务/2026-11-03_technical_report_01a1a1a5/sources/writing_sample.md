# AUAR·雪妃：设计报告正文写作示例

对应 [九章目录](report_outline.md)。本文件把已有资料转成可进入正文的段落和表格，说明设计报告如何落笔；不是最终提交稿。示例中的实验数值沿用注明条件的历史记录，本轮未重测。最终版本、原始问答和完整复现未确认处如实保留。

## 一、全文怎么组织

以“桌面交互需要同时感知用户、组织计算、生成回答并控制单轴执行；本项目如何用 KV260 与主机协同实现，并用证据验证”为全文主线。

每个技术小节采用五步：**遇到的问题→采用的设计→选择依据→实际实现→验证与限制**。讲原理后接本项目配置；放图后解释数据方向或关键机制；放实验表后分析收益及代价。

先写架构、接口、实现和实验，再整理 AI、Skill 与复现，最后完成背景、摘要和结论。各章引用相同的版本和数据来源。

## 二、摘要示例

AUAR·雪妃面向桌面交互场景，设计了基于 AMD KV260 的多模型视觉感知、语音交互与单轴执行系统。KV260 的 PS 负责采集、视觉预后处理、任务调度、音频与业务状态管理，PL 集成 B4096 DPU 和自研运动监督逻辑，Windows 主机承担现有语言模型与语音合成。系统围绕模型适配、计算资源共享、命令许可和回答交付开展设计，并将实际调试经验整理为可复用的接口校验与测试生成 Skill。

历史固定输入实验中，YuNet 的 ARM FP32 与 DPU INT8 路径中位耗时分别为 124.02 ms 和 61.41 ms，SFace 分别为 520.86 ms 和 13.56 ms。两项对照同时改变执行硬件与数值精度，反映对应路径的综合变化。项目已形成联合硬件、视觉部署、交互软件及离线 Skill 的阶段证据；最终统一版本的整机验收、完整构建复现和部分现场测量按实际记录补充。

关键词：KV260；软硬件协同；多模型推理；执行监督；语音交互

定稿时根据最终保留的功能与实测更新摘要，不把所有指标都堆入摘要。

## 三、第 1 章怎么写：背景、相关工作与贡献

### 可采用的背景段落

桌面交互终端需要持续判断用户的位置与身份，在交谈过程中同步显示、声音和动作。将视觉、语音和运动模块集成到同一嵌入式平台后，各任务会共同使用 CPU、内存和设备接口；模型等待、结果过期及网络返回延迟可能导致交互状态不一致。因此，本项目重点解决多任务协作条件下的感知、回答和执行衔接问题。

本项目采用 KV260 与局域网主机协同的架构。板端负责真实输入输出、视觉推理、状态管理和受监督执行，主机承担计算量较大的语言模型与语音合成。该划分结合了项目现有模型环境与板端资源条件，形成可逐模块验证的桌面交互原型。

### 相关工作如何接着写

分三类介绍实际用到的基础：目标检测/跟踪、人脸检测/特征、AMD 推理与控制平台。每类说明来源、作用、本项目采用部分和仍需完成的适配。模型名称与算法名称不作为团队原创成果；正式引用从现有报告文献索引逐条核实。

### 贡献如何落笔

围绕三条线写：单 DPU 上多模型与 PS 预后处理的组织；PS 上下文校验与 PL 独立租约/PWM 的协同；回答交付、播放确认、界面和记忆状态的一致性。每条紧接对应章节和证据，有严格对照的地方再讨论量化收益。

**放图表：**整机/场景照片，相关工作表，需求—设计响应—验证指标表。

## 四、第 2 章怎么写：先让读者看懂整机

### 可采用的总体设计段落

系统由感知输入、板端处理、主机推理和执行输出四部分组成。相机与 MCP01 接入 KV260，板端完成图像与音频采集。视觉网络的 DPU 子图在 PL 上运行，PS 完成图像转换、后处理、身份匹配和业务调度。语音转写及会话上下文由板端组织为请求，Windows 主机返回回答与音频，板端负责结果接受、播放、字幕和角色状态更新。单轴运动请求由 PS 形成，并由自研 PL 监督逻辑校验后输出 PWM。

## 五、第 3 章怎么写：说明分工依据，再说明接口

### 可采用的划分段落

网络卷积等适合现有 INT8 推理硬件的子图部署到 DPU，图像采集、动态目标处理和身份匹配由 PS 实现。多模型调度需要结合任务优先级和当前业务状态，因此位于 PS 侧。PWM 的时间基准、租约到期和输出许可由自研 PL 逻辑实现，以便上层任务暂停或失联时仍按既定规则关闭输出。语言模型与语音合成运行在 Windows 主机，沿用项目已经建立的模型环境。

正文随后放任务划分表，列执行位置、依据、数据传输代价和约束。

### 寄存器小节可这样写

自研运动 IP 通过 32 位 AXI4-Lite 接口接收控制事务。软件先写入会话、代次、序号、目标脉宽和租约等影子字段，再写 COMMIT 命令。硬件依据当前绑定、参考和使能状态，校验上下文、连续序号、目标范围及租约；接受后更新目标和剩余许可时间。软件还需读回业务状态与接受序号，确认命令是否生效。

寄存器表列地址、字段、访问属性、有效位、单位、复位值及异常行为。正文重点解释 COMMIT、ACK、STOP 与租约，完整表放附录。当前实现将接受命令后的许可时长交由 PL 管理，源帧时效在 PS 检查；报告中的保证范围与这一实现一致。

**放图表：**划分表、最终接线图、关键寄存器表、提交/应答时序图。待完成的寄存器合理性审查结果不能预写为通过。

## 六、第 4 章怎么写：逐模块解释实现

### 视觉模块示例

视觉链路使用同一相机源保存图像序号和时间信息。YOLOX-Nano 提供目标检测结果，跟踪过程维持目标轨迹；YuNet 输出人脸框与关键点，PS 完成解码、筛选和对齐；SFace 提取身份特征，由 PS 执行归一化和模板匹配。模板与特征模型版本配套，匹配证据不足时保留 UNKNOWN。

## 七、第 5 章怎么写：用优化案例组织结果

### 可采用的模型迁移段落

为降低板端人脸处理路径的计算开销，项目对 YuNet 和 SFace 进行目标平台适配、INT8 量化与 DPU 部署。迁移过程中分别检查模型算子兼容、输入输出顺序、数值一致性和任务质量，再使用固定输入进行 ARM FP32 与 DPU INT8 路径对照。

| 模型与测试范围 | ARM FP32 中位耗时 | DPU INT8 中位耗时 | 样本 |
| --- | --- | --- | --- |
| YuNet，含预后处理 | 124.02 ms | 61.41 ms | 40 次固定输入 |
| SFace，含输入输出转换 | 520.86 ms | 13.56 ms | 8 次已对齐输入 |

结果显示，对应测试条件下迁移路径的耗时降低。由于对照同时改变硬件与数值精度，该结果反映组合路径变化。SFace 输入已经对齐，且样本量较小，不能将该数值作为完整身份业务的端到端时延。量化后的任务质量与误接收、误拒绝结果在相邻小节报告。

![历史固定输入路径对照，使用时保留图注中的测试条件](../2026-11-02_性能曲线与原生截图_01a19c53/性能曲线/09_CPU与DPU固定输入耗时对比.png)

### 资源表之后的分析示例

| 指标 | 联合窄版 | 联合宽版 |
| --- | --- | --- |
| LUT | 66,969 | 66,960 |
| FF | 124,189 | 124,192 |
| BRAM Tile | 93.5 | 93.5 |
| URAM | 56 | 56 |
| DSP | 710 | 710 |

宽版将位置字段扩展为 12 位，并配套更新控制接口，以保存最高 2500 µs 的命令脉宽。两版全平台资源接近，表明此次能力扩展在这些资源类别上没有明显增加总用量。差值同时受实现布局影响，不能将其当作单个 IP 的精确成本或显著资源压缩收益。机械零点和行程根据实物标定另行报告。

### 其他优化怎样写

调度优化写原始等待/图龄问题、尝试过的策略、采纳或否决理由及有效结果变化；语音优化写首正文、台词可交付、首 PCM、板端播放等事件的定义和阶段结果。历史窗口可作为阶段观察，严格收益由配对实验支持。每项结果说明质量、CPU/内存、丢弃或降频代价。

第 5 章结束前列出最终版本的功能、异常与持续运行验收。保存记录、最终共同运行结果和本次是否重测分别说明。

## 八、第 6 章怎么写：把 AI 协作写成可核验案例

一例一页左右，按以下顺序：工程目标、原始提示词、关键回答、首次实现、失败证据、补充交互与人工判断、实际修改、验证结果、最终采用版本。原始提示词和回答从真实记录引用，缺失处注明；这部分示例只提供写法。

### 现有纠错记录可以这样展开

在 PYNQ 测试生成工具开发中，首轮测试发现完成判定与超时检查的顺序存在问题。合同规定软件观察期限为 100 ms，测试将完成标志延迟到 200 ms 才被观察到。原逻辑先接受完成，再检查超时，导致迟到结果被当作成功。

修正后，轮询先检查读回后的观察时刻是否已超时，再判断完成标志。原有反例与正常完成用例保留为回归，已有记录中 15 项单元测试最终通过。该修正限定于软件轮询的观察时间，不能中断已经阻塞的 MMIO，也不提供硬件最坏执行时间证明。

本例的原始提示词、关键回答、代码差异和日志分别作为附件关联。其他案例选 FPGA 联合工程、DPU 适配、语音或记忆优化中记录完整的实际过程。

协作流程图画实际采用的“任务/证据输入—AI 候选—人工核对—工具验证—接受或纠错—产物冻结”。若没有真实多智能体运行记录，按人工—AI 协作工作流描述。

## 九、第 7 章怎么写：解释 Skill 如何从案例中产生

### 可采用的提炼段落

项目将接口调试中反复出现的问题抽象为合同驱动的代码与测试生成方法。实际观察表明，HWH 中存在地址窗口并不保证寄存器信息完整，因此工具将元数据匹配、不完整与冲突分别处理。超时判定顺序的失败被保留为反例，以检查迟到完成是否仍被错误接受。

为检验生成过程对不同任务的适用性，离线初版使用同一生成器处理加法和 CRC 两例，改变实例、寄存器布局和完成语义，将模拟模块与参考实现分开。已有保存结果包含 15 项单元测试、36 个加法和 37 个 CRC 用例，以及新目录和解压复现记录。当前范围为离线软件生成与模拟；真实 PYNQ、跨板及非作者复用按未验证项列出。

随后展示“失败/观察—抽象规则—包内产物—验证—边界”表，说明用户输入合同和 HWH 后会得到什么、怎样运行示例、遇到什么条件应停止或补充配置。

## 十、第 8 章怎么写：给执行步骤，不省略输入

每步同时写执行位置、前提、真实命令、预期输出、失败处理与证据文件。最终填写格式如下：

| 阶段 | 必须写清的内容 |
| --- | --- |
| 获取输入 | 工程版本、校验、外部 IP/DCP、模型和测试数据取得方法 |
| 搭建硬件 | 最终接线、供电、存储卡、外设、网络和参考条件 |
| 安装环境 | 各端系统、Vivado/Vitis/Vitis AI、运行库与模型服务版本 |
| 构建 FPGA | 实际四套 bench、仿真/构建/导出入口、约束与配套工件检查 |
| 准备模型 | 原模型、适配、校准、量化、目标编译及固定向量比对 |
| 安装软件 | 板端、相机、控制器、主机各自的运行根、配置和依赖 |
| 启动自检 | 实际启动入口、设备/模型/界面与服务就绪检查 |
| 验收结束 | 固定场景、通过与失败判据、停止/恢复、原始回执 |

例如，现有离线 Skill 的一个真实入口为：进入 `skill/pynq-contract-testgen/` 后执行以下命令，将输出写到指定目录。

```bash
python3 -B scripts/reproduce.py --out /tmp/pynq_demo_01
```

该命令属于 Skill 离线复现；完整整机另需自己的真实入口和验收。当前完整工程还需依据 11 月 3 日取件审查补齐外部设置模板、原生源码构建依赖、固定输入取得和部署映射。未实跑的步骤注明待验证，不构造不存在的一键入口。

## 十一、第 9 章怎么写：回到目标与证据

### 可采用的结论段落

本项目围绕桌面交互任务，形成了 KV260 与 Windows 主机协同的系统结构，并完成多模型视觉部署、自研执行监督和交互业务的阶段实现。固定输入测试及已有实现报告支持相应模型路径与硬件资源结论，离线 Skill 将部分接口失败经验整理为可复用检查与测试。最终共同运行版本、完整构建输入、现场参数和整机验收继续按实际证据收拢，后续工作围绕这些已明确的缺口展开。
