# GitHub方法核查与当前人脸转轴卡动诊断

2026-10-25。用户明确症状：人脸持续移动时一顿一顿，跨边界响应慢或不明确，希望随脸速调节且边缘快速响应。本轮通过用户指定的GitHub插件搜索并读取上游README/源码，同时检查continuous-v2r2现役源码及最新板端报告，做纯软件反例回放。没有连接板卡、改变配置/保护/阈值/范围、切服务或发运动命令。

**结论：GitHub有可复用方法，但当前优先问题是边界启停/确认与离散命令时序，不能靠直接换PID或加大速度解决。** 最新代码已经具有脸图像速度反馈、中值滤波和加速度限制；本轮不是把这些功能误判成尚未开发。实体是否还有齿隙、死区、供电或负载因素，尚未用真实运动记录排除。

## 当前代码中能直接核实的问题

代码位于[continuous_face_control.py](../../语音共享文件/deliverables/2026-10-24_pan_follow_shadow/source/continuous_v2r2/continuous_face_control.py)与[continuous_session.py](../../语音共享文件/deliverables/2026-10-24_pan_follow_shadow/source/continuous_v2r2/continuous_session.py)。

1. **同一条边界同时承担起动和停止。** 控制器182—200行使用原始脸位置判定：回区立刻速度清零，越界又需连续确认。session 34—38、84—85行在回区时finish并重建控制器。边界抖动会反复销毁感知历史、清速度和重新确认；这是代码行为，不是猜测硬件故障。
2. **确认与首次位移存在多级等待。** 首次确认3帧、越线2帧、ARM后要求新帧；新的控制器不继承source，因此首个ARM后帧的dt为0、不改变位置。随后还有加速度限制和整数微秒舍入。ARM后新帧规则应保留，但感知确认/时间计算可以重新设计，不能只把所有确认关掉。
3. **平滑与控制频率相互作用。** 三点因果中值在单调信号上约滞后一份样本，后接80ms位置低通和100ms速度低通。信号快时仍同样滤波，响应与抖动难兼顾。真实延迟取决于输入序列，不能把三个常数直接相加成实测延迟。
4. **请求速度不等于命令实际推进速度。** PS每个新源最大4µs：若新源10Hz，即使请求60µs/s，稳态最大命令变化也只有40µs/s；这是条件算式，不是认定现场脸源恒为10Hz。当前有真实模板匹配补帧，需采其新源时间分布。若每100ms只改变几µs，PL在一个20ms PWM周期内到达目标后等待下一命令，具有停阶的可能。
5. **回区时直接清零绕过正常减速度。** 现有120µs/s²约束只在越界分支生效，不能宣传所有普通起停都平滑。故障STOP与普通回区的平滑目标必须分别定义。
6. **当前速度是图像残差速度。** 相机随轴时，脸的像素速度包含相机转动的影响。可以用于图像闭环反馈，但不能直接称人的真实角速度或未标定的前馈量。
7. **左边界本身极晚。** 最新规则是脸框接近画面左端2px才触发，而face_flow拒绝跨出图像的框。快速向左时可能先发生测量失效；应明确左侧目标保留区，不能只增大控制增益。右侧用户80.6472%线保持，不擅自移动。

## 适合本项目的改造顺序

**第一阶段优先改PS，不先重做PL或换检测模型。**

1. 感知历史与运动段生命周期分开。正常回区后保留同一轨迹的近期真实位置/速度历史；新目标、过期、断流必须重建，不能沿用旧目标。ARM后仍须新源才有输出，但用明确的运动时间起点避免无必要的额外零dt帧；每个动作仍绑定有效证据。
2. 让界面明确显示“区内保持/正在跟随/正常减速/丢脸停止/到行程边界”，配一个当前跟随方向。不能把软件行程限制和图像边界混成同一种状态。
3. 以One Euro替换固定位置低通做同输入A/B，轻量离群点门控处理偶发坏框，不把中值、EMA和One Euro全部串上。高速降低滞后，低速压抖，按本机坐标单位标定。
4. 目标脉宽变化率由“越界距离＋有方向的图像运动速度”产生；明显持续向外时快速跟进，接近回区时在边界外提前减速，停稳后不重新起步。速度上限/加速度应有同机验证，不能直接抬高60或解除每源4µs门槛。
5. 单独核查小步累计、舍入、请求速度与实际步进速度，记录真实命令间隔。命令平滑但轴仍跳才把重点转向舵机死区、齿隙、供电/负载；不能把其他舵机的5µs死区当本机参数。

**边界语义需要明确，不能暗中更改。** 通用防反复切换方法是两条不同的起动/停止线（滞回）或一段可见的回落带。若起动线不变、停止线向内移，就会允许在旧线以内继续一点运动，改变用户之前“回区立即停”的规则。默认先保留回区即停，使用区外提前减速、持续感知历史和更清楚状态；只有把回落带作为明确产品选项后才采用空间滞回。还不能用“平滑刹车”为理由在丢脸或许可过期后延长动作。

**第二阶段：确有离散命令停阶再上轨迹层。** Ruckig开源速度接口可生成一轴连续速度/加速度状态，20ms节拍与既有50Hz PWM相配；必须从上一轨迹状态接续，不能每次目标变化都从零速重新规划。这里说的是脉宽命令轨迹；未标定不输出虚构角度/实际速度。

当前合同“重复源不产生新命令、不续lease”意味着不能直接把PS循环改50Hz，拿同一张脸反复提交。高频轨迹要显式定义一个新鲜观测批准的有限轨迹段：每个执行点沿用同一source及原始绝对截止，新控制tick不算新图像，不能延长期限；最坏调度抖动/制动时间要计入剩余预算。这个合同变化需新反例和适配验证，普通会话相对租约不自动满足。否则先保留现有新源驱动方式并测第一阶段改善。

Ruckig速度接口不替代位置限位、硬件STOP、PL4µs/周期限制或机械验证。接近行程末端要提前检查剩余制动距离，不能先生成越界轨迹再硬截断却声称jerk仍连续。开源README的min/max位置约束标为Pro，因此本机边界校验仍需外层自己明确实现/验证。

## 下轮验证要回答的问题

- 用同一个已确认目标、同输入/阈值/实际边界，重复慢移/快移/回区/换向，记录每次源帧、年龄、边界状态、ARM/COMMIT/finish原因及脉宽。
- 分别计越线到首个有效命令、命令到实体开始动、区外滞留、正常回区反复启停次数、软件行程触限。取样必须区分检测、模板匹配和失效，不只看总YOLO帧率。
- 对照慢速噪声和快速移动两组，改滤波不能只展示抖动下降而不报延迟；反之亦然。
- 旧帧/冻结/丢脸/多人/换轨迹/断流/停止仍拒绝或停，不用取消保护换顺滑。现场参数、真实波形和人的实际角速度本轮均未测。

本轮交付是方法筛选、原代码静态诊断和离线反例；没有修改生产控制器，也没有声称卡动已经修好。下一步最小改动应先针对PS确认/状态清理与滤波，保留现役固件和已有硬件监督。
