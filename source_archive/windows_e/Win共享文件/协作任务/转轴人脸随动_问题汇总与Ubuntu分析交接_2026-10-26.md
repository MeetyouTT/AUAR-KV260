# 转轴人脸随动：问题汇总与 Ubuntu 分析交接

整理日期：2026-10-26，America/Los_Angeles。主要运行证据截至共享资料记录的 2026-10-26 05:13 UTC（洛杉矶 10 月 25 日约 22:13）。

用户目的：把连续多轮转轴开发中的问题集中交给 Ubuntu 侧阅读、分析和后续解决。用户反复反馈：起转晚、跟随延迟、运动不平滑、顿挫或抽搐，有时越线后看不到明显动作。

本轮只进行了资料、源码、GitHub/官方文档核查及隔离软件模拟，没有修改业务代码、配置、固件，没有部署、重启或试转。本文是交接依据，不是新一轮实体验收结果；后续操作承接用户最新指令及实际设备状态，不根据本文自动启动随动或回中。

## 1. 先读结论与处理优先级

最有现场依据的主线是：**有效人脸坐标和检测锚存在间断或老化，运动因此反复停止、重新确认；正常回区又直接清零轨迹速度；较小的脉宽变化与未标定机构叠加，可能造成“等一下才动、动一下又停”。**

目前不能认定“DPU 算力不足”“DPU 模型输出错误”或“舵机硬件损坏”是唯一根因。DPU 执行只是采集、调度、跟踪、发布、控制、实体响应链路中的一段。

| 优先顺序 | 问题 | 证据强度 | 后续重点 |
| --- | --- | --- | --- |
| 第一批 1 | 有效人脸源不连续、检测锚老化 | 历轮现场记录反复出现；r10 真人效果未复验 | 分清采集、调度等待、推理、跟踪拒绝、发布各段 |
| 第一批 2 | YuNet 的更新需求与共享 DPU 调度、上下游有效期缺少完整对齐 | 源码确认结构；实际贡献需分段测量 | 为运动提供及时新锚，避免仅“成功完成”却无法消费 |
| 第一批 3 | 固定模板跟踪失败后必须等新检测才能恢复 | 源码确认，现场有对应拒绝原因 | 同输入比较跟踪鲁棒性、恢复时间，保留真实当前像素验证 |
| 第一批 4 | 正常回区立即清零速度/加速度 | 当前源码确认；原需求包含回区立即停 | 明确位置冻结与平滑减速之间的产品取舍 |
| 第一批 5 | 命令量化、低速起步与机构未标定 | 软件行为确认；机械原因未实测 | 测真实脉宽响应、最小有效变化、负载与角度关系 |
| 同步补齐 | 完整链路测量与版本对应不足 | 资料确认 | 把源码版本、有效坐标、命令、实体响应放在同一时间线上 |
| 调参修正 | 配置中的部分滤波参数没有接入实际滤波器 | 源码及隔离输入对照确认 | 接通或删除无效参数，记录真实生效参数 |
| 保护专项 | 源时效检查与实际 COMMIT 之间仍有时间窗口 | 模拟寄存器故障注入复现，未证实现场发生 | 独立审查相对租约与源绝对截止，不能与体验根因混为一谈 |

不要通过延长旧图有效期、取消丢脸停止或清故障计数来换取表面连续。

## 4. 逐项问题、原因与建议

### Q01：有效人脸坐标不连续、检测锚接近截止

**确定事实：** 历轮有 `UNCONFIRMED`、`SOURCE_EXPIRED`、`FACE_MEASUREMENT_REJECTED`、`FACE_ANCHOR_EXPIRED` 等记录，伴随反复 ARM/运动段重建。主检测约10Hz或预览流畅不能证明人脸运动源连续。

**尚未确定：** 每类失效分别由真实离场/低头/遮挡、检测漏检、调度等待、锁等待、模板失配或发布延迟贡献多少；r10在可用真人输入下是否仍有同样比例。

**建议：** 对同一条真实源帧建立分段时间线，并按失效原因统计有效间隔。先定位丢失点，不能先靠放宽250ms/500ms期限续用旧坐标。

### Q02：运动所需的新鲜度与共享DPU任务安排没有完整闭环

**源码事实：** YOLO有主任务期限，YuNet和SFace经过可选任务准入；人脸源需要YuNet提供及时检测锚，但姓名识别与运动定位的频率需求不同。

**时效不一致：** 底层 `FaceTargetService` 默认 `ttl_ms=1000`，创建调用未显式覆盖；检测准入使用该输入期限。运动层却要求检测锚小于500ms、当前像素小于250ms。允许生产端继续处理某些对运动已经太旧的帧，是结构上的浪费风险；这不等于已证明它是全部现场老化的原因。

**建议：**

- 保留唯一DPU所有者及既有硬件/故障保护，为随动开启期间的YuNet设置可测量的最大更新间隔和提交/完成期限。
- 让SFace按身份业务需求低频或按事件运行，评估其与YuNet争用的实际影响；不能在无依据时直接取消身份功能。
- 对运动相关请求，准入时预留推理、后处理、当前帧跟踪、发布与提交预算，不只检查“此刻还没过期”。
- 仅缩短TTL可能增加丢弃，必须同时解决服务机会。总预算不够时明确调整任务频率或成本，不能增加线程强抢同一个DPU或另造第二owner。
- 原约100ms检测节拍已经实现，应查实际完成间隔和尾部延迟，不重复修复旧200ms默认值。

### Q03：固定模板匹配对外观变化敏感，失败恢复依赖下一个检测锚

**源码事实：** 当前 `FaceFlow` 在320×240图像上使用固定检测锚模板做NCC匹配，设有边缘裁切/双固定子块补偿。主匹配没有一般性的连续尺度/旋转模型。一次真实匹配失败后清除 `template/box/binding`，直到出现新检测锚才可重新建立模板。

**影响推断：** 转头、距离变化、局部遮挡或边缘情况下，跟踪可能先失配，再等待DPU重新确认，形成明显空档。这与“DPU执行慢”不是同一件事。匹配阈值0.80与检测分数0.90属于不同量，不能简单互相替代或一起下调。

**建议：**

- 用同输入对比现NCC与ROI稀疏LK光流、前后向一致性检查及几何一致性筛选，必要时评估尺度/旋转适应；不要未经板测直接替换。
- 特征限定在已确认的人脸区域，保留目标代次、多脸和误匹配保护；不能改为看身体就继续运动。
- DPU负责发现/重新确认/纠偏，PS跟踪在每张新图上测量当前坐标；SFace姓名不应成为每次坐标发布的前置。
- 失败或质量不足时仍停止。提高恢复速度靠更及时的新锚和更可靠的当前像素验证，不能给旧框换时间戳、无限滚动模板或取消500ms真锚上限。

**已做的事：** 当前已经有最新帧入口、真实当前像素测量、固定锚与边缘补偿，v12还分离了人脸锁。不要把这些当作尚未开发再重复实现。

### Q04：正常回区直接清零轨迹状态，边界附近可能反复起停

**源码事实：** r10 `continuous_session.py` 的 `SAFE_ZONE_HOLD` 分支把p/v/a设成当前脉宽、0、0；不确定回区和源位移预算耗尽也有类似清零。Ruckig生成的平滑轨迹在这些外层分支被截断。

**需求背景：** 原规则要求回区立即冻结位置。这是已经存在的产品取舍，不应把“回区即停”擅自改成区内继续滑行。丢脸/过期/硬件故障停止与正常构图回落必须分开。

**建议：** 明确正常回区是否允许有限制动。若允许，使用连续状态减速，并评估不同启动/停止边界或稳定条件；若仍要求位置立即冻结，则诚实标注这些边界不保证连续jerk，不能宣称全程平滑。

### Q05：低速与整数脉宽输出造成迟动，机构参数尚未知

**软件确认：** r10边界附近静止人脸可能得到2µs/s请求速度。整数微秒输出要积累约半个微秒才能第一次改变命令，忽略加速也约需250ms；持续阶段每变化1µs约需500ms。实际首次变化还取决于初值舍入、轨迹和新源到达，不能把该估算当整机固定延迟。

**机械待证：** 真实舵机的最小有效脉宽变化、起动门槛、齿隙、惯性、供电压降、线束负载和安装是否松动均未完成匹配测量。不能把其他舵机的死区参数直接套到本机。

**建议：** 在已确认方向、停止和有限行程下建立“目标脉宽→实际运动”的基线，再确定速度/加速度/量化策略。不能仅提高20ms循环频率或盲目增加增益。µs、µs/s、角度和角速度必须分别记录，未标定前不输出虚构角速度。

### Q06：宽保持区、左右参考不同，以及重新确认时间影响主观延迟

**源码事实：** 左边界看脸框左沿，右边界看脸中心，区内不转。脸已经移动但尚未越线时，按设计不会动作。左右响应不能直接按相同中心坐标距离比较。

**启动事实：** r10需要2张确认新图，ARM后仍需真实新源；区内可预备ARM但不COMMIT。该策略可减少某些起步等待，不能消除失跟恢复和轨迹/舍入延迟；r10真人效果仍待验证。

**建议：** 区分越线前等待、越线到首个不同目标、命令到实体起动三个阶段。明确目标是越界纠偏还是持续维持构图，不能暗改现有边界或删除ARM后新图要求。

### Q07：部分滤波调参项未接入实际算法

**本轮确认：** `EdgeConfig.filter_tau_ms`、`velocity_filter_tau_ms`出现在配置校验和报告中，但当前OneEuro用另一套初始化参数。将两者从30/30改到500/300，同一组合成输入的滤波位置、图像速度与请求速度序列完全一致；源码也未用它们设置滤波器。

**建议：** 接通这些配置或删除/标记为兼容字段，并报告实际生效的OneEuro截止频率、beta等。`median_window`当前主要用于兼容诊断，不能误读为中值、EMA、OneEuro仍三重串联，也不能按旧EMA参数反复盲调。

### Q08：仍需检查控制热路径的尾部耗时，但已修复项不得重复归因

**历史确认：** 控制线程曾每0.5s同步格式化约211KB报告；相同报告的独立格式化约123/155/245ms，但这不是直接采到的原线程耗时。r8/r10已改为精简实时报告、停止后保存完整有界轨迹；批量MMIO读取也已接入，减少逐寄存器文件检查。

**当前待证：** 实时报告仍同步写，循环还读取边界文件并做SHA等工作；批量读取也不等于无I/O。r10无脸窗口控制回合最大21.085ms，不能代替有人运动负载的尾延迟结果。

**建议：** 先测真实负载下publish、step、tick、MMIO、排队等耗时和>100ms次数；只有发现阻塞才针对改动。诊断保持有界、低开销，避免为查延迟重新引入大日志阻塞。

### Q09：提交前时效检查与硬件COMMIT之间存在时间窗口

**隔离复现：** 使用共享 `PulseDriver` 及依赖的原driver，模拟寄存器在最后检查后、实际COMMIT前暂停300ms。源时间10.000s，图像截止10.250s，COMMIT发生10.300s，driver仍返回ACCEPTED，写入相对lease230ms；模拟硬件租约截止10.530s。

**边界：** 这是Python驱动加模拟寄存器的故障注入，没有真实MMIO或PWM；并未证实现场发生300ms提交暂停。下一轮软件可能检测迟到并STOP，但不能消除已经发生的过期提交。不能据此宣称实板必定多动230ms，也不能把它当已证实的抽搐主因。

**原因：** 软件检查原始时间，硬件目前从接收COMMIT起计相对租约；PL不知道真实源绝对截止。native提交路径也未携带该源截止。

**建议：** 独立审查提交时序，补充暂停在最终检查前后、COMMIT前后、旧lease到期等故障注入。native侧收紧窗口和提交后停止可减少风险，但不能被描述为严格消除了最终检查与写入之间的竞态。若要求硬件独立保证源截止，需要设计可信时钟/期限合同及配套PL/驱动验收，另作专项；不要为修体验立即混改联合固件。

### Q10：整链验收、界面状态与版本闭包不足

**验收缺口：** 大量测试证明软件规则、ACK或寄存器读回，不能证明真实机械平顺。原FakeDevice提交后立即更新pulse，无法覆盖实际20ms PWM帧边界、机械死区/惯性和负载。260→200ms为合成输入首指令结果，不是机械延迟。

**状态表达：** “自动模式开启”“有效人脸”“ARM预备”“PWM active”“目标脉宽变化”“实体运动”是不同状态。尤其r10区内ARM不启动PWM，不能用ARM次数直接计算动作次数，界面开启也不代表有效跟随。

**版本缺口：** 根README、多个aura树、历史交付与最新板端运行根并存。底层默认值可能被入口覆盖，报告顶部新记录可能覆盖下方历史。修复必须对应当前boot、源指纹、配置、模型和最终实际入口。

**建议：** 固定一个候选闭包，给每轮数据附版本与输入条件；用同一帧时间线核对真实动作。保留失败与故障计数，不把测试数增加当成体验关闭，也不让旧交付覆盖较新线上源。

## 6. Ubuntu侧建议的分析与处理流程

### 阶段A：先确认真实基线，取得无运动的时序数据

1. 读取当前boot、固件/DT、服务、实际入口、全部包装层、源码/配置指纹与当前停止状态；本文PID和旧boot只作检索依据。
2. 在不主动输出转轴动作的前提下，观察有脸、慢移、快移、转头、边缘和短暂遮挡；按当前用户指令安排现场配合。
3. 为同一源帧保留以下数值字段，尽量复用现有埋点，必要时采样，避免记录正文/原始图像或大报告阻塞业务。

| 测量段 | 必要字段/指标 |
| --- | --- |
| 采集与入队 | frame_id、真实capture时间、offer时间、实际采集间隔、替换/丢帧数量 |
| DPU前 | 预处理耗时、准入等待、被拒/重试/截止次数、输入源龄 |
| DPU执行 | 实际submit/完成及原生release时点、DPU子图运行时间、超限/恢复状态；原生lease耗时不等于纯DPU核计算时间 |
| DPU后 | 后处理、检测发布、检测锚源龄、连续检测间隔、阳性/阴性/多脸 |
| 当前帧跟踪 | 当前source时间、anchor时间、匹配方式/质量、snapshot等待、处理开始/结束源龄、逐类拒绝原因 |
| 发布与消费 | 发布/收到时间、排队长度、有效独立source数、最大有效坐标间隔；同source重复包另计 |
| 运动 | 越线时点、请求速度、ARM/COMMIT/QUIESCE/STOP、首个不同target、width/target、每次停止原因 |
| 实体 | 实际开始动/停稳、方向、明显跳动/过冲，与命令时间对应；未测项标未知 |

4. 如需AMD profiler，采用本机实际VART版本对应工具；对本KV260参考Vitis AI 3.0资料，不照搬Versal AI Edge Gen2的新VART-ML接口。采集本身的额外开销也要说明。

### 阶段B：根据时间分布决定修哪里

| 观测结果 | 首要判断 | 优先处理 |
| --- | --- | --- |
| DPU前等得久、实际执行短 | 调度或CPU准备造成延迟 | YuNet期限/更新机会、准备位置、最新帧准入，评估SFace争用 |
| DPU实际执行时间长或抖动大 | 模型/运行时/搬运/资源竞争 | 同输入profile，必要时才考虑模型或执行路径调整 |
| DPU锚及时，但当前帧匹配经常拒绝 | 跟踪脆弱或场景困难 | 同输入比较NCC与质量受控跟踪及恢复路径 |
| 同图CPU检出而DPU漏检/框异常 | 可能有量化、预后处理或模型精度差异 | 同图输出/坐标缩放/阈值核对；不能由一次HTTP延迟推定量化错误 |
| 新鲜坐标已到，但不同target很晚才出现 | 控制/确认/量化造成迟动 | 查看边界、p/v/a清零、请求速度、舍入与源位移预算 |
| target/width平顺而实物跳动 | 机械/电气原因优先级上升 | 测PWM、最小有效变化、负载、齿隙和供电 |

### 阶段C：形成最小候选，逐项验证

建议顺序：时效合同和调度机会 → 跟踪恢复 → 正常边界的运动连续性 → 机构匹配。Q09保护专项并行在逻辑上单列，不与体验改动混成不可归因的大改。

先复用已完成的独立锁、最新帧入口、OneEuro、Ruckig、batch MMIO和已有故障保护。选择一个明确问题制作候选，离线反例和版本核对通过后，再按用户最新指令在唯一板端控制入口验证，保留回退与全部失败记录。不得并发抢UART、DPU或运动锁。

## 7. 建议验收指标：用于讨论，不是已有成绩

| 指标 | 建议口径 |
| --- | --- |
| 有效坐标频率 | 在清晰单脸持续可见条件下，先以8～10个独立新source/s为讨论目标；以真实相机能力为上限，不用NDJSON包数凑数 |
| 当前坐标年龄 | 可先讨论P95≤150ms，实际图像250ms硬期限继续执行；报告尾部和最大值 |
| 有效坐标间隔 | 可先讨论最长≤200ms，分别报告慢移/快移/转头/边缘；真实离场不计成应持续跟踪的正例 |
| 检测锚 | 单独统计源龄与最大刷新间隔，500ms硬期限不放宽；确保正常场景不长期贴着截止运行 |
| 起动延迟 | 分别报告越线→首个不同target、target→实体起动；先测基线再定门槛，不能用控制回合或软件合成延迟替代 |
| 平顺性 | 正常持续越界中的非预期停启次数、边界反复切换、过冲和实体跳动，注明输入与负载 |
| 保护 | 丢脸/多脸/换目标/冻结/错boot/断流/旧源仍拒绝或停止；不能靠牺牲这些条件达标 |
| 整机 | 同一版本下有人三模型请求、语音与UI并发，记录全部故障/恢复及实际回退；短窗不称长稳 |

100ms控制源目标周期、20ms轨迹tick、50Hz PWM和物理响应是不同指标，不能互相代替。上述门槛是方案建议，需结合现场能力与用户体验确认，尚未证明达到。
