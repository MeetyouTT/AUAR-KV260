## 对应 AURA 的材料

| 材料 | 本项目应包含的内容 |
| --- | --- |
| FPGA 工程 | 实际联合 DPU＋运动 IP 的 RTL/BD/Tcl/XDC、构建步骤、配套 BIT/XSA 等输出、资源与时序报告 |
| 板端 PS 软件 | 当前正式相机、三模型推理/调度、身份/跟随、GUI、硬件访问库的源码与构建方法、配置和 systemd 启停/检查脚本 |
| 板端固件运行包 | 与源码及软件接口一致的 `.bit.bin`、`.dtbo`、`.xclbin`、`shell.json` 及校验清单；实际采用的启动组件按复现需要说明 |
| Windows 上位机 | 当前语音、模型服务、身份/记忆衔接与玩偶画面合成的源码、依赖、模型配置和启动/停止/健康检查方法 |
| 模型说明 | 模型来源、版本、许可、精度、编译参数、SHA 和下载/准备方法；可分发的板端模型按许可提供 |
| 设计报告 | 应用、架构与软硬件划分、真实创新、接口、优化前后对比、资源时序、已知问题和从零复现步骤 |
| 实测证据 | 与最终版本匹配的检测/识别、语音、跟随与停止保护、通信、冷启动和恢复记录；指标须链接原始数据及测量脚本 |
| Skill 与 AI 协作记录 | 从实际开发失败和修正中提炼可复用工作流/模板/校验脚本等，并附真实提示词、关键回答、修正和验证记录 |
| 开源交付 | GitHub/Gitee 仓库、许可和第三方依赖说明，固定 release/tag/commit 与校验清单 |
| 演示材料 | 准备整机演示视频，时长/格式按后台要求；进入决赛后另按通知准备现场装置与英文海报 |

`.elf` 按实际实现提交：当前 AURA 业务主要为 Linux Python 与 C/C++ 库，指南按实际采用的实现方式收取 PS 软件，没有单列要求每个作品必须另做一个裸机 ELF。

## 实际执行顺序

1. 确认报名后台的赛道、组别、报告模板、附件格式/大小、视频要求和截止时间。
2. 完成当前人脸跟随的固件/boot 绑定恢复，核验启动提速和整机并发；把实际完成范围、待验证内容与未来工作写清。
3. 以板卡和 Windows 实际运行版本合并成一个 release，保存模型、源码、固件、配置与接口的指纹。2026-10-30 实读 GUI 已是新的 identity-bridge 版本，不能仅依据旧共享 GUI 快照封版。
4. 在同一最终版本上完成实测并汇总数据；从干净目录按文档重建/部署，记录成功与失败边界。
5. 整理工程、报告、Skill、协作记录和视频，准备开源仓库与对应版本快照；公开发布与实际比赛上传由用户明确安排后执行。
6. 在队伍后台按栏目上传，核对上传文件和仓库版本一致，确认系统最终提交成功，并保留提交回执和所交包的 SHA。

当前没有新鲜的完整最终包验收结果。人脸跟随最近只读状态为 FAULT：加载的是 `kv260-benchmark-b4096` 纯 DPU 固件，运动配置仍引用旧 boot 的联合固件上下文；启动提速也尚未完成新 boot 实测。上述问题属于封版前需要核验的事项，不能用历史某次 READY 替代本次完成。
