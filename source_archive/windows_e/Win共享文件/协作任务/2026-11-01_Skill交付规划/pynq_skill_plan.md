## 1. 与现有三包的关系

原 A/B/C 三个通用 Skill 继续保留。本方案是可单独提交、用于争取 PYNQ 方向加分的补充候选，不将原三包改名为 PYNQ 包。

## 2. 建议做什么

建议名称：`pynq-contract-testgen`。

中文主题：接口契约驱动的 PYNQ 调用代码与验收骨架生成。

用户提供 IP 接口合同、可用的 HWH 元数据、测试向量和黄金参考；工具检查声明，生成面向 PYNQ 的寄存器访问封装、测试入口及验证报告骨架。第一阶段在 Ubuntu 上验证生成器与生成代码的模拟行为，PYNQ 真实环境验证另列阶段。

选择这一范围的原因：与既有工件配对、寄存器合同、版本/证据和测试经验相关；无需大型模型，也无需先迁移整机系统；接口合同、代码生成和诊断流程可通过更换配置复用于其他题目。

## 3. 首版范围

首版限定为：AXI4-Lite、32 位标量寄存器、显式读写权限与副作用、按声明进行的启动/完成轮询及超时。寄存器偏移、IP 实例名、输入输出、位宽、符号和控制语义全部由合同提供。

DMA、AXI-Stream、多字寄存器原子性、中断、DFX、自定义设备运行时等不作为首版默认支持项。遇到不支持的类型应返回明确状态，不能生成表面成功的调用代码。

通用性来自同一生成器支持不同 IP、寄存器布局和受支持的板卡配置。不同器件仍需各自构建的 bitstream 和匹配元数据，不能将同一个 `.bit` 文件直接用于所有板卡。

## 4. 输入与输出

| 输入 | 必要内容 |
| --- | --- |
| IP 合同 JSON | 实例名、地址范围、寄存器名称/偏移/访问权限、位域、数据类型、读写副作用、启动/完成语义、超时 |
| HWH 元数据 | IP 实例、地址窗口，以及实际存在的寄存器/字段信息；缺项标明来源与验证缺口 |
| 工件清单 | bit/HWH 的版本、来源、SHA256、声明目标和构建关系；清单匹配不等于真实硬件已匹配 |
| 测试向量与参考 | 输入、预期输出、整数溢出或容差规则、黄金参考实现 |
| 环境配置 | 包路径、PYNQ/Python 版本要求、目标板配置、输出位置 |

| 输出 | 作用 |
| --- | --- |
| `driver.py` | 生成与合同一致的 PYNQ IP 访问封装；按实际元数据选择受支持的访问方式 |
| `test_ip.py` | 正常输入、黄金参考比对、超时和错误用例骨架 |
| `quickstart.md` | 说明对应 PYNQ 环境下的准备和执行方式 |
| `contract_report.json` | 已核对项、冲突、缺失项、不支持项及证据层级 |
| `validation_report.md` | 输入/工具/合同版本、测试结果及未验证事项 |

核心约束：不猜寄存器，不自动遍历写寄存器，不把缺少的元数据当成已验证；对有读清除等副作用的寄存器按合同处理。

## 5. 为什么与 PYNQ 有实际关系

生成结果明确面向 `pynq.Overlay`、`ip_dict`、`DefaultIP.read/write`，以及元数据充分时的 `register_map`。PYNQ 官方说明 Overlay 使用 bit/HWH；`Overlay(..., download=False)` 可避免构造时立即下载，但仍属于需要合适 PYNQ 设备环境的 API，不能据此宣称普通 PC 已完成 PYNQ 运行。

一个当前实际观察：本机 wide 工程 HWH 的 `aura_m3_regs_0` 模块中未发现 `REGISTER` 元素。静态来源为：

`/home/ghmd/aura-pan-wide-20261028/platform/platform/platform.gen/sources_1/bd/bd/hw_handoff/kv260_ispMipiRx_vcu_DP.hwh`

这说明生成器要能区分 IP 地址窗口与细粒度寄存器说明。不能因为有 HWH 就假定任意 `register_map.<name>` 都存在；合同显式给出的偏移若缺少元数据对照，应报告为声明输入、尚未与 HWH 验证，而不是自动补造寄存器。此观察不是当前 PYNQ 已运行失败的证据。

## 6. 用什么例子证明复用

建议准备两个与 AURA 业务无关的小例子，例如 32 位加法 IP 与 CRC 计算 IP。两者使用不同的实例名和寄存器布局，只替换合同、测试数据及黄金参考，生成器核心不变。

AURA 的接口材料作为来源和附加案例；实际运动寄存器的写测试不纳入通用样例的默认执行。

还应提供合同错位、重复寄存器、超范围偏移、只读寄存器写入声明、缺少必需元数据、未知协议、超时和错误参考等反例。目标是检验具体故障检测能力，不以文件数量或用例数量作为通用性的证明。

## 7. 验证分层和当前状态

| 层级 | 内容 | 当前状态 |
| --- | --- | --- |
| 文档/来源检查 | 官方方向、当前环境限制、既有 HWH 静态观察 | 本轮已核对 |
| 离线生成器验证 | 校验合同、生成代码可解析、反例按预期拒绝 | 待实现与验证 |
| 生成代码模拟验证 | 用模拟 IP 检查地址/读写顺序、黄金比对与超时 | 待实现与验证 |
| 真实 PYNQ 验证 | 实际导入 PYNQ、加载匹配 Overlay、访问 IP、核对结果 | 未验证，当前无环境 |
| 另一板卡复用 | 相同核心工具配另一板卡工件和配置执行 | 未验证 |

可以按实际范围交付经过验证的离线生成器和模板，但报告必须明确未完成的 PYNQ 实际执行层级；不能把离线模拟、普通 Linux MMIO 或 VART 运行当成 PYNQ 板测。作品本体的官方板级验证要求仍需满足。

## 9. 建议执行次序

1. 先审阅范围与合同格式，保留原三包。
2. 后续恢复实现时，完成小型生成器及独立正反例，固定来源与输入输出。
3. 由另一位队员在新目录换合同复用，记录离线层结果。
4. 若安排真实 PYNQ 验证，可在独立 SD 卡上准备经核对兼容的官方 Ubuntu 与 Kria-PYNQ；先确认启动固件和系统兼容条件，再安排设备窗口。本轮不安装或切换系统。
5. 真实运行成功后补充固定环境、板卡、bit/HWH、日志和参考比对，逐层更新状态。
