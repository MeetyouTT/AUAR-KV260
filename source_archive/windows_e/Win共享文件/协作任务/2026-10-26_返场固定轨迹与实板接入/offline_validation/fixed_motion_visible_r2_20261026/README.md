# 5秒可见往返r2：按实际时间跳过旧计划点

旧visible实板仅4个ACK、0.0836秒即被`SUBMISSION_SPACING_NO_CATCHUP`中止，全部target/width1420。第2、3次提交分别耗25.876/29.568ms，仍在100ms租约内；旧for-loop随后追赶已过时的20ms计划点，造成短间隔再提交。

本独立r2只改core调度：每次ACK返回后至少20ms才再提交，提交前按实际elapsed选择最新到时的计划点；跳过旧点、不补发。每条记录`planned_index`和`skipped_slots`，总数最多248，不要求恰好248。5秒绝对截止、40ms结束预留、1402..1420批准窗口、15µs总偏移、1µs单步、原租约/ACK/未知width保护都保持。只有最后已接受计划状态回参考且速度/加速度为零，实际STOP读回也为1420，才能给出正常完成。

如果下次合法提交已进入结束预留区且已回参考，就直接QUIESCE，不额外短睡等待最后一个重复保持点。原`plans.json`、`plan_fixed.py`、`fixed_bench_adapter.py`与visible1逐字相同；计划仍是251点、−10/0/+10/0µs/s的1.5/1/1.5/1秒。冻结计划里的248表示最多可提交点数，实际次数由本轮调度证据给出。

29项本地测试通过。相同实测调用耗时注入：旧core复现4ACK后失败，r2完成245ACK/跳3点并返回1420；单次19ms为248ACK（尚未跨整格，无需跳点），31ms为247ACK/跳1点；重复10～35ms调度抖动完成127ACK/跳121点；前90次持续慢提交完成143ACK/跳105点。所有成功模型的实际COMMIT间隔≥20ms，原5秒截止不延长，最小目标1405，最终1420/STOP。抖动模型尾部最后约0.5秒恢复及时调度，不能当成任意最坏尾部暂停保证。101ms暂停造成真实租约失效仍拒绝，迟到deadline及Q09反例仍失败STOP。

`MODEL_RESULTS.json`含完整模型命令；`REAL_DELAY_REPLAY.json`区分实际板端失败证据和注入耗时的软件对照。`CODE_MANIFEST.json`绑定运行模块和原冻结计划。CLI仍默认PLAN_ONLY、直接`--execute`拒绝；主终端负责本boot参考/独占owner/新有限收据入口。

本子任务未连接板卡、改生产或执行实体动作。Q09的native最后写入暂停仍未解决；本r2尚未实体复验，模型通过不代表手感已通过。
